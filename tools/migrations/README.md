# Миграции формата карточек

Когда меняется структура/формат markdown-файлов городов (схема карточки —
`system/schema/card_schema.md`, формат листа персонажа, формат дневника и т.п.) —
**существующие файлы пользователей не правятся вручную**. Вместо этого здесь
добавляется миграция, которая чинит все старые файлы автоматически при
следующем старте сервера (см. `web/lib/migrations.js`, вызывается из
`web/server.js` при каждом `app.listen`).

## Когда нужна миграция

Если правка делает старый формат **невалидным** или **читающимся иначе**:
переименование поля, смена синтаксиса секции, новое обязательное поле без
обратной совместимости. Если старый формат продолжает читаться корректно
(парсер и так понимает оба варианта) — миграция не нужна.

## Формат файла

`NNN_slug.js`, `NNN` — порядковый номер (определяет порядок применения). Два вида
миграции — контентная (правит текст одного файла на месте) и структурная (переносит/
переименовывает папки, создаёт новые файлы). Модуль экспортирует контракт одного вида,
не оба сразу.

### Контентная (самый частый случай)

```js
module.exports = {
  description: 'короткое описание, что чинит миграция',
  // Должна быть идемпотентной: false на уже мигрированном файле —
  // иначе миграция будет повторно применяться при каждом старте сервера.
  test(text)    { return /- \*\*Старое поле:\*\*/.test(text); },
  migrate(text) { return text.replace(/- \*\*Старое поле:\*\*/, '- **Новое поле:**'); },
};
```

Раннер (`web/lib/migrations.js: runMigrations`) обходит все `cities/<город>/**/*.md`,
прогоняет через `test()` каждую миграцию по порядку номеров и применяет `migrate()`
там, где `test()` вернул `true`. Пишет файл обратно только если что-то изменилось.

### Структурная (перенос папок, создание новых файлов)

`test(text)`/`migrate(text)` работают над содержимым УЖЕ существующего файла — этот
контракт не подходит, если миграции нужно физически переместить/переименовать папки
или создать файлы, которых раньше не было (например `district.md` при бэкофилле).
Для этого — контракт `migrateFs`, вызывается один раз на город (не на файл):

```js
module.exports = {
  description: 'короткое описание структурного изменения',
  // { cityDir, citySlug, root, log } — cityDir/citySlug/root уже абсолютные пути;
  // log(msg) пишет в тот же лог, что и контентные миграции. Возвращает { changed: N } —
  // сколько структурных операций выполнено (для сводки в консоли/tools/run_migrations.js).
  // Должна быть идемпотентной: на уже мигрированных данных — { changed: 0 }.
  migrateFs({ cityDir, log }) {
    let changed = 0;
    // … fs.renameSync/fs.mkdirSync/fs.writeFileSync по своей логике …
    return { changed };
  },
};
```

Пример — `002_district_rayon_paths.js` (перенос `locations/district_NN/<район>/` →
`locations/<район>/`, с починкой markdown-ссылок на перенесённые пути) и
`003_district_md_backfill.js` (создание `district.md` для папок районов, где его
ещё нет). Порядок номеров между контентными и структурными миграциями общий и
соблюдается строго — структурная миграция, переносящая папки, обязана иметь номер
меньше структурной миграции, которая создаёт файлы по НОВЫМ путям.

## Ручной запуск

```
node tools/run_migrations.js
```

Сервер делает то же самое автоматически при каждом старте — ручной запуск нужен
только для проверки/CI, без поднятия веб-сервера.
