# Анализ: загрузка изображений в библиотеке, вкладка «Смертные», новые поля смертных/охотников

**Собрано:** Аналитик, 2026-08-08. Один запрос пользователя, три независимых по коду, но
частично зависимых по порядку доработки (Часть III использует данные, которые заполняет
Часть II) части. Ниже — раздельный анализ каждой, с решениями и рисками.

---

# Часть I — Загрузка изображений для карточек библиотеки

## 1. Текущее состояние

Все изображения библиотеки сегодня — **read-only, генерируются отдельным инструментом**
(`tools/generate_library_art.js`, не веб), кладутся в `web/public/img/system/library/<section>/
<slug>.png` и подхватываются на чтении через `_artFileSet(section)`
(`web/routes/library.js:221-226`) — набор PNG-файлов читается на каждый GET-запрос без кэша.
Проверка наличия арта **везде захардкожена на `.png`**: `art.has(x.slug + '.png')`
(`_withArt`, `:226`), `artFiles.includes(slug + '.png')` (`loadDisciplines`/`loadPsychics`,
`:56, :96`). Загрузки через веб для библиотеки нет вообще.

**Готовый прецедент для переиспользования** — загрузка портрета персонажа,
`POST /api/characters/:slug/upload-image` (`characters.js:581-647`): тело запроса — JSON
`{ base64, ext }` (не `multipart/form-data`, не `multer` — в проекте multer не используется
нигде), `validateImageUpload(base64, ext)` (`web/lib/http.js:35-59`) проверяет расширение по
белому списку (`jpg/jpeg/png/webp/gif`) И магические байты содержимого (значит не просто
доверяет `ext` из тела запроса — реальная проверка, что байты действительно похожи на
заявленный формат). Персонажи допускают **несколько** изображений на карточку (последовательная
нумерация `slug_01.jpg`, `slug_02.png`, …) — библиотеке это не нужно, у записи ровно один слот.

## 2. Декомпозиция запроса

1. Кнопка загрузки изображения в детейл-модалке записи библиотеки (та же модалка, где сейчас
   уже есть «✏ Редактировать»/«🗑 Удалить»/«📋 Создать свою копию», K1 + Часть II
   `2026-08-08-discipline-picker-techspec.md`).
2. Загрузка **заменяет** уже существующее изображение (не добавляет второе, не требует сначала
   удалить старое).
3. Если изображения не было — новому присваивается имя по slug записи (тот же паттерн, что уже
   ожидает `_artFileSet`/`_withArt` для отображения).
4. Работает для **всех** категорий библиотеки — явно не ограничено дисциплинами/кланами, значит
   включает и пять новых категорий «Смертные» (Часть II) с самого их появления, не отдельной
   доработкой позже.

## 3. Решения Аналитика

### 3.1 Формат загрузки — только PNG, не весь список `validateImageUpload`

**Проблема:** `validateImageUpload` (переиспользуется без изменений, п.1) допускает
jpg/jpeg/png/webp/gif — но ВСЯ читающая сторона библиотеки (`hasArt`, `<img src=".../slug.png">`
во всех `_lib*CardsHtml`/`_lib*DetailHtml` рендерерах, десятки мест) жёстко предполагает `.png`.
Загрузка `slug.jpg` не сломает загрузку (файл на диске появится), но **никогда не отобразится**
— карточка продолжит считать, что арта нет (`hasArt` ищет только `.png`), а прямых `<img>`
ссылок на `.jpg` в разметке нет вовсе.

**Решение:** сервер принимает только `ext === 'png'` для этого конкретного эндпоинта (проверка
до вызова `validateImageUpload`, отдельно от общего белого списка — тот остаётся неизменным для
персонажей/локаций, у них своя, отдельная, уже работающая многоформатная логика). Не
переписываем читающую сторону под мультиформат — это отдельная, ощутимо более крупная
доработка (десятки мест) ради возможности, которую никто не просил (пользователь не просил
загружать не-PNG, только «заменить изображение»). Frontend конвертирует любой выбранный файл в
PNG на лету перед отправкой (`<canvas>.toBlob('image/png')` — стандартный API, без новых
зависимостей) — пользователь может выбрать jpg/скриншот, но на сервер всегда уходит PNG;
если конвертация в браузере не удалась (редкий кейс) — понятная ошибка, а не молчаливый
«загрузилось, но невидимо».

### 3.2 Имя файла — всегда `<slug>.png`, без нумерации

В отличие от персонажей (несколько портретов), у записи библиотеки один слот — имя файла
детерминировано (`<slug>.png`) и не меняется между «первой» и «заменяющей» загрузкой: сама
операция записи (`writeFileAtomic`) уже atomic-перезаписывает существующий файл тем же путём —
никакой отдельной ветки «если файла нет — создать, если есть — удалить и создать» не нужно,
`writeFileAtomic` идемпотентна в этом смысле по конструкции (тот же путь, что уже используют
`_discTemplate`/`_clanTemplate` и т.д. для замены `.md`-файлов авторских записей).

### 3.3 Один эндпоинт на все категории, не 8+ копий

`POST /api/library/:kind/:slug/image` (JSON `{ base64 }`, `ext` не нужен в теле — п.3.1 фиксирует
его как `png` безусловно) — один параметризуемый маршрут, каталог арта берётся из общей таблицы
`{kind → каталог}` (та же, что уже неявно используется в `_artFileSet(section)` — стоит явно
свести её в один объект-константу, если её ещё нет, раз число потребителей растёт с 4 до 9+ с
Частью II). Не требует различать MD-track/JSON-track — оба уже одинаково используют
`_artFileSet(section)`/`_withArt` для чтения, значит и запись одинакова для обеих.

### 3.4 Доступность — не только у авторских записей

**Важное отличие от Правки/Удаления:** права редактирования текста канона защищены (`custom`)
по причинам из `2026-08-08-library-canonical-edit-analysis.md` (canon — версионируемый файл,
`update.bat` затирает правки). **Изображение — не тот же случай.** Файлы `web/public/img/…` не
исключены из релизной сборки (`tools/release-exclude.json` их не трогает) и версионируются точно
так же, как `.md`-канон — то есть формально загрузка картинки поверх канонической записи
рискует тем же самым (правка отслеживаемого файла, откат на `update.bat`). Раз пользователь
явно попросил загрузку «для карточек библиотеки» без оговорки «только авторских» — фиксирую
это явно как решение, а не молчаливое расширение: **загрузка доступна для любой записи, включая
каноническую**, с тем же предупреждением по духу, что уже стоит в
`2026-08-08-library-canonical-edit-analysis.md` §1 — эта конкретная правка канона (замена PNG)
переживёт обновление ничуть не лучше, чем правка текста. Технически риск идентичен, но
последствие мягче: слетевшая картинка — это откат к сгенерированному арту (какой-то арт всё
равно есть/появится через `generate_library_art.js`), не потеря авторского текста. Считаю это
приемлемым и не блокирую фичу, но фиксирую в риск-таблице (§4) — если пользователь сочтёт риск
неприемлемым, реализация ограничивается `custom`-записями одной строкой на роутере.

## 4. Риск/сложность

| Аспект | Оценка | Комментарий |
|---|---|---|
| Backend-эндпоинт | низкий | копирует уже проверенный паттерн `upload-image` персонажей, `writeFileAtomic` уже идемпотентна |
| PNG-only ограничение | низкий | одна строка проверки + `<canvas>`-конвертация на фронте (стандартный API) |
| Кнопка в детейл-модалке | низкий | тот же `.v20-disc-detail-actions`, что уже используют Правка/Удаление/Форк |
| Риск потери правки на `update.bat` для канона | принят, не блокирует | см. §3.4 — мягче, чем потеря текста; можно ограничить до `custom`, если пользователь захочет пересмотреть |
| Кэш-инвалидация | низкий | `_artFileSet` уже читает каталог на каждый запрос без кэша (п.1) — новый файл виден сразу, инвалидировать нечего |

# Часть II — Новая вкладка библиотеки «Смертные»

## 1. Текущее состояние

Вкладка «Сородичи» (`index.html:730-772`) — образец структуры второго уровня: `.tab-bar`
(верхний уровень, `data-tab`) → `.disciplines-subtab-bar` с `data-kin-group` (второй уровень,
СВОЙ обработчик в `scripts.js`, намеренно не переиспользует `.tab-btn`-делегат — иначе клик
внутри «Сородичи» гасил бы активность самой вкладки «Сородичи», см. комментарий `:739-744`) →
`.kindred-subpanel` на каждую из трёх (Кланы/Секты/Титулы). Загрузка данных — `loadKindred(which)`
(`v20-sheet.js:1573-1592`) — **не generic-цикл**, три отдельных if-блока, по одному на кланы/
секты/титулы, каждый со своим кэшем (`_clansCache`/`_sectsCache`/`_titlesCache`) и своим
рендерером карточек/детейла (`_libClanCardsHtml`/`_libSectCardsHtml`/`_libTitleCardsHtml` и
детейл-аналоги) — **не потому что не додумались обобщить**, а потому что у Кланов/Титулов есть
собственные поля (Дисциплины+Слабость у клана; Принадлежность+Негативный-бейдж у титула),
которых нет у Секты — генерализация трёх разных форм card/detail не была бы чище, чем три явных
функции.

Бэкенд той же тройки (`library.js:109-596`) — тоже три отдельных, почти идентичных блока
(loader + `_xTemplate` + POST/PUT/DELETE) на клан/секту/титул. **В отличие от фронтенда,
здесь у Клана/Титула нет реальной причины для раздельного кода** — различия сводятся к разному
набору строковых полей в шаблоне, ничего структурно уникального. Достоинства/недостатки/факты
биографии (JSON-track) уже прошли этот путь раньше — там ровно та же ситуация (3 почти
одинаковых блока) была обобщена в один параметризуемый `_jsonLibRoutes({...})`
(`library.js:608-663`) при добавлении третьей JSON-категории.

## 2. Декомпозиция запроса

1. Новая вкладка верхнего уровня «Смертные», **после «Сородичи»**, до «Дисциплины».
2. Внутри — 5 под-вкладок: «Правительственные службы», «Религиозные организации», «Криминал»,
   «Гражданские организации», «Должности» (в тексте задачи — с опечатками; далее везде
   нормализованное написание).
3. Явно не оговорено пользователем: набор полей записи в каждой под-вкладке, есть ли своя
   форма создания, показывается ли изображение — по умолчанию считаю «то же, что у остальной
   библиотеки» (Часть I применяется к ним без исключений, см. Часть I п.2.4).

## 3. Решения Аналитика

### 3.1 Единая схема поля записи — по образцу «Секты», не «Титула»/«Клана»

Все 5 категорий структурно — **справочник названий с описанием**, без полей, специфичных для
конкретного типа (у «Секты» их тоже нет — `source`/`note`/`description`, ничего больше). Ничего
в запросе не намекает на что-то вроде «Негативный» у Титула или «Дисциплины клана» у Клана для
организаций смертных или должностей. **Решение: все 5 категорий используют одну и ту же схему
записи, что и «Секты»** (имя, источник, примечание, описание) — не 5 разных форм, а 5
экземпляров уже проверенной формы. Если впоследствии понадобится, например, «Должности» с
доп.полем (аффилиация-организация, как у Титула — «Принадлежность») — отдельная доработка
позже, не предвосхищаем здесь.

### 3.2 Бэкенд — обобщённый MD-track фабричный хелпер, не 5 копий

Ручное дублирование блока «loader + template + POST/PUT/DELETE» приемлемо для 3 копий
(Кланы/Секты/Титулы, уже так и есть), но добавление ещё 5 **идентичных друг другу** (п.3.1)
копий доводит дублирование до 8 почти одинаковых блоков подряд в одном файле — тот самый порог,
после которого сам проект уже проходил обобщение (JSON-track, `_jsonLibRoutes`, п.1). **Решение:
завести аналогичный `_mdLibRoutes({ apiName, dir, extraNote })`-хелпер**, реализующий
loader+`_genericMdTemplate`+POST/PUT/DELETE один раз, зарегистрировать им все 5 новых категорий
(и, по желанию Разработчика при реализации — опционально мигрировать на него же существующую
«Секты», раз схема идентична; Кланы/Титулы, у которых схема реально другая, остаются как есть,
без изменений). Экономит ~450 строк (5 × ~90 строк текущего паттерна на категорию) против
буквального копирования блока «Секты» пять раз.

### 3.3 Каталоги и имена секций

`system/library/mortal-government/`, `mortal-religious/`, `mortal-crime/`, `mortal-civic/`,
`mortal-positions/` — плоско, без вложенности `mortal/<sub>/` (проект нигде не вкладывает
подкаталоги внутри `system/library/`, кроме `disciplines/paths` — внутренней технической детали
самих Путей, не пользовательской категории; плоская схема — единственный текущий прецедент для
пользовательских категорий). Те же имена секций — для `web/public/img/system/library/
mortal-government/<slug>.png` и т.д. (Часть I §3.3 общий эндпоинт читает каталог по той же
таблице `kind → каталог`).

### 3.4 Фронтенд — 5 экземпляров одной параметризуемой функции, не 5 копий

Зеркалит решение §3.2: раз все 5 категорий используют одну схему (§3.1), их
card/detail-рендереры **не обязаны** повторять паттерн «у Кланов/Титулов своя функция,
потому что своя схема» — здесь схема одна, значит один параметризуемый набор функций
(`_libMortalOrgCardsHtml(section)`/`_libMortalOrgDetailHtml(rec)`/`ensureMortalOrgSection(section)`
с кэшем `Map<section, list>` вместо пяти одноимённых переменных `_govCache`/`_religiousCache`/…)
переиспользуется во всех пяти под-вкладках. Второй уровень вкладок — тот же паттерн
`data-kin-group`-делегата, что уже есть у «Сородичи» (§1), просто на новый набор значений
(например `data-mortal-group="government|religious|crime|civic|positions"`) и свой контейнер
`#tab-lib-mortal`/`.mortal-subpanel`.

### 3.5 Позиция вкладки

Пользователь явно попросил «после Сородичи» — `data-tab="lib-mortal"`
(`index.html`, вставить между `:731` и `:732`, кнопка после «Сородичи», перед «Дисциплины»);
`.tab-panel` для неё — сразу после `</div>` закрытия `#tab-lib-kindred` (`:772`), перед
`#tab-lib-disciplines` (`:774`) — порядок кнопок и порядок панелей должны совпасть, иначе
Tab-навигация клавиатурой пойдёт не по видимому порядку.

## 4. Риск/сложность

| Аспект | Оценка | Комментарий |
|---|---|---|
| Бэкенд (`_mdLibRoutes` фабрика + регистрация 5 категорий) | средний | новый обобщающий хелпер — риск не в сложности, а в аккуратном переносе уже проверенной логики (custom-гейт, slug-коллизии, `_deleted/`-корзина) без регрессии для существующих потребителей, если «Секты» тоже мигрируют на него |
| Фронтенд (вкладка + 5 под-вкладок + параметризованные рендереры) | средний | объём разметки/делегатов сравним с уже сделанным K5 (Сородичи, 2026-08-04) — прецедент есть, копировать структуру, не изобретать |
| Форма создания/правки | низкий | `_LIB_KIND_CONFIG` (library-authoring.js) уже общий на все категории — 5 новых записей конфига, по образцу «sects» (`title/fields`, без `fieldLabels`/`categoryRecordKey`) |
| Загрузка изображений (Часть I) | низкий | новые категории автоматически покрыты общим эндпоинтом Часть I §3.3, если секции зарегистрированы в общей таблице `kind → каталог» |
| Совместимость с Частью III | — | Организация/Должность (Часть III) читают именно эти 5 категорий — реализация Части III блокируется завершением Части II (порядок ниже) |

# Часть III — Поля Секта / Роль в секте / Организация / Должность (смертный, охотник)

## 1. Текущее состояние — найден реальный пробел в поддержке «охотника»

**Значимая находка, не входила в объём запроса:** `INFO_FIELDS_BY_LINEAGE`
(`scripts.js:2012-2076`) содержит явные наборы полей для `vampire`/`fairy`/`mortal` — но **не
для `hunter`**. `infoFieldsFor(lineage)` (`:2093-2095`) для любой линейки без явного ключа
откатывается на `INFO_FIELDS_GENERIC` (`:2078-2092`) — общий минимум для «оборотней/магов/
охотников», который **не включает `profession`** и вообще структурно ближе к вампиру/фее
(`race`, `sect`-как-«Фракция», `hierarchy`), чем к смертному. При этом V20-лист персонажа уже
считает охотника смертным на уровне механики: `_resolveSheetLineage`
(`server.js:714-721`) явно матчит `/hunter|охотник/` → `'mortal'` (тот же `character_sheet_
mortal.md`, что и для смертных, `server.js:707`) — то есть бэкенд уже относится к охотнику как к
смертному, а вкладка «Информация» — нет. Задача пользователя («на карточке смертного и
охотника») требует эту рассинхронизацию исправить как предпосылку, иначе новые поля
физически некуда добавлять для охотника (ветки `hunter` в `INFO_FIELDS_BY_LINEAGE` просто нет).

**Решение:** завести `INFO_FIELDS_BY_LINEAGE.hunter`, идентичный (после правок ниже)
`INFO_FIELDS_BY_LINEAGE.mortal` — не алиас (`hunter: mortalFields` через одну переменную), а
собственный литерал: сегодня совпадают, но у охотника в V20 есть Numina/практики, которых нет у
рядового смертного (уже отражено в отдельном месте, `v20-sheet.js:75`, `:1940` — организация
психических способностей по «Шаг 8» листа смертного касается «экстрасенсов/практиков», не
общего поля «Информация») — деривация через общую переменную создала бы риск, что будущая
чисто-смертная правка (например, добавление поля, специфичного для обычного человека) незаметно
утечёт и охотнику. Явное дублирование двух литералов здесь безопаснее одной точки правды —
такое исключение из «не дублировать» уже встречалось в этой сессии (клан vs титул,
`_LIB_FIELD_RECORD_KEY`, techspec Часть I §2 discipline-picker) ровно по той же причине: две
вещи, которые СЕЙЧАС совпадают, но не обязаны совпадать логически.

`REQUIRED_INFO_KEY` (`:2098`, `{ vampire: 'clan', fairy: 'race', mortal: 'profession' }`) —
`profession` остаётся обязательным полем-якорем и для смертного, и (новое) для охотника,
независимо от его новой позиции в массиве (см. §3.4) — обязательность это про «всегда видимое
поле», не про порядок.

## 2. Декомпозиция запроса

1. Поле «Секта» на карточке смертного/охотника — выбор из библиотеки «Сородичи → Секты».
2. Если «Секта» заполнена — появляется поле «Роль в секте» (свободный текст, источник не
   указан пользователем — не библиотечный пикер).
3. Поле «Организация» — выбор из библиотеки «Смертные», из 4 под-вкладок (все, кроме
   «Должности»).
4. Поле «Должность» — появляется, если «Организация» заполнена; выбор из библиотеки
   «Смертные → Должности».
5. Поле «Профессия» — переместить сразу после «Должность».

## 3. Решения Аналитика

### 3.1 Ключ поля «Секта» — переиспользовать `sect`, не заводить новый

У вампира уже есть поле с ключом `sect`/лейблом «Секта» (`scripts.js:2018`) — свободный текст.
Смертный/охотник получает **семантически то же понятие** (принадлежность к секте Сородичей —
Камарилья/Шабаш/Анархи и т.д., просто со стороны человека — гуля, союзника, осведомлённого
смертного), только с UI-пикером вместо чистого текста. Один ключ `sect` на всю карточку — уже
устоявшийся в проекте принцип (одно и то же понятие = один ключ поля, независимо от линейки,
например `hierarchy`/`role`/`belonging` уже общие для vampire/fairy/mortal). Вампирская версия
поля **не трогается** — остаётся простым текстом без пикера (не входит в объём запроса; при
желании добавить пикер и туда — отдельная маленькая доработка, не эта).

Пикер — **одиночный выбор** (клик заменяет значение и закрывает панель), НЕ toggle-мультивыбор
как у Дисциплин: пользователь не просил «несколько сект», а у персонажа физически одна секта.
Технически — тот же паттерн, что уже даёт пикер Титула (не пикер Дисциплин) —
`char-detail.js:1131-1166`/`:1250-1281`, минимальная переделка (другой источник данных
`/api/library/sects`, тот же клик-оверрайт).

### 3.2 Новые ключи полей — `sectRole`, `organization`, `position`

Три новых ключа, три новых лейбла в `EDITABLE_FIELD_MAP` (`web/lib/db.js:516+`, отвечает за
запись значения обратно в `.md`-карточку) и три новых сопоставления лейбл→ключ в парсере
карточки (`web/lib/parsers/character.js`, рядом с `:119, :141` — `if (k === 'Роль в секте')
c.sectRole = v; if (k === 'Организация') c.organization = v; if (k === 'Должность') c.position =
v;`). Механическая, невысокая по риску правка — тот же паттерн, что уже есть для каждого
существующего поля.

### 3.3 «Организация» — пикер с группировкой по 4 под-вкладкам, не плоский список

Источник — 4 из 5 категорий Части II (без «Должностей» — она отдельное поле). Пикер запрашивает
все 4 эндпоинта и объединяет результат клиентской стороной, с группировкой по разделу (4
именованные группы — «Правительственные службы»/«Религиозные организации»/«Криминал»/
«Гражданские организации» — а не слитный список без подписи, откуда какая запись): по духу
ближе к группировке «Клановые/Все» в пикере Дисциплин (несколько именованных `.v20-lib-list`
внутри одной панели), чем к одногрупповому пикеру Титула/Секты. Одиночный выбор (как «Секта»,
§3.1) — «организация» у персонажа тоже одна.

### 3.4 «Должность» — пикер по образцу «Титула», условная видимость от «Организации»

Источник — `/api/library/mortal-positions` (одна плоская группа, без под-группировки — как у
пикера Титула). Одиночный выбор.

### 3.5 Условная видимость — CSS-переключение существующей строки, не вставка/удаление DOM

**Ключевое техническое решение, определяющее сложность реализации.** VIEW-режим уже прячет
пустые необязательные поля классом `cdet-opt-empty` (`char-detail.js:52-54`) — но эта строка
**остаётся в DOM**, просто визуально скрыта; не создаётся заново при появлении значения. Тот же
механизм подходит и для EDIT-режима: строки «Роль в секте»/«Должность» **всегда присутствуют**
в наборе полей линейки (значит и всегда есть в DOM, как любое другое поле), но получают
доп.класс, скрывающий их, пока триггер-поле (`sect`/`organization` соответственно) пусто; live
input-обработчик на триггер-поле переключает класс при вводе — прямое расширение уже
существующего в этой же вкладке паттерна реактивности (Клан → пересборка datalist/пикера
Дисциплин, `char-detail.js:1237-1244`/discipline-picker techspec Часть I §5.1). **Не** проектируем
динамическую вставку/удаление DOM-узла строки — это потребовало бы отдельной ветки в generic
restore-логике `_exitInfoEdit` (`.cdet-key + *`, discipline-picker techspec §6), которая сегодня
предполагает «строка всегда была и остаётся», а не «строка появилась/исчезла посреди
редактирования». CSS-скрытие полностью избегает этого класса рисков — та же причина, по которой
Часть II discipline-picker техспеки уже выбрала не-скрытие элемента из списка, а его пометку
(§3.4 того документа) для похожей проблемы «элемент должен то появляться, то исчезать».

Начальное состояние при входе в режим редактирования — не всегда «скрыто»: если у персонажа уже
заполнена Секта/Организация (даже до входа в правку), «Роль в секте»/«Должность» должны сразу
показываться редактируемыми, не требовать лишнего клика/ввода в Секту, чтобы проявить уже
существующее значение.

### 3.6 Порядок полей — итоговый массив `mortal`/`hunter`

Явное требование — «Профессия» сразу после «Должность». Остальной порядок (куда именно вставить
блок Секта/Роль-в-секте/Организация/Должность/Профессия относительно уже существующих полей)
пользователем не оговорён — предлагаю встроить его на текущее место `profession` (было
третьим полем, сразу после «Пол»), сохраняя его как единый смысловой блок «принадлежность/
занятость» в начале карточки, а не раскидывая по всему массиву:

```
status, statusDetails, gender,
sect, sectRole,              // новое — секта + условная роль в ней
organization, position,      // новое — организация + условная должность
profession,                  // перемещено (было 4-м полем, стало 7-м)
birthYear, location, relatives, attitude, hierarchy, role, nature, demeanor,
belonging, want, fear, leverage
```

Массив `hunter` — идентичен (см. §1, отдельный литерал, не алиас).

## 4. Риск/сложность

| Аспект | Оценка | Комментарий |
|---|---|---|
| `INFO_FIELDS_BY_LINEAGE.hunter` (новый) | низкий | копия mortal-массива, но требует явного решения «литерал, не алиас» (§1) — не забыть при реализации |
| Пикеры Секта/Организация/Должность | средний | 3 новых пикера, из них 2 (Секта, Должность) — прямые копии уже отработанного паттерна Титула; «Организация» — прямая копия паттерна группировки Дисциплин (переиспользование, не изобретение) |
| Условная видимость (§3.5) | средний | новый, но узкий по границам механизм (CSS-класс + input-делегат) — основной источник сложности всей Части III, единственное реально новое поведение, которого нигде в проекте ещё нет |
| `EDITABLE_FIELD_MAP`/парсер карточки | низкий | механическая правка по образцу существующих полей |
| Зависимость от Части II | блокирует | «Организация»/«Должность» физически не работают, пока не существует библиотека «Смертные» с данными — реализовывать строго после Части II |

# Рекомендованный порядок реализации (все три части)

1. **Часть II** (вкладка «Смертные» + 5 категорий) — фундамент, ничего в Части III не
   заработает без неё.
2. **Часть I** (загрузка изображений) — независима от остальных двух, можно параллельно с
   Частью II или после неё; единственная связь — секции «Смертные» из Части II должны быть
   зарегистрированы в общей таблице `kind → каталог» Части I §3.3, если она делается позже.
3. **Часть III** (поля смертного/охотника) — последней, зависит от Части II (§3.3/3.4 этого
   документа).

Каждая часть — самостоятельная по объёму техспека Системного аналитика (структурно они не
пересекаются в затрагиваемых файлах настолько, чтобы писать их одним документом); порядок
передачи на техспеку может следовать порядку реализации выше или по предпочтению пользователя.
