### 2.4 Что фактически создаёт «Новый НПС» vs. НПС модуля (нужно для П.1)

Два независимых механизма создания персонажа/НПС в проекте:

**A. `POST /api/characters`** (`routes/characters.js`, вызывается формой `#tab-new-npc`) —
создаёт **сразу канонiчного** персонажа в `characters/<линейка>/<slug>/`: полное имя, пол,
принадлежность, все специфичные для линейки поля (клан/секта/поколение/сир — вампир;
seeming/двор/дом — фея; племя/каста — оборотень; традиция — маг), биография, внешность,
арт. Персонаж сразу попадает в `characters_index.md` и грид «Персонажи».

**B. `POST /api/chronicles/:chr/modules/:mod/npc`** (`routes/modules/npc.js`, вызывается
вкладкой «НПС» внутри конкретного модуля) — три режима:
- `pc`/`canon` — просто ссылка на уже существующего канонiчного персонажа (ничего не создаёт).
- `modular` — создаёт **черновой** stub-НПС: только имя, ВСЕГДА `Линейка WoD: mortals`,
  `Пол: Неизвестно`, `Принадлежность: Эпизодический персонаж`, `Статус: Активен` — 8 строк,
  без единого специфичного для линейки поля. Хранится **внутри модуля**
  (`modules/<mod>/npc/<slug>/`), НЕ в `characters/` — не виден в общем гриде «Персонажи»
  до продвижения.

**Продвижение эпизодического НПС в канон** (уже реализовано, `routes/modules/npc.js:269-367`):
- `GET .../npc/:slug/promote-check` — проверяет 3 условия: НПС выжил (`survived`), фигурировал
  в финале модуля (`inFinale`), фигурировал в нескольких модулях (`inMultipleModules`).
- `POST .../npc/:slug/promote` — при выполнении всех условий (или `force:true`) копирует
  папку НПС в `characters/<выбранная линейка>/`, чинит поле «Линейка WoD» и эмодзи в
  заголовке (было жёстко `mortals`/🎭 — фикс FIX-14, см. комментарий в коде), правит
  «Родной город», регистрирует в `characters_index.md`.

**Вывод:** механизм B — это не «то же самое, что и A, просто по-другому называется». Это
намеренно облегчённый черновик для одноразовых НПС сцены, который либо остаётся черновиком
и удаляется вместе с модулем, либо явно продвигается в канон через отдельный, уже готовый
процесс. Подробнее — П.1 ниже.

### 2.5 Что делает старый `log-session` vs. новая пара «Сессия»+«Сессии модуля» (нужно для П.3)

**Старый** `#tab-log-session` → `POST /api/log-session` → `buildSessionPlan()`
(`routes/tools.js:304-482`) — один транзакционный «план изменений» с превью (dry-run + хэш
подтверждения, чтобы не записать устаревший план) на **семь** видов артефактов одним
действием:
1. Запись события в `chronicles/<chr>/events.md` (+ создание хроники/модуля, если новые).
2. `npc.md` нового модуля, при необходимости.
3. `finale.md` stub («⏳ ОЖИДАЕТ ГЕНЕРАЦИИ»), если отмечен флаг финала.
4. **Дневник-stub** для каждого отмеченного участника (`characters/…/journal/<период>.md`) —
   с комментарием Мастера, зарезервированным для последующей генерации прозы ИИ.
5. Нити — создание новых и закрытие отмеченных, в `open_threads.md`.
6. **Патч статуса персонажа** (например, торпор/гибель) для отмеченных участников —
   прямо в карточке `characters/…/<slug>.md`.
7. Инлайн-создание черновой карточки НПС для неопознанного участника (если указана линейка).
   Плюс: штамп «Состояние мира» в `archive/events.md` и фоновая пересборка индекса города.

**Новое** (по словам пользователя — уже фактическое положение дел):
- Страница **«Сессия»** (`page-session`, `session-screen.js`) — экран для ведения сцены
  вживую: выбор хроники/модуля, сценарий, список НПС, аудио, заметки по сцене/сессии.
  Кнопка «→ Записать сессию» переkey к следующему пункту.
- Панель **«Сессии»** на странице модуля (`modp-panel-sessions`, `modules.js:1665-1701`,
  API `POST/PUT/DELETE /api/chronicles/:chr/modules/:mod/session`,
  `routes/modules/sessions.js:26-53`) — добавляет **одну** запись `{дата, сыграно сцен,
  статус, заметки}` в `sessions.md` этого модуля. Редактируется/удаляется точечно.

**Различия — что реально не покрыто новой парой экранов:**

| Что делал `log-session` | Есть в новой паре? |
|---|---|
| Единая запись факта сессии (дата/сцены/заметки) | ✅ да, через «Сессии» модуля |
| Живой режим ведения сцены (НПС/аудио/заметки по ходу игры) | ✅ да, через страницу «Сессия» — то, чего в старом инструменте вообще не было |
| Создание новой хроники/модуля прямо из формы логирования | ❌ нет — модуль создаётся отдельным явным действием («+ Модуль») |
| Дневник-stub с комментарием Мастера по итогам сессии | ❌ нет нигде в новой паре |
| Патч статуса персонажа (торпор/гибель и т.п.) по итогам сессии | ❌ нет — только через ручное редактирование карточки |
| Создание/закрытие нитей по итогам сессии | ❌ нет — только через страницу «Нити» отдельно |
| Инлайн-создание черновой карточки НПС по итогам сессии | ❌ нет — только через «НПС» модуля (см. §2.4) отдельно |

Функционально «Сессия»+«Сессии модуля» — это НЕ подмножество/суперсет старого инструмента, а
другая модель работы: старый был «зафиксировать всё одним действием сразу после сессии»,
новый — «вести сцену вживую (недоступно раньше) + отдельно зафиксировать факт», а
дневники/статусы/нити/черновые-НПС теперь нужно вести каждое своим отдельным действием.
Самая заметная потеря — **дневник-stub с комментарием Мастера**: это единственное место в
проекте, которое гарантированно не даёт забыть про дневник после сессии (сейчас — только
через явную ручную вкладку «Дневники» в карточке персонажа, инициатива на Мастере).
Раз пользователь называет старый инструмент устаревшим осознанно — предполагается, что это
принятое решение, а не случайная потеря; фиксирую здесь только для явности, чтобы решение
было с полной картиной, а не «тихо потерялось при удалении вкладки».

### П.1 — Убрать вкладки «Новый НПС», «Модуль», «Сессия»

**«Новый НПС» — ✅ РЕАЛИЗОВАНО в этой сессии.** По ходу реализации обнаружилась ошибка в
исходном анализе ревизии 1: точку входа не пришлось строить с нуля — на странице «Персонажи»

Оборотня/Мага/Охотника форма шла не через `POST /api/characters`, а через устаревший
CLI-инструмент `new_npc.js` (`/api/tool/new_npc`) — без обязательных Племя/Традиция (FIX-9)

1. `LINEAGE_DEFS` (`scripts.js`) — Оборотень/Маг/Охотник переведены на `endpoint:'characters'`,
   поля переименованы под реальный API-контракт (`tribe`/`auspice`/`tradition`, было
   `Clan`/`Sect` с заглавной буквы под старый CLI), добавлены биография/внешность.
2. `modalSubmit` — убрана мёртвая `else`-ветвь (CLI-путь), теперь все 6 линеек идут одним
   и тем же кодом через `POST /api/characters`.
3. `index.html`/`scripts.js` — вкладка `new-npc` (тег + панель + весь код формы
   `btn-new-npc`/`_updateNpcForm`/`_clearNpcClanSectOnLineageChange`) удалена из
   «Инструменты»; дефолтная активная вкладка сдвинута на «Модуль».
4. Тесты (`ui.test.js`, `ui-full-flow.test.js`, `all.test.js`) переписаны под новую точку
   входа; по пути найден и исправлен реальный, не связанный с этой задачей race

   без явной синхронизации следующий тест может словить stale element).

Механизм создания НПС внутри модуля (§2.4-Б) и продвижение в канон — **не трогались**, это
самостоятельная, полноценно реализованная функция другого назначения.

**«Модуль» и «Сессия» — не реализовано, остаётся спецификацией.** Пользователь в этой сессии

### П.2 — Механика закрытия МОДУЛЯ (переадресовано с хроники пользователем) — ✅ в основном уже существовало

**Важная переадресация в этой сессии:** изначально (ревизия 2) речь шла о закрытии ХРОНИКИ.
Пользователь уточнил: «7 вещей одним действием» нужно прикрутить к закрытию МОДУЛЯ — тому
моменту, когда по модулю накопились сессии и есть все результаты. Закрытие хроники как
отдельная функция вкладки «Ещё» (`btn-close-chr` → `tools/close_chronicle.js`) этим не
затронуто и остаётся как в ревизии 2 (статус + финальная заметка + закрытие нитей, без
дневников/хронологии).

**Ключевая находка:** для закрытия МОДУЛЯ в проекте уже существовал развитый эндпоинт —
`POST /api/chronicles/:chr/modules/:mod/close` (`routes/modules/lifecycle.js:204-335`,
кнопка «🔒 Закрыть модуль» на странице модуля, `modules.js:2711-2756`) — покрывающий
БОЛЬШУЮ часть исходного списка из 7 пунктов ещё до этой сессии:

| Из списка «7 вещей» | Статус в `/close` |
|---|---|
| Запись события в хронику | ✅ уже есть — AI собирает каноничную запись из журнала сессий, дописывает в `events.md` |
| Финал-stub | ✅ уже есть, причём **сильнее stub'а** — AI сразу пишет полный `finale.md` по фактам сыгранных сессий |
| Дневник-stub с комментарием Мастера | ✅ уже есть **отдельным механизмом**: чекбокс «Сгенерировать дневники» (`modp-close-diaries-check`, по умолчанию выключен) в том же диалоге закрытия — при включении вызывает **полную** AI-генерацию прозы по каждому участнику с реальной, распарсенной из поля «Время» модуля датой (`_parsePeriodFromModuleTime`), а не сегодняшней. Сильнее, чем лёгкий stub — решено ничего не добавлять сверху (см. ниже). |
| Создание хроники/модуля | Н/П — closing работает над уже существующим модулем, создавать нечего |
| Нити | ❌ не автоматизировано — сознательное решение (см. ниже) |
| Патч статуса персонажа | ❌ не автоматизировано — сознательное решение (см. ниже) |
| Инлайн-создание НПС | Н/П — участники модуля уже определены через `npc.md` (§2.4), новых имён на этом шаге не появляется |

**Сделано в этой сессии** — только одна маленькая правка: в список `reminders`, который
эндпоинт уже возвращал (и клиент уже показывал тостом после закрытия), добавлена строка
«Статусы персонажей (торпор/гибель и т.п.) — обновить вручную на карточке» — раньше эта
тема вообще не упоминалась, хотя была в исходном списке «7 вещей». Плюс рефакторинг:
`diaryToneFor`/`CLAN_DIARY_STYLE` (тон дневниковой прозы по клану) вынесены из `routes/tools.js`
в `routes/modules/shared.js` — на будущее это общий источник для обоих мест, где рождаются

**Почему нити и статус НЕ автоматизированы — явное решение, не недосмотр:**
