**Дата:** 2026-08-04 · **Роль:** Системный аналитик · **База:** [workplan](2026-08-04-city-view-tabs-workplan.md) (V1–V5, карта покрытия)

Открытых вопросов workplan'а не осталось — решения (контейнер «Правила и
ограничения», перенос «Значимых мест» в «Географию», размещение «Сеттинга»)

## Сквозное техническое решение — почему НЕ нужен новый REST-ресурс

Первая идея для CRUD «Значимых мест» — REST-ресурс по образцу районов
(`POST/PUT/DELETE /api/cities/:slug/districts/:id`, отдельные файлы
`district.md`). **Не подходит**: районы — самостоятельные сущности со своей
папкой, «Значимые места» — это просто одна секция `city.md`
(`## Значимые места`), без файловой структуры. Использовать тяжёлый
REST-per-record ради одной текстовой секции — не нужный масштаб.

**Найден прямой прецедент в этом же проекте** — «Ключевые точки» локации
(`web/routes/locations.js:196`, `key === 'keyPoints'`): значение уже
приходит с клиента **готовой markdown-таблицей** и пишется в файл как
есть (regex-replace секции, без прогона через какой-либо построчный
нормализатор). Клиент (`_collectLocDetKeyPoints`,
`web/public/scripts/locations.js`) сам собирает все строки формы в
`| Место | Описание |` и шлёт одним PUT — «Добавить»/«Удалить» ряд —
чисто DOM-операции, ни одна не бьёт по сети; в сеть уходит только «Сохранить».

**Решение:** «Значимые места» — тот же паттерн. Один PUT
`/api/cities/:slug` с `fields.landmarks = <готовая таблица>`, без новых
эндпоинтов. Добавить/Удалить запись — DOM-операции над карточками, не
запросы.

### Препятствие, которое иначе тихо сломало бы таблицу

`PUT /api/cities/:slug` сейчас (`web/routes/cities.js:414-425`) для
**каждого** ключа из `CITY_SECTIONS` прогоняет значение через
`upsertCitySectionFromForm` → `citySectionBody` (= `_citySection`,
`web/lib/parsers/city.js:30`):

```js
function _citySection(txt) {
  const lines = String(txt == null ? '' : txt).split('\n').map(l => l.trim()).filter(Boolean);
  return lines.length ? lines.map(l => l.startsWith('-') ? l : `- ${l}`).join('\n') : '- …';
}
```

Эта функция **безусловно добавляет `- ` к каждой строке**, не
начинающейся с дефиса. Отправь мы туда строку `| Название | Описание |` —
получим `- | Название | Описание |` в файле, таблица сломана с первого же
сохранения. Это не гипотетический риск — тот же класс проблемы уже ловили
в этом проекте раньше (round-trip байт-в-байт, §A1.6).

**Контракт:** в цикле `for (const [key, heading] of CITY_SECTIONS)`
(`web/routes/cities.js`) добавить специальный случай **до** общей ветки —
по образцу уже существующих спецкейсов `keyPoints`/`vtmText` в
`web/routes/locations.js`:

```js
for (const [key, heading] of CITY_SECTIONS) {
  if (typeof b.fields[key] !== 'string') continue;
  if (key === 'landmarks') {
    // Таблица уже собрана клиентом целиком — писать как есть, БЕЗ
    // citySectionBody/бул­летизации (сломала бы «| Название | Описание |»).
    if (b.fields[key].trim() === (currentParsed.sections[key] || '').trim()) continue;
    const { text, created } = upsertCitySection(cityMd, heading, b.fields[key]);
    cityMd = text;
    sectionsWritten.push(created ? `${key} (создана)` : key);
    continue;
  }
  // … существующая общая ветка (upsertCitySectionFromForm) без изменений
}
```

`upsertCitySection` (не `-FromForm`) уже экспортирован из
`web/lib/city_md_writer.js` — пишет тело секции как есть, без нормализации.
Импорт в `cities.js` добавить рядом с уже импортированным
`upsertCitySectionFromForm`.

**«Unchanged section skip»** продолжает работать корректно: `parseCityMd`
(`web/lib/parsers/city.js:87-96`) снимает только префикс `- ` — строки
таблицы (`| ... |`) под этот паттерн не попадают и проходят в
`currentParsed.sections.landmarks` без изменений, так что сравнение
«прислали то же самое → не трогаем файл» работает и для табличного
формата (проверяется в §V5 приёмкой на round-trip).

**Экранирование `|` в ячейках:** переиспользовать `escapeTableCell`/
`unescapeTableCell` (`web/lib/parsers/shared.js`, уже используются для
`political_state.md` — тот же класс проблемы «`|` в названии двигает
колонки», FIX-2). Название/описание записи могут содержать `|` — без
экранирования это сломает разбор таблицы при следующем чтении.

## V1 · Каркас вкладок

**Бизнес-смысл:** заменить единый markdown-дамп на 4 явные вкладки —
структура последовательно ведёт GM от идентификации города к деталям.

**Поток:**
1. `_renderCityView()` — вместо `<div class="md-body">${mdToHtmlBlock(body)}</div>`
   рендерит таб-бар + 4 панели, по образцу уже существующего
   `.cdet-tab-bar`/`.city-edit-tabs` (форма редактирования, те же классы —
   визуальное единообразие, не второй способ переключать вкладки в
   проекте).
2. Переключение — тот же паттерн делегирования на `document`, что уже
   обрабатывает `data-city-tab` в форме редактирования (`city.js`,
   `document.addEventListener('click', …)` где проверяется
   `[data-city-tab]`) — расширить существующий обработчик или завести
   параллельный на `[data-city-view-tab]`, если делегирование конфликтует
   с логикой редактирования (обе формы используют один и тот же
   `#city-detail-content` контейнер, но не одновременно — просмотр и
   редактирование переключаются, не сосуществуют, так что коллизий по
   DOM нет; отдельный дата-атрибут всё равно чище для читаемости кода).
3. Активная вкладка по умолчанию — «Общая» (первая), не запоминается
   между открытиями (как и `_renderCityEdit`, которая всегда открывается
   на «Поля»).

**Данные:** без изменений — все 4 панели рендерятся из уже загруженного
`_cityDetail` (`d.parsed.sections`, `d.districts`, `d.locations`),
дополнительных запросов не требуется.

**Приёмка:**
- Открытие города показывает таб-бар с 4 вкладками, активна «Общая».
- Переключение вкладок не делает сетевых запросов (весь контент уже в
  `_cityDetail`).
- Кнопки «✏ Редактировать»/«🗑 Удалить»/«← К городам» в шапке — без
  изменений, видны при любой активной вкладке (шапка — вне таб-панелей).

   read-only текст внутри, тем же паттерном, что и остальные поля вкладки.
   Свёрнут по умолчанию (симметрично редактированию/созданию).

сохранения нет ни у одного поля (кроме отдельно оговорённых «Значимых
мест» на вкладке «География», см. V5).

**Обработка ошибок:** нет — нет сетевых операций.

**Краевые случаи:**
- Пустая секция (`- …` → после `parseCityMd` пустая строка) — показывать
  плейсхолдер `«— не заполнено —»`, не пустое место без подписи (иначе
  неясно, поле не заполнено или вкладка не догрузилась).

**Приёмка:**
- Все 10 текстовых полей + группа показывают именно то содержимое, что
  видно в форме редактирования тех же ключей (сверка вручную на Париже).
- Группа «Правила и ограничения города» содержит ровно 3 поля — mortals/

## V5 · Вкладка «География»

**Состав:** Районы (без изменений), Значимые места (редизайн, CRUD),
Ключевые локации (read-only текст), Охотничьи угодья (read-only текст).

### Районы
Без изменений — `_cityViewDistrictsHtml()` переносится в панель
«География» как есть.

### Значимые места — редизайн под карточки

**Формат хранения** (новый, вместо буллет-листа) — markdown-таблица:
```
## Значимые места
| Название | Описание |
|---|---|
| Опера Гарнье | Главный Элизиум, вотчина Toreador |
```
Пустая секция — та же таблица с шапкой и без строк данных, ЛИБО, если
строк нет вовсе — сохранить текущий плейсхолдер `- …` (не переписывать
пустые/нетронутые города только ради смены формата — файл не трогается,
пока пользователь не откроет и не сохранит запись сам).

**Парсинг для чтения** (новая функция `parseLandmarkRows(text)`,
`web/lib/parsers/city.js`, по аналогии с `parsePoliticalFactions`):
- Строки вида `| Название | Описание |` → `{ name, desc }`.
- **Обратная совместимость:** секция ещё не в табличном формате (старый
  буллет-лист, как сейчас у Парижа/Balmont/Париж_1 — везде плейсхолдер
  `- …`, но у гипотетического города с реальными буллетами) — строка без
  `|` в начале трактуется как `{ name: строка без буллета, desc: '' }`.
  Не терять данные при первом открытии старого города, не требовать
  ручной миграции.

**UI (карточки, вкладка «География»):** переиспользовать 1:1 визуальный
паттерн «Ключевых точек» локации (`.hooks-item`/`.hooks-input`/
`.hooks-del-btn`/`.hooks-add-btn`, `web/public/styles.css:6254+`,
`web/public/scripts/locations.js` — `keyEditHtml`/`_collectLocDetKeyPoints`)
— тот же UX, что уже отгружен и знаком пользователю по локациям, не
третий вариант «строка + удалить + добавить» в проекте:

```html
<div id="city-landmarks-list">
  <div class="hooks-item">
    <input class="hooks-input city-landmark-title-inp" placeholder="Название…">
    <input class="hooks-input city-landmark-desc-inp" placeholder="Описание…">
    <button class="hooks-del-btn" title="Удалить">✕</button>
  </div>
  …
</div>
<button class="hooks-add-btn" id="city-landmarks-add">+ Добавить запись</button>
<button class="btn-submit" id="city-landmarks-save">✓ Сохранить</button>
```

Новые CSS-классы — только ширина колонок (аналог уже существующих
`.keypt-place-inp`/`.keypt-desc-inp`, `styles.css`):
```css
.city-landmark-title-inp { flex: 0 0 30%; }
.city-landmark-desc-inp  { flex: 1; }
```

**Поток (события):**
1. «+ Добавить запись» — добавляет пустую `.hooks-item` в DOM. Чисто
   клиентское действие, сети нет (как «Добавить точку» у локаций).
2. «✕» на строке — удаляет строку из DOM. Чисто клиентское действие.
3. «✓ Сохранить» — `_saveCityLandmarks()`:
   - собирает все `.hooks-item` из `#city-landmarks-list` в массив
     `{name, desc}` (по образцу `_collectLocDetKeyPoints`, фильтр пустых
     строк — если и название, и описание пусты, строка пропускается);
   - строит markdown-таблицу через `escapeTableCell` на каждой ячейке;
   - `PUT /api/cities/:slug` с `{ fields: { landmarks: <таблица> } }` —
     **единственный** сетевой вызов на весь цикл добавления/удаления
     нескольких записей (не по одному запросу на строку);
   - по успеху — `showToast('Значимые места сохранены', 'success')` +
     обновление `_cityDetail`/перерисовка панели (без полной перезагрузки
     страницы — обновить `_cityDetail.parsed` из ответа PUT, как уже
     делает `_saveCityEdit()` после сохранения).

**Обработка ошибок:**
- PUT вернул `!ok` — `showToast(r.error, 'error')`, DOM-состояние карточек
  не сбрасывается (пользователь не теряет введённое, может поправить и
  нажать «Сохранить» снова) — тот же принцип, что уже применяется к
  ошибкам сохранения города в целом.

**Краевые случаи:**
- 0 записей + нажатие «Сохранить» — секция уходит в состояние
  «пусто» (не крашится на пустой таблице): писать как `- …` (тот же
  плейсхолдер, что и остальные секции при отсутствии контента, а не
  таблицу с одной пустой шапкой без строк — красивее и единообразнее с
  остальными секциями city.md).
- **Round-trip:** открыть панель на городе с уже сохранёнными записями →
  ничего не менять → нажать «Сохранить» → файл не должен измениться
  байт-в-байт (тот же принцип, что уже проверяется тестами для всех
  остальных точечных секций, §A1.6 прошлого цикла) — прямое следствие
  «unchanged section skip», см. сквозное решение выше.
- Название/описание содержат `|` — не ломает таблицу при следующем чтении
  (проверяется экранированием, см. сквозное решение).

**Приёмка:**
- Добавление 2 записей + сохранение → `city.md` содержит корректную
  таблицу из 2 строк под `## Значимые места`.
- Перезагрузка страницы города после сохранения → карточки
  восстанавливаются из файла в том же составе.
- Удаление записи + сохранение → строка пропадает из файла.
- Старый формат (буллет-лист, если встретится) → при открытии не падает,
  показывает буллеты как записи без описания; после первого «Сохранить»
  переходит в табличный формат.

### Ключевые локации / Охотничьи угодья
Простой read-only рендер текста секции — тот же паттерн, что текстовые
поля вкладки «Общая» (V2), без структурных карточек: явного запроса на
CRUD для этих двух полей не было, только «отображать данные».

## Порядок реализации

1. **V1** — каркас вкладок, блокирует всё остальное (панели рендерятся
   внутрь него).
2. **V2, V3, V4** — независимы друг от друга после V1, каждая — просто
   read-only рендер уже существующих распарсенных структур. Можно вести
   параллельно/в любом порядке.
3. **V5, часть «Районы/Ключевые локации/Охотничьи угодья»** — тривиальна,
   как V2-V4, без зависимостей.
4. **V5, часть «Значимые места»** — отдельно и последней: единственная
   задача цикла, меняющая формат хранения данных и требующая правки
   бэкенда (`web/routes/cities.js`, спецкейс `landmarks`) — самая
   рискованная, делать с тестами на round-trip до переноса в остальные
   города.

## Общая приёмка цикла

- `npm run test:all` — 0 регрессий; новые тесты — round-trip таблицы
  landmarks (байт-в-байт при пустом изменении), парсинг legacy-буллетов,
  экранирование `|` в названии/описании записи.
- Ручная проверка (headless CDP): все 4 вкладки на Париже показывают
  ожидаемые данные; добавление/удаление/сохранение записи в «Значимых
  местах» проходит без ошибок; `cities/paris/city.md` MD5 не меняется на
  шагах, где ничего не сохранялось.
