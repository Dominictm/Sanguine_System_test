# Анализ: правка/удаление канонических записей библиотеки

**Собрано:** Аналитик, 2026-08-08.

**Запрос пользователя** (уточнён через вопрос): расширить существующий CRUD
библиотеки (сейчас — только авторские записи, `custom: true`) на канонические
записи V20 (дисциплины/психика/кланы/секты/титулы/достоинства/недостатки/
факты биографии, все из `system/library/`).

---

## 1. Executive Summary

Технически «просто снять проверку `custom`» — тривиально (одна строка на
каждый из ~16 PUT/DELETE-обработчиков в `web/routes/library.js`). Но это
**сломает канонический контент на каждом обновлении Рассказчика**, а не
просто «рискованно»: `update.bat` синхронизирует релизную ветку `test`
командой `git reset --hard origin/test` безусловно, без диалога
(`update.bat:126`, `CLAUDE.md` подтверждает это как осознанное решение — «при
обновлении сразу делает `git reset --hard` без диалога»). Канонические файлы
`system/library/**/*.md` — версионируемые (`git ls-files` подтверждает, не в
`.gitignore`, не в `tools/release-exclude.json`) и **не исключены** из
пересборки `test`. Прямая правка такого файла — это локальная модификация
отслеживаемого файла; следующий `update.bat` откатит её без предупреждения.
Удаление канонической записи (текущий паттерн — `fs.rename` в `_deleted/`)
столь же неустойчиво: git восстановит исходный файл на прежнем месте при
следующем `reset --hard`, а «удалённая» копия останется висеть в `_deleted/`
как дубликат — путаница, а не потеря данных, но тоже сюрприз для пользователя.

Прямая правка «в лоб» — не откладываемый риск, а гарантированная потеря
работы Рассказчика при первом же `update.bat`. Нужен другой механизм —
**оверлей поверх канона**, не правка канона на месте (см. §3).

---

## 2. Ключевые инсайты

- **Защита `custom`-only — не декоративная, а структурно обоснованная.**
  Она уже сегодня использует единственный паттерн, который переживает
  `git reset --hard`: создание НОВОГО файла остаётся неотслеживаемым
  (`git status` — untracked) до тех пор, пока никто не закоммитит его в
  `test`, а Рассказчик никогда не коммитит на своём чек-ауте. Поэтому
  авторские записи сегодня благополучно переживают обновления — это
  подтверждает, что untracked-новый-файл — рабочий, уже проверенный
  практикой паттерн, а не гипотеза.
- **Библиотека реально бывает двух «треков» с разной механикой хранения**:
  MD-track (дисциплины/психика/кланы/секты/титулы — один файл на запись) и
  JSON-track (достоинства/недостатки/факты биографии — один массив на
  категорию, запись — элемент массива). Любое решение должно работать для
  обоих одинаково, иначе получится два разных поведения под одной кнопкой.
- **Целевой пользователь этой конкретной фичи — не разработчик (`master`), а
  Рассказчик на релизной ветке `test`.** Форма создания авторских записей
  существует именно для того, чтобы ГМ добавлял хоумбрю-контент для своего
  города без похода в код. Значит сценарий «отредактировал канон → потерял
  правку на `update.bat`» — не краевой случай, а основной ожидаемый способ
  использования фичи, если её реализовать «в лоб».

---

## 3. Варианты решения

### Вариант A — прямая правка канонического файла (то, что буквально просят)
Снять проверку `custom` в PUT/DELETE. **Не рекомендуется**: гарантированная
потеря правок на первом `update.bat` (см. §1). Даже с предупреждением в UI
(«эта правка не переживёт обновление») — это порочный UX: разработка фичи,
специально созданной, чтобы прятать необходимость трогать код руками, но с
предупреждением «на самом деле не сохраняется по-настоящему».

### Вариант B — «оверлей» поверх канона (рекомендуется)
Правка/удаление канонической записи не трогает исходный `.md`/JSON-элемент,
а создаёт **отдельный, новый (untracked) файл-перекрытие** — тот же паттерн
хранения, что уже проверен на создании авторских записей:
- Правка: `system/library/<section>/_overrides/<slug>.md` (MD-track) или
  оверлей-запись с тем же `slug` и флагом `overridesCanonical: true`
  (JSON-track) — при чтении лоадер сначала берёт канонический список, затем
  накладывает оверлеи по `slug` (значения оверлея побеждают).
- Удаление: тот же оверлей-файл, но с флагом `hidden: true` — лоадер
  фильтрует запись из выдачи, не трогая исходник. «Восстановить каноническую
  запись» — просто удалить файл оверлея (естественная, обратимая операция).
- В UI разница видна пользователю: у канонической записи с активным
  оверлеем — бейдж «✏️ Изменено» (не «Авторское») + доп. кнопка «↺ Вернуть
  оригинал».

Сложность: умеренная, локализована. Нужно на каждый из 8 GET-лоадеров
(`web/routes/library.js`) добавить один merge-проход (канон + оверлеи по
slug), и завести аналогичный набор PUT/DELETE, которые не проверяют
`custom`, а просто пишут/удаляют оверлей-файл. Формат хранения близко
копирует уже существующий для custom-записей — не новая архитектура, а то же
решение, применённое второй раз с другим целевым файлом.

### Вариант C — вообще не трогать канон, только явно разрешить «форкнуть»
Кнопка у канонической записи «Создать свою копию на основе этой» —
предзаполняет форму создания авторской записи текущими значениями канона,
пользователь сохраняет как новую (`custom: true`) запись с новым slug/именем.
Канон остаётся нетронутым и видимым отдельно; у пользователя — своя копия по
уже отработанному пути (создание). Ноль нового бэкенд-кода — обвязка чисто
фронтенд (предзаполнение формы данными записи вместо пустой).
Не решает «удалить каноническую запись», зато не решает и её крайне дёшево
для «отредактировать под себя» — вероятно, закрывает 80% реальных запросов
Рассказчика («хочу немного другую версию Доминирования») без риска путаницы
из Варианта B (два одноимённых источника данных для одного slug).

---

## 4. Риск/сложность

| Аспект | Оценка | Комментарий |
|---|---|---|
| Вариант A (прямая правка) | — | не рекомендован: гарантированная потеря данных на `update.bat` |
| Вариант B (оверлей) | средний-высокий | требует merge-логики в 8 лоадерах + новый набор PUT/DELETE без `custom`-гейта + новое UI-состояние «Изменено»/«Вернуть оригинал»; самый полный по функциональности |
| Вариант C (форк-копия) | низкий | чисто фронтенд, переиспользует всю существующую инфраструктуру создания; не закрывает «удалить канон» |
| Совместимость с `update.bat` | решена только у B и C | оба хранят изменения как новые untracked-файлы — тот же проверенный паттерн, что у существующих авторских записей |

---

## 5. Рекомендация Аналитика

Начать с **Варианта C** (низкий риск, почти бесплатно, закрывает типовой
сценарий «доработать канон под свою хронику» без риска рассинхронизации) и
явно зафиксировать с пользователем, нужен ли впоследствии Вариант B
(полноценная правка/скрытие канона на месте, с индикацией «изменено») —
это отдельная, более тяжёлая техспека, которую стоит делать только если
форк-копии (C) окажется недостаточно на практике.

**Вариант A запрашивать не стоит** — буквальная реализация того, что было
сформулировано в задаче, тихо ломается первым же `update.bat` пользователя;
это стоит держать в голове как жёсткое ограничение, а не как то, что можно
«просто попробовать и посмотреть».
