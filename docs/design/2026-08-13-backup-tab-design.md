# UX/UI-дизайн — вкладка «Бэкап» в разделе «Инструменты»

> Роль-автор: **Дизайнер**. Адресат: **Разработчик**.
> Вход: [`2026-08-13-backup-tab-workplan.md`](2026-08-13-backup-tab-workplan.md) (Аналитик),
> [`2026-08-13-backup-tab-techspec.md`](2026-08-13-backup-tab-techspec.md) (Системный аналитик).
> Дата: 2026-08-13.

Техспека задаёт контракты API и структуру данных; этот документ — визуальная иерархия,
раскладка, состояния элементов и микрокопирайт поверх неё. Ничего из контрактов техспеки
(эндпоинты, имена полей, двухфазный `inspect`/`commit`) не меняется — здесь только то, что
техспека сознательно оставила фронтенду («см. B1.3», «на усмотрение разработчика»).

**Сценарий использования, определяющий тональность:** это не ежедневный инструмент, а
редкая операция «на всякий случай» — либо рутинное «сделать копию перед экспериментом»,
либо паническое «я что-то сломал, откатываю». Второй сценарий требует отдельного
визуального регистра: тревога уместна только в блоке восстановления, всё остальное —
спокойная утилитарная панель, как соседние вкладки «Инструментов».

Существующий язык интерфейса переиспользуется целиком: `.ls-section`/`.ls-sec-title`
(лог-сессии), `.chr-modal-*` с чекбоксом-разблокировкой (удаление модуля/хроники),
`--c-danger*` токены. Новых токенов и новой модальной системы не вводится.

## D1. Структура вкладки — три блока сверху вниз

```
┌─ tab-panel#tab-backup ────────────────────────────────────────────┐
│                                                                     │
│  💾 ГОРОДА                                            [ls-section] │
│  ☐ Выбрать все                                                     │
│  ☐ Париж         198 МБ                                            │
│  ☐ Балмонт          3 МБ                                           │
│  ☐ Париж (1)        1 МБ                                           │
│  [Создать бэкап]                                                   │
│  (прогресс / вывод — output-area)                                  │
│                                                                     │
│  ⚙ НАСТРОЙКИ                                          [ls-section] │
│  Ключи AI и назначения генераций — отдельным архивом.              │
│  ⚠ Содержит ключи AI в открытом виде. Не пересылайте архив.        │
│  [Сохранить настройки]                                             │
│                                                                     │
│  ⚠ ВОССТАНОВЛЕНИЕ ИЗ БЭКАПА                    [ls-section danger] │
│  Заменит текущие данные города. Перед заменой старая версия        │
│  переносится в «Удалённые», её можно вернуть вручную.              │
│  [Загрузить бэкап…]                                                │
│                                                                     │
└─────────────────────────────────────────────────────────────────┘
```

Порядок блоков — по возрастанию риска: создание (безопасно) → настройки (нейтрально) →
восстановление (разрушительно). Это работает как порядок чтения: пользователь, скроллящий
сверху вниз, доходит до опасной операции последней, увидев сначала мирный контекст, а не
наоборот.

Вкладка в `.tab-bar` — последней по счёту (после «Инструкции»): редкая операция не должна
конкурировать за первое место с «Учёт данных», которым пользуются постоянно.

```html
<button class="tab-btn" data-tab="backup">💾 Бэкап</button>
```

## D2. Блок «Города» — список, выбор, кнопка

### D2.1 Список городов

Каждая строка — не голый чекбокс, а полноценная кликабельная область (весь `<label>`,
не только 16×16px квадрат — правило проекта: touch-цели ≥44px на `pointer: coarse`,
см. `CLAUDE.md` п.5 про фронтенд). Размер — вторым столбцом, моноширинным начертанием,
чтобы колонка цифр не «прыгала» при разной длине названия.

```html
<div class="ls-section">
  <div class="ls-sec-title">💾 Города</div>

  <label class="bkp-city-row bkp-city-row--all">

  </label>

    <label class="bkp-city-row">
      <input type="checkbox" class="bkp-city-cb" value="paris">
```

«Выбрать все» — отдельная строка над списком, не кнопка сбоку: так поведение чекбокса
(тристейт — снимается сам, если пользователь потом вручную снял один из городов) читается
как естественная часть списка, а не отдельная команда. Синхронизация индетерминированного
состояния — на JS, обычный `indeterminate` DOM-флаг.

### D2.2 Кнопка «Создать бэкап» — состояния

| Состояние | Вид | Условие |
|---|---|---|
| Пусто выбрано | `disabled`, `opacity:.4` (уже есть в `.btn-submit:disabled`) | 0 чекбоксов отмечено |
| Готова | обычный `.btn-submit` | ≥1 город выбран |
| Идёт архивация | текст меняется на «Архивирую…», кнопка `disabled` | после клика, пока job `running` |
| Ошибка | кнопка возвращается в «Готова», под ней текст ошибки | job `error` |

Кнопка **не превращается в спиннер молча** — рядом со строкой прогресса нужен текст,
потому что архивация Парижа может идти минуту и дольше, и «зависшая» кнопка без обратной
связи выглядит как баг, а не как работа.

### D2.3 Прогресс — честно индетерминированный

`Compress-Archive` не отдаёт постадийный прогресс в байтах — техспека (B2.2) не
предусматривает polling внутри задачи, только `running`/`done`/`error`. **Не рисовать
процентную полосу, которая ничего не измеряет** — фальшивый прогресс-бар хуже его
отсутствия. Вместо процентов — индетерминированная анимация (переиспользовать
`.loading-state .spinner`, [`styles.css:2685`](../../web/public/styles.css#L2685)) плюс
счётчик прошедшего времени текстом:

```html
<div class="bkp-progress" id="bkp-progress">
  <div class="spinner"></div>
  <span>Архивирую Париж… <span id="bkp-elapsed">0:14</span></span>
</div>
```

```css
.bkp-progress {
  display: flex;
  align-items: center;
  gap: 10px;
  margin-top: 14px;
  color: var(--text2);
  font-size: var(--fs-md);
}
```

По завершении — не просто скрыть блок, а на пару секунд показать «Готово» зелёным
(`var(--c-success)`) перед тем, как открылся диалог сохранения (D2.4) — иначе переход
от спиннера сразу к системному файловому диалогу читается как случайный скачок.

### D2.4 «Куда сохранить»

`showSaveFilePicker()` — системный диалог ОС, вне контроля дизайна интерфейса. Единственное,
что проектируется на этой стороне, — состояние после отмены диалога (`AbortError`,
[техспека B2.3](2026-08-13-backup-tab-techspec.md#b23-диалог-куда-сохранить)): кнопка
и прогресс-блок должны вернуться в состояние «готово, файл на сервере», а не молча
исчезнуть — пользователь может передумать и всё равно захотеть сохранить файл, повторный
клик не должен запускать архивацию заново. Дать отдельную кнопку «Сохранить файл» на
экране «Готово», не завязанную на повторный вызов `/api/backup/city`.

## D3. Блок «Настройки»

Кнопка без чекбоксов — архив всегда «весь набор настроек» целиком (техспека B3.1 не
предполагает частичного выбора). Текст-предупреждение — не отдельным всплывающим
тултипом (`.field-tip`), а видимой строкой рядом с кнопкой: пользователь должен увидеть
её до клика, не после, и не только при наведении.

```html
<div class="ls-section">
  <div class="ls-sec-title">⚙ Настройки</div>
  <p class="form-hint" style="font-style:normal;margin-bottom:14px">
    Ключи AI-провайдеров и назначения генераций — отдельным архивом, без данных городов.
  </p>
  <div class="bkp-settings-warn">
    ⚠ Архив содержит ключи AI в открытом виде — не пересылайте его.
  </div>
  <button class="btn-submit btn-secondary" id="bkp-settings-btn">Сохранить настройки</button>
</div>
```

```css
.bkp-settings-warn {
  display: flex;
  align-items: center;
  gap: 8px;
  padding: 8px 12px;
  margin-bottom: 14px;
  background: rgba(184, 134, 11, .07);
  border: 1px solid rgba(184, 134, 11, .3);
  border-radius: var(--r-sm);
  color: var(--gold);
  font-size: var(--fs-md);
}
```

Это тот же визуальный класс тревоги, что `.chr-modal-warn`
([`styles.css:5607`](../../web/public/styles.css#L5607)) — «жёлтое предупреждение», не
«красная опасность»: утечка ключей — риск при неосторожном шаринге файла, а не разрушение
данных при нажатии самой кнопки. Смешивать с красным регистром блока восстановления (D5)
нельзя — иначе оба предупреждения обесценивают друг друга одинаковой интенсивностью.

`.btn-secondary` (золотой контур, [`styles.css:2559`](../../web/public/styles.css#L2559)),
не основной `.btn-submit` — операция вспомогательная, не главное действие вкладки.

## D4. Блок «Восстановление» — danger zone

Единственный красный блок на вкладке. Визуально отделяется рамкой в цвете опасности,
не просто ещё один `.ls-section`:

```html
<div class="ls-section bkp-danger-zone">
  <div class="ls-sec-title bkp-danger-title">⚠ Восстановление из бэкапа</div>
  <p class="form-hint" style="font-style:normal">
    Заменит данные выбранного города текущей версией из архива. Перед заменой старая
    версия переносится в «Удалённые» — её можно вернуть вручную, но не автоматически.
  </p>
  <input type="file" id="bkp-restore-input" accept=".zip" hidden>
  <button class="btn-submit bkp-restore-btn" id="bkp-restore-trigger">Загрузить бэкап…</button>
</div>
```

```css
.bkp-danger-zone {
  border-color: rgba(139, 0, 0, .35);
  background: color-mix(in srgb, var(--bg2) 92%, var(--accent) 8%);
}

.bkp-danger-title { color: var(--c-danger-text); }

.bkp-restore-btn {
  background: rgba(139, 0, 0, .15);
  border-color: var(--accent);
  color: var(--c-danger-text);
}

.bkp-restore-btn:hover:not(:disabled) {
  background: rgba(139, 0, 0, .3);
}
```

Цвета — те же переменные, что уже несут смысл «опасно» в остальном интерфейсе
(`.city-del-btn`, [`styles.css:4609`](../../web/public/styles.css#L4609);
`.chr-modal-btn.danger`, [`styles.css:5700`](../../web/public/styles.css#L5700)) —
не изобретается новый оттенок красного.

Кнопка **не запускает `inspect` сама по себе** — она открывает системный выбор файла
(`<input type="file">`), а `inspect` стартует сразу после выбора файла, без
промежуточного клика «Загрузить». Первая точка, где пользователь реально видит
последствия, — это модалка сводки (D5), не файловый диалог.

## D5. Модалка подтверждения восстановления

Это самый ответственный экран во всей задаче — единственное место, которое стоит между
пользователем и заменой 198 МБ живых данных архивом месячной давности. Техспека (B4.3)
оставляет его рендер на усмотрение фронтенда; здесь — конкретный дизайн.

### D5.1 Почему не generic `showConfirm()`

В проекте уже есть готовый диалог подтверждения, `showConfirm(message, {danger})`
([`utils.js:98`](../../web/public/scripts/utils.js#L98)), но он принимает один
экранированный текстовый `message` — годится для «Удалить хронику "Х"?», не годится
для сводки по нескольким городам с разными размерами, числом файлов и статусом
(замена/новый). Здесь нужна структура, а не строка.

Ровно для этого случая в проекте уже есть более тяжёлый паттерн — `.chr-modal-backdrop`
с произвольным HTML в `.chr-modal-body` и чекбоксом-разблокировкой опасной кнопки, уже
использованный для удаления модуля (`#modp-delete-modal`,
[`index.html:569-582`](../../web/public/index.html#L569-L582)). Переиспользуется он,
не изобретается третий вид модалки.

### D5.2 Разметка

«Восстановить» физически не может сработать, пока пользователь не отметил чекбокс
осознанно.

не выдумывать новую пару цветов там, где семантика та же самая.

Если в архиве **только** новые города (ни один `exists`) — риска нет, чекбокс-разблокировку
можно не требовать (на усмотрение разработчика при реализации: тот же диалог с уже
активной кнопкой «Восстановить», без чекбокса, либо чекбокс всегда, ради простоты одной
реализации на оба случая). Дизайнерски приемлемо и то, и другое — жёсткого требования нет.

### D5.4 Ошибка при `inspect`

Битый/чужой архив (400 от `/restore/inspect`, техспека B4.2) — модалка **не открывается**.
Ошибка показывается там же, где кнопка «Загрузить бэкап…» (D4), тем же паттерном, что и
ошибка архивации (D2.2): текст под кнопкой, кнопка снова активна. Не нужен отдельный тип
уведомления — `showToast(message, 'error')` (уже используется по всему приложению,
судя по вызовам в `utils.js`) достаточен, раз речь о единственной строке текста, а не
о структурированной сводке.

## D6. Мобильная адаптация

`.tab-panel` внутри `#page-tools` не имеет собственного брейкпоинта — значит вкладка
наследует общую адаптивность страницы. Единственное специфичное место — строка города
(D2.1) и строка сводки восстановления (D5.3): обе используют `flex` в ряд с именем,
метаданными и (в D5.3) бейджем. На узких экранах (≤480px, соответствует существующим
точкам излома по проекту) бейдж переносится под текст, а не сжимает название города:

```css
@media (max-width: 480px) {
  .bkp-restore-item { flex-wrap: wrap; }
  .bkp-restore-item-name { flex: 1 1 100%; }
}
```

Для `.bkp-city-row` перенос не нужен — там всего два элемента (имя + размер), они не
теряют читаемость в один ряд даже на 360px при текущей типографике (`--fs-lg` = 17px).

## Сводная таблица состояний (для чек-листа разработчика)

| Компонент | Состояния |
|---|---|
| Кнопка «Создать бэкап» | disabled (0 выбрано) → активна → «Архивирую…» disabled → готово (кнопка сохранения) / ошибка (текст + кнопка снова активна) |
| Прогресс архивации | индетерминированный спиннер + прошедшее время — **не** процентная полоса |
| Кнопка «Сохранить настройки» | активна → короткая индикация «Готово» (синхронная операция, полноценный прогресс не нужен) |
| Кнопка «Загрузить бэкап…» | активна → (после выбора файла) блокируется на время `inspect` → модалка сводки / текст ошибки |
| Модалка восстановления | кнопка «Восстановить» disabled, пока не отмечен чекбокс подтверждения |
| Список городов | пусто (loading-state на первую загрузку) → список с размерами; ошибка загрузки размеров — не блокирует чекбоксы, город просто без цифры справа |

## Вне объёма дизайна

- Экран прогресса восстановления после подтверждения (`commit`) — по паттерну D2.3
  (спиннер + текст «Восстанавливаю Париж…»), отдельного дизайна не требует, тот же
  компонент `.bkp-progress`.
- Иконки/иллюстрации — вкладка утилитарная, как соседние («Учёт данных», «Инструкции»),
  декоративный арт не предусмотрен ни у одной вкладки этого раздела.
