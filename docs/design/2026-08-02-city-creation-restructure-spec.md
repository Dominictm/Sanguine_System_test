# Реструктуризация формы создания города — спецификация (revision 1)

> Роль: Аналитик. Документ для передачи Системному аналитику перед реализацией.
> Статус: **план, разработка не начата.**

---

## 1. Резюме (Executive Summary)

Запрошенное изменение — не косметическая правка формы, а смена структуры данных
`city.md`: сейчас все 16 секций (`CITY_SECTIONS` в
[`web/lib/parsers/city.js:10-27`](../../web/lib/parsers/city.js)) — плоские
буллет-списки из multi-line textarea, без вложенности. Новая форма вводит
**вложенные, повторяемые блоки** (Район → тип/влияние/описание → Локации
внутри района), которых сегодня в модели данных города не существует вообще.

Это меняет не только UI, но и всю цепочку: `cityScaffold()` → `city.md` →
`parseCityMd()` (обратный разбор для формы редактирования) → синк с
`archive/political_state.md` → паритет с CLI (`tools/new_city.js`) →
валидацию/схему. Раздел 3 — карта того, что конкретно затронуто.

Также два уточнения по фактическому состоянию (см. §2) расходятся с
формулировкой задачи:
- «Районы» сегодня **не связаны** с текстом секции city.md «## Районы» —
  это два независимых поля (один создаёт папки, другой — прозу).
- Модалки «создание локации» **не существует** — есть плоская форма на
  вкладке Инструменты → Ещё. Пункт «используем модалку» в задаче — это
  новая сущность, а не переиспользование существующей.

## 2. Текущее состояние (as-is)

### 2.1 Форма создания города сегодня

`page-city-new` → `<details id="city-create-spoiler">`
([`web/public/index.html:920-969`](../../web/public/index.html)) — не модалка,
разворачивающийся блок на странице «Города». Поля: Название, Год, Сеттинг
(текст), Политический ландшафт (textarea), **Фракции** (единственный
структурированный редактор — `city-factions-editor`, chip/field-компонент,
`_collectFactions()`), Ключевые локации (textarea), Лейтмотивы, Специфика
ответа, Чего избегать, Источники, Районы (**одна строка, через запятую**).

`POST /api/cities` → `cityScaffold()`
([`web/lib/parsers/city.js:105-214`](../../web/lib/parsers/city.js)) строит:
- `city.md` из `CITY_SECTIONS` — просто `## Заголовок\n- пункт\n- пункт`,
  никакой вложенности;
- `archive/political_state.md` — таблица «Карта фракций» (роль/персонаж/
  клан/примечание, синкается отдельным парсером `parsePoliticalRecords()`)
  + таблица «Баланс сил — обзор» (фракция/сила %/территория/угроза);
- пустые папки `locations/district_NN/<slug>/` — **только папки**, без
  файла с метаданными района. Имя района берётся из CSV-строки `districts`,
  слагифицируется, папка создаётся — и всё. Никакого типа района, влияния
  секты/клана или описания района нигде не хранится.

### 2.2 «Районы» в city.md vs папки district_NN — независимые пути

Секция `## Районы` в самом city.md — это **отдельное** поле `districts`
free-text textarea? Нет — сверка кода показывает: единственное поле
`city-districts` в форме используется ДВАЖДY с разными эффектами:
1. как `payload.districts` → `cityScaffold()` → создаёт папки
   `locations/district_NN/<slug>/`;
2. это же значение НЕ попадает в `CITY_SECTIONS` — секции «Районы» в
   city.md соответствует **другое**, ныне не выведенное в форму поле
   (`fields.districts` не читается в `buildCityMd`, только `districtsCsv`
   читается в `cityScaffold` для папок). На практике сейчас никто не
   заполняет прозу «## Районы» через веб-форму создания — только через
   ручное редактирование city.md или через `PUT` с `fields.districts` как
   текстом (эти два смысла поля `districts` — CSV-для-папок vs
   текст-для-секции — уже сегодня перегружены одним именем; при
   реструктуризации это стоит разъединить явно, а не унаследовать
   путаницу).

### 2.3 Локация — форма, не модалка

`tools/tab-more` → блок «📍 Новая локация»
([`web/public/index.html:1025-1036`](../../web/public/index.html)): 4 плоских
поля (Округ/код, Название, Зона `safe|neutral|dangerous`, Район опц.),
кнопка «Создать локацию». Работает поверх той же логики, что
`tools/new_location.js` (CLI) — карточка локации со стандартным шаблоном
(`Атмосфера`, `VtM-контекст`, `Сценарные крючки`, промт для арта). Формы
живут в разных, несвязанных местах — Города (создание домена) и
Инструменты (создание локации); сегодня между ними нет передачи контекста
(округ/район не может быть предзаполнен из формы создания города).

Проверил и на диске: `cities/balmont/locations/district_01/podzemnyy_dok/`
(единственная существующая непарижская локация в репо на сейчас) — обычная
карточка локации, никакого файла метаданных района рядом с ней. Подтверждает
§2.1 — структурных данных о районе сегодня нигде нет.

### 2.4 Единственный существующий образец структурированного вложенного редактора

«Фракции» (`city-factions-editor`) — единственное поле формы создания города,
которое уже не textarea, а компонент со своим состоянием (чипы/поля,
`_collectFactions()` на сборке, тот же компонент переиспользуется в модалке
редактирования города). Это готовый паттерн для «Района» и вложенных в него
«Локаций» — не изобретать новый UI-подход, а тиражировать этот.

## 4. Развёрнутый план по разделам формы (то, что просил пользователь)

### 4.1 Как в задаче (1–11), уточнено под текущую архитектуру

1. **Название** — как есть, без изменений.
2. **Год** — как есть, без изменений.
3. **Сеттинг** — как есть (`city-description`), без изменений.
4. **География города** — новый блок:
   - Текстовое описание города — новое поле (сегодня похожего поля нет;
     ближайший аналог — `city-description`/«Сеттинг», но это про тон и канон,
     а не про физическую географию — оставить отдельным полем).
   - Повторяемый **Район** (карточка, по образцу `city-factions-editor`):
     - Наименование района
     - Тип района — дропдаун (Спальный / Деловой / Пром-зона /
       Туристический / Гетто — плюс see §4.3 предложение добавить ещё
       варианты)
     - Влияние в районе — два поля (Секта, Клан) — **источник значений**:
       список сект/кланов уже есть в системе (`system/rules/*`,
       `LINEAGE_DEFS` в scripts.js для кланов) — использовать те же
       перечни, что и в карточке персонажа, а не заводить третий
       отдельный список.
     - Текстовое описание района
     - Локации — выбор из существующих (нужен API-эндпоинт «локации
       этого города/района» для списка) ИЛИ кнопка «+ Локация»,
       открывающая создание локации **с предзаполненным округом/районом**
       (см. §3 — сегодня такой передачи контекста нет, это новая
       интеграция, не переиспользование).
5. **Политический ландшафт** — отдельный блок:
   - Главенство секты — дропдаун из существующих сект + «Независимые
     кланы» + «Независимый город».
   - Продолжение — см. п.6, теперь уточнено пользователем (было открытым
     вопросом в §4.2 предыдущей ревизии).
6. **Занятые должности в городе** — два повторяемых под-блока внутри
   «Политический ландшафт»:
   - **Властители города.** Строка: Должность — дропдаун (Князь, Сенешаль,
     Шериф, Хранитель Элизиума; плюс возможность вписать вручную) +
     Персонаж — выбор из существующих персонажей города ИЛИ ручной ввод
     текстом. Если персонаж выбран из списка — **на его карточке должно
     проставляться поле «Иерархия»** (см. ниже, это НОВАЯ интеграция).
   - **Примогенат.** Та же строчная структура, но вместо дропдауна
     должностей — дропдаун кланов (один Примоген на клан); второе поле —
     имя Примогена, выбор из существующих ИЛИ ручной ввод. Так же, если
     персонаж выбран из списка — проставляется «Иерархия» на его карточке.

   **ИСПРАВЛЕНИЕ (найдено при передаче Дизайнеру, п.6 предыдущей ревизии
   был неточен):** такой редактор — Должность (дропдаун+своё) + Персонаж
   (datalist: существующий ИЛИ вручную) + повторяемые строки — **уже
   существует и работает**, но только в МОДАЛКЕ РЕДАКТИРОВАНИЯ города, не
   в форме создания (`_cityPolEditorHtml`/`_polRowHtml`/
   `_collectPoliticalRows`, `web/public/scripts/city.js:152-230,299-312`).
   Он уже пишет корректные строки в ту же секцию `city-political`, которую
   сервер и так парсит в «Карту фракций» — весь этот путь работает
   сегодня, никакой новой архитектуры для этого не нужно. Реальная работа
   по п.6 — **перенести** уже готовый компонент в форму СОЗДАНИЯ (по тому
   же принципу, что `city-factions-editor` уже переиспользуется между
   созданием и редактированием), и **расширить** список должностей:
   сейчас `CITY_POLITICAL_ROLES = ['Князь', 'Шериф', 'Сенешаль',
   'Примаген']` (`city.js:89`) — заметьте опечатку «Примаген» вместо
   «Примоген», и нет «Хранителя Элизиума». «Клан» для Примогена сегодня
   отдельным полем не выбирается — берётся автоматически из карточки
   персонажа (`clanByName.get`, см. техспеку §4.1) при синке с «Картой
   фракций»; нужно ли пользователю ЯВНО выбирать клан из дропдауна (как
   просил пользователь) при живом автоопределении — вопрос для Дизайнера,
   не для этого документа.
7. **Значимые места города.** Повторяемая строка: локация — выбор из
   уже существующих локаций города (доп. фильтр по округу/району опционально)
   + Статус локации — дропдаун (Элизиум, Приёмная князя, Убежище, Шериф,
   Сенешаль). Технически — та же схема риска, что и в п.6: выбор из
   существующего объекта подразумевает запись обратно в карточку ЭТОЙ
   локации, а не только в city.md — см. предупреждение ниже.

   **ИСПРАВЛЕНИЕ (тот же класс находки, что в п.6):** редактор «Отмеченные
   локации» с ровно такой структурой (Тип-дропдаун+своё, Название —
   datalist существующих ИЛИ новое имя) **уже существует** в модалке
   редактирования (`_cityLocEditorHtml`/`_locRowHtml`/
   `_collectLocationRows`, `city.js:177-199,318-339`) — и даже больше:
   если вписанное название НЕ совпадает с существующей локацией, при
   сохранении реально создаётся карточка локации (`POST /api/locations`,
   «фаза K», `_saveCityEdit`). Сегодня `CITY_LOCATION_TYPES = ['Элизиум']`
   (`city.js:90`) — только один тип, остальные 4 из запроса пользователя
   отсутствуют. Реальная новая работа по п.7 — перенос компонента в форму
   создания + расширение списка типов; **запись статуса НАЗАД в
   существующую выбранную локацию (в поле «Зона»/«Контроль») сегодня
   ДЕЙСТВИТЕЛЬНО отсутствует** — это по-прежнему честно новая интеграция,
   не найдена готовой нигде (в отличие от остального в этом пункте).
8. **Лейтмотивы и атмосфера** — поле уже есть в форме (`city-leitmotif`),
   без изменений.
9. **Источники** — поле уже есть в форме (`city-sources`), без изменений.
10. **Чего избегать** — поле уже есть в форме (`city-avoid`), без изменений.
11. ~~Источники~~ — **убрано, подтверждённый дубль п.9** (снято по
    прямому указанию, не самовольно).

**П.7 — РЕШЕНО: переиспользуем существующие поля локации, новое поле не
заводим.** У локации уже есть «Зона» (`ZONE_CLASS_LABELS`, значение
`elysium` = «🏛️ Элизиум» — уже ровно то же значение, что в списке
статусов п.7) и «Контроль» (`loc.control`, свободный текст, показан в
детальной модалке). Логичное разведение (зафиксировано как рабочее
предположение — не переспрашивал отдельно, но это прямое следствие
«переиспользуем поля»):
- Статус **«Элизиум»** → пишет в поле «Зона» локации (устанавливает
  значение `elysium`);
- Статусы **«Приёмная князя» / «Убежище» / «Шериф» / «Сенешаль»** → пишут
  в поле «Контроль» (свободный текст) — под них нет отдельного enum
  сегодня, «Контроль» ближе всего по смыслу и уже существует.

Это снимает вопрос «новое поле или нет» (§9, риск таблица) — но НЕ снимает
вопрос записи-назад и «осиротевшего» статуса при смене/снятии (см. ниже,
всё ещё открыто).

### 4.2 «Занятые должности» / «Главенство секты» vs «Карта фракций» — уточнено

Хорошая новость по сравнению с предыдущей ревизией: связка «Должность +
Персонаж» (Властители) и «Клан + Персонаж» (Примогенат) — это **не третий
источник истины**, а ровно та же форма данных, что уже хранит и
синхронизирует `archive/political_state.md` → «Карта фракций»
(`Должность | Персонаж | Клан | Примечание`, см. `syncPoliticalStateTable()`/
`parsePoliticalRecords()`, `web/routes/cities.js:127-185`). Сегодня туда
пишут из свободного текста `city-political` через хрупкую эвристику
(«роль: имя» построчно) — то, что просит пользователь, по сути замена
этого текстового ввода на настоящую структурную форму (дропдауны +
выбор персонажа) поверх ТОЙ ЖЕ таблицы, не создание новой. «Клан» для
Примогена в существующей таблице уже есть отдельной колонкой и уже
автозаполняется из карточки персонажа (`clanByName.get(r.name)`,
`cities.js:178`) — дропдаун кланов для Примогената, вероятно, лучше
трактовать как выбор ТОГО, какое место в «Карте фракций» заполняется
(«Примоген (Тремер)» как текст Должности), а не как отдельную колонку.

**Отдельный, по-настоящему новый кусок работы: запись в карточку
персонажа.** Проверил код (`web/lib/parsers/character.js:130`,
`web/public/scripts/scripts.js:1972` и др.) — поле «Иерархия» на карточке

## 5. Ключевая архитектурная развилка — РЕШЕНО

Где физически живут структурные данные района/локации:

- ~~(A) Вложено в сам city.md~~ — отклонено.
- **(B) Отдельный структурный файл** (по аналогии с тем, как «Карта
  фракций» уже отделена от `city.md` в `political_state.md`) —
  **выбрано пользователем.** Не трогает существующий
  `buildCityMd`/`parseCityMd`, дешевле и безопаснее для существующих
  городов; продолжает паттерн проекта «city.md + отдельные archive/*.md
  под конкретные срезы данных».

### 5.1 Вопросы §5.1 — РЕШЕНО (файл на район)

Пользователь выбрал: **файл на район**, не единый `archive/districts.md`
на весь город. Это не просто другой вариант того же вопроса — он **снимает
вопрос «связующий ключ» полностью**, а не просто решает его:

- Файл лежит **внутри самой папки района**:
  `locations/<district-slug>/district.md` — рядом со вложенными папками
  локаций этого района (`locations/<district-slug>/<location-slug>/<location-slug>.md`).
  Путь без «округа» (`district_NN`) — см. §8, эта нумерация убрана из
  схемы отдельным решением уже после написания этого раздела; здесь путь
  сразу приведён к финальному виду. Тот же паттерн «сущность = папка +
  `<slug>.md`», что уже используют персонажи и локации — район просто
  получает свою карточку в своей же папке, вместо новой отдельно живущей
  структуры.
- Связующего ключа (имя-совпадение между двумя разными файлами) **не
  существует как отдельной проблемы** — папка района и её метаданные это
  один и тот же путь. Разойтись им физически невозможно (в отличие от
  сегодняшнего бага `districts`-CSV vs секция «## Районы», §2.2, где это
  два несвязанных места). Это и есть версия «исправлено, как должно
  быть» — самим выбором структуры, а не валидацией/синком постфактум.
- Формат — markdown-карточка по аналогии с `<slug>.md` локации
  (`tools/new_location.js`, шаблон с ⚠️-плейсхолдерами): Название,
  Тип района, Влияние (Секта/Клан), Текстовое описание. `district.md` —
  рабочее имя файла (не «districts.md» и не совпадает с именем папки —
  чтобы не путать с файлом локации, у которой имя файла = слаг папки).

**Бэкофилл для существующих городов — решено: да, мигрируем и старые.**
`paris`, `balmont` получают `district.md` в папках районов (поля —
плейсхолдеры ⚠️, как у прочих шаблонов при бэкофилле). Пути папок при
этом сами меняются — см. §8, бэкофилл `district.md` и переход на схему
без «округа» — фактически одна и та же миграция, не две последовательные.
По правилу `CLAUDE.md` про `tools/migrations/` — оформляется как миграция
(`tools/migrations/`), прогоняется автоматически при следующем старте
сервера (`web/lib/migrations.js`), как и любая другая миграция формата
файлов города.

**CLI-паритет — решено: отдельный файл поддерживает паритет естественно.**
Раз это независимый файл (не вложенность в city.md), генерация
`district.md` — такая же простая write-операция что для CLI
(`tools/new_city.js` при создании районов; вероятно, понадобится и новый
`tools/new_district.js` по аналогии с `new_location.js`, если район нужно
будет добавлять в существующий город post-factum, не только при создании
города), что и для веба — через общую функцию-строитель (по образцу
`buildCityMd`/`cityScaffold` — единый источник для CLI и `routes/cities.js`).
Паритет не требует специальной работы сверх обычного «одна функция, два
вызывающих».

**Добавление района в уже существующий город — теперь часть плана (было
смежным вопросом, зафиксировано пользователем).** Сегодня район можно
завести только в момент создания города (CSV-поле при создании). Раз
район — полноценная сущность со своей карточкой (`district.md`), нужен
отдельный вход для «добавить район в уже существующий город» — по аналогии
с тем, как локация добавляется в любой момент через `tools/new_location.js`
+ форму на вкладке Инструменты:
- **`tools/new_district.js`** (CLI) — по образцу `tools/new_location.js`:
  `node tools/new_district.js <city> "<Название>" [тип] [секта] [клан] [описание]`,
  создаёт `locations/<slug>/district.md` в существующем городе (папка не
  должна уже существовать — та же проверка, что у `new_location.js`).
- **Веб-эндпоинт** — `POST /api/cities/:slug/districts`, тем же телом
  полей, что форма «Район» из §4.1, через общую функцию-строитель с CLI
  (см. паритет выше).
- **UI-вход** — вероятно, кнопка «+ Район» на странице города (`page-city`,
  где сегодня отображаются детали домена) — вне формы создания города,
  раз район должен заводиться и после того, как город уже существует.

## 8. Убрать «Округ», унифицировать до Город → Район → Локация

Пользователь решил: числовой «округ» (`district_NN`) убирается из схемы
как отдельный уровень пути. Итоговая иерархия — ровно два уровня вложенности
всегда: **Город → Район → Локация**
(`cities/<city>/locations/<район-слаг>/<локация-слаг>/<локация-слаг>.md`).

### 8.1 Что реально лежит на диске сегодня (проверено, не предполагаю)

Три РАЗНЫХ фактических паттерна одновременно, несмотря на то, что
`CLAUDE.md` документирует один («`locations/district_NN/<район>/<локация>/`
(глубина гибкая)»):

- **Paris, основной паттерн** (≈20 связок): строго
  `district_NN/<район-слаг>/<локация-слаг>/` — например
  `district_01/luvr/il_de_la_site/`, `district_18/monmartr/pigal/`.
  Округ здесь — реальный парижский arrondissement (осмысленный номер, не
  случайный), район — квартал внутри него (Лувр, Монмартр).
- **Paris, исключения** (уже сегодня нарушают «основной» паттерн):
  `la_defans_bd/la_defans_bd/` и `metro_podzemnyy/stantsiya_prizrak_metro/`
  — глубина 2 БЕЗ округа (район сразу под `locations/`); `orli_yug/` —
  глубина 1, локация прямо под `locations/`, вообще без промежуточного
  уровня.
- **Balmont**: `district_01/podzemnyy_dok/` (округ+локация, без района) —
  СОСУЩЕСТВУЕТ с `Другие/skladskaya_zona_za_supermarketom/` и
  `Ценр/metro/` — районы без округов вообще, уже в проде, сегодня.

Вывод: «гибкая глубина», которую `CLAUDE.md` разрешает явно, уже привела
к трём разным фактическим паттернам в двух городах. Унификация — это не
только приведение новой формы к дизайну, но и наведение порядка в уже
накопившемся расхождении; часть данных (Balmont: `Другие`, `Ценр`) уже
фактически близка к целевой схеме, но это скорее совпадение, чем
намеренное следование ей.

### 8.2 Судьба «округа» как понятия

Номер округа (arrondissement) — не бессмысленный технический артефакт для
Парижа, это часть сеттинга/лора. Предлагаю (нужно подтверждение): округ
не пропадает совсем, а **демоте́тся из уровня пути в обычное текстовое/
числовое поле внутри `district.md`** (например «Округ: 1-й» — чисто
описательное, не участвует в адресации файлов). Так лор не теряется, но
адресация становится единообразной для всех городов независимо от того,
использует ли их сеттинг вообще понятие «округ» (не у каждого города оно
есть по смыслу — Balmont, судя по `Другие`/`Ценр`, явно обходится без
него).

### 8.3 Что затронуто

- **`tools/new_location.js`** — сегодня первый параметр (`districtRaw`)
  принимает ЛИБО число (→ `district_NN`), ЛИБО слаг. Числовая ветка
  убирается целиком; параметр становится обязательным «район» (переименовать
  и в коде, и в тексте usage — не оставлять переменную `district`, если
  по смыслу это уже «район», чтобы не унаследовать путаницу вроде §2.2).
- **Форма Инструменты→Ещё**, поле `loc-district` (сегодня лейбл «Округ/код
  *», подсказка «1 или district_01») — переименовать в «Район *», убрать
  намёк на числовой код; поле `loc-rayon` («Район опц.») в текущем виде
  дублирует новый смысл `loc-district` и, видимо, должно быть удалено —
  сегодня это два поля ровно потому, что было три уровня (округ + опц.
  район), при двух уровнях он один.
- **Эндпоинт создания локации** — та же правка сигнатуры параметров.
- **`CLAUDE.md`** (корневой, «Структура проекта») — формулировка
  `locations/district_NN/<район>/<локация>/ (глубина гибкая)` требует
  правки на новую, жёстко двухуровневую схему без «гибкости» глубины.
- **Миграция физических папок** (`tools/migrations/`) — самая рискованная
  часть плана целиком:
  - переименование/перенос папок всех существующих локаций Парижа (≈20
    связок округ+район) и Balmont;
  - должна сохранить рабочими все внутренние markdown-ссылки
    (`tools/validate_links.ps1` — обязательный прогон после миграции,
    не факультативный);
  - решить судьбу локаций без района (`orli_yug` и подобные депth-1
    случаи) — присвоить им район явно при миграции (например
    самих себя как «район=локация», как уже сделано для `la_defans_bd`),
    а не оставить не мигрированными;
  - для Balmont (`Другие`, `Ценр`) миграция — это в лучшем случае
    переслаговка (`Ценр` → `centr`, заодно опечатка), не создание с нуля;
    стоит явно решить, правится ли опечатка попутно или миграция трогает
    только структуру, не контент.

### 13.6 Редактирование «Уровень опасности» и «Маскарад» в форме локации

Проверил код — обе величины сегодня **нельзя отредактировать через веб**:

- **«Уровень опасности»** — не отдельное поле вообще, а эмодзи внутри
  текста поля «Зона» (`zoneDangerLevel()` ищет 🟢/🟡/🔴 подстрокой в
  значении «Зона», `locations.js:44-46`). Форма редактирования локации
  (`openLocEditModal`) даёт дропдаун `loc-edit-zone` — но там только 3
  опции (🟢/🟡/🔴, голые эмодзи), тогда как реальный домен «Зоны»
  (`zoneClass()`) — 5 категорий: Элизиум/Носферату/Нейтральная/Опасная/
  Локация. Через этот дропдаун физически невозможно поставить
  «🏛️ Элизиум»/«🟣 Носферату» — только danger-цвет.
- **«Маскарад»** — вообще без UI редактирования. Поле `masqueradeLevel`
  парсится из отдельной инлайн-строки `**Маскарад:** эмодзи` внутри
  секции VtM-контекста (`web/lib/parsers/location.js:86-91`), но ни
  `openLocEditModal`, ни `PUT /api/locations/:slug/fields` (`fieldMap` в
  `web/routes/locations.js:210`) его не знают — нет ни select-поля в
  форме, ни ключа записи на сервере.

**Найден смежный риск при проверке** (не баг, который сейчас портит
реальные данные — проверил, ни у одной локации в `cities/` сегодня нет
«🏛️ Элизиум»/«🟣 Носферату» в поле «Зона» на диске, — но ловушка на
будущее): `_saveLocEdit` шлёт `zone` **всегда**, даже пустым значением
(комментарий в коде: «Always include every field so empty string clears
the existing value», `locations.js:973`). Если бы у локации в «Зоне» было
«🏛️ Элизиум» — при открытии формы дропдаун `loc-edit-zone` не нашёл бы
совпадения ни с одной из 3 опций, показал бы пустое значение, и **сохранение
ЛЮБОГО другого поля формы (не обязательно «Зоны») тихо стёрло бы «Элизиум»
из «Зоны»** — сервер полностью перезаписывает всю строку `**Зона:**`
переданным значением. Сейчас не стреляет только потому, что такой
категории ни у одной локации нет на диске. Решение этого пункта (развести
«Зону»/«Опасность» на два реальных поля, дать дропдауну полный домен
`zoneClass()`) закрывает и эту дыру, а не только добавляет удобство
редактирования.

Открытый вопрос для Системного аналитика/Дизайнера — та же развилка, что
уже стояла для «Значимых мест» (§4.1 п.7): «Опасность» остаётся
производной от текста «Зоны» (тогда дропдауну «Зона» в форме нужны все 5
категорий + скрытая логика извлечения danger-эмодзи оттуда), или
становится отдельным собственным полем на карточке локации (тогда «Зона»
хранит только категорию, «Опасность» — отдельная строка `**Опасность:**`
эмодзи, симметрично тому, как уже устроен «Маскарад»). Второе чище и сразу
даёт «Маскарад»/«Опасность» одинаковый, предсказуемый паттерн реализации.

### 14.2 Архитектурный риск — slug локации не уникален глобально

Не часть исходного плана §13 — обнаружено QA при тестировании нового
§9 (`PUT /api/locations/:slug/district`): `POST /api/locations`
проверяет коллизию имени только внутри целевого района, не по всему
городу, поэтому две локации с одинаковым названием в разных районах
создаются обе без ошибки — а дальнейшая адресация по голому slug
(`PUT /fields`, `DELETE` и т.д.) в такой ситуации резолвится
неоднозначно (воспроизведено — запись ушла не в ту карточку).

**Решено (роль «Аналитик»):** включить проверку уникальности slug по
всему городу при создании (`POST /api/locations`), явная ошибка `409`
при столкновении — без авто-суффикса к имени, тем же паттерном, что уже
использует создание района/города в этом проекте. Реальных дублей slug
в текущих данных нет (проверено), правка ничего не ломает задним числом,
только закрывает возможность появления новых. Полный контракт — техспека
§16.3.

не связанным друг с другом:

1. **Форма СОЗДАНИЯ города** (`_cityDistrictsEditorHtml()`,
   `city.js:438-443`) — единственное место, где район можно **создать**.
   Повторяемые карточки (Название/Тип/Влияние-Секта/Влияние-Клан/Описание,
   `_districtCardHtml`), собираются `_collectDistrictCards()`
   (`city.js:444-455`) и после успешного `POST /api/cities` отправляются
   по одному через `POST /api/cities/:slug/districts`
   (`scripts.js:1759,1799-1808`) — создаёт настоящий `district.md`.
   **Доступно только в момент создания города.**

2. **Форма РЕДАКТИРОВАНИЯ уже существующего города**
   (`_renderCityEdit()`/`_saveCityEdit()`) — секция «Районы» здесь **не**
   особый случай в `CITY_SECTION_DEFS.map()`
   (`_renderCityEdit`, `city.js:747-757` — special-cased только `political`/
   `factions`/`locations`, `districts` попадает в `else`-ветку) — это
   голая `<textarea data-city-field="districts">`, привязанная к тексту
   секции city.md «## Районы» (свободная проза, буллет на строку). При
   сохранении (`_saveCityEdit`, `city.js:978-983`) эта проза улетает в
   `fields.districts` как есть — **никак не связана** с `district.md`-
   сущностями. Через эту форму **нельзя** ни отредактировать существующий
   `district.md` (имя/тип/влияние/описание), ни создать новый.

3. **Страница ПРОСМОТРА города** (`_cityViewDistrictsHtml()`,
   `city.js:600-658`, реализовано в §13.2 выше) — показывает карточки
   существующих `district.md`-сущностей (Тип/Влияние/Описание), даёт
   **привязать уже существующую локацию** к району (дропдаун + «Привязать»,
   `PUT /api/locations/:slug/district`) и **создать новую локацию** сразу в
   районе (кнопка «+ Создать новую» → `_openDistrictLocationModal` →
   модалка создания локации с предзаполненным районом). Но **не даёт
   отредактировать сами поля района** (имя/тип/влияние/описание) — на
   карточке нет кнопки «Редактировать» вообще, хотя бэкенд для этого уже
   готов и покрыт тестами: `PUT /api/cities/:slug/districts/:districtSlug`
   (`routes/cities.js:502-532`) существует, работает, но **не вызывается
   ни из одного места фронтенда**.

Итог: создать район можно только при создании города; отредактировать
существующий район нельзя нигде; добавить локацию в район можно только со
страницы просмотра, не из формы редактирования.

### 15.2 Запрошено

В форме редактирования уже существующего города — раздел «Районы», в
котором можно:
- **редактировать существующие районы** (задействовать уже готовый, но
  сейчас нигде не используемый `PUT /api/cities/:slug/districts/:districtSlug`);
- **добавлять локации** в район (та же операция, что уже есть на странице
  просмотра, `PUT /api/locations/:slug/district` — вопрос лишь в том, где
  ещё её показывать, см. §15.3);
- **создавать новые районы** для уже существующего города (сегодня это
  умеет только форма создания — нужен путь и после того, как город уже
  создан).

### 15.3 Открытые вопросы для Системного аналитика

- **Переиспользовать `_districtCardHtml`-компонент из формы создания
  (§15.1 п.1) или собрать новый.** Карточка там уже умеет
  Название/Тип/Влияние-Секта/Влияние-Клан/Описание — тех же полей
  достаточно и для редактирования. Разница: создание собирает ВСЕ карточки
  в массив и шлёт их пачкой только после успешного `POST /api/cities`
  (город физически ещё не существует до этого момента) — редактирование
  работает с уже существующими районами по одному, значит нужен режим
  «карточка = уже сохранённая сущность» (значения из `GET /districts`
  вместо пустого шаблона, сохранение по своей кнопке через `PUT
  .../districts/:slug`, а не общей кнопкой формы города). Тот же класс
  развилки, что уже решался в плане модалки локации для «Сенсорной
  палитры» (`2026-08-02-location-card-modal-plan.md` §3/§6) — общий
  визуальный паттерн, но не один в один переиспользуемый компонент из-за
  разных моделей сохранения.
- **Судьба свободнотекстовой секции «## Районы» city.md (§15.1 п.2).**
  Сегодня это независимое от `district.md` поле (тот же разрыв, что уже
  зафиксирован для «Значимых мест»/«Иерархии» в других пунктах плана) —
  если форма редактирования начинает управлять районами через
  `district.md`-сущности, что происходит с textarea `districts` в
  `CITY_SECTION_DEFS`? Варианты: (a) убрать textarea совсем, раз районы
  теперь полноценные карточки — как уже сделано для «Фракции»/«Властители
  города»/«Примогенат»; (b) оставить как общий нарративный комментарий
  «о районах в целом» отдельно от списка формальных сущностей (по
  аналогии с тем, как «Политический ландшафт» сочетает нарратив и
  структурные записи, `_collectPoliticalRows`). Рекомендация — (a), для
  консистентности с уже принятым решением по остальным структурным
  секциям, но нужно подтверждение (это меняет формат city.md для уже
  существующих городов, у которых в «## Районы» может быть реальный
  рукописный текст — Париж, например, см. `cities/paris/city.md:130-131`,
  там просто плейсхолдер «- …», но нельзя полагаться на то, что так у
  всех).
- **Где теперь живёт «привязать локацию к району» — в форме
  редактирования, на странице просмотра, или в обоих местах.** Страница
  просмотра уже даёт эту операцию (§13.2, реализовано). Дублировать её в
  форме редактирования — лишний код ради того же результата; альтернатива
  — форма редактирования отвечает только за CRUD самих районов (имя/тип/
  влияние/описание/создание), а «добавление локаций» пользователь по-
  прежнему делает на странице просмотра после сохранения формы. Нужно
  решить, что именно понимается под «добавлять локации» в запросе — то же
  самое действие в новом месте, или пользователь не знал, что оно уже
  есть на странице просмотра (тогда достаточно просто оставить всё как
  есть и не дублировать).

### 15.4 Решено (роль «Аналитик»)

**По компоненту (первый вопрос §15.3):** переиспользовать. Форма
редактирования переиспользует `_districtCardHtml()`/`_cityDistrictsEditorHtml()`
из формы создания (`city.js:376,438-443`) как визуальный компонент карточки
района, но с режимом «уже существующая сущность»: значения из `GET
/api/cities/:slug/districts` вместо пустого шаблона, своя кнопка
«Сохранить» на карточку → `PUT /api/cities/:slug/districts/:districtSlug`
(не общая кнопка формы города, как у создания). Кнопка «+ Добавить район» у
уже существующего города создаёт карточку в режиме «новая» → по нажатию её
собственной кнопки сохранения уходит `POST /api/cities/:slug/districts`
(та же семантика, что при создании города, только по одной карточке за
раз, не пачкой после сохранения формы). `_collectDistrictCards()`
(`city.js:444-455`) для этого сценария не подходит как есть (собирает ВСЕ
карточки разом) — при реализации нужна версия, читающая/сохраняющая ОДНУ
карточку.

**По секции «## Районы» city.md (второй вопрос §15.3):** оставить как
дополнительный (не единственный) источник данных — не убирать textarea
целиком. При любых изменениях районов (создание/редактирование/удаление
`district.md`-сущности через новый UI) секция «## Районы» в city.md должна
обновляться автоматически, синхронно с изменением. Технически — тот же
паттерн, что уже реализован для двустороннего синка «Фракции» ↔ панель
«Влияние фракций» (техспека §11; `_replaceCitySection()`/
`_syncCityFactionsList()`, `web/routes/archive.js:97-129`): точечная
замена ТОЛЬКО секции «## Районы» (не полный `buildCityMd`-ребилд — тот
ломает рукописное форматирование, см. предупреждение в самой
`_replaceCitySection`), запись — по одной строке на район (имя района,
формат по аналогии с тем, что уже даёт список фракций), не блокирующая
операция (сбой синка — `warning` в ответе, не откат уже сохранённого
`district.md`, тот же non-blocking паттерн). При создании/редактировании/
удалении района через новый UI — дописать/поправить/убрать
соответствующую строку в «## Районы»; секция остаётся редактируемой и
руками (описание/нарратив вокруг списка не трогается, только сам список
имён синкается по аналогии с тем, как `_syncCityFactionsList` не трогает
остальной текст city.md за пределами своей секции).

**По «добавлять локации в район» (третий вопрос §15.3) — проверено:**
- API: `PUT /api/locations/:slug/district` (привязка/перенос
  существующей локации) покрыт тестами и зелёный (`Районы (District) —
  POST/GET/PUT /api/cities/:slug/districts`, `PUT
  /api/locations/:slug/district — привязка/перенос локации между
  районами` — 10/10, `web/tests/all.test.js`).
- UI, привязка уже существующей локации (дропдаун + «Привязать» +
  `showConfirm`): покрыт UI-тестом, зелёный (`Город — страница просмотра:
  карточки районов и привязка локации`, `web/tests/ui.test.js`).
- UI, «+ Создать новую» (`_openDistrictLocationModal` → форма создания
  локации с предзаполненным и задизейбленным полем «Район») — тестами не
  был покрыт вообще, проверено вручную живьём (создан район «Проверочный
  район» в тестовом городе, клик «+ Создать новую» → поле «Район»
  предзаполнено значением района и задизейблено, создана локация
  «Проверка привязки» → физически легла в
  `locations/proverochnyy_rayon/proverka_privyazki/` — то есть работает
  корректно от кнопки до файла на диске).

Оба пути «добавления локации в район» уже работают на странице просмотра
end-to-end. Решение — **не дублировать** в форме редактирования: новый
раздел «Районы» там отвечает только за CRUD самих районов (создание/
редактирование карточки — имя/тип/влияние/описание), «добавление локаций»
остаётся на странице просмотра, как и сегодня — она открывается сразу
после сохранения формы редактирования (`_saveCityEdit()` вызывает
`_renderCityView()`, `city.js:1033`), так что путь «отредактировал район в
форме → добавил в него локацию на той же вкладке» уже непрерывный, без
лишнего перехода.

Разработка не начата.

## 16. Находки QA по разделу «Города» (2026-08-04)

> Роль «Тестировщик» провела сквозной прогон раздела: создание городов с нуля
> (API + реальный браузер), заполнение всех полей, добавление районов/локаций/
> персонажей, round-trip редактирования всех 16 секций, граничные случаи.
> Ниже — разбор Аналитика поверх переданного отчёта: что подтверждено, какая
> у находок общая причина, и что из этого следует делать.

### 16.0 Что подтверждено рабочим (не требует правок)

Round-trip редактирования всех 16 секций city.md — 16/16 без потерь. Локация:
20 полей (метаданные, зона, опасность, сенсорика, VtM-таблица, ключевые точки,
крючки, промты) — все сохраняются и читаются обратно. Создание персонажа с
записью «Иерархии» из формы города, привязка и создание локации в районе —
работают end-to-end до файла на диске. Валидация года при создании — корректна.

### 16.1 Общая причина двух главных находок — асимметрия «создание vs редактирование»

Три поверхности работы с городом разошлись в том, какой объём модели данных
они покрывают:

| Поверхность | Секций city.md | Механизм записи |
|---|---|---|
| Форма создания (`page-city-new`) | **8 из 16** | `POST /api/cities` → `cityScaffold` → `buildCityMd` |
| Форма редактирования (`_renderCityEdit`) | **16 из 16** | `PUT /api/cities` → `buildCityMd` (полный ребилд) |
| Вкладка «Markdown» | всё, сырым текстом | `PUT` с `cityMd` (запись как есть) |

Отсюда обе критичные находки: §16.2 (создание не даёт заполнить половину
модели) и §16.3 (редактирование, дающее всю модель, физически недоступно для
города с рукописными секциями — потому что полный ребилд их уничтожит).

### 16.2 🔴 Восемь секций нельзя заполнить при создании города

`POST /api/cities` пробрасывает в `cityScaffold` whitelist из 9 полей
(`routes/cities.js:100-106`). QA отправила в запросе все 16 — восемь молча
отброшены, без ошибки: `landmarks`, `hunting`, `edicts`, `mortals`,
`calendar`, `tech`, `limits`, `naming`.

**Почему это не косметика:** пять из восьми — рабочий вход AI-генерации.
`limits`/`edicts`/`hunting`/`tech` собираются в блок «ОГРАНИЧЕНИЯ ГОРОДА»
(`buildCityConstraints`, `lib/context_builder.js:238-261`), `naming` — в блок
«ИМЕННИК И ФАКТУРА» (`buildCityNaming`, там же :285-294). Оба подмешиваются в
системные промты генерации сценариев и локаций.

Замер на живых городах (роль «Тестировщик»):

```
qa_testgorod   constraints=ПУСТО  naming=ПУСТО   ← создан со ВСЕМИ полями в запросе
qa_uiflow      constraints=ЕСТЬ   naming=ЕСТЬ    ← после правки через форму редактирования
paris          constraints=ПУСТО  naming=ПУСТО   ← основной рабочий город
```

**Практический вывод:** механизм «живого города» (миграция 001 завела секции,
`context_builder` умеет их читать) на сегодня простаивает — в Париже эти
секции пустые, а заполнить их в момент создания города негде вообще. Это не
регресс реализации §13, а не закрытая с самого начала дыра: секции добавлялись
миграцией в файл, но точку ввода для них не завели ни в одной форме, кроме
generic-textarea редактирования.

### 16.3 🔴 У Парижа вкладка «Поля» заблокирована целиком

`_cityHasCustomSections()` (`city.js:94-98`) дизейблит структурную вкладку,
если в city.md есть хоть один заголовок вне канонического набора. У Парижа
таких четыре:

- «Парижская специфика сценария» — по смыслу дубль канонической «Специфика ответа»
- «Чего избегать (парижское)» — дубль «Чего избегать»
- «Источники (Париж)» — дубль «Источники»
- «Уточняющие вопросы перед написанием сценария (Париж)» — **своя, канонического аналога нет**

Канонических «Специфика ответа»/«Чего избегать»/«Источники» у Парижа при этом
нет вовсе — то есть первые три расхождения это чистое переименование 1:1, без
коллизий. Балмонт и новые города не затронуты (0 кастомных секций).

**Блокировка обоснована, а не произвольна** — проверено по коду: `PUT
/api/cities` с `fields` делает `cityMd = buildCityMd(b.fields)`
(`routes/cities.js`), то есть **полный ребилд файла из 16 канонических
секций**. Любая рукописная секция при сохранении через форму «Поля» была бы
уничтожена. Дизейбл — законный guard против потери данных.

**Важно для планирования:** переименование трёх секций миграцией **не снимет
блокировку** — четвёртая («Уточняющие вопросы…») канонического аналога не
имеет и продолжит блокировать форму. То есть вариант «просто переименовать»
задачу не решает, вопреки первому впечатлению.

**Это уже решённый в проекте класс задачи.** Ровно та же проблема — полный
`buildCityMd`-ребилд разрушает рукописный city.md Парижа — всплыла при
реализации §11 (двусторонний синк фракций) и была закрыта точечной заменой
ОДНОЙ секции вместо ребилда: `_replaceCitySection()` в
`web/routes/archive.js:89-106` (там же в комментарии зафиксировано, почему
ребилд применять нельзя). Тот же приём здесь снимает и первопричину, и
блокировку.

### 16.4 🟡 Следствие того же расхождения: синк фракций у Парижа не работает

У Парижа нет секции «## Фракции» вообще. Воспроизведено на копии: при
добавлении фракции на странице «Фракции» `political_state.md` обновляется,
city.md — нет, в ответ приходит `warning` «синк пропущен» (§11 задумывал это
как редкую деградацию, а для Парижа это постоянное состояние).

### 16.5 🟡 Создание города с районами плодит дубликаты папок

UI после `POST /api/cities` вызывает `POST /districts` на каждый район.
Результат на диске (проверено реальным прогоном формы):

```
locations/district_01/testovyy_kvartal/.gitkeep   ← фантом от cityScaffold (старая схема)
locations/testovyy_kvartal/district.md            ← настоящая District-сущность
```

`cityScaffold` (`lib/parsers/city.js:198-211`) всё ещё создаёт обёртки
`district_NN/`, хотя §8 этого плана их отменил («Убрать Округ, унифицировать
до Город → Район → Локация»). Фантомы пустые, в UI не видны (`GET /districts`
требует `district.md`), но остаются в репозитории навсегда и путают при
просмотре файловой структуры.

### 16.6 🟡 Год не валидируется при редактировании

`POST` отклоняет нецифровой год, `PUT` — принимает: сохранён
`# QA Brauzergorod, не-год-вообще — сеттинг города`. Год попадает в шапки
карточек персонажей и локаций, то есть расходится по данным города.

### 16.7 🟡 CSV районов утекает в текст секции «Районы» одной строкой

Два района дают в city.md один буллет `- Первый Ку,Второй Ку` вместо двух.
Причина — `buildCityMd` получает `fields.districts` тем же CSV, что
`cityScaffold` использует для создания папок, и прогоняет его через
`_citySection()` как обычный текст.

### 16.8 Поля, недоступные через UI, но нужные для ведения города

| Что | Состояние | Приоритет |
|---|---|---|
| 8 секций при создании (§16.2) | только через редактирование, и то если не заблокировано | 🔴 |
| Редактирование района после создания города | UI нет; `PUT /api/cities/:slug/districts/:slug` готов и покрыт тестами, но не вызывается ниоткуда | 🔴 (уже §15) |
| Удаление района | нет ни API, ни UI — ошибочный район сносится только руками из ФС | 🟡 |
| Переименование района меняет только подпись | папка навсегда со старым слагом («Совсем Другое Имя» в `testovyy_kvartal/`) | 🟡 (осознанно, §2.4 техспеки) |

### 16.9 Решения и очередь работ (роль «Аналитик»)

**Решено — порядок и способ:**

1. **Точечная запись секций вместо полного ребилда в `PUT /api/cities`**
   (закрывает §16.3 и §16.4 одной правкой, снимает первопричину).
   Переиспользовать уже существующий и проверенный на этих же данных
   `_replaceCitySection()` — вынести из `web/routes/archive.js` в общий модуль
   (`lib/parsers/city.js` рядом с `buildCityMd`, либо `lib/city_sections.js`),
   не копировать второй реализацией. `PUT` с `fields` правит только те секции,
   что реально пришли, остальной файл (включая рукописные секции Парижа) не
   трогает. `buildCityMd` остаётся для СОЗДАНИЯ города с нуля — там ребилд
   корректен по определению.
   После этого — **снять дизейбл** `_cityHasCustomSections` с вкладки «Поля»
   (сама функция может остаться для предупреждающей плашки «у города есть
   свои секции, они сохранятся как есть» — информирование вместо запрета).
   Переименование парижских секций миграцией при этом **не требуется** (см.
   §16.3 — оно всё равно не решало задачу); отдельный вопрос ниже.
2. **Пробросить 8 секций в `POST /api/cities`** (§16.2) — расширить объект,
   передаваемый в `cityScaffold` (`routes/cities.js:100-106`). Backend-правка
   в несколько строк, отдельно от вопроса, показывать ли их в форме создания.
3. **Убрать `district_NN/`-обёртки из `cityScaffold`** (§16.5) — наследие
   отменённой §8 схемы. Проверить на существующих городах, что пустые
   обёртки нигде не читаются, и решить, нужна ли миграция-уборка уже
   созданных фантомов (в Париже они есть).
4. **Валидация года в `PUT`** (§16.6) — тем же правилом `/^\d{3,4}$/`, что
   уже стоит в `POST`. **CSV районов** (§16.7) — при сборке секции «Районы»
   разбивать по запятой в отдельные буллеты.
5. **DELETE района** (§16.8) — добавить в скоуп §15 вместе с редактированием
   района. Операция удаляет `district.md`; отдельно решить судьбу локаций
   внутри удаляемого района (перенос в «Другие» / запрет удаления непустого
   района — рекомендую запрет с явной ошибкой, тем же паттерном 409, что уже
   принят для коллизий slug в §16.3 техспеки).

**Открытый вопрос для Системного аналитика (нужно решение перед п.2):** где
показывать 8 секций, ставших доступными на бэкенде. Форма создания уже
длинная; варианты — (a) добавить их сразу, сгруппировав под сворачиваемым
блоком «Правила и ограничения города» (эти секции логически однородны: чем
генерация ограничена и на чём основана); (b) не трогать форму создания, а
после успешного создания города вести пользователя на страницу города с

**Отдельно, не блокирует ничего:** привести парижские «Парижская специфика

## 17. 🔴 Перенос локации между районами не обновляет ссылки на неё (2026-08-04)

> Найдено при прогоне `tools/validate_links.ps1` после работ по §16. Подтверждено
> на реальных данных Парижа. Пользователь подтвердил формулировку задачи:
> «при привязке локации надо не только переносить файл, но и менять ссылки на него».

### 17.1 Дефект

`PUT /api/locations/:slug/district` (§9.2 техспеки — привязка/перенос локации в
район) физически переносит папку локации через `fs.rename`, но **не трогает
markdown-ссылки на неё** в остальных файлах города. Все ссылки, указывавшие на
старый путь, становятся битыми молча — ни ошибки, ни предупреждения в ответе.

Живой пример на данных Парижа (локация переехала `villet` → `antrepo`):

```
[FILE]   cities/paris/chronicles/sluchaynye_gosti/modules/dengi_ne_problema/dengi_ne_problema.md
[LINK]   ../../../../locations/villet/sklad_kanal_yurk/sklad_kanal_yurk.md
[TARGET] cities/paris/locations/villet/sklad_kanal_yurk/sklad_kanal_yurk.md   ← файла там больше нет
```

**Масштаб.** В данных сейчас 30 markdown-ссылок на карточки локаций (`grep` по
`cities/`, форма `locations/<район>/<локация>/<локация>.md`). Ссылаются модули,
хроники, `archive/*`, карточки персонажей и соседние карточки локаций. То есть
любой перенос локации, у которой есть входящие ссылки, ломает от одной до
пяти ссылок за клик — а самая связанная локация (`opera/opera_garne`) имеет 5.

**Автоматического восстановления сегодня нет.** Кнопка «Проверка → Исправить
автоматически» (`validate_links.ps1 -Fix`) чинит только битые ссылки на
**изображения** (`Where-Object { $_.IsImage }`, `tools/validate_links.ps1:75-76`);
ссылки на `.md` она лишь показывает. Пользователю остаётся править их руками,
предварительно догадавшись запустить проверку.

### 17.2 Задача шире одной ручки — все операции, двигающие карточку

Пользователь верно обозначил проблему как глобальную. Инвентаризация операций,
меняющих физический путь локации:

| Операция | Двигает | Чинит ссылки | Статус |
|---|---|---|---|
| `PUT /api/locations/:slug/district` (§9.2) | `locations/<A>/<loc>/` → `locations/<B>/<loc>/` | ❌ нет | **дефект, этот пункт** |
| `DELETE /api/locations/:slug` | → `locations/_deleted/<slug>_<ts>/` | ❌ нет | см. §17.4 — отдельный вопрос |
| `POST /api/import/locations` | создаёт по `dirRelPath` | н/д (не перенос) | ок |
| Миграция 002 (округ→район) | массовый перенос всех локаций | ✅ **да** | эталон, см. §17.3 |

Глубина вложенности при переносе между районами **не меняется** (оба пути —
`locations/<район>/<локация>/`), поэтому ИСХОДЯЩИЕ ссылки внутри самой карточки
(`../../../characters/…`) остаются валидными. Ломаются только ВХОДЯЩИЕ — это
существенно упрощает задачу по сравнению с миграцией 002, которой приходилось
чинить оба направления.

### 17.3 Решение уже написано и проверено — переиспользовать, не изобретать

Ровно эта задача решена в `tools/migrations/002_district_rayon_paths.js`, когда
та же операция выполнялась массово:

- `fixLinks(cityDir, renameMap, log)` (строки 139-172) — обходит все `.md`
  города и заменяет `locations/<oldRel>` → `locations/<newRel>` по регулярке
  с границей `(?=[/)]|$)`, аккуратно с BOM, сортируя карту переименований по
  убыванию длины пути (чтобы длинный путь не был перекрыт совпадением с более
  коротким префиксом). Работает с любой глубиной `../` — потому что матчит не
  относительный префикс, а хвост `locations/<путь>`.
- вторая функция (строки 174+) чинит ИСХОДЯЩИЕ ссылки при смене глубины —
  **для этого пункта не нужна** (глубина не меняется, см. §17.2).

**Решение (роль «Аналитик»):** вынести `fixLinks()` из миграции 002 в общий
модуль (`web/lib/` — рядом с `db.js`/`parsers`, доступно и серверу, и
tools-скриптам) и вызывать его из `PUT /api/locations/:slug/district` сразу
после успешного `fs.rename`, с `renameMap` из одной записи
`{ oldRel: '<A>/<loc>', newRel: '<B>/<loc>' }`. Миграция 002 после выноса
импортирует его же — одна реализация, не копия. Тот же принцип, что уже принят
для `_replaceCitySection` в §16.9 п.1.

**Обработка ошибок — non-blocking, по уже принятому в проекте паттерну:**
перенос папки к моменту фикса ссылок уже произошёл и откатывать его из-за сбоя
записи чужого файла нельзя (тот же вывод, что для `_syncCityFactionsList` в §11
и синка персонажей/локаций в §4.2/§5.2). Сбой → `warning` в ответе
`PUT /district` рядом с уже существующими `movedFrom`/`movedTo`, а фронтенд
показывает его тостом (`_attachLocationToDistrict` уже умеет показывать ошибки).
В ответ полезно добавить `linksUpdated: <число файлов>` — чтобы пользователь
видел, что перенос затронул не только папку.

### 17.4 Открытые вопросы для Системного аналитика

- **`DELETE /api/locations/:slug`.** Мягкое удаление уводит карточку в
  `_deleted/`, входящие ссылки после этого битые. Чинить их автоподстановкой
  нельзя — цели больше нет. Варианты: (a) ничего не делать (текущее поведение,
  битые ссылки остаются и всплывают в проверке); (b) предупреждать ДО удаления
  («на эту локацию ссылаются N файлов») и показывать список — по образцу
  `showConfirm` при привязке, которая уже предупреждает о физическом переносе;
  (c) снимать ссылку, оставляя текст (как `-Fix` делает для изображений).
  Рекомендация — (b): решение остаётся за Рассказчиком, а данные не портятся
  молча. Требует «обратного индекса» ссылок — той же функции обхода, что и
  `fixLinks`, только в режиме подсчёта, без записи.
- **Персонажи.** Такой же перенос/переименование папки для персонажей в проекте
  есть (`tools/migrate_char.js`, переименование через модалку по slug —
  FIX-4b). Проверить отдельной задачей, чинит ли он входящие ссылки на карточку
  персонажа (в данных их заведомо больше, чем на локации), и если нет —
  переиспользовать тот же вынесенный `fixLinks` с префиксом `characters/`
  вместо `locations/`. В скоуп этого пункта не входит, но проблема того же
  класса и, вероятно, того же решения.
- **Стоит ли расширить `validate_links.ps1 -Fix`** до починки `.md`-ссылок,
  когда файл однозначно находится в другом месте (поиск по имени карточки).
  Это страховка «на потом» для уже накопленных битых ссылок и для случаев,
  когда файл двигали мимо интерфейса (руками в проводнике/git). Отдельная
  задача, не блокирует основной фикс.

### 17.5 Немедленное следствие для текущих данных

В `cities/paris` сейчас **одна** битая ссылка — та, что в примере §17.1
(последствие уже сделанного переноса `sklad_kanal_yurk`). После реализации
пункта она чинится вручную один раз (или прогоном `fixLinks` с картой
`villet/sklad_kanal_yurk` → `antrepo/sklad_kanal_yurk`); задним числом
автоматически ничего не исправится, потому что старого пути на диске уже нет и
восстановить карту переименований система не может.
