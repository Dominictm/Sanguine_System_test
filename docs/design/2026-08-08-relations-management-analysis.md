# Анализ: доработка «Связи и отношения» — управление постоянными/авторскими связями, разделение поля, взаимность, авто-пары, цвет графа

**Роль:** Аналитик · **Дата:** 2026-08-08

## Executive Summary

Запрошенная доработка (9 пунктов) затрагивает **пять слоёв системы одновременно**: формат
хранения связи в MD-карточке персонажа, серверный классификатор типа связи, клиентскую форму
редактирования вкладки «Отношения», новую библиотеку «Постоянных связей» (которой сегодня не
существует) и граф (`web/public/scripts/graph.js`). Это не точечная правка — это отдельная
подсистема, сопоставимая по объёму с уже сделанной сегодня библиотекой «Смертные» (Часть 4
мастер-техспеки), но с дополнительным структурным риском: нужно менять формат уже
**существующих данных** (связи есть в карточках персонажей прямо сейчас, во всех городах).

**Главная находка**: то, что выглядит как «просто добавить пикер и модалку», на самом деле
требует пересмотра того, откуда вообще берётся «тип связи» на графе — сегодня это не
сохранённое значение, а **классификатор по ключевым словам**, вычисляемый заново при каждом
чтении карточки (`categorizeRel(desc)`, `web/lib/parsers/character.js:69-83`). Явного поля
«тип» в данных нет вообще. Пункты 3, 5, 6, 7, 8 запроса требуют, чтобы тип **стал настоящим
структурированным значением** — это меняет формат MD-строки связи и требует миграции для уже
существующих данных (как `tools/migrations/007_title_from_hierarchy.js`, но сложнее — там было
переименование лейбла, здесь — разбор свободного текста на два поля).

Ниже — разбор по каждому пункту с находками в реальном коде, затем сводка архитектурных развилок,
требующих решения перед техспекой, и рекомендуемый порядок реализации (фазами — объём слишком
большой для одного захода).

## Текущее состояние (что реально есть в коде — важно для контекста ниже)

- **Хранение**: одна MD-строка на связь под `- **Отношения:**\n  - Имя[, Имя2] — свободный
  текст`. Парсер — `web/lib/parsers/character.js:187-202`. Одна строка может относиться сразу к
  НЕСКОЛЬКИМ целям через запятую (`Джуди, Мария — подруги`) — важно учитывать при проектировании
  формы с двумя полями.
- **«Тип» связи не хранится** — вычисляется заново при каждом парсинге картой ключевых слов
  `categorizeRel(desc)` (`character.js:69-83`): 11 категорий (`familiar`, `family`, `sire`,
  `childe`, `enemy`, `ally`, `romantic`, `suspicious`, `loyalty`, `secret`, `acquaintance`) +
  дефолт `neutral`. **«Гуль»/«Домитор» в этом классификаторе нет вообще** — такая связь сегодня
  молча попадает в `neutral` (серый, без своего цвета на графе).
- **Связь однонаправленная по хранению**: карточка персонажа A хранит СВОЮ строку про B;
  автоматической записи в карточку B при сохранении сегодня нет. Граф (`web/routes/
  dashboard.js:104-125`) сам дедуплицирует пару в одно ребро, если запись есть С ОБЕИХ сторон
  (и умеет показывать разный текст с каждой стороны — `fromChar`/`fromChar2`), но это только
  чтение/визуализация, не запись — п.4 запроса («взаимно» с автозаписью в другую карточку) это
  качественно новая возможность, а не расширение существующей.
- **Форма редактирования** (`web/public/scripts/char-detail.js:181-186, 518-523`) — одна строка
  = поле имени (даталист по `STATE.characters`) + **одно** текстовое поле с даталистом
  `REL_TYPE_OPTIONS`. Несмотря на CSS-класс `.cdet-rel-type-inp`, это поле хранит **весь**
  свободный текст, попадающий в `description` — пользователь может ввести что угодно, включая
  фразы длиннее одного слова.
- **Два независимых, рассинхронизированных списка «типов»**:
  - `REL_TYPE_OPTIONS` (`web/public/scripts/scripts.js:188`) — 9 русских строк для даталиста
    формы: `['Семья', 'Сир/Чайлд', 'Фамильяр', 'Союзник', 'Враг', 'Преданность', 'Нейтральный',
    'Знакомый', 'Тайная связь']`.
  - `REL_LABELS`/`REL_COLORS` (`web/public/scripts/graph.js:10-40`) — 13 ключей (англ. слаги),
    используются для цвета/подписи/легенды графа: `family, sire, childe, familiar, ally, enemy,
    loyalty, romantic, suspicious, acquaintance, secret, neutral, aggregate`.
  - Эти списки **не соответствуют друг другу**: в даталисте формы нет отдельно «Чайлд»
    (только комбо «Сир/Чайлд»), нет «Романтика»/«Подозрение», которые есть в `REL_LABELS`. Оба
    списка — хардкод в JS, никакой библиотеки (`system/library/...`) для типов связи сегодня нет
    — в отличие от дисциплин/кланов/титулов, у которых такая библиотека уже есть и её
    CRUD-инфраструктура (`_mdLibRoutes`, `library-authoring.js`) уже построена сегодня же, в
    рамках Части 4 мастер-техспеки.
- **«Домитор»/«Гуль» уже упоминаются в проекте, но не как структурная связь**: `system/schema/
  card_schema.md:52-57` фиксирует конвенцию — домитора фамильяра указывают **словом** в свободном
  тексте «Отношений» («домитор»/«хозяин»), а собственно «Гуль» — это отдельный, несвязанный
  механический бэкграунд (`system/library/backgrounds/ghoul.json`, шкала 1-5), не тип связи.
  Формализация «Домитор»/«Гуль» как пары структурных типов связи (п.7,8) — по сути реализация
  того, что схема давно описывает словами, но код не умеет посчитать.
- **Вкладка «Фамильяр»** (`char-detail.js:70-83`) — ТРЕТЬЕ место в коде, парсящее `description`
  регуляркой (`/фамильяр/i`) для отдельной цели (найти карточку хозяина). Если тип связи станет
  структурированным полем — эта проверка должна переключиться на него вместо regex по прозе,
  иначе после доработки останется хрупким дублирующим путём с собственным риском рассинхрона.
- **`/api/characters` уже отдаёт `relationships[]` целиком** (`web/routes/
  characters.js:123-126`, никакой урезки) — граф прогревает `STATE.characters` этим же эндпоинтом
  ещё до открытия страницы (`graph.js:81-87`). Значит «сбор Авторских связей по файлам
  персонажей» (п.2) можно сделать **без нового API** — чисто на клиенте, агрегацией уже
  загруженного `STATE.characters[].relationships[].description`, только на СЕРВЕРЕ такого списка
  сегодня нет нигде готового, собирать по всем персонажам сразу — это НОВАЯ операция (сейчас
  каждая карточка читает только свои связи, сквозного разреза по всем персонажам города для этой
  цели не существует).

## Разбор по пунктам

### П.1 — Кнопка «Добавить связи» рядом со «Сбросить»

Простая находка: «Сбросить» — это `#btn-reset` на странице «Граф» (`index.html:188`,
`graph.js:472-486`), НЕ кнопка в модалке персонажа (в тексте запроса нет уточнения, но других
кандидатов на «сбросить» рядом со связями в коде нет). Значит модалка управления связями —
общая, per-город, открывается со страницы графа, а не из карточки конкретного персонажа. Простое
добавление кнопки в тулбар — рисков нет.

### П.2 — Модалка «Постоянные связи» / «Авторские связи»

**«Постоянные связи»** — по факту новая библиотека (аналог дисциплин/кланов/титулов), которой
сегодня не существует. Рекомендация: заводить её **тем же паттерном**, что уже построен сегодня
для «Смертные» — один MD-файл на тип связи в `system/library/relation-types/` (или похожее имя),
`_mdLibRoutes`-фабрика (`web/routes/library.js`, уже обобщена и параметризуема) даёт CRUD почти
бесплатно. Разница с дисциплинами/кланами: тип связи не нуждается в длинном «Описании» —
достаточно имени + (см. развилки ниже) цвета/ключа-слага/маркера «авто-парная» связь для Сир↔Чайлд
и Домитор↔Гуль.

**«Авторские связи»** — вычислимый список, не хранилище: агрегация уникальных значений
`description`, которые встречаются в `relationships[]` **хотя бы одного** персонажа города и
**не совпадают** ни с одним именем из «Постоянных связей». Источник данных уже загружен
(`STATE.characters`, см. находку выше) — можно строить полностью на клиенте без нового эндпоинта
для ЧТЕНИЯ. Для действия «Сделать постоянной» — нужен только POST на создание записи в новой
библиотеке (уже есть паттерн — `_mdLibRoutes` включает POST).

**Открытый вопрос** (см. развилки ниже): что происходит с уже существующими карточками, где
эта же строка использовалась как `description`, — остаётся ли текст как есть (теперь совпадает
с именем нового «постоянного» типа и перестаёт попадать в «Авторские»), или требуется
back-fill структурного поля «тип» у всех совпавших записей? Это прямо завязано на решение по
п.3 ниже.

### П.3 — Разделение «Вид отношений» на короткий тип + развёрнутое описание

Это не косметика поля — это смена формата хранения. Три связанных решения:

1. **Формат MD-строки.** Сейчас `Имя — текст`. Нужен третий компонент (тип). Разделитель должен
   не встречаться в реальных данных произвольно — нужно выбрать его аккуратно и параллельно
   проверить существующие карточки на предмет коллизии (аналогично тому, как в этой сессии уже
   проверялось для faction-picker'а формат «Русское (English)»).
2. **Обратная совместимость.** У ВСЕХ городов уже есть карточки с текущим форматом (одно поле).
   Нужна миграция (`tools/migrations/`, паттерн есть — `007_title_from_hierarchy.js`, но сложнее:
   не переименование лейбла, а разбор текста). Практичный путь — не пытаться угадать «короткий
   тип» из старого текста регуляркой при миграции (это будет неточно для нестандартных формулировок
   пользователей), а оставить старые записи как есть с пустым «типом» и фоллбэком на уже
   существующий `categorizeRel(desc)` для графа/цвета, пока пользователь не отредактирует
   строку вручную через новую форму. Это снижает риск миграции (ничего не переписывается
   насильно), но означает, что **классификатор по ключевым словам остаётся в коде
   бессрочно** как фоллбэк для legacy-данных — не «временный костыль на переходный период».
3. **Пикер для короткого поля.** По аналогии с уже реализованными сегодня пикерами
   (Дисциплины/Титулы/Секта/Организация) — короткое поле должно быть picker+свободный ввод из
   «Постоянных связей», не голый datalist, иначе связь между этим полем и новой библиотекой
   (п.2) чисто визуальная, а не функциональная.

Побочный эффект (см. «Текущее состояние» выше): вкладка «Фамильяр» (`char-detail.js:70-83`)
сегодня находит хозяина через `/фамильяр/i` по `description` — после появления структурного поля
эту проверку стоит переключить на него, иначе останется два независимых, потенциально
рассинхронизированных способа определить одно и то же.

### П.4 — Чекбокс «Взаимно», авто-запись в карточку второго персонажа

Новая возможность, не расширение существующей — сегодня сохранение связи трогает только ОДНУ
карточку (`PUT /api/characters/:slug/relations`, `web/routes/characters.js:292-328`, работает с
одним `cardPath`). Нужно: при сохранении со включённым «Взаимно» — дополнительно прочитать/
переписать карточку персонажа-цели, добавив туда обратную связь.

**Критический открытый вопрос — как система узнает при СЛЕДУЮЩЕМ редактировании/удалении, что
конкретная связь была создана как взаимная**, чтобы каскадно обновить/удалить и вторую сторону?
Запрос прямо говорит «по умолчанию не активен, для каждой строки чекбокс свой» — то есть при
повторном открытии формы чекбокс не восстанавливается автоматически в «включено» для уже
существующих взаимных связей. Если полагаться только на состояние чекбокса в форме — то
редактирование ранее-взаимной связи БЕЗ повторного включения чекбокса развяжет стороны
(перестанет обновлять вторую карточку), что выглядит как тихая потеря синхронизации, а не явное
решение пользователя. Варианты:
- **(A) Явный маркер в данных** — при сохранении с «Взаимно» дописывать в MD-строку скрытый
  признак (или отдельное поле, если формат уже становится структурированным по п.3) — тогда при
  следующем сохранении система сама видит, что связь помечена как взаимная, и обновляет обе
  стороны независимо от текущего состояния чекбокса в форме (чекбокс становится, по сути,
  предпросмотром/подтверждением уже сохранённого состояния, подтягиваясь при открытии формы).
  Надёжно, но требует ещё одного изменения формата хранения поверх уже запланированного п.3.
- **(B) Вывод по совпадению** — при сохранении смотреть, есть ли у карточки-цели строка,
  указывающая обратно на текущего персонажа с «парным» типом (см. п.5-7) или идентичным текстом,
  и, если да, править её синхронно, без отдельного маркера. Не требует изменения формата, но
  ненадёжно для произвольных «взаимных» связей без авто-пары (Союзник, Враг, Тайная связь и
  т.п.) — по какому признаку тогда решать, что две независимо введённые строки на разных
  карточках — это «одна взаимная связь», а не два случайных совпадения? Риск неверного каскада.

Рекомендую (A) — надёжнее, и раз п.3 уже меняет формат хранения строки связи, добавить туда же
признак взаимности — не отдельная последующая миграция, а часть одной и той же техспеки формата.
Но это решение стоит держать явным, не тихим умолчанием — фиксирую в сводке развилок ниже.

### П.5-7 — Авто-пары (Сир↔Чайлд, Брат↔Сестра, Домитор↔Гуль)

Технически — частный случай п.4 (взаимная запись), но с ДВУМЯ дополнительными свойствами:
1. Тип **второй** стороны не совпадает с типом первой (это не зеркалирование одного и того же
   значения, а таблица соответствия: Сир→Чайлд, Домитор→Гуль, Чайлд→Сир, Гуль→Домитор).
2. Для Брат/Сестра — конкретное значение зависит от `gender` целевого персонажа (`GENDER =
   ['Мужской', 'Женский']`, `web/routes/characters.js:75` — ровно два значения, обязательны для
   всех линеек при создании персонажа, так что пропущенного пола у современных карточек не
   бывает; у легаси-карточек, заведённых до этого требования, теоретически возможно — стоит
   решить, что показывать, если пол цели не заполнен: скорее всего просто не проставлять
   авто-тип и не чек-боксить «Взаимно» автоматически, с уведомлением, а не молчать).

Чекбокс «Взаимно» в этом случае, по тексту запроса, «проставляется автоматически» — то есть эти
три пары типов должны быть отдельно помечены в библиотеке «Постоянных связей» (п.2) как
«авто-парные» с указанием типа-партнёра (и, для Брат/Сестра, зависимостью от пола) — обычной
текстовой записи «Постоянной связи» для этого недостаточно, нужно доп. поле в её структуре.

### П.8 — Базовый набор из 11 типов

Прямое сопоставление с существующими данными:

| Из запроса | Уже есть как | Примечание |
|---|---|---|
| Сир | `sire` (классификатор + `REL_LABELS`) | есть |
| Чайлд | частично — `childe` есть в `REL_LABELS`/классификаторе, но НЕТ отдельно в `REL_TYPE_OPTIONS` даталиста (только комбо «Сир/Чайлд») | нужно развести |
| Брат | нет — сегодня всё в одном `family` | новый |
| Сестра | нет — см. выше | новый |
| Гуль | нет нигде как тип связи | новый |
| Домитор | нет нигде как тип связи (см. «Текущее состояние») | новый |
| Фамильяр | есть | есть |
| Союзник | есть (`ally`) | есть |
| Враг | есть (`enemy`) | есть |
| Семья | есть (`family`) — но теперь пересекается по смыслу с новыми Брат/Сестра | требует решения по иерархии/приоритету |
| Тайная связь | есть (`secret`) | есть |

Это будет **seed-набор** «Постоянных связей» библиотеки (п.2) — 11 стартовых записей, часть с
маркером авто-парности (п.5-7).

### П.9 — Автогенерация цвета для новых типов

Сегодня `REL_COLORS` — фиксированный объект (`graph.js:10-24`), 13 ключей. Любой тип за
пределами этого набора уже сейчас молча получает цвет `neutral` (`graph.js:276`,
`REL_COLORS[d.type] || REL_COLORS.neutral`) — то есть про полностью «пользовательские» типы
(из «Постоянных связей», сверх seed-набора п.8) сегодня рисуются неотличимо друг от друга.
Технически два пути:
- **Детерминированный хеш строки типа → HSL-цвет** — без изменений хранения, стабилен между
  перезагрузками (одинаковый тип всегда даёт одинаковый цвет), не требует нового поля.
- **Случайный цвет, сохраняемый в записи «Постоянной связи»** (генерируется один раз при
  создании типа, дальше хранится как обычное поле библиотечной записи) — соответствует
  буквальной формулировке запроса «случайным образом» и позволяет пользователю быть
  предсказуемо привязанным к «своему» цвету навсегда, а не к результату хеш-функции. Требует
  доп. поля в структуре записи (не проблема — раз структура и так новая, п.2).

Рекомендую второй вариант — раз «Постоянная связь» и так становится полноценной библиотечной
записью (п.2, п.5-7 уже требуют доп. полей), хранить цвет там же последовательно со всем
остальным, а не городить отдельный недетерминированный-но-стабильный хеш.

## Ключевые архитектурные развилки — нужно решение перед техспекой

1. **Формат MD-строки связи** (тип + описание + признак взаимности) — три под-значения вместо
   одного текста. Конкретный синтаксис — задача Системного аналитика, но принцип (см. п.3, п.4-A)
   нужно утвердить: короткий тип и признак взаимности хранятся структурно, длинное описание —
   свободным текстом, как сейчас.
2. **Миграция старых данных** — рекомендация: НЕ пытаться автоматически разложить старый
   свободный текст на тип+описание при миграции (риск неточной догадки на реальных, уже
   написанных пользователем данных по всем городам) — оставить legacy-записи с пустым
   структурным типом, графу/цвету продолжать пользоваться `categorizeRel(desc)` как фоллбэком
   бессрочно. Требует подтверждения — альтернатива (одноразовая эвристическая миграция,
   основанная на том же `categorizeRel`) тоже возможна, но её результат придётся вручную
   проверять по каждому городу.
3. **Структура записи «Постоянная связь»** — минимум: имя, цвет (п.9), опциональный
   «тип-партнёр» + «зависит от пола» (п.5-7). Нужно решить, заводить ли её как MD-библиотеку
   (переиспользование `_mdLibRoutes`, быстрее в реализации) или как более компактный JSON-массив
   (как merits/flaws/backgrounds — `_jsonLibRoutes`) — MD не даёт особого выигрыша здесь (нет
   длинного «Описания» для прозы), JSON, вероятно, проще и достаточен.
4. **Взаимность старых/предсуществующих совпадений** — при первом включении фичи в городе, где
   пользователь уже вручную дублировал связи на обеих карточках (без всякого чекбокса), система
   не должна интерпретировать это как «взаимная связь» и начать её каскадно трогать — маркер
   взаимности появляется только у НОВЫХ, явно так помеченных связей.

## Рекомендуемый порядок реализации (фазами — объём велик для одной техспеки/PR)

1. **Фаза 1** — библиотека «Постоянные связи» (п.2 левая часть, п.8 seed, п.9 цвет) — по
   образцу уже готовой инфраструктуры «Смертные», наименьший риск, не трогает формат карточек.
2. **Фаза 2** — разделение поля в форме + формат хранения + миграция-фоллбэк (п.3) — самая
   рискованная часть, инфраструктурная база для всего остального.
3. **Фаза 3** — «Авторские связи» (п.2 правая часть) + «Сделать постоянной» — зависит от Фазы 1
   (нужна библиотека, куда переносить) и Фазы 2 (нужно структурное поле типа, чтобы отличать
   «совпадает с постоянной» от «авторская»).
4. **Фаза 4** — «Взаимно» + авто-пары (п.4-7) — зависит от Фаз 1-3 целиком (нужны структурные
   типы, признак взаимности в формате хранения, «тип-партнёр» в библиотеке).
5. **Фаза 1** можно отдать в реализацию независимо и раньше остальных; Фазы 2-4 — строго
   последовательны.

Рекомендую передать этот документ Системному аналитику для техспеки как минимум Фазы 1
(наименее рискованная, максимально независимая) и зафиксировать развилки §«Ключевые
архитектурные развилки» как часть входных данных для техспек последующих фаз.
