# Анализ: дедупликация пикеров фракций города + мульти-титулы + клановый фильтр дисциплин

**Роль:** Аналитик · **Дата:** 2026-08-08 · **Для:** Системного аналитика (следующий шаг — техспека)

## Executive Summary

Запрошены три правки:

1. **Страница города → вкладка «Фракции»**: пикеры «из библиотеки» (Секты/Независимые
   кланы/Фракции смертных/Государственные фракции) должны скрывать уже добавленные записи.
2. **Модалка персонажа → поле «Титул»**: разрешить выбор НЕСКОЛЬКИХ титулов из библиотеки
   (по образцу «Дисциплин»).
3. **Модалка персонажа → поле «Дисциплины»**: фильтр по клану (клановые — первыми, остальные —
   ниже), по образцу фильтра по секте у «Титулов».

**Результат разбора:**

- **П.1 — реальный гэп, есть точное решение.** Все четыре пикера сейчас показывают полный
  список библиотеки без учёта уже добавленного. Правка небольшая, локализована в
  `web/public/scripts/city.js`, один и тот же паттерн для всех четырёх разделов.
- **П.2 — реальная фича, но с архитектурной ловушкой.** Поле `hierarchy` («Титул в городе»)
  сегодня и на фронте, и на бэке жёстко считается **одиночным** значением. Бэкенд
  (`web/routes/cities.js`) при сохранении карты фракций города **перезаписывает это поле
  целиком** при назначении персонажа на политическую роль (Князь/Примоген и т.п.) — если
  превратить поле в мульти-значение только на фронте, эта синхронизация начнёт **молча стирать**
  вручную добавленные титулы. Нужно править и бэкенд, не только пикер.
- **П.3 — уже реализовано.** Клановый фильтр для «Дисциплин» (группа «Клановые» первой, «Все
  дисциплины» — под ней) уже есть в коде (`_renderDisciplinePickerLists`,
  `char-detail.js:1422-1449`) — это часть уже сделанной в этой сессии «Части 1: пикер
  дисциплин». Действие не требуется, только подтверждение в отчёте.

## 1. Дедупликация пикеров фракций города (п.1 запроса)

### 1.1 Текущее состояние

Файл `web/public/scripts/city.js`, функция `_renderFactionPickerList(which, query)`
(строки 753–780) — общая точка рендера для всех четырёх панелей-пикеров:

| `which` | Источник данных | Где хранится «уже добавлено» |
|---|---|---|
| `sects` | `ensureSects()` → `_sectsCache` | чипы `.cdet-faction-chips[data-faction-group="sects"] .cdet-faction-chip` |
| `clans` | `ensureClans()`, фильтр `sect === 'Независимые'` | чипы `.cdet-faction-chips[data-faction-group="clans"]` |
| `mortal` | `ensureMortLib('religious'\|'crime'\|'civic')`, 3 подгруппы | строки в `textarea[data-city-field="factions-mortal-list"]` |
| `state` | `ensureMortLib('government')` | строки в `textarea[data-city-field="factions-state-list"]` |

Сейчас фильтрация — только по поисковому запросу (`!q || name.toLowerCase().includes(q)`),
без учёта того, что запись уже добавлена. Из-за этого список пикера позволяет добавить один
и тот же клан/секту/организацию дважды. Для `sects`/`clans` повторный клик по уже добавленной
записи в списке фактически работает как toggle-remove (обработчик клика в блоке `if (which ===
'sects' || which === 'clans')`, строки 796-802, ищет существующий чип и удаляет его) — то есть
бага дублирования как такового для этих двух разделов почти нет (повторный клик убирает), но
пункт запроса не про это: пользователь хочет, чтобы уже добавленное **не отображалось в списке
выбора вообще**, чтобы не приходилось искать его глазами среди ещё не добавленных.
Для `mortal`/`state` то же самое: клик по уже добавленной строке в списке — toggle (строки
803-812, `idx !== -1 ? splice : push`), опять же уже добавленное просто не должно светиться в
самом списке выбора.

### 1.2 Рекомендация

Единая точка правки — `_renderFactionPickerList`. Перед тем как строить HTML списка,
вычислить множество уже добавленных имён для конкретного `which` и отфильтровать кандидатов:

- `sects`/`clans`: `Set` из `dataset.faction` всех чипов в соответствующей
  `.cdet-faction-chips[data-faction-group="…"]` (те же чипы, что уже читает `_collectFactions`).
- `mortal`: `Set` из строк `textarea[data-city-field="factions-mortal-list"]` — фильтр общий
  для всех трёх подгрупп (religious/crime/civic), т.к. на выходе это один плоский список строк.
- `state`: `Set` из строк `textarea[data-city-field="factions-state-list"]`.

Правку нужно применить и в handler'е клика по кнопке 📚 (открытие панели вызывает
`_renderFactionPickerList(which, '')` — уже подхватит фильтр), и в handler'е `input` на поиске
(`_renderFactionPickerList(m[1], e.target.value)` — тоже подхватит автоматически, отдельно
трогать не нужно), а также **после самого добавления/удаления** — сейчас после клика по
элементу списка (строки 792-813) панель не перерисовывается, просто добавляется чип. Нужно
дозвать `_renderFactionPickerList(which, currentSearchValue)` в конце этого блока, чтобы
только что добавленная запись сразу пропала из списка (и чтобы удаление чипа — клик по чипу,
строки 816-818 — тоже возвращало запись обратно в список, если панель открыта).

**Симметрия с «Дисциплинами»/«Титулами»**: концептуально это тот же паттерн, что
`_disciplineAlreadyIn`/✓-пометка в пикере дисциплин, только без ✓ (эти пикеры — не toggle
внутри одного текстового поля, а add/remove из независимого хранилища чипов/строк) — здесь
корректнее не помечать, а **скрывать целиком**, как и просит запрос.

### 1.3 Что НЕ входит

«Другие фракции» — свободный `textarea`, не привязан к библиотеке, вкладка пикера у него нет,
дедупликация неприменима (сам пользователь ответственен за неповторяющиеся строки).

## 2. Мульти-выбор титулов (п.2 запроса)

### 2.1 Текущее состояние поля `hierarchy`

Поле называется на разных линейках по-разному («Титул», «Иерархия», «Титул в городе» в MD),
но везде это **одно поле, одна строка**:

- Парсер (`web/lib/parsers/character.js:138`): `c.hierarchy = v` — присваивание, не список.
- Пикер (`char-detail.js:1275-1310`, `key === 'hierarchy'`): клик по записи в
  `#cdet-title-picker` **заменяет** всё значение поля (`titleInput.value =
  item.dataset.cdetTitle`, `char-detail.js:1573-1580`) и **закрывает** панель — принципиально
  другое поведение, чем у «Дисциплин» (там — добавление токена через запятую, панель остаётся
  открытой, элементы помечаются ✓, повторный клик снимает).
- Приоритет по секте/клану **уже реализован** (`_renderTitlePickerLists`, строки 1533-1557) —
  ровно то же самое разбиение «приоритетные/все», которое запрошено для дисциплин по клану
  (см. §4). Технически «титулы фильтруются по секте» уже готовы как референс-паттерн.

### 2.2 Критическая находка — конфликт с синком «Титула» из карты фракций города

`web/routes/cities.js`, функция `syncPoliticalCharacterHierarchy` (строки 268–306),
вызывается при сохранении города и **синхронизирует поле `hierarchy` персонажа с его
политической ролью** (Князь/Сенешаль/Примоген и т.п. из блока «Властители города» +
«Примогенат» на карте фракций):

- При назначении: `writeCharacterCardField(city, char, hierarchyMdKey, value)`, где
  `value = "${role} города ${cityDisplay}"` — **полная перезапись** поля, невзирая на то, что
  там было раньше (строка 302).
- При снятии роли: поле очищается (`''`), но **только если** текущее содержимое **точно равно**
  ожидаемой строке `${role} города ${cityDisplay}` (строка 292, `!== expected` → `continue`,
  «ручная правка — не трогаем», задокументированное поведение §4.4 техспеки
  2026-08-02-city-creation-restructure).

Это писалось в расчёте на то, что `hierarchy` — **одна** строка. Если превратить поле в
мульти-значение (через запятую, как «Дисциплины»), оба сценария ломаются:

1. **Назначение роли поверх вручную выбранных титулов** — если у персонажа уже стоит, скажем,
   `"Шериф"` (добавлен вручную через новый мульти-пикер), а на карте фракций города его
   назначают Примогеном, `syncPoliticalCharacterHierarchy` **затрёт** значение на
   `"Примоген города Париж"` целиком — `"Шериф"` исчезнет без предупреждения. Это тихая потеря
   данных, а не крайний случай — это будет происходить при **каждом** сохранении города, где
   персонаж на политической роли.
2. **Снятие роли перестаёт срабатывать корректно** — если поле стало `"Примоген города Париж,
   Шериф"`, точное сравнение `!== expected` больше никогда не совпадёт → строка 292 всегда
   `continue`, т.е. при снятии роли с персонажа старый политический титул **навсегда останется**
   в списке (не только не почистится «умно» — не почистится вообще, даже вручную его придётся
   искать и убирать через тот же пикер).

### 2.3 Рекомендация

Многотитульность реализуема, но `syncPoliticalCharacterHierarchy` нужно переписать на ту же
модель токенов, что уже есть у «Дисциплин» (`_cdetDisciplineTokens`/`_disciplineTokenMatches`
как референс для аналогичной пары на бэкенде): не сравнивать/перезаписывать поле целиком,
а **добавлять/убирать один конкретный токен** `"${role} города ${cityDisplay}"` из
разделённого запятыми списка, оставляя остальные токены нетронутыми. Это работа над той же
функцией, что уже существует — не новый модуль, но она обязательно входит в объём задачи,
иначе фича на фронте будет незаметно портить данные, записанные городской картой фракций.

Второстепенно (уточнить у Системного аналитика/пользователя при технической проработке,
не блокирует анализ):
- Формат разделителя — запятая, как у дисциплин (`", "` при join), для консистентности.
- `_titleItemHtml`/клик-хендлер (`char-detail.js:1528-1580`) переписать по образцу
  `_disciplineItemHtml`/discItem-хендлера (1418-1421, 1594-1617): ✓-пометка уже выбранных,
  toggle add/remove по клику, панель не закрывается после выбора.
- Нужна функция-аналог `_disciplineTokenMatches` для титулов — сопоставление токена (строки в
  поле) с записью библиотеки. У дисциплин сложная эвристика из-за формата «Русское (English)»;
  у титулов имя в библиотеке уже голое русское (`t.name`, без скобок — см. пример «Князь» в
  `system/library/titles/knyaz.md`), так что сопоставление проще: прямое сравнение строк
  (с `trim()`/case-insensitive), без варианта с англ. частью.
- `⚠️`-маркер негативного титула (`_titleItemHtml`, строка 1530) при мульти-выборе должен
  сохраняться как часть каждого добавленного токена (как сейчас) — не требует изменений.

## 3. Клановый фильтр для дисциплин (п.3 запроса)

**Уже реализовано** — `_renderDisciplinePickerLists` (`char-detail.js:1422-1449`), часть уже
выполненной в этой сессии «Части 1: пикер дисциплин» master-техспеки. Логика:

```
priority = дисциплины клана текущего персонажа (v20ClanInfo(clan).disciplines)
rest     = все остальные
```

Группа «Клановые» рендерится первой (и скрывается, если пуста — клан не выбран или дисциплин
нет), «Все дисциплины» — второй. Это **буквально** тот же паттерн, который запрошен по образцу
«фильтр по секте у Титулов» (`_renderTitlePickerLists`, приоритет по секте/клану персонажа —
структурно идентичный код). Действий не требуется.

## Порядок реализации (рекомендация для техспеки)

1. **П.1 (дедуп пикеров фракций)** — простая, локальная правка, без рисков для данных.
   Можно реализовать первой/отдельно.
2. **П.2 (мульти-титулы)** — включает обязательную правку бэкенда
   (`syncPoliticalCharacterHierarchy`) вместе с фронтом (пикер `char-detail.js`), иначе
   фронтенд-фича тихо конфликтует с существующей синхронизацией «Титула» с картой фракций
   города. Тестовый сценарий должен явно включать: персонаж с вручную добавленным вторым
   титулом → назначение на карте фракций города политической роли → сохранение города → второй
   титул должен остаться на месте (регресс-проверка находки §2.2).
3. **П.3** — не требует работы, только подтвердить в финальном отчёте, что уже покрыто.
