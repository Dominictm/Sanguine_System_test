## 0. Главная находка перед дизайном: почти всё уже спроектировано

Прежде чем предлагать layout для пп.6–7 («Занятые должности», «Значимые
места города»), проверил модалку РЕДАКТИРОВАНИЯ города
(`web/public/scripts/city.js`) — и там уже есть готовый, рабочий визуальный
паттерн для ровно этой задачи:

- **«Держатели ключевых должностей»** (`_cityPolEditorHtml`) — повторяемые
  строки `.cdet-rel-row.cdet-pol-row`: дропдаун должности (+ «Другое…» →
  текстовое поле), поле имени с `<datalist>`-автодополнением по
  существующим персонажам (можно вписать и то, чего в списке нет), кнопка
  «✕» на строку, кнопка «+ Добавить запись» под списком.
- **«Отмеченные локации»** (`_cityLocEditorHtml`) — та же структура:
  дропдаун типа (+ «Другое…»), поле названия с datalist по существующим
  локациям; если вписанное имя новое — под строкой раскрывается доп.
  блок (Район, Заметка) для будущей настоящей карточки.

Это ЗНАЧИТ: дизайн-задача — не «нарисовать 2 новых блока с нуля», а:
1. **Перенести** этот уже готовый визуальный паттерн в форму СОЗДАНИЯ
   города (сейчас там просто `<textarea>` — `city-political`/
   `city-locations`), тем же приёмом, каким туда уже перенесён
   `city-factions-editor` (единый компонент между создать/редактировать).
2. **Расширить словари** — `CITY_POLITICAL_ROLES` (нет «Хранителя
   Элизиума», опечатка «Примаген»/«Примоген») и `CITY_LOCATION_TYPES`
   (сейчас только «Элизиум» — нет остальных 4 статусов).
3. **Спроектировать** ровно 2 действительно новых куска UI, которых нет
   нигде: (а) визуальное разведение «должность» vs «клан Примогена» — см.
   §1; (б) как показывать пользователю новую механику записи-назад в
   карточку персонажа/локации — см. §3.

## 1. Как показать Примогенат — РЕШЕНО (вариант B)

Пользователь просил дропдаун КЛАНОВ вместо дропдауна должностей для
Примогената. Сегодняшний компонент — один общий дропдаун «Должность» на
все роли, «Примаген» — просто ещё одна строка в нём (клан для примогена
эта форма не спрашивает вообще — он сегодня подтягивается автоматически
из карточки выбранного персонажа при синке в «Карту фракций»).

Два пути, оба технически реализуемы поверх уже готового компонента:

**A — Не трогать структуру, просто заменить одну строку.** В общем
дропдауне «Должность» вместо одной опции «Примоген» — ничего не меняем
визуально; клан пишется в «Свою должность» (текстом, как «Примоген
(Вентру)»). Минимум работы, но НЕ даёт пользователю дропдаун кланов, как
он просил буквально — только более длинный текст в свободном поле.

**B — Отдельная под-секция «Примогенат» под «Властителями».** Визуально
идентичная строка-структура, но с ДРУГИМ дропдауном (список кланов вместо
списка должностей), под отдельным заголовком секции — ближе всего к
буквальной формулировке запроса. Требует небольшого дублирования кода
компонента (два похожих, но разных дропдауна вместо одного), но UI
остаётся предсказуемым: пользователь видит «Примогенат» как отдельный,
явно озаглавленный блок, а не спрятанную опцию в общем списке должностей.

**Решено пользователем — вариант B**: отдельная под-секция «Примогенат»
со своим дропдауном кланов, визуально отделённая от «Властителей города»
(§2), не спрятанная опция в общем списке должностей.

## 2. Расположение в форме создания города

Сегодняшняя форма — `<details class="city-create-spoiler">`, последовательность
`.form-group`/`.form-row` (Название/Год → Сеттинг → Политический ландшафт
→ Фракции → Ключевые локации → Лейтмотивы → Специфика → Чего избегать →
Источники → Районы-CSV). После реструктуризации (§4 плана Аналитика)
порядок блоков:

```
1. Название · Год                              (.form-row, как сейчас)
2. Сеттинг                                       (без изменений)
3. ГЕОГРАФИЯ (новый заголовок-разделитель)
   └ Текстовое описание города
   └ Район ×N (повторяемая карточка, см. §2.1)
       └ [+ Локация] → модалка локации, «Район» предзаполнен и disabled
4. ПОЛИТИЧЕСКИЙ ЛАНДШАФТ (существующий заголовок)
   └ Главенство секты (дропдаун)
   └ Фракции (существующий city-factions-editor, без изменений)
   └ Властители города   (перенесённый _cityPolEditorHtml, роли из п.1)
   └ Примогенат           (вариант B из §1 — свой блок, свой дропдаун)
5. ЗНАЧИМЫЕ МЕСТА ГОРОДА (новый заголовок = перенесённый _cityLocEditorHtml,
   но «Тип» → «Статус локации», список расширен до 5 значений)
6. Лейтмотивы и атмосфера / Специфика ответа / Чего избегать / Источники
   (без изменений, порядок как сейчас)
```

### 2.1 Визуальная структура блока «Район» (повторяемая карточка)

По аналогии с `.cdet-rel-row`, но плотнее (у района больше полей, чем у
одной строки «должность+имя») — предлагаю карточку, а не строку:

```
┌ Район 1 ─────────────────────────────────────── [✕ Удалить] ┐
│ Наименование района*        [___________________]           │
│ Тип района                  [Спальный ▾]  (можно вписать)    │
│ Влияние — Секта              [___]   Клан  [___]             │
│ Описание                    [textarea, 2 строки]             │
│ ─────────────────────────────────────────────────────────── │
│ Локации в районе:                                            │
│  • Театр Лицей                                    [Открыть]  │
│  • [+ Добавить локацию]  → модалка, Район уже выбран (disabled)│
└────────────────────────────────────────────────────────────┘
[+ Добавить район]
```

Каждая карточка — `.form-group`-подобный блок с более заметной рамкой
(`border:1px solid var(--border)`, `border-radius:var(--r-sm)`, паддинг
как у `.loc-card`, НЕ как у плоской строки) — район визуально «тяжелее»
одной строки должности, потому что несёт больше данных; смешивать его с
`.cdet-rel-row` (одна строка) было бы неверной иерархией.

## 3. Как показать запись-назад в карточку персонажа/локации

Это НАСТОЯЩАЯ новая механика (см. техспеку §4.2/§5.2) — при выборе
существующего персонажа/локации форма города МОЛЧА пишет в чужой файл.
Молчаливость здесь плохой UX: пользователь должен видеть, что происходит,
иначе решение «поставил Шерифа — а почему у персонажа само поменялось
поле „Иерархия“?» будет для него сюрпризом.

**Предложение:**
- Рядом с полем выбора персонажа/локации — маленькая подпись-хинт (в
  духе уже существующего `field-tip`/`cdet-rels-hint`): «При выборе
  существующего персонажа его карточка получит запись в поле „Иерархия“
  автоматически» — показывается один раз при первом появлении блока, не
  на каждой строке (иначе шумно).
- При сохранении, если бэкенд вернул `warnings[]` (см. техспеку §4.2 шаг
  5 — не заблокировавшая сохранение ошибка записи в чужую карточку) —
  показать через уже существующий `showToast(msg, 'warning')` (проект уже
  везде использует этот паттерн для некритичных ошибок), НЕ модальным
  диалогом — сохранение города прошло успешно, это дополнительная,
  некритичная информация.

## 4. Состояния и мелкие детали (per role-чеклист «состояния элементов»)

- **Пустой список районов/должностей/локаций** — как у `_polRowHtml()`
  сегодня: одна пустая строка-заготовка сразу видна (не голая кнопка
  «+ Добавить») — так пользователь сразу понимает форму первой строки,
  не гадает.
- **Поле «Район» в модалке локации, открытой из блока Района** —
  предзаполнено + `disabled` (сероватый фон по стандартному стилю
  disabled-инпута проекта), с подписью под полем «Локация будет привязана
  к этому району» — так пользователь не пытается его менять и не путается,
  почему поле нередактируемо.
- **Дропдаун «Тип района»/«Статус локации» с опцией «Другое…»** — при
  выборе «Другое…» текстовое поле рядом должно получить `autofocus`
  (уже так работает в `_polRowHtml`/`_locRowHtml` — просто подтверждаю,
  что перенос обязан сохранить это поведение, не растерять при копировании).
- **Touch-таргеты** — кнопки «✕ Удалить»/«+ Добавить запись»/«+ Добавить
  район» — свериться, что на `pointer:coarse` они ≥44px по высоте (правило
  из `CLAUDE.md` для фронтенда) — сегодняшние `.cdet-rel-del-btn`/
  `.cdet-rel-add-btn` в модалке редактирования стоит перепроверить перед
  копированием в форму создания, а не полагаться, что раз работает в одном
  месте — значит ок и в другом (разный контекст плотности формы).

---

## 5. Решено

«Значимые места города» пишут в ДВА места одним действием: city.md-строка
«Ключевые локации» (как уже делает существующий компонент, без изменений)
И `zone`/`control` карточки локации (новая часть). Пользователь увидит
последствия в обоих местах после сохранения — это ожидаемое поведение,
не побочный эффект.

## 6. Заметка в «Отмеченные локации» (техспека §8)

Третье поле — короткий `<input type="text">`, не textarea: заметка по
смыслу («действует только по ночам») — однострочная аннотация, а не проза.
Встраивается в существующий `.cdet-loc-row` (Тип-select + Название-input)
третьим полем в тот же flex-ряд:

```
[Статус ▾] [Название локации·······] [Заметка (опц.)····] [✕]
```

Если ряд станет слишком тесным на узких экранах — `.cdet-loc-row` уже
`flex`-контейнер (по образцу `.cdet-rel-row`), проверить перенос на мобильной
ширине при реализации (правило проекта — touch-таргеты и адаптив, но
здесь это, скорее всего, обычный `flex-wrap`, не требует нового паттерна).

## 7. Страница просмотра города (техспека §9)

### 7.1 Карточки района — read-only вариант

`_districtCardHtml()` уже даёт нужную структуру полей — для read-only
рендера НЕ нужен второй компонент: те же подписи (Наименование/Тип/
Влияние/Описание), но вместо `<input>`/`<select>` — просто текст, как уже
делает `metaViewHtml` в детальной модалке локации (`locdet-table`/
`locdet-row`/`locdet-key`+`locdet-val` — готовый паттерн «список пар
ключ-значение», переиспользовать его же для района на странице города, а
не изобретать третий способ показывать пары «подпись: значение» в
проекте).

### 7.2 «Привязать существующую локацию» — новый элемент UI

Внутри каждой карточки района на странице ПРОСМОТРА (не путать с формой
создания, там уже есть «+ Добавить локацию» → модалка СОЗДАНИЯ новой) —
второй, отдельный элемент: выпадающий список уже существующих локаций
ГОРОДА, которые ещё не в этом районе (исключить те, что уже здесь), плюс
кнопка «Привязать»:

```
Локации в районе:
 • Театр Лицей                                    [Открыть]
 • [Выбрать существующую локацию ▾]  [Привязать]
 • [+ Создать новую]
```

Два разных действия («Привязать существующую» и «Создать новую») должны
визуально различаться — не одна кнопка с неочевидным вторым смыслом:
привязка существующей локации переносит её физическую папку (техспека
§9.2, `fs.rename`), это операция с более заметным последствием, чем
создание пустой новой карточки — заслуживает отдельного подтверждающего
диалога (`showConfirm`, уже используется в проекте для похожих необратимых
действий) перед вызовом `PUT /api/locations/:slug/district`, а не тихого
срабатывания по одному клику на дропдауне.

### 7.3 Состояния

- Локаций, доступных для привязки, нет (все уже распределены по районам
  или город совсем новый) — дропдаун показывает заглушку «Нет свободных
  локаций» и дизейблится, кнопка «Привязать» тоже дизейблится — не прятать
  элемент целиком, чтобы пользователь понимал, что опция существует, а не
  что её забыли добавить.
- После привязки — карточка района должна обновиться сама (либо
  перерисовать список локаций района, либо просто перезагрузить страницу
  просмотра города) — без этого пользователь не увидит результат клика.

## 8. Единый empty-state (техспека §10)

Визуальный компонент уже существует и не меняется (`.chars-empty`) — здесь
для Дизайнера нет новой работы по форме, только по контенту: при аудите
(отдельная подзадача, техспека §10.2) для каждого раздела `hint` должен
называть КОНКРЕТНОЕ действие («Нажми «+ Добавить район» выше», не «создайте
запись») — тот же принцип конкретности, что уже видно в примере для
«Фамильяров» («Кнопка «+ Создать» подставит принадлежность сама»).

## 9. Синхронизация «Фракции» (техспека §11)

Чисто бэкенд — оба существующих UI (chip-редактор в описании города,
панель «Влияние фракций» на странице «Фракции») не меняются визуально.
Нет дизайн-работы по этому пункту.

## 10. Значок опасности ⚔️ (техспека §12)

Уже полностью специфицировано (замена константы) — визуально ⚔️ должен
идти в той же позиции и с тем же кеглем, что уже занимает 🎭 у Маскарада
(единообразие двух парных осей на одной карточке) — отдельно проверить
при реализации, что ⚔️ не рендерится избыточно крупным в шрифте, которым
набраны бейджи (эмодзи разных семейств иногда дают разную визуальную
массу при одном font-size — быстрая визуальная проверка на живой
странице локации, не только в коде).

## 11. Опасность/Маскарад/VtM-поля (техспека §13)

### 11.1 `loc-edit-modal` — где размещается «Опасность»

Сегодня `.loc-edit-row2` («Зона» + «Контроль») — один ряд из двух полей.
С разделением «Зоны» и «Опасности» на два поля туда просится третье —
предлагаю **не** сжимать всё в один 3-колоночный ряд (плотно, разные по
смыслу пары), а перегруппировать:

```
[Зона ▾]           [Опасность ▾]
[Контроль··········································]
```

«Зона» и «Опасность» — теперь родственная пара (то, чем раньше было одно
поле), логично идут рядом; «Контроль» — самостоятельное поле, получает
свою полноширинную строку, как уже сделано для «Адреса» выше по этой же
форме (`.chr-form-group` без `.loc-edit-row2`) — переиспользуем уже
существующий паттерн формы, не изобретаем новый.

### 11.2 «Зона» — дропдаун обязан расшириться

Важное следствие архитектурного решения техспеки §13.1, которого не было
явно в контракте: раз «Опасность» больше не парсится из эмодзи внутри
«Зоны», у дропдауна `loc-edit-zone` пропадает причина ограничиваться
3 цветными опциями — он должен показывать ПОЛНЫЙ домен `zoneClass()`,
иначе категории «Элизиум»/«Носферату» по-прежнему останутся недостижимы
через веб-форму (та же дыра, что уже описана в плане §13.6, просто
частично не закрытая, если тронуть только «Опасность» и забыть «Зону»):

```html
<select class="chr-form-input" id="loc-edit-zone">
  <option value="">—</option>
  <option value="🏛️ Элизиум">🏛️ Элизиум</option>
  <option value="🟣 Носферату">🟣 Носферату</option>
  <option value="🟡 Нейтральная">🟡 Нейтральная</option>
  <option value="🔴 Опасная">🔴 Опасная</option>
</select>
```

(«📍 Локация» — дефолт при пустом значении, отдельной опцией не нужен,
как и сегодня с «—»).

### 11.3 Вкладка «VtM» детальной модалки — форма по полям

Переиспользовать `.locdet-field-row`/`.locdet-field-lbl`/`.locdet-field-inp`
— тот же паттерн, что уже использует соседняя вкладка «Метаданные» в ЭТОЙ
ЖЕ модалке (`metaEditHtml`, `locations.js:349-353`) — не собирать новый
визуальный язык, когда рядом уже есть подходящий:

```
Статус            [_______________]
Фракция           [_______________]
Постоянные фигуры [_______________]
Угрозы            [_______________]
Маскарад          [Низкий ▾]
────────────────────────────────────
Описание (проза)
[textarea, как сейчас]
```

«Маскарад» — единственное поле из пяти как `<select>` (3 опции low/medium/
high, тот же паттерн, что теперь и у «Опасности» в п.11.1) — остальные
четыре свободный текст, `<input>`, не `<select>`: значения слишком
вариативны для готового списка («Постоянные фигуры» — имена персонажей,
«Угрозы» — свободная проза).

## 12. Сенсорная палитра формы редактирования (техспека §14)

### 12.1 Не копировать классы `.cdet-rel-row` буквально

`.cdet-rel-row`/`.cdet-loc-row` — визуальный язык city.js (форма города,
модалка редактирования города). `loc-edit-modal` — другая форма, другой
установленный класс-нейминг (`chr-form-group`/`chr-form-label`/
`chr-form-input`/`chr-form-textarea`, `loc-edit-*` префикс). Новый ряд
канала сенсорики должен получить СВОИ классы в этом же нейминге
(`loc-edit-sens-row`, например), не тащить `cdet-*`-классы в чужой модуль
— иначе он визуально не будет принадлежать форме, в которой живёт (разный
паддинг/шрифт/отступы между двумя семействами классов, если их не свести
явно).

### 12.2 Layout

Заменяет `#loc-edit-sensory` textarea на месте (та же позиция в форме,
после «Атмосферы»):

```
Сенсорная палитра
┌──────────────────────────────────────────────┐
│ [Свет ▾]      [textarea, 2 строки]        [✕] │
│ [Звук ▾]      [textarea, 2 строки]        [✕] │
│ [Запах ▾]     [textarea, 2 строки]        [✕] │
└──────────────────────────────────────────────┘
[+ Добавить канал]
```

`.loc-edit-body` уже скроллится (`overflow-y:auto`, `styles.css:12147-12153`)
— расширение этого поля с одной textarea до нескольких строк-каналов не
ломает layout модалки, просто увеличивает длину скролла; отдельно
перестраивать модалку не нужно.
