# Данные для техспеки: «Статус» заменяет «Зона контроля»

**Собрано:** Аналитик, 2026-08-06. **Передаётся:** Системному аналитику на техспеку
(после ответов пользователя на открытые вопросы ниже).

**Задача пользователя (дословно, 4 пункта):**
1. Вырезать весь функционал «Зона контроля».
2. В модальном окне локации в графе «Статус» должно отображаться значение из
   «Отмеченные локации» столбец «Статус локации» — **только это значение**
   (без заметки).
3. Взять значения, доступные для выбора статуса локации (тот же список, что
   уже используется в «Отмеченных локациях» города), и реализовать «Статус»
   похожим образом на то, как сейчас устроена «Зона контроля» (жёсткий
   выбор из списка, а не свободный текст).
4. НЕ добавлять это поле в форму создания локации.
5. Продумать обратную запись: изменение «Статуса» в модалке локации должно
   менять соответствующую запись в «Отмеченных локациях» карточки города.

## 2. Как «Статус» должен выглядеть и вести себя (замена п.2-3 задачи)

### 2.1 Текущее состояние поля

`loc.locStatus` — сейчас **свободный текст**, строка markdown-таблицы внутри
`## VtM` (не `**Label:**`-бюллет, см. `web/lib/parsers/location.js:62-71`).
Редактируется как `<input>` на VtM-вкладке (`locdet-vtm-status`,
`web/public/scripts/locations.js`, добавлено сегодня в рамках плана «карточка
локации» §7.3). Синкается ОДНОСТОРОННЕ (город → локация) из «Отмеченных
локаций» города как `[Город] <Тип>[ — <Заметка>]` (`syncSignificantPlaceStatus`,
`web/routes/cities.js`).

### 2.2 Что меняется

- **Источник значений** — тот же список, что `CITY_LOCATION_TYPES`
  (`web/public/scripts/city.js:83`): Элизиум / Приёмная князя / Убежище /
  Шериф / Сенешаль.
- **`<input>` → `<select>`** на VtM-вкладке (`locdet-vtm-status`) — тот же
  паттерн, что уже есть у «Опасность»/«Маскарад» на этой же вкладке (селект с
  фиксированными опциями).
- **Бейдж в `.locdet-legend-row`** — заменяет «Зона контроля» на своём месте
  (тот же слот в шапке модалки), показывает ТОЛЬКО тип (без маркера
  `[Город]` и без заметки) — «ЭЛИЗИУМ», «ШЕРИФ» и т.д., по аналогии с
  прежним `badge-loc-*`.
- **Хранение значения** — раз поле теперь строгий enum из 5 значений, а не
  произвольный текст с маркером-заметкой, **формат `[Город] <Тип> — <Заметка>`
  для самого поля `**Статус**` VtM-таблицы больше не нужен** — значение
  становится просто одним из 5 слов («Элизиум» и т.п.), без маркера и без
  заметки. Заметка остаётся **только** в «Отмеченных локациях» города, в
  модалке локации не отображается и не редактируется (буквально требование
  п.2 задачи — «только это значение»).
- **Существующие карточки со свободным текстом в «Статусе»** (например,
  «Опера Гарнье» — «Главный Элизиум Парижа. Насилие абсолютно запрещено…», не
  входит ни в одно из 5 значений) — `<select>` не найдёт совпадения (та же
  логика, что уже у «Опасность»/«Маскарад» — `.includes(v)`-матчинг),
  откроется на пустом «—». Сам текст в файле не пострадает, пока
  пользователь не сохранит вкладку явно с новым выбором — тогда он будет
  перезаписан чистым значением типа. **Это ожидаемая, а не побочная потеря**
  — то же самое уже принято пользователем ранее сегодня для городского синка
  («синк всегда побеждает»), просто теперь это применимо и к прямому
  редактированию в модалке локации.

## 3. Механизм обратной записи (п.5 задачи)

### 3.1 Контракт

При сохранении VtM-вкладки локации с изменённым «Статусом» — обновить (или
создать) структурную запись `Тип: Название[ — Заметка]` в секции
«Локации» (`sec.locations`) карточки ГОРОДА, той же локации.

### 3.2 Технически

- Нужен **новый серверный эндпоинт** (или расширение существующего
  `PUT /api/locations/:slug/fields`) — при записи `locStatus` дополнительно
  находит/обновляет/создаёт строку в `cities/<город>/city.md`. Это **не** тот
  же путь, что `syncSignificantPlaceStatus` (тот идёт из PUT города В
  локацию) — нужен путь В ОБРАТНУЮ сторону, из локации В город.
- **Поиск нужной записи в city.md** — по имени локации, тем же способом,
  каким сегодня чинился баг сопоставления коротких/полных имён
  (`_locNameKnown`/аналог на сервере, см. фикс `syncSignificantPlaceStatus`
  чуть выше сегодня) — нужно применить ТУ ЖЕ логику сопоставления «короткое
  имя vs. полный заголовок карточки» и здесь, иначе обратная запись создаст
  ВТОРУЮ, дублирующую запись вместо обновления существующей для локаций с
  «слитным» заголовком (как «Опера Гарнье»).
- **Заметка** — при обновлении существующей записи заметка (третье поле
  строки) должна остаться нетронутой (задача явно не просит её трогать из
  модалки локации). При СОЗДАНИИ новой записи (локация раньше не была ни в
  каком статусе) — заметка пустая.

### 3.3 Решения пользователя по открытым вопросам

1. **Фильтр «Все зоны»** (страница «Локации», `#loc-filter-zone`) —
   **переделывается под «Статус»**, не убирается. Опции — 5 значений
   `CITY_LOCATION_TYPES` вместо 4 категорий Зоны; фильтрация в
   `renderLocations()` — по чистому значению `loc.locStatus` (после того как
   оно перестало быть маркер+заметка строкой, прямое сравнение, `zoneClass()`
   для этого больше не нужен).
2. **Бейдж «Статус»** — **только в детальной модалке** (`.locdet-legend-row`),
   на компактную карточку сетки НЕ возвращается. Компактная карточка
   остаётся как сделана сегодня (⚔️ Опасность + 🎭 Маскарад, без бейджа типа
   локации).
3. **Сброс «Статуса» в модалке локации при непустой заметке в городе** —
   **запрещён**. Если у записи в «Отмеченных локациях» есть заметка — выбор
   «—» в select локации отклоняется (не даёт сохранить/предупреждает),
   пользователь должен снять статус явно через Географию города, где видит
   и может при желании сохранить/перенести заметку. Если заметки нет —
   сброс проходит свободно, запись в городе удаляется целиком.

## 4. Итоговый контракт для Системного аналитика

### 4.1 Удалить (Тема «Вырезать Зону»)
- Клиент: `ZONE_CLASS_LABELS`, `zoneClass()`, `.loc-zone-icon`/`.locdet-no-img`
  фоллбэк на зону (нужна новая, не-зонная заглушка-иконка для безартовых
  карточек — например нейтральная 📍 без категорий), бейдж «Зона контроля» в
  `.locdet-legend-row`, `#loc-edit-zone` (select в форме создания/редактирования
  — убрать полностью, ничего не добавляя взамен, п.4 задачи).
- Разметка: `#loc-edit-zone` из `#loc-edit-modal` (`index.html:1276-1283`).
- CSS: `.badge-loc-*` (5 классов) — можно удалить или оставить неиспользуемыми
  (реализующий решает, нулевой риск в обоих случаях).
- Бэкенд: `zone` можно оставить в `fieldMap`/парсере как неиспользуемый
  (решение §1, «оставить поле в данных») — либо убрать из `fieldMap`, раз
  писать в него больше не из чего (UI-точки записи не будет) — **уточнить
  при реализации**, не блокирует контракт.

### 4.2 Переделать (Тема «Статус как Зона»)
- `#loc-filter-zone` → фильтр по `CITY_LOCATION_TYPES` (5 опций), логика
  фильтрации — прямое сравнение `loc.locStatus === value` (после отказа от
  маркер-формата, см. §4.3).
- `.locdet-legend-row` — заменить бейдж «Зона контроля» на «Статус» (та же
  позиция, первый элемент строки), значение — `loc.locStatus` как есть (уже
  чистое, без маркера/заметки после правки формата хранения).
- VtM-вкладка (`locdet-vtm-status`) — `<input>` → `<select>` с опциями
  `CITY_LOCATION_TYPES` (+ пустая «—»), тот же паттерн, что уже есть у
  «Опасность»/«Маскарад» на этой вкладке.
- Форма создания локации (`#loc-edit-modal`) — «Статус» туда не добавляется
  (п.4 задачи уже выполняется тем, что там и не было отдельного поля под
  VTM-таблицу).

### 4.3 Формат хранения — меняется

Сейчас `loc.locStatus` = `[Город] <Тип>[ — <Заметка>]` (маркер+заметка,
писалось только городским синком). После этой задачи — **чистое значение
одного из 5 типов**, без маркера, без заметки (заметка целиком остаётся на
стороне города). Значит:
- `SIGNIFICANT_PLACE_TYPES`/`_significantPlaceValue()`/`CITY_CONTROL_MARKER`
  (`web/routes/cities.js`) — правятся синхронно: город тоже должен писать в
  локацию ЧИСТЫЙ тип, не маркированную строку с заметкой (иначе два
  направления синка будут писать данные в разных форматах и конфликтовать
  друг с другом на каждом сохранении любой из сторон).
- Логика «сброс при снятии статуса» в `syncSignificantPlaceStatus`
  (сейчас — `current.trim().startsWith(conf.value)`, т.е. проверка по
  маркеру) — тоже нужно переписать под чистое сравнение (`current === тип`),
  раз маркера больше нет.
- **Миграция НЕ нужна для уже синканных карточек** сегодняшним кодом (напр.
  «Опера Гарнье», сейчас `[Город] Элизиум — Главный Элизиум, 9-й округ») —
  при следующем touch (сохранении с любой стороны) значение просто
  перепишется в новый чистый формат; ничего специально мигрировать не
  требуется, эффект тот же, что уже принят пользователем сегодня («синк
  всегда побеждает»).

### 4.4 Новое — обратная запись (город ← локация)

Новый серверный путь: при сохранении VtM-вкладки локации с изменённым
`locStatus` —
1. Найти запись `Тип: Название[ — Заметка]` в `sec.locations` города по
   имени локации, **тем же сопоставлением коротким/полным именем**, что
   сегодня чинилось для чтения (`_locNameKnown` на клиенте /
   аналогичная логика на сервере, `syncSignificantPlaceStatus`).
2. Если запись есть — обновить ТОЛЬКО тип, заметку не трогать.
3. Если записи нет, а пользователь выбрал непустой статус — создать новую
   запись `Тип: Название` (без заметки).
4. Если пользователь выбирает «—» (снять статус) — см. §3.3 п.3: заблокировать,
   если есть заметка; если заметки нет — удалить запись целиком.
5. Точка записи — та же секция `locations` города, тот же
   `upsertCitySectionFromForm`/точечный путь, что уже используется для
   правки секций без полного ребилда city.md (см. фикс §16.3 из более
   ранней техспеки этого же цикла — переиспользовать, не дублировать).

### 4.5 Риск гонки «город ↔ локация»

Если Рассказчик редактирует Статус локации и сохраняет Географию города
одновременно (два открытых окна/вкладки) — возможен конфликт последней
записи (last-write-wins на уровне файла `city.md`, обычный для этого
проекта риск при параллельном редактировании, ничем не хуже уже принятых
рисков в других частях приложения — специальной блокировки не требуется).

4 (обратная запись, самая рискованная часть, в последнюю очередь и отдельно
тестируется).
