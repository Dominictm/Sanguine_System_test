## A2. «Иерархия» → «Титул» (переименование + миграция + пикер из библиотеки)

### 2.1 Фактическое состояние данных (проверено grep по `cities/*/characters/**/*.md`)

В реальных карточках обнаружены **два разных исторических лейбла**, не один, как предполагал
анализ:

1. **`- **Иерархия в городе:** значение`** — канонический, читаемо-/записываемый лейбл.
   `EDITABLE_FIELD_MAP.hierarchy = 'Иерархия в городе'` (`web/lib/db.js:527`, сверено
   2026-08-07 — было `:487`, сдвинулось) — единственный лейбл, который реально пишет
   `PUT /api/characters/:slug/fields` (роут `web/routes/characters.js:213`, сверено
   2026-08-07 — было процитировано `:264-278`, номер устарел) и
   `syncPoliticalCharacterHierarchy` (`web/routes/cities.js:273`, сверено 2026-08-07 —
   было `:265-297`, функция сдвинулась на 8 строк, дальше в теле пропорционально). Встречается
   в **29 карточках** Парижа на 2026-08-07 (было «~28» на 2026-08-06 — за сутки прибавилась
   одна, естественный дрейф данных, не повод пересчитывать техспеку).
2. **`- **Парижская иерархия:** значение`** — **более старый, орфанный лейбл**, который
   предшествовал введению «Иерархия в городе» (комментарий в `cities.js` датирует
   текущую схему техспекой `2026-08-02-city-creation-restructure-techspec.md §4.2-4.4`).
   Он **не входит** в `EDITABLE_FIELD_MAP` — ничего никогда не пишет туда через UI. Но:
   - читается парсером как алиас через `/иерархи/i.test(k)` (`character.js:138` — точное
     совпадение с исходной техспекой, строка не сдвинулась);
   - читается отдельным fallback-путём в дайджесте НПС-модуля:
     `web/routes/modules/shared.js:245` (точное совпадение, не сдвинулось) —
     `field(/\*\*Парижская иерархия:\*\*.../) || field(/\*\*Иерархия в городе:\*\*.../)`.
   - На 2026-08-07 встречается в **26 карточках** (было «~20» — тоже дрейф данных за сутки,
     не структурная неточность).
   - **В одной карточке (`emiliya_indra_landorg.md`) это по-прежнему ЕДИНСТВЕННЫЙ источник**
     (перепроверено 2026-08-07) — «Иерархия в городе» там нет вовсе.

Это меняет форму миграции и объём правок парсера относительно того, что предполагал анализ:
переименовывать нужно **только канонический лейбл** (`Иерархия в городе`), а не оба —
«Парижская иерархия» остаётся нетронутым легаси-текстом (см. §2.3 почему это безопаснее, чем
пытаться его тоже мигрировать).

### 2.2 Ключевое архитектурное решение — устраняет коллизию без лайнейко-условной логики

Анализ предлагал переименовать md-лейбл в голое **«Титул»** и защититься от коллизии с фейским
`if (k === 'Титул') c.title = v` (`character.js:158`) через лайнейко-условный regex
(`/^(иерархи|титул)/i`, но только не для `fairy`). Парсер `parseCharacter()` сейчас **не имеет
ни одной лайнейко-условной ветки** в цикле разбора полей (все `if` применяются к каждому файлу
одинаково, `lineage` в теле функции для выбора полей не используется) — вносить туда первое
ветвление ради одного поля увеличивает риск непропорционально задаче.

**Решение: новый md-лейбл `Титул в городе`** (не голое «Титул») — по образцу уже существующего
`Иерархия в городе`. Он лексически не пересекается с фейским лейблом `Титул`, поэтому:
- никакой лайнейко-условной логики в парсере не нужно — просто ещё один `if (k === …)`;
- фейские карточки, у которых уже есть строка `- **Титул:**` (Двор), не задеваются вообще —
  ни regex, ни миграцией (в них никогда не может появиться `Титул в городе`);
- `EDITABLE_FIELD_MAP.hierarchy` меняется одной строкой, без per-lineage override
  (`FIELD_LABEL_BY_LINEAGE`, `characters.js:29-31`, по аналогии с фейским `location` — **не
  нужен**, т.к. лейбл один и тот же для vampire/mortal/generic).

UI-лейбл (то, что видит пользователь в форме) — просто **«Титул»** (короче, естественнее в
интерфейсе); md-лейбл в файле — **«Титул в городе»** (длиннее, но однозначен и непересекаем).
Это уже такое расхождение и сегодня: сейчас UI показывает «Иерархия», а в файл пишется
«Иерархия в городе» (`INFO_FIELDS_BY_LINEAGE.vampire` даёт `['hierarchy','Иерархия']` при том,
что `EDITABLE_FIELD_MAP.hierarchy` = `'Иерархия в городе'`) — паттерн не новый, только текст меняется.

### 2.3 Правки — парсер (`web/lib/parsers/character.js`)

Строка 138, было:
```js
if (/иерархи/i.test(k))                     c.hierarchy     = v;   // «Иерархия в городе» / устар. варианты
```
Стало (добавляем точное совпадение на новый лейбл, СТАРЫЙ regex-фоллбэк остаётся навсегда как
страховка на нераспознанные/немигрированные варианты — включая orphan «Парижская иерархия»,
которую мы сознательно не трогаем):
```js
if (/иерархи/i.test(k) || k === 'Титул в городе') c.hierarchy = v;   // «Титул в городе» (совр.) / «Иерархия в городе» / «Парижская иерархия» (легаси, не пишется UI)
```
Порядок совпадений внутри одного файла не меняется: поля разбираются построчно сверху вниз,
`c.hierarchy` каждый раз перезаписывается последним совпавшим — «Парижская иерархия» (выше в
файле) продолжает перекрываться нижестоящим каноническим полем ровно как сегодня. Для
`emiliya_indra_landorg.md` (только легаси-поле) ничего не меняется — значение по-прежнему
читается.

**Почему не мигрировать «Парижская иерархия» тоже:** массовая замена лейбла в карточках, где он
дублирует нижестоящее поле, создала бы **вторую строку `- **Титул в городе:**` в одном файле**
(коллизия лейблов внутри карточки — заведомо хуже статус-кво). Дедуп по содержимому (удалить
дубль, если текст совпадает) — не идемпотентная в общем случае операция (что если текст ПОЧЕМУ-ТО
разошёлся у какой-то карточки — потеря данных без ручной проверки). Оставить как есть — ноль
риска, поле уже нигде не пишется через UI, только читается как фоллбэк.

### 2.7 Миграция (`tools/migrations/`)

Контентная миграция. **Известно точно на 2026-08-07** (было «предположительно 004» на момент
техспеки — с тех пор добавились три несвязанные миграции той же недели):
`tools/migrations/001_city_liveliness_sections.js` … `006_location_status_marker_cleanup.js`
(последняя — фикс-план «Статус заменяет Зону», см. отдельную техспеку) — **следующий свободный
номер `007`**. Свериться перед реализацией всё равно стоит (`ls tools/migrations/`) — номер
живой, может снова уйти вперёд между этой правкой и стартом реализации A2.

`tools/migrations/007_title_from_hierarchy.js`:

```js
'use strict';
// «Иерархия»→«Титул» (2026-08-06, char-loc-city-fields техспека §A2): переименование
// md-лейбла «Иерархия в городе» → «Титул в городе» у вампиров/смертных/generic-линеек
// (оборотни/маги/охотники). НЕ трогает fairies (у них «Титул» — другое поле, титул при
// Дворе) и НЕ трогает орфанный легаси-лейбл «Парижская иерархия» (не входит в контракт
// EDITABLE_FIELD_MAP, оставлен как read-only фоллбэк — см. техспеку §A2.3).
module.exports = {
  description: 'Переименование md-лейбла «Иерархия в городе» → «Титул в городе» (вампиры/смертные/generic)',
  test(text)    { return /^- \*\*Иерархия в городе:\*\*/m.test(text); },
  migrate(text) { return text.replace(/^- \*\*Иерархия в городе:\*\*/gm, '- **Титул в городе:**'); },
};
```

**Почему без лайнейко-фильтра внутри миграции — можно применять ко всем `.md` без разбора:**
раннер миграций (`web/lib/migrations.js: runMigrations`, см. `tools/migrations/README.md`)
обходит `cities/<город>/**/*.md` целиком, не различая линейку персонажа по пути (только по
папке `characters/<линейка>/`, которую тест здесь не парсит). Но лейбл `Иерархия в городе`
**физически не может встретиться** ни в одной карточке феи — грепом по `cities/*/characters/fairies/**/*.md`
подтверждено (**действие для реализации**: прогнать этот grep перед публикацией миграции —
в момент написания техспеки в репозитории физически присутствуют только Парижские вампиры/
смертные с этим лейблом, папка `fairies/` в проверенных городах или пуста, или использует
собственный «Титул»/не заводила «Иерархия в городе» никогда, т.к. `INFO_FIELDS_BY_LINEAGE.fairy`
всегда писал под лейблом `Иерархия`, читай — не под «...в городе»-вариантом канонической схемы
вампиров/смертных). Если grep всё же найдёт совпадение в `fairies/` — не страшно: `test()`
матчится по буквальному тексту лейбла, не по линейке, миграция просто переименует и там; риск
чисто гипотетический и не требует блокировки перед реализацией, но стоит проверить один раз.

Идемпотентность: `test()` возвращает `false` на уже мигрированном тексте (нет больше
`Иерархия в городе`) → повторных применений при рестартах сервера не будет.

**Затронутые карточки** (проверено на момент анализа, `cities/paris/characters/**`, ~28 файлов
с `Иерархия в городе`; `cities/parizh_1/**`, 1 файл — черновой/тестовый город, лейбл там иной,
`Иерархия в городе: пропр`, тоже матчится штатно).

### 2.8 Пикер «из библиотеки Титулов» (`GET /api/library/titles`)

**Решение открытого вопроса о фильтрации** (§0, п. A2.1): показывать **все** записи `Title[]`
(DTO — см. техспеку Титулов §4), но с секцией-приоритетом сверху — записи, чей `affiliation`
содержит (case-insensitive substring, не точное совпадение) текущее значение поля «Секта»
персонажа **ИЛИ** текущее значение поля «Клан» — идут первыми под подзаголовком «По вашей
секте/клану», остальные — ниже под «Все титулы». Устраняет проблему, которую поднял Аналитик
(персонаж-Ассамит с `Секта: Камарилья` не находил бы титулы клана Ассамитов при точном
совпадении) — Ассамит увидит и «Камарилья»-титулы (по секте), и «Ассамиты»-титулы (по клану) в
приоритетной секции, а Инкогню/гости всё равно видят полный список ниже, ничего не спрятано
безвозвратно.

### 3.2 Дисциплины — `<datalist>` с клановой сортировкой (подтверждаю рекомендацию Аналитика)

**Решение открытого вопроса** (§0): `<datalist>`, не кастомный виджет. Обоснование сверх того,
что уже привёл Аналитик: решение пользователя §0.2 буквально ограничивает объём работы «только
автодополнение» — свой JS-виджет (позиционирование дропдауна, keyboard nav, клик вне-закрытие)
это уже отдельный UI-компонент с собственным набором edge cases (мобильный тач, доступность),
несоразмерный заявленному объёму задачи. Гарантия сортировки браузером не даётся, но это
проверяемый факт постфактум (visual QA в тест-плане, §7), не блокер для старта реализации —
если на практике окажется, что порядок подсказок ломается в целевом браузере (Chrome/Edge,
десктоп — единственная среда использования проекта, см. `system/rules/` — не мультибраузерный
публичный продукт), эскалация на кастомный виджет остаётся follow-up задачей, не частью этой.

```js
} else if (key === 'disciplines') {
  input = document.createElement('input');
  input.className = 'cdet-field-input';
  input.dataset.field = key;
  input.value = current;
  input.placeholder = 'Неизвестно';
  input.setAttribute('list', 'cdet-disciplines-list');

```

Токенизация по запятой — даталист работает на ПОСЛЕДНЕМ токене ввода (браузер сам фильтрует
`<option>` по совпадению текущего значения всего инпута с началом опции — **важно**: нативный
`<datalist>` фильтрует по совпадению ВСЕГО значения поля, не последнего токена после запятой,
значит после первой введённой дисциплины подсказки для второй перестанут появляться, пока
пользователь не откроет их заново с чистого поля). Это ограничение штатного `<datalist>`,
неустранимое без JS-обвязки; **минимальный компромисс, соответствующий духу §0.2** — обновлять
список опций `<datalist>` по событию `input` на поле «Дисциплины», подставляя в `<option value>`
уже НАБРАННЫЙ текст + предлагаемое имя (`"${текущий_текст_до_последней_запятой}, ${discName}"`),
так браузер продолжает матчить полное значение и подстановка добавляет дисциплину к списку, а
не заменяет его:

```js
function _cdetDisciplinesDatalistOptions(currentValue, clanName) {
  const prefix = currentValue.replace(/[^,]*$/, '').replace(/,\s*$/, ''); // всё, кроме последнего токена
  const already = new Set(currentValue.split(',').map(s => s.trim().toLowerCase()).filter(Boolean));
  const info = clanName ? v20ClanInfo(clanName) : null;               // v20-sheet.js
  const clanDiscs = new Set((info?.disciplines || []).map(d => d.toLowerCase()));
  const names = (_disciplinesCache || []).map(d => d.name)
    .filter(n => !already.has(n.toLowerCase()))
    .sort((a, b) => (clanDiscs.has(b.toLowerCase()) ? 1 : 0) - (clanDiscs.has(a.toLowerCase()) ? 1 : 0) || a.localeCompare(b, 'ru'));
  return names.map(n => `<option value="${escAttr((prefix ? prefix + ', ' : '') + n)}">`).join('');
}
```
Слушатель — на `input`-событие поля «Дисциплины» И поля «Клан» (пересборка при смене клана,
требование п.3 анализа):
```js
document.addEventListener('input', e => {
  const discInput = e.target.matches('.cdet-field-input[data-field="disciplines"]')
    ? e.target : (e.target.matches('.cdet-field-input[data-field="clan"]')
      ? document.querySelector('.cdet-field-input[data-field="disciplines"]') : null);
  if (!discInput) return;
  const clanVal = document.querySelector('.cdet-field-input[data-field="clan"]')?.value.trim() || '';
  const dl = document.getElementById('cdet-disciplines-list');
  if (dl) dl.innerHTML = _cdetDisciplinesDatalistOptions(discInput.value, clanVal);
});
```
`ensureDisciplines()` вызывается вместе с `ensureClans()/ensureSects()` в
`_ensureCdetLibDatalists()` (§3.1) — единая точка первичной загрузки всех трёх библиотек при
входе в режим редактирования.
