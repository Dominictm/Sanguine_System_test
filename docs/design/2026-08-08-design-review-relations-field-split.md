# Дизайн-ревью: разделение «Вид отношений» на тип + описание (Фаза 2)

**Роль:** Дизайнер. **Входные данные:**
[2026-08-08-relations-field-split-techspec.md](2026-08-08-relations-field-split-techspec.md)
(Системный аналитик, Фаза 2). Разметка/код уже детально расписаны — UX-аудит поверх готового
технического решения перед передачей Разработчику.

**Аудитория и сценарий:** тот же Рассказчик за десктопом. Отдельный нюанс этой фазы: строка
связи в редактировании превращается из одной строки в две (шапка + описание) — впервые в этом
блоке карточки персонажа появляется многострочный повторяющийся элемент списка, а не однострочный
ряд полей. Это меняет требования к визуальной группировке, которых раньше просто не было нужно.

---

## 1. Новая кнопка-пикер — переиспользовать `.cdet-lib-pick-btn`, не заводить `.cdet-rel-type-pick-btn`

Техспека §2.1/§4 вводит новый класс `.cdet-rel-type-pick-btn` с CSS с нуля. В проекте уже есть
готовый, полностью оформленный класс ровно для этой роли — кнопка 📚 рядом с полем,
открывающая пикер из библиотеки — `.cdet-lib-pick-btn` (`styles.css:3640-3652`), которым уже
пользуются пикеры Дисциплин/Титулов/Секты/Организации/Должности. У него уже есть то, чего нет в
предложенном в техспеке варианте: фиксированный `32×32px` (визуальная консистентность с
остальными такими кнопками в этой же карточке) и `@media (pointer: coarse) { width/height: 44px
}` — обязательное правило проекта для touch-целей (`CLAUDE.md`), которое новый класс в текущем
виде техспеки не покрывает вовсе.

**Рекомендация**: `class="cdet-lib-pick-btn"` вместо `class="cdet-rel-type-pick-btn"` в
`_relRowHtml` (§2.1), убрать одноимённый CSS-блок из §4 полностью — новых правил не требуется.
По той же причине стоит обернуть `input.cdet-rel-type-inp` + кнопку в `.cdet-field-with-pick`
(`styles.css:3638`, тоже уже существует и уже даёт `display:flex; gap:6px` для ровно такой пары)
— тогда специального выравнивания под эту конкретную кнопку в разметке вообще не понадобится.

## 2. Строка «Отношения» в редактировании стала двухстрочной — нужна визуальная группировка, которой раньше не требовалось

`#cdet-rels-rows` (`styles.css:3745-3749`) разделяет строки только `gap: 8px`, без рамки/фона —
для однострочных полей (текущее состояние) этого достаточно: сам факт «одна строка = одна связь»
был очевиден просто по вертикальному расположению. С этой техспекой строка становится
**двухуровневой** (шапка «имя + тип + 📚 + ✕» сверху, `<textarea>` описания на всю ширину
снизу) — при нескольких связях подряд граница между «конец описания связи №1» и «начало шапки
связи №2» перестаёт быть однозначной на глаз, особенно при беглом просмотре длинного списка.
Ровно та же проблема уже была решена для РЕЖИМА ПРОСМОТРА этой же секции — `.cdet-rel`
(`styles.css:4215-4222`) имеет `border-bottom` между записями (`.cdet-rel:last-child` его
убирает) — но в режиме РЕДАКТИРОВАНИЯ аналога нет, и раньше не требовалось.

**Рекомендация**: добавить `.cdet-rel-row` лёгкую группирующую рамку — не копировать
`border-bottom` буквально (в списке с `gap` между строками нижняя граница создаст двойной
отступ), а тонкую полупрозрачную рамку по всему блоку строки, например:
```css
.cdet-rel-row {
  display: flex;
  flex-direction: column;
  gap: 6px;
  padding: 8px;
  border: 1px solid rgba(139, 0, 0, .15);
  border-radius: var(--r-sm);
}
```
(цвет — тот же оттенок, что уже использует `.cdet-rel` в просмотре, `rgba(139, 0, 0, …)`, для
согласованности между двумя режимами одной и той же вкладки).

## 3. Бейдж типа в просмотре — не курсив, иначе сливается с уже курсивным описанием

Техспека §2.6/§4 задаёт `.cdet-rel-type { color: var(--gold); font-style: italic; }`. Но
`.cdet-rel-desc` (`styles.css:4232-4237`, уже существующий, ниже него) **уже** курсивный
(`font-style: italic`). Три строки подряд — обычное имя, курсивный золотой тип, курсивное серое
описание — тип и описание визуально сближаются курсивом сильнее, чем их разделяет цвет,
особенно при беглом чтении: сам смысл разделения поля («тип» — это категория/ярлык, «описание»
— проза) размывается, если оба выглядят как один и тот же регистр текста.

**Рекомендация**: убрать `font-style: italic` у `.cdet-rel-type`, вместо этого — та же
типографика, что уже маркирует «это ярлык, не проза» в этой карточке: `letter-spacing`/
`font-family: var(--f-heading)`, как у соседнего `.cdet-rel-name` (`styles.css:4224-4230`) —
тип тогда визуально роднится с ИМЕНЕМ (оба — короткие структурные ярлыки), а не с прозой
описания под ним:
```css
.cdet-rel-type {
  font-family: var(--f-heading);
  font-size: var(--fs-sm);
  letter-spacing: .05em;
  color: var(--gold);
}
```

## 4. Ширина поля «Имя» (38%) — техспека сама просит пересмотреть, уточняю направление

Техспека (§4) прямо оставляет это открытым для дизайн-проверки. С добавлением кнопки 📚 (32px)
к уже существующим полю имени (`flex: 0 0 38%`), полю типа (`flex: 1`) и кнопке ✕ в одной строке
— при типичной ширине модалки карточки персонажа поле «Вид отношений» рискует остаться
слишком узким для короткого, но не однословного значения («Тайная связь», «Сир/Чайлд» и т.п.).

**Рекомендация**: снизить долю имени до `32%` — оно и так автодополняется из даталиста
существующих персонажей (менее критично видеть его целиком построчно, ввод обычно завершается
через автодополнение), тогда как поле типа для вписывания собственного значения нуждается в
пространстве больше. Не критичная правка, довести на живом ревью при реализации.
