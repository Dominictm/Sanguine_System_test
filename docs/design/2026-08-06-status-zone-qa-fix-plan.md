## 1. 🟡 Отсутствует миграция старого маркер-формата «Статус»

### 1.1 Причина

Форматы данных на диске до и после фичи «Статус заменяет Зону»:

- **До:** `_significantPlaceValue()` (уже удалена из `cities.js`) писала в поле
  локации маркер+заметку: `[Город] <Тип>[ — <Заметка>]`.
- **После (2026-08-06):** прямой синк (`syncSignificantPlaceStatus`,
  `web/routes/cities.js`) пишет только чистый тип — `<Тип>`, без маркера и
  заметки (заметка теперь живёт исключительно в `city.md`).

Прямой синк перезаписывает поле локации только когда меняется соответствующая
запись в «Отмеченных локациях» города. Карточки, которые не были затронуты
повторным сохранением вкладки «География» **после** выката фичи, остаются со
старым форматом на диске. Проверено `grep` по `cities/*/locations/` — во всех
городах ровно один такой случай:

```
cities/paris/locations/opera/opera_garne/opera_garne.md:31:
| **Статус** | [Город] Элизиум — Главный Элизиум, 9-й округ |
```

(`city.md` при этом уже содержит клинию `Элизиум: Опера Гарнье — Главный
Элизиум, 9-й округ` — источник истины актуален, но карточка локации отстала.)

**Наблюдаемое поведение:** в детальной модалке локации бейдж «Статус»
показывает `[ГОРОД] ЭЛИЗИУМ — ГЛАВНЫЙ ЭЛИЗИУМ, 9-Й ОКРУГ` вместо цветного
«ЭЛИЗИУМ» — класс `badge-status-other` (безопасный фолбэк, без падения UI, но
несоответствие визуальному контракту фичи).

Это ровно случай, для которого в `CLAUDE.md` предписан протокол миграции:
«Если меняется формат файлов городов… добавь миграцию в `tools/migrations/`».
Прямой прецедент — `tools/migrations/005_location_district_label_rename.js`
(переименование поля карточки локации, контентная миграция, регэксп-замена по
всем `cities/**/*.md`).

### 1.2 Контракт исправления

Новый файл `tools/migrations/006_location_status_marker_cleanup.js` —
контентная миграция (см. `tools/migrations/README.md`), автоматически
применяется при каждом старте сервера (`web/lib/migrations.js`) плюс через
`node tools/run_migrations.js`.

```js
'use strict';
// Чистка старого маркер-формата «Статус» ([Город] Тип[ — Заметка]) под новый
// чистый формат (Тип), введённый техспекой «Статус заменяет Зону» (2026-08-06).
// Заметка при чистке ОТБРАСЫВАЕТСЯ — она уже дублируется в city.md
// («Отмеченные локации»), карточка локации хранить её больше не должна
// (см. §4 техспеки status-replaces-zone-techspec.md).
//
// Найдено ролью «Системный аналитик» при подготовке фикс-плана по отчёту QA
// (2026-08-06) — grep по всем cities/*/locations/ на момент написания нашёл
// ровно один непереехавший случай (cities/paris/locations/opera/opera_garne),
// но миграция общая, не точечная под этот файл.
//
// Идемпотентна: карточка без «[Город]» в значении «Статус» уже мигрирована
// или никогда не использовала маркер-формат — test() вернёт false.

const { CITY_LOCATION_TYPES } = require('../../web/lib/significant_places');

const TYPES_RE = CITY_LOCATION_TYPES.map(t => t.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')).join('|');
const STATUS_ROW_RE = new RegExp(
  `(\\|\\s*\\*\\*Статус\\*\\*\\s*\\|\\s*)\\[Город\\]\\s*(${TYPES_RE})(?:\\s+—\\s+[^|]*)?(\\s*\\|)`
);

module.exports = {
  description: 'чистка маркер-формата «Статус» ([Город] Тип — Заметка → Тип), 2026-08-06',
  test(text) { return STATUS_ROW_RE.test(text); },
  migrate(text) { return text.replace(STATUS_ROW_RE, '$1$2$3'); },
};
```

Ключевые решения:
1. **Регэксп бьёт только по 5 известным типам** (`CITY_LOCATION_TYPES`, общий
   источник с `significant_places.js` — не дублируем список), а не по
   произвольному тексту после `[Город]` — если в поле окажется маркер с
   незнакомым типом (гипотетически, вручную вписанный), миграция его не
   тронет: безопаснее пропустить нестандартный случай, чем угадать намерение.
2. **Заметка отбрасывается**, не переносится — она уже есть в `city.md`,
   дублировать её на карточке избыточно (текущая архитектура фичи и так
   хранит заметку только в одном месте).
3. Использует существующий общий модуль `web/lib/significant_places.js` —
   `require('../../web/lib/significant_places')` (путь от
   `tools/migrations/` до `web/lib/`), не копирует список типов.

### 1.3 Что НЕ меняется

- `syncSignificantPlaceStatus`/`findRecordIndexForLocation` — логика синка уже
  корректна (подтверждено QA), миграция чинит только historical данные на
  диске, не код.
- `city.md` — не трогаем, он уже в правильном формате.

## 2. 🔴→(без фикса) Свободный текст «Статус» из старой схемы теряется при сохранении VTM-вкладки

### 2.1 Причина

VTM-таблица локации (`## 🩸 VtM-контекст / Маскарад`) — сквозной формат для
Статус/Фракция/Постоянные фигуры/Угрозы/Маскарад, существовавший **до** фичи
«Статус заменяет Зону». Поле «Статус» изначально было свободным текстом —
описанием политического статуса места (кто контролирует, спорная территория и
т.п.), никак не связанным с «Отмеченными локациями» города. Пример реальных
данных (`cities/paris/locations/antrepo/gar_dyu_nor/gar_dyu_nor.md:26`):

```
| **Статус** | Нейтральная транзитная зона — никто не предъявляет прав официально; Сеттиты контролируют прилегающую сеть улиц |
```

`grep -rn "\*\*Статус\*\*" cities/*/locations/` на момент написания находит
**~24 таких карточки** в `cities/paris` (плюс несколько пустых/уже
проставленных валидным типом или маркером — те не затронуты).

Фича «Статус заменяет Зону» превратила это поле в `<select>` из ровно 5
значений (`CITY_LOCATION_TYPES`) + пусто. Постановка задачи (роль «Аналитик»,
2026-08-06) была прямой: «В графе Статус должно отображаться значение из
Отмеченных локаций… Только это значение» — репурпоз поля был осознанным
решением, но объём существующих данных в нём на момент постановки задачи не
был известен.

**Эмпирически подтверждённое поведение** (тестовый прогон, throwaway-город,
без затрагивания реальных данных): для локации с непустым свободным текстом
в «Статус» —
1. `<select>` не находит совпадающий `<option>` → браузер выбирает первый
   пункт (`value=""`, «—»); UI не различает «статуса нет» и «статус есть, но
   не входит в 5 типов».
2. Открытие вкладки VTM в режиме редактирования и **сохранение по любой
   причине** (например, правка одной лишь Фракции) отправляет
   `vtmTable.locStatus: ''` — сервер (`PUT /api/locations/:slug/fields`,
   ветка `vtmTable`) пишет пустую строку в поле «Статус» карточки; при
   сериализации таблицы пустая строка означает **удаление строки целиком**
   (подтверждено тем же прогоном — при пустых `locStatus`/`figures`/`threats`/
   `masquerade` в одном запросе все четыре строки исчезли из таблицы, осталась
   только непустая «Фракция»). Свободный текст восстановить неоткуда — это
   единственное место его хранения.

### 2.2 Решение

**Вопрос был явно вынесен пользователю** (роль «Системный аналитик», в рамках
этой же техспеки) — куда переносить существующий свободный текст «Статус»
миграцией, чтобы не потерять его при выкате: в «Атмосферу», в отдельное новое
поле, или не переносить.

**Решение пользователя: не переносить — принять потерю.**

Это значит:
- Код фичи «Статус заменяет Зону» не меняется по этой находке — репурпоз поля
  остаётся как спроектировано (§4 `2026-08-06-status-replaces-zone-techspec.md`).
- Миграция для переноса свободного текста **не создаётся**.
- Существующий свободный текст в ~24 карточках Парижа **не защищён** — он
  переживёт выкат в виде «мусора» в `<select>` (тихо игнорируется как «—»)
  ровно до первого сохранения VTM-вкладки той локации пользователем, после
  чего будет замещён либо пустым значением, либо одним из 5 типов, если
  пользователь выберет статус явно.
- Это задокументированное, осознанное решение (не забытый край) — заносится
  сюда, чтобы при повторном обнаружении («почему пропал текст статуса у Gare
  du Nord») не расследовать заново: это ожидаемое поведение, принятое
  2026-08-06.

### 2.3 Что НЕ делается

- Никакой миграции для находки §2.
- Никакой защиты/предупреждения в UI при сохранении VTM-вкладки локации, чьё
  текущее значение «Статус» не входит в 5 типов (например, диалог
  подтверждения) — не запрошено, не реализуется в рамках этого фикс-плана.

## 3. Тест-план

**§1 (миграция маркер-формата):**
- `node tools/run_migrations.js` на реальном дереве `cities/` → карточка
  Опера Гарнье получает `| **Статус** | Элизиум |`; `git diff` не затрагивает
  никакие другие файлы (единственный реальный случай на момент написания).
- Идемпотентность: повторный запуск миграции сразу после первого — нулевой
  diff (`test()` возвращает `false` на уже мигрированной строке).
- Юнит на `migrate()`/`test()` изолированно (throwaway-строка с типом,
  отсутствующим в `CITY_LOCATION_TYPES`, — например `[Город] Неизвестный —
  Заметка`) → `test()` возвращает `false`, строка не тронута (защита от
  угадывания намерения на нестандартном типе).
- После миграции — UI-проверка (headless CDP, throwaway-город): бейдж «Статус»
  Опера Гарнье в детальной модалке показывает «ЭЛИЗИУМ» / `badge-status-elysium`
  вместо «—»/`badge-status-other`.

**§2:** без фикса — тест-плана нет. Решение зафиксировано в §2.2 как
пройденная точка (не открытый вопрос).

   (`web/lib/migrations.js`), регресс на остальные 5 миграций не ожидается
   (независимые `test()`-гейты по разным паттернам).
4. Один коммит — миграция + результат её прогона на `cities/paris` (если
   `cities/` версионируется в этом репозитории; если нет — коммитится только
   файл миграции, сервер применит её сам при следующем старте).
