## 1. Находка при подготовке спецификации: два параллельных пути создания локации

Не было в плане Аналитика — вскрылось при проектировании контракта. Сейчас
в системе ДВА независимых способа создать локацию, с разной глубиной пути:

| Путь | Где вызывается | Глубина | Эндпоинт/механизм |
|---|---|---|---|
| A | Форма «📍 Новая локация», Инструменты→Ещё (`loc-district`+`loc-rayon`+`loc-zone`) | до 3 уровней (`district_NN`/`<rayon>`/`<loc>`) | `runNodeTool('new_location', …)` → спавнит `tools/new_location.js` |
| B | Внутренний вызов из карточки города («Значимые локации», `city.js:175,594`, фаза K) | 1 уровень (`<district-slug>`/`<loc>`) | `POST /api/locations` (`routes/locations.js:276`) — JSON, без спавна процесса |

Путь B **уже сегодня** двухуровневый — случайно совпадает с целевой схемой
Город→Район→Локация из плана (§8 плана Аналитика), но принимает только один
параметр `district` (без отдельного `rayon`). Путь A поддерживает
трёхуровневую вложенность и сегодня фактически создаёт реальные данные
Парижа (округ+район).

**Решение для контракта ниже:** новый компонент «модалка локации» (решено
в плане Аналитика, п.6 итогового списка) вызывает **путь B**
(`POST /api/locations`), расширенный под новую схему (см. §3) — не спавнит
CLI. Путь A (форма в Инструменты→Ещё) — либо удаляется в пользу новой
модалки, либо остаётся как алиас, вызывающий тот же `POST /api/locations`
вместо `runNodeTool`. Итоговое решение — за Разработчиком на этапе
реализации, но раздвоение путей создания трогать нельзя молча: если
оставляем оба входа, оба обязаны писать по ОДНОЙ схеме.

## 2. Entity: District

### 2.1 Бизнес-смысл

Район — структурная единица географии города, ранее не существовавшая как
самостоятельная сущность (была либо CSV-строкой при создании города, либо
папкой `district_NN` без метаданных). Хранит тип района, влияние
секты/клана и описание; содержит локации как дочерние объекты по факту
размещения в файловой системе (не через явную ссылку — принадлежность
районом определяется путём `locations/<district-slug>/...`).

### 2.2 Схема файла `district.md`

```markdown
# 📍 <Название района>

- **Тип района:** <enum DistrictType | свободный текст>
- **Округ:** <опционально, свободный текст — лор, не адресация>
- **Влияние:** <Секта | ⚠️> / <Клан | ⚠️>

## Описание

<свободный текст>
```

`DistrictType` (значения дропдауна, свободный ввод разрешён поверх):
`Спальный`, `Деловой`, `Пром-зона`, `Туристический`, `Гетто`, плюс
предложенные в плане Аналитика §4.3: `Элизиум/культурный`, `Портовый`,
`Университетский`, `Заброшенный`.

### 2.3 Парсер/строитель — `web/lib/parsers/district.js` (новый модуль)

Зеркалит `web/lib/parsers/city.js` (`buildCityMd`/`parseCityMd` →
`buildDistrictMd`/`parseDistrictMd`), общий источник для CLI и веба —
тот же принцип, что уже действует для `cityScaffold`.

```
buildDistrictMd({ name, type, sect, clan, description }) → string (markdown)
parseDistrictMd(raw) → { name, type, sect, clan, description }
```

### 2.4 Эндпоинты

**`POST /api/cities/:slug/districts`** — создать район в существующем городе.

- Preconditions: город `:slug` существует; `name` непустой; slug(name) ещё
  не занят папкой в `locations/`.
- Body: `{ name: string, type?: string, sect?: string, clan?: string, description?: string }`
- Flow: slugify(name) → проверка коллизии → `mkdir locations/<slug>/` →
  `writeFileAtomic(.../district.md, buildDistrictMd(body))`.
- Response 200: `{ ok: true, slug, name }`
- Errors: `400` — нет `name`/не удалось собрать slug; `404` — город не
  найден; `409` — папка района с таким slug уже существует.
- Edge case: район с пустым `type`/`sect`/`clan` — допустим, поля
  необязательны (только `name` обязателен), `buildDistrictMd` подставляет
  `⚠️`-плейсхолдеры по конвенции проекта.

**`PUT /api/cities/:slug/districts/:districtSlug`** — редактировать район
(аналог `PUT /api/locations/:slug/fields`). Body — частичные поля
`{ type?, sect?, clan?, description? }`. Переименование района (смена
`name`/slug) — **вне рамок этой правки**: потребовало бы переноса всех
дочерних папок локаций, не запрошено в плане, явно не проектируем.

**`GET /api/cities/:slug/districts`** — список районов города (для
дропдаунов: пикер локации при создании, пикер «Значимые места», редактор
формы города). Response: `[{ slug, name, type, sect, clan }]`.

**Не проектируется (вне плана):** `DELETE` района — не запрошено;
удаление района с непустыми дочерними локациями — открытый вопрос,
которого явно не было в плане Аналитика, поднимать его сейчас было бы
скоуп-крипом.

### 2.5 CLI-паритет — `tools/new_district.js`

Сигнатура: `node tools/new_district.js <city> "<Название>" [тип] [секта] [клан] [описание]`
— вызывает тот же `buildDistrictMd`, ту же проверку коллизии, что и
`POST /api/cities/:slug/districts` (единый источник, по образцу
`tools/new_city.js`/`POST /api/cities`).

## 3. Location — изменение схемы пути и контракта создания

### 3.1 Путь (после миграции §6)

`cities/<city>/locations/<district-slug>/<loc-slug>/<loc-slug>.md` —
ровно 2 уровня всегда. Параметр `district` в существующем
`POST /api/locations` **семантически переименовывается в «район»**
(значение то же — slug района), но само имя параметра в API можно не
трогать, если не создаёт двусмысленности с новой сущностью District
(рекомендация: оставить `district` как имя поля в теле запроса ради
обратной совместимости вызовов, но в UI-лейблах везде писать «Район»).

### 3.2 `POST /api/locations` — расширение контракта

Текущий контракт (`routes/locations.js:276`) сохраняется, добавляется:

- **Precondition (новая):** если `district` передан и соответствующий
  `locations/<slugify(district)>/district.md` НЕ существует — запрос всё
  равно проходит (создание локации не должно требовать, чтобы район уже
  существовал как формальная сущность — иначе это ломает уже работающий
  путь B и пользователей, у которых район ещё не заведён как District).
  Локация создаётся в папке с этим slug'ом в любом случае — папка района
  без `district.md` продолжает быть валидной (соответствует текущему
  поведению `distFolder = slugify(district) || 'Другие'`).
- Изменение дефолта: `'Другие'` как фолбэк для пустого `district` — решить,
  остаётся ли (сегодня так и есть в коде), учитывая, что теперь `district`
  задумывается как обязательное поле в новой модалке локации (UI-уровня
  required, не серверного) — сервер может оставить старый permissive
  фолбэк без изменений, не ужесточаем API.

### 3.3 Новый компонент — модалка локации

Аналог `#char-modal` (двухшаговая: выбор... тут одношаговая форма).
Поля: `Название*`, `Район*` (дропдаун из `GET /api/cities/:slug/districts`
+ опция «Новый район…», инлайново дергающая `POST /api/cities/:slug/districts`
перед сохранением локации), `Зона` (enum, как сегодня), `Адрес`,
`Контроль`. Вызывается из двух точек:
- как самостоятельная модалка (замена формы в Инструменты→Ещё);
- встроенно из блока «Район» на форме создания/редактирования города, с
  предзаполненным и задизейбленным полем «Район».

Оба входа зовут **один и тот же** `POST /api/locations` — см. находку §1.

## 4. Political roles — «Властители города» и «Примогенат»

> **ИСПРАВЛЕНИЕ ПОСЛЕ ПЕРВОЙ РЕВИЗИИ.** При передаче Дизайнеру обнаружено:
> редактор с ровно такой структурой (Должность-дропдаун+своё + Персонаж —
> datalist существующих ИЛИ ручной ввод, повторяемые строки, кнопка
> «+ Добавить запись») **уже реализован и работает** в модалке
> редактирования города (`_cityPolEditorHtml`/`_polRowHtml`/
> `_collectPoliticalRows`, `web/public/scripts/city.js:152-230,299-312`)
> — просто не выведен в форму СОЗДАНИЯ. Он уже производит те самые строки
> `city-political`, которые `parsePoliticalRecords()`/
> `syncPoliticalStateTable()` синкают в «Карту фракций» — весь путь до
> `political_state.md` **уже работает сегодня**, DTO/API ниже не нужны.
> Актуальный объём работы для этой части: (1) перенести существующий
> компонент в форму создания (как уже сделано с `city-factions-editor`),
> (2) расширить `CITY_POLITICAL_ROLES` (сейчас `['Князь','Шериф',
> 'Сенешаль','Примаген']`, `city.js:89` — опечатка «Примаген», нет
> «Хранителя Элизиума»), (3) реализовать запись в карточку персонажа
> (`hierarchy`) — единственный кусок, которого нет нигде, см. §4.2 ниже,
> она не отменяется этой находкой.

### 4.1 Модель данных

Не новая сущность — уже существующая таблица «Карта фракций» в
`archive/political_state.md`
(`Должность | Персонаж | Клан | Примечание`), см. `parsePoliticalRecords()`/
`syncPoliticalStateTable()`, `web/routes/cities.js:127-185`, наполняемая
уже существующим UI (см. врезку выше). Ниже — не новый DTO для нового
API, а формальное описание того, что уже производит `_collectPoliticalRows()`,
нужное только для проектирования части §4.2 (запись в карточку персонажа),
которой сегодня действительно нет:

```
PoliticalRoleRow = {
  role: string,        // 'Князь'|'Сенешаль'|'Шериф'|'Хранитель Элизиума'|произвольный текст
                        // Примоген — вопрос дизайна: отдельный kind с дропдауном
                        // кланов, или та же строка «Должность» с ролью «Примоген (<Клан>)»
                        // как сегодня — см. дизайн-документ
  characterSlug?: string,  // если выбран существующий персонаж
  characterName?: string,  // ручной ввод текста (взаимоисключимо с characterSlug)
}
```

Ровно одно из `characterSlug`/`characterName` — precondition; оба
одновременно или оба пустые — `400`.

### 4.2 Поток сохранения (city update, расширение `PUT /api/cities/:slug`)

1. Собрать `PoliticalRoleInput[]` из формы (Властители + Примогенат вместе).
2. Прочитать **предыдущее состояние** ролей для этого города (уже
   существующий паттерн `prevRoles` в `cities.js:196-203` — расширить его,
   чтобы читать не только «роль», но и то, какой `characterSlug` был на
   ней раньше).
3. Построить новые строки «Карты фракций» — уже делает существующий
   `_collectPoliticalRows()`/`syncPoliticalStateTable()`/
   `parsePoliticalRecords()`, без изменений (`{role, name, name2}`).
4. **Diff предыдущих и новых `characterSlug` по каждой роли:**
   - слаги, которые ВЫБЫЛИ (были в предыдущем состоянии, отсутствуют в
     новом, или на той же роли теперь другой персонаж) → для каждого
     выбывшего персонажа вызвать `PUT /api/characters/:slug/fields`
     (`web/routes/characters.js:213`) с `{ hierarchy: '' }` (очистка) —
     **только если** текущее значение `hierarchy` на его карточке
     совпадает с текстом снимаемой роли (защита от затирания вручную
     переписанного пользователем поля — см. edge case ниже).
   - слаги, которые ПОЯВИЛИСЬ или сохранили роль → `PUT .../fields` с
     `{ hierarchy: '<Должность> города <Название>' }` (или аналогичный
     шаблон текста — финальную формулировку зафиксировать при
     реализации).
5. Обе операции (запись `political_state.md` + запись в карточки
   персонажей) — **не в одной транзакции** (нет транзакций между файлами
   в этой системе нигде). Порядок: сначала `political_state.md` (уже
   существующий, проверенный путь), потом карточки персонажей. Если шаг
   5 (запись в карточку персонажа) не удался для одного из персонажей —
   **не откатывать** `political_state.md` и **не проваливать весь
   запрос** — логировать ошибку, продолжать по остальным персонажам,
   вернуть `200` с полем `warnings: string[]` (по одному на каждую
   неудавшуюся запись).

### 4.3 Обработка ошибок

| Ситуация | Код | Поведение |
|---|---|---|
| `characterSlug` указан, но персонаж не найден (удалён/переименован) | — (не блокирует) | Пропустить запись в карточку, добавить в `warnings`, город всё равно сохраняется. |
| Текущее значение `hierarchy` персонажа не совпадает с ожидаемым при попытке очистки | — (не блокирует) | Не перезаписывать (см. edge case ниже), просто не трогать поле, без ошибки. |
| Два `PoliticalRoleInput` ссылаются на одного персонажа в разных ролях одновременно | `400`? | Открытый вопрос реализации — вероятно, допустимо (один вампир может быть и Шерифом, и представлять клан), тогда `hierarchy` содержит обе роли через разделитель — уточнить при реализации, не было в плане Аналитика буквально. |

### 4.4 Краевой случай: пользователь вручную отредактировал «Иерархию»

Если персонаж был назначен «Шерифом» через форму города (значит
`hierarchy = 'Шериф города Париж'`), а затем пользователь вручную
переписал поле «Иерархия» на карточке персонажа на что-то своё («Бывший
Шериф, в опале») — при последующем снятии роли в форме города
автоматическая очистка **не должна** затирать это ручное значение (иначе
теряется контент, который человек осознанно написал). Отсюда — сверка
«текущее значение совпадает с ожидаемым перед снятием» в §4.2 шаг 4:
если не совпадает — не трогаем, просто отвязываем роль от персонажа в
`political_state.md`, ручной текст на карточке остаётся как есть.

## 5. Significant places — «Значимые места города»

> **ИСПРАВЛЕНИЕ ПОСЛЕ ПЕРВОЙ РЕВИЗИИ.** Тот же класс находки, что в §4:
> редактор «Отмеченные локации» (Тип-дропдаун+своё, Название — datalist
> существующих ИЛИ новое имя, при новом имени реально создаёт карточку
> через `POST /api/locations` после сохранения города) уже существует в
> модалке редактирования (`_cityLocEditorHtml`/`_locRowHtml`/
> `_collectLocationRows`, `city.js:177-199,318-339`). Сегодня
> `CITY_LOCATION_TYPES = ['Элизиум']` (`city.js:90`) — только 1 значение
> из 5 запрошенных. **Важный нюанс, которого не было в предыдущей
> ревизии:** этот редактор пишет выбранный «Тип: Название» СТРОКОЙ в
> текстовую секцию city.md «Ключевые локации» — а НЕ в поле `zone`/
> `control` самой карточки локации. Значит, если реализовать решение
> плана Аналитика («переиспользуем `zone`/`control`») буквально поверх
> уже существующего компонента, получится ДВОЙНАЯ запись факта — текстовая
> строка в city.md (уже есть, бесплатно) и новая запись в файл локации
> (то, что описано в §5.2 ниже, всё ещё нужно реализовывать). Это не
> противоречие, а тот же паттерн, что уже принят для персонажей в §4
> (city.md-строка — для нарратива/нового списка, `political_state.md`
> — структурная таблица, [новое] поле персонажа — для самой карточки) —
> просто нужно явно понимать, что пишем в ДВА места одним действием, не
> путать с заведением нового третьего источника. **Решено пользователем:
> да, пишем в оба места одним действием** — строка в city.md «Ключевые
> локации» (уже делает существующий `_collectLocationRows()`, без
> изменений) И запись в `zone`/`control` карточки локации (новая часть,
> §5.2 ниже). Не «или/или» — оба, синхронно, одним сохранением формы.

### 5.1 Модель данных

Переиспользует существующие поля Location: `zone` для статуса
«Элизиум», `control` для остальных четырёх статусов (решено в плане
Аналитика, п.7) — **плюс** существующая city.md-строка «Тип: Название»
(`_collectLocationRows()`, без изменений). Список «выбранных значимых
локаций», который видит форма при открытии на редактирование, читается
из city.md-строк (как и сегодня) — `zone`/`control` карточки локации
пишутся синхронно при сохранении, но не являются источником для
восстановления списка в форме (не читаются обратно при открытии формы —
избегает ситуации «откуда форма знает, что читать», раз мест хранения
теперь два: пишем в оба, читаем из одного, city.md остаётся source of
truth для состава списка).

```
SignificantPlaceInput = {
  locationSlug: string,
  status: 'elysium' | 'reception' | 'haven' | 'sheriff_post' | 'seneschal_post'
}
```

### 5.2 Поток сохранения

Симметричен §4.2, но diff проще, чем предполагалось в первой ревизии —
**источник предыдущего состояния теперь city.md-строки, не сканирование
`zone`/`control`** (см. §5.1):

1. Прочитать предыдущее состояние из уже существующих city.md-строк
   «Тип: Название» (тот же принцип `previousRoles`, что и в §4.2 —
   ничего нового изобретать не нужно, source of truth для diff'а один).
2. `_collectLocationRows()` пишет новые строки в city.md — без изменений,
   существующий путь.
3. Diff по `locationSlug` (кто выбыл из списка «Значимых мест» по
   сравнению с предыдущими city.md-строками) → для выбывших сбросить
   `zone`/`control` на карточке локации; для оставшихся/новых — записать.
   Само определение «кто выбыл» больше не зависит от анализа текста
   `control` — только от diff'а city.md-строк, что снимает часть риска
   §5.3 ниже (сам diff надёжен), но не весь.

## 8. Заметка в «Отмеченные локации» (план §13.1)

### 8.1 Модель данных

Расширяет существующую строку `{ type, name }` (`_parseLocationLines`/
`_locationRowToLine`, `city.js`) третьим полем `note`. Формат city.md-
строки — добавить через тире, а не двоеточие (двоеточие уже занято под
`Тип: Название`, второе использование сломало бы `_isStructuredCityLine`/
`_parsePoliticalLines`-подобный парсинг): `Статус: Название — Заметка`.
Разбор — `line.split(/\s+—\s+/)`, часть до тире парсится, как сегодня
(`Тип: Название`), часть после — `note`.

### 8.2 Куда пишется, помимо city.md-строки

Решено по аналогии с уже реализованным в этой ревизии §5 (Significant
places пишут в ДВА места одним действием): заметка добавляется к тому же
маркированному тексту, что уже пишется в `control` карточки локации
(`syncSignificantPlaceStatus`, §5.2/§5.3) — не заводит отдельное поле.
Формат: `[Город] Статус — Заметка` (маркер `[Город]` уже используется для
статуса, заметка просто дописывается через то же тире-разделение, тем же
regex при сбросе/пересчёте, что уже написан для §5.3).

### 8.3 Обработка ошибок / edge cases

- Заметка пустая — тире не добавляется вообще (не хранить пустой хвост
  `Статус: Название — `).
- Заметка содержит символ «—» — экранировать/заменить на похожий символ
  при записи (тот же принцип, что `sanitizeInlineText`/замена `|` на `∣`
  в других местах этого файла), иначе парсинг обратно разъедет поля.

## 9. Страница просмотра города — паритет с формой создания (план §13.2)

### 9.1 Структурная отрисовка районов

`GET /api/cities/:slug/districts` уже реализован (§2.4) — `_renderCityView()`
(`city.js:573-604`) добавляет блок карточек района ПЕРЕД/ПОСЛЕ рендера
`mdToHtmlBlock(body)`, используя тот же визуальный компонент, что форма
создания (`_districtCardHtml`, в режиме read-only: без input/select,
просто подписанные значения) — не новый компонент с нуля, адаптация
существующего рендера в non-editable вид.

### 9.2 Привязка существующей локации к району — новый эндпоинт

**`PUT /api/locations/:slug/district`** (новый, отдельный от
`PUT /api/locations/:slug/fields` — намеренно: это не одна из «обычных»
инлайн-метаданных, это операция с физическим побочным эффектом).

- Body: `{ district: string }` (slug района).
- Precondition: локация существует; район `district` — валидный slug
  (папка `locations/<district>/` существует ИЛИ создаётся неявно — решить
  при реализации: строго требовать существующий район, или создавать
  папку на лету, симметрично тому, как `POST /api/locations` сегодня
  терпимо создаёт `distFolder`, если его не было).
- Flow: **физически переносит папку локации**
  `locations/<old-district>/<loc-slug>/` → `locations/<district>/<loc-slug>/`
  (`fs.rename`, атомарно на одной файловой системе — тот же примитив, что
  `writeFileAtomic` уже использует) — ПОТОМ правит `**Округ:**` внутри
  самой карточки (тот же `fieldMap`-паттерн, что `district` в
  `PUT /fields`, но как часть этой же операции, не отдельным запросом).
- Response: `{ ok: true, movedFrom, movedTo }`.
- Errors: `404` — локация не найдена; `409` — в целевом районе уже есть
  локация с таким же slug (коллизия имени при переносе); `400` — район не
  указан/невалидный slug.

### 9.3 Edge cases

- Перенос локации САМОЙ В СЕБЯ (район не изменился) — `200` no-op, не
  ошибка.
- Локация с изображениями/art/ — `fs.rename` папки целиком переносит и
  `art/`, никаких дополнительных шагов (тот же вывод, что уже
  подтверждён в этой сессии на миграции округ→район — `fs.rename`
  директории переносит вложенные файлы, включая gitignored, потому что
  работает на уровне файловой системы, не git).
- **Ссылки на локацию** (character/chronicle markdown, ссылающиеся на
  старый путь) — тот же риск, что был у миграции округ→район (план §9,
  «Высокая» серьёзность) — `tools/validate_links.ps1` должен прогоняться
  и здесь, но при разовом переносе ОДНОЙ локации, не города целиком, риск
  меньше по объёму, тот же по характеру. Рекомендация — синхронный вызов
  fix-логики уже существующей `POST /api/validate-fix`
  (если такой эндпоинт уже есть в проекте — уточнить у Разработчика при
  реализации) сразу после переноса, а не полагаться на то, что пользователь
  сам вспомнит прогнать проверку.

## 13. Опасность/Маскарад — редактируемые поля (план §13.6 + `2026-08-02-location-card-modal-plan.md` §4)

Оба источника плана описывают одну и ту же работу — см. явное
пересечение, зафиксированное в `location-card-modal-plan.md` §4. Здесь —
единый контракт на оба одновременно, чтобы не делать дважды.

### 13.1 Решение архитектурной развилки (план §13.6, вариант «б»)

«Опасность» становится собственным полем карточки локации, отдельным от
«Зоны» — не производным от эмодзи внутри текста «Зоны». Новая инлайн-
метаданные строка `**Опасность:**` эмодзи, симметрично уже существующему
`**Маскарад:**`. «Зона» при этом сужается до чисто категориального
значения (`zoneClass()`: Элизиум/Носферату/Нейтральная/Опасная/Локация,
без эмодзи-уровня опасности внутри) — `zoneDangerLevel()` переключается
читать НОВОЕ поле `**Опасность:**`, а не парсить эмодзи из «Зоны».

### 13.2 Расширение `PUT /api/locations/:slug/fields`

Новый ключ `dangerLevel` (пишет `**Опасность:**`) добавляется в `fieldMap`
(`web/routes/locations.js:210`) — тем же простым inline-паттерном, что
`zone`/`control` уже используют, никакой новой логики парсинга не нужно.

### 13.3 Табличные VtM-поля (Статус/Фракция/Постоянные фигуры/Угрозы/Маскарад)

Это НЕ инлайн-метаданные (не `**Ключ:**` на одной строке с остальными),
а строки markdown-ТАБЛИЦЫ внутри секции VtM-контекста
(`| **Статус** | значение |`, `web/lib/parsers/location.js:60-70`) —
`fieldMap`-паттерн (line 210) сюда не подходит буквально, нужен отдельный
обработчик в `PUT /api/locations/:slug/fields`:

```js
if (key === 'vtmTable') {
  // value — объект { locStatus?, faction?, figures?, threats?, masquerade? }
  card = card.replace(
    /(## (?:🩸\s+)?(?:VtM[^\n]*|Контекст[^\n]*)\n+)([\s\S]+?)(\n## |\n---|$)/i,
    (_, hdr, body, tail) => {
      const LABELS = { locStatus:'Статус', faction:'Фракция', figures:'Постоянные фигуры',
                        threats:'Угрозы', masquerade:'Маскарад' };
      let newBody = body;
      for (const [k, label] of Object.entries(LABELS)) {
        if (!(k in value)) continue;
        const esc = label.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
        const row = `| **${label}** | ${sanitizeInlineText(value[k]).replace(/\|/g,'∣')} |`;
        const re  = new RegExp(`\\|\\s*\\*\\*${esc}\\*\\*\\s*\\|[^\\n]*\\|`);
        newBody = re.test(newBody) ? newBody.replace(re, row) : `${newBody.trimEnd()}\n${row}`;
      }
      return `${hdr}${newBody}${tail}`;
    }
  );
  continue;
}
```

Прозу (`vtmText`) не трогает — оба обработчика (`vtmText` и новый
`vtmTable`) работают над одной и той же секцией независимо, порядок
вызова в цикле `for (const [key, rawValue] of Object.entries(fields))`
не важен, т.к. оба используют одну и ту же секцию как область поиска
заново на каждый вызов (текущее содержимое `card`, не кэш).

### 13.4 Клиент — форма по полям вместо textarea (детальная модалка, вкладка VtM)

`vtmEditHtml` (`locations.js:374-375`) — заменить на 5 полей (текстовые
инпуты — не dropdown, значения свободные: «Статус» — короткий статус вроде
«🟢 Активна», «Фракция»/«Постоянные фигуры»/«Угрозы» — свободный текст;
«Маскарад» — `<select>` с 3 опциями, как `loc-edit-zone`, но со своими
эмодзи-уровнями) + textarea прозы как было. `_locSavePanel('vtm')`
(`locations.js:632-633`) — добавить сборку `fields.vtmTable = {...}` рядом
с уже существующим `fields.vtmText`.

### 13.5 Обработка ошибок

Пустое значение любого из 5 полей — валидно, стирает соответствующую
строку таблицы (не создаёт `| **Статус** |  |` с пустым значением —
удалять строку целиком, если новое значение пусто, симметрично тому, как
`vtmText`-ветка уже не создаёт лишних пустых строк).

подобную функцию, НЕ писать новую — тот же формат, что уже пишет
детальная модалка). Backend не меняется — `sensoryPalette` уже принимается
`PUT /api/locations/:slug/fields` как есть.

### 14.2 Обязательные каналы (план `location-card-modal-plan.md` §2, ещё не реализовано)

## 15. Миграция бэкофилла «Опасность» (критично — блокирует мёрдж)

### 15.1 Проблема

§13.1 развёл «Опасность» на собственное инлайн-поле, отдельное от «Зоны» —
`zoneDangerLevel()` на клиенте теперь читает `loc.dangerLevel`
(`**Опасность:**` карточки), а не парсит эмодзи из `**Зона:**`, как раньше.
Миграция для существующих карточек не была написана вместе с §13 — находка
роли «Тестировщик» при глубоком тестировании реализации.

Проверка на реальных данных (обход `cities/*/locations/**/*.md` в Node, без
`grep` — `grep -E` в среде разработки некорректно матчит многобайтовые
UTF-8 emoji внутри `[…]`-класса символов, совпадая по отдельным байтам, а не
по символам целиком; первая оценка через `grep` дала завышенное «28 из 28»,
перепроверено и исправлено на точный обход перед фиксацией контракта):
**23 из 28** карточек локаций (`paris` + `balmont`) — старого формата,
эмодзи 🟢/🟡/🔴 живёт внутри `**Зона:**` (например
`cities/paris/locations/antrepo/gar_dyu_nor/gar_dyu_nor.md` →
`**Зона:** 🔴 Опасная / Сеттиты`), поле `**Опасность:**` не заполнено ни у
одной. Оставшиеся 5 (`opera_garne`, `la_defans_bd`, `luvr_zakrytye_galerei`,
`metro_shatle_le_al`, `panteon/metro_sen_mishel`) используют в «Зоне»
маркеры без цветового уровня (`🏛️ Элизиум`, `🔵 Вентру` и т.п.) — для них
`zoneDangerLevel()` и до этой правки возвращал `'unknown'`, бейдж не
отображался и раньше — не регрессия, не входят в область миграции.

После деплоя без миграции бейдж «Уровень опасности» в
`.locdet-legend-row` детальной модалки (`web/public/scripts/locations.js`,
`dLvl !== 'unknown'`) молча перестаёт отображаться на этих 23 существующих
локациях — не ошибка, тихая деградация уже готового контента.

### 15.2 Решение — контентная миграция

Новый файл `tools/migrations/004_danger_level_backfill.js`, контентный
контракт `test(text)`/`migrate(text)` (см. `tools/migrations/README.md`) —
раннер (`web/lib/migrations.js`) применяет автоматически на каждом старте
сервера, обходя `cities/<город>/**/*.md`; `district.md` естественно не
матчится (там нет поля `**Зона:**` вообще — не нужно отдельно
исключать по имени файла).

```js
function _extractDangerEmoji(zoneVal) {
  if (zoneVal.includes('🟢')) return '🟢';
  if (zoneVal.includes('🟡')) return '🟡';
  if (zoneVal.includes('🔴')) return '🔴';
  return null;
}

module.exports = {
  description: 'Бэкофилл **Опасность:** из эмодзи, ранее жившего внутри **Зона:**',
  test(text) {
    if (/\*\*Опасность:\*\*/.test(text)) return false; // уже есть — идемпотентность
    const m = text.match(/\*\*Зона:\*\*\s*([^|\n]+)/);
    return !!(m && _extractDangerEmoji(m[1]));
  },
  migrate(text) {
    const m = text.match(/\*\*Зона:\*\*\s*([^|\n]+)/);
    const emoji = _extractDangerEmoji(m[1]);
    // Два реальных формата карточки на диске (проверено дословным прогоном по обоим
    // городам перед фиксацией контракта — см. §15.5): (1) стандартный pipe-delimited
    // формат _locCardTemplate — новое поле вставляется между «Зона» и следующим «|»;
    // (2) более старый «одна метаданные-строка на буллет», без «|» вообще (пример —
    // cities/balmont/locations/podzemnyy_dok/…/podzemnyy_dok.md) — если первый паттерн
    // не сработал, добавляем отдельным буллетом сразу после строки «Зона», тем же
    // стилем. Без этой развилки migrate() на файле формата (2) молча не менял бы ничего
    // (test() продолжал бы возвращать true на каждом старте сервера — псевдо-идемпотентность
    // без реального результата), что и вскрылось при проверке перед сдачей контракта.
    if (/\*\*Зона:\*\*\s*[^|\n]+\|/.test(text)) {
      return text.replace(
        /(\*\*Зона:\*\*\s*[^|\n]+)(\|)/,
        `$1| **Опасность:** ${emoji} $2`
      );
    }
    return text.replace(
      /(\*\*Зона:\*\*\s*[^\n]+)(\n)/,
      `$1\n- **Опасность:** ${emoji}$2`
    );
  },
};
```

### 15.3 Что НЕ трогаем (осознанно, по рекомендации Тестировщика)

- Текст `**Зона:**` не переписывается и не «очищается» от эмодзи — категориальный
  разбор `zoneClass()` матчит по подстроке («опасн», «носферату» и т.п.) и
  продолжает работать корректно даже с «грязным» старым текстом вроде
  `🔴 Опасная / Сеттиты`. Чистка «Зоны» — отдельная, не запрошенная задача,
  не часть этой миграции.
- Карточки, где в «Зоне» нет ни одного из трёх эмодзи (напр.
  `🏛️ Элизиум`, `🟣 Носферату` без цветового уровня) — `test()` возвращает
  `false`, поле «Опасность» не создаётся; бейдж на них и раньше не
  отображался (`zoneDangerLevel` вернул бы `'unknown'` и до этой правки),
  это не регрессия, оставляем как есть.

### 15.4 Обработка ошибок / краевые случаи

- Идемпотентность — `test()` возвращает `false`, если `**Опасность:**` уже
  присутствует (созданная вручную через новый UI карточка, или уже
  смигрированный файл при повторном старте сервера).
- Если `test()` вернул `true`, но по каким-то причинам паттерн замены в
  `migrate()` не сработал (совпадение испорчено внешней правкой между
  вызовами) — раннер пишет файл только при реальном изменении текста
  (`web/lib/migrations.js`, см. README «Пишет файл обратно только если
  что-то изменилось»); в худшем случае это no-op на конкретном файле, не
  падение всего прогона — не требует отдельной обработки в самой миграции.
- Порядковый номер `004` — после `003_district_md_backfill.js`; не зависит
  от структурных миграций 002/003 по содержанию (не трогает пути), но
  порядок соблюдён по общей нумерации проекта.

### 15.5 Приёмка

- `node tools/run_migrations.js` на текущих `cities/paris`/`cities/balmont`
  проставляет `**Опасность:**` всем 23 карточкам с цветовым эмодзи в
  «Зоне» (проверено дословным прогоном предложенной выше пары
  `test`/`migrate` по обоим городам перед фиксацией контракта — 23
  успешных изменения, 0 проблем, включая нестандартный буллет-формат
  `podzemnyy_dok.md`, см. врезку в §15.2). Повторный запуск —
  `{ changed: 0 }` для этой миграции (идемпотентность подтверждена).
- В браузере: любая из этих 23 локаций (напр. Gare du Nord, Катакомбы)
  снова показывает бейдж «Уровень опасности» в детальной модалке без
  ручного редактирования карточки.

## 16. Неуникальность slug локации между районами (архитектурный риск, не блокирует)

### 16.1 Находка

Роль «Тестировщик»: `POST /api/locations` проверяет коллизию имени только
**внутри целевого района** (`routes/locations.js`, `locFile` включает
`distFolder`) — глобальной проверки уникальности slug по городу нет.
Воспроизведено: две локации с одинаковым названием в разных районах
создаются обе без ошибки.

`findLocMdPath(slug, city)` (`web/lib/db.js`) — единый механизм резолвинга
slug→файл, на котором построены `PUT /api/locations/:slug/fields`, `DELETE
/api/locations/:slug`, `POST /api/locations/:slug/upload-image` и ЧТЕНИЕ
(шаг до проверки коллизии) в новом `PUT /api/locations/:slug/district`
(§9.2) — обходит дерево `cities/<город>/locations/` и возвращает ПЕРВОЕ
совпадение по слагу. При дублирующемся slug результат недетерминирован
(зависит от порядка обхода файловой системы), не от намерения вызывающего.

Подтверждено тестом: `PUT /fields` с двумя одноимёнными локациями в разных
районах записал значение в ту, что была создана РАНЬШЕ, а не в ту, которую
пользователь только что имел в виду — молча, без ошибки.

### 16.2 Что уже смягчает риск

Сам новый `PUT /api/locations/:slug/district` (§9.2) не пострадал в
проверенном сценарии — его собственная проверка `409` («в целевом районе
уже есть локация с таким именем папки») отработала раньше, чем дошло бы до
физического переноса. Риск сегодня актуален для `PUT /fields`/`DELETE`/
`upload-image` — у них такой защиты нет, потому что они не сверяют, что
резолвнутая локация — именно та, на которую рассчитывал вызывающий (нечем
сверять: запрос содержит только slug).

### 16.3 Решено (роль «Аналитик») — вариант (a), глобальная уникальность slug

Рассмотрены три варианта (полная формулировка альтернатив — см. историю
документа): (a) проверка коллизии по всему городу при создании; (b)
резолвинг по полному пути `district/slug` вместо голого slug — архитектурно
чище, но требует правки контракта `PUT /fields`, `DELETE`, `upload-image`,
нового `PUT /district` И клиента (сейчас везде передаётся только slug) —
непропорционально большой рефакторинг ради риска, ни разу не
воспроизведённого в реальном использовании; (c) не трогать — отклонено,
потому что риск не гипотетический: репро явно показал молчаливую запись
не в ту карточку, а данные хроник/локаций правит Рассказчик вручную и
такую подмену не обязательно заметит сразу.

**Выбран (a).** Дешёвая, точечная правка (один эндпоинт), устраняет
причину, а не один из симптомов, и не меняет контракт остальных
эндпоинтов/клиента. Перед решением проверил реальные данные — дублей slug
внутри `cities/paris/locations`/`cities/balmont/locations` сегодня **нет**
(0 из 26 в Париже, 0 из 3 в Балмонте) — значит включение проверки не
блокирует ничего из уже существующего, backfill/миграция не нужны, это
чистое ужесточение на будущее.

**Контракт для Разработчика:**

- `POST /api/locations` (`web/routes/locations.js`) — precondition
  расширяется с «нет коллизии в целевом районе» на «нет коллизии по ВСЕМУ
  городу»: перед `fs.mkdir(locDir, …)` проверить через уже существующий
  `getAllLocations(city)` (или эквивалентный обход), есть ли локация с
  таким же `slug` в ЛЮБОМ районе — не только в `distFolder`.
- Ответ при коллизии — **явная ошибка `409`**, без авто-суффикса к slug:
  `{ error: 'Локация «<name>» уже существует в районе «<конфликтующий
  район>» — выбери другое название' }` (называем район конфликта — иначе
  пользователь не поймёт, где искать существующую карточку). Авто-суффикс
  (`-2`, `-3`…) отклонён — в проекте нет ни одного прецедента такого
  паттерна (`POST /api/cities/:slug/districts`, `POST /api/cities` — везде
  явная ошибка с текущим 409, не молчаливая мутация имени), заводить новый
  UX-паттерн ради одного эндпоинта — лишняя сложность.
- Тот же путь создания (`generate: true` — AI-генерация карточки) не
  выделяется отдельно: проверка стоит ДО генерации/записи файла, значит
  действует одинаково для обоих режимов одного и того же эндпоинта.
- Не входит в объём: `findLocMdPath()` при этом остаётся резолвером «по
  первому совпадению» (вариант (b) не выбран) — для локаций, у которых
  коллизия слага уже как-то возникла ДО включения этой проверки (в реальных
  данных сейчас таких нет, см. выше), риск §16.1/§16.2 формально
  сохраняется теоретически; фиксировать отдельной защитой в `PUT
  /fields`/`DELETE` не требуется, раз причина закрыта на входе.
