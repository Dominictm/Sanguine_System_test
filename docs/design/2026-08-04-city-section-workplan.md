## 4. Что нужно от Системного аналитика по каждому пункту

### A1 — точечная запись секций city.md 🔴 корневой

**Решено (Аналитик):** переиспользовать `_replaceCitySection()`
(`web/routes/archive.js:97-106`) — вынести в общий модуль, не копировать второй
реализацией. `PUT /api/cities` с `fields` правит только пришедшие секции,
рукописные секции (Париж: «Уточняющие вопросы…») не трогает. `buildCityMd`
остаётся только для СОЗДАНИЯ города с нуля. После этого снять `disabled` со
вкладки «Поля»; `_cityHasCustomSections` оставить для информирующей плашки, а не
запрета.

**Нужен контракт на:**
- куда выносится `_replaceCitySection` (кандидат: `web/lib/parsers/city.js` рядом
  с `buildCityMd`), сигнатура, кто ещё её импортирует;
- поведение `PUT`, когда секции в файле нет вообще (создавать в каноническом
  месте или пропускать с `warning` — сейчас `_replaceCitySection` возвращает `null`);
- поведение, когда пришло `fields`, но файл рукописный: какие секции считаются
  «пришедшими» (все 16 из формы всегда, или только изменённые);
- совместимость: `PUT` с `cityMd` (вкладка Markdown) не меняется;
- набор тестов: рукописный city.md (образец — Париж) переживает сохранение формы
  без потери кастомных секций и форматирования.

**Риск:** это правка пути записи главного файла города. Обязательны тесты на
реальном образце Парижа до мёрджа — прецедент §11 (полный ребилд разрушил
`paris/city.md`) уже был.

### A2 — 8 секций в `POST /api/cities` 🔴

**Решено:** расширить объект, передаваемый в `cityScaffold`
(`web/routes/cities.js:100-106`) ключами `landmarks`, `hunting`, `edicts`,
`mortals`, `calendar`, `tech`, `limits`, `naming`. Backend-правка в несколько строк.

**Нужен контракт на:** UI-часть — где показывать поля (см. §5 «Открытые вопросы»,
вопрос ОВ-1); backend без UI бесполезен, но и наоборот тоже.

**Обоснование приоритета:** 5 из 8 секций напрямую питают промты генерации
(`buildCityConstraints`, `buildCityNaming`) — сейчас у свежесозданного города они
пусты, то есть генерация идёт без ограничений домена и без именника.

### A3 — раздел «Районы» в форме редактирования 🔴 (после A1)

**Решено:** переиспользовать `_districtCardHtml()`/`_cityDistrictsEditorHtml()`
в режиме «существующая сущность» — значения из `GET /districts`, сохранение по
своей кнопке на карточку (`PUT .../districts/:slug`), «+ Добавить район» →
`POST .../districts`. Секцию «## Районы» city.md вести как **дополнительный
источник**: при любом изменении района синкать список автоматически, механизмом
из A1. Привязку локаций в форму НЕ дублировать (она уже работает на странице
просмотра).

**Нужен контракт на:**
- формат строки района в «## Районы» (только имя? имя + тип?) и правило
  разрешения расхождений, если пользователь правил секцию руками;
- `_collectDistrictCards()` сегодня собирает ВСЕ карточки разом — нужна версия
  на одну карточку;
- поведение при конфликте слагов и при переименовании (папка не переименовывается
  — §2.4 техспеки, осознанно);
- non-blocking семантика синка «## Районы» (по образцу `_syncCityFactionsList`).

### B1 — ссылки при переносе локации 🔴

**Решено:** вынести `fixLinks()` из `tools/migrations/002_district_rayon_paths.js:139-172`
в общий модуль и вызывать из `PUT /api/locations/:slug/district` после `fs.rename`
с `renameMap` из одной записи. Миграция 002 после выноса импортирует ту же функцию.
Ошибка синка — `warning` в ответе, не откат переноса. В ответ добавить
`linksUpdated: <число файлов>`.

**Нужен контракт на:** сигнатуру вынесенной функции; где живёт (сервер + tools
должны видеть); что считается «городом» для обхода (границы поиска ссылок);
тесты — перенос локации с входящими ссылками из модуля/хроники/архива.

**Упрощение:** глубина вложенности при переносе не меняется, поэтому ИСХОДЯЩИЕ
ссылки внутри карточки чинить не нужно — только входящие. Вторая, сложная
функция миграции 002 здесь не требуется.
