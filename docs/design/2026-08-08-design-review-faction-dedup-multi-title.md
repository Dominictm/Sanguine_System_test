# Дизайн-ревью: дедупликация пикеров фракций города + мульти-титулы персонажа

**Роль:** Дизайнер. **Входные данные:**
[2026-08-08-faction-dedup-and-multi-title-techspec.md](2026-08-08-faction-dedup-and-multi-title-techspec.md)
(Системный аналитик, Часть 7 — дедуп пикеров, Часть 8 — мульти-титулы). Разметка/код в техспеке
уже детально расписаны — это точечный UX-аудит поверх готового технического решения перед
передачей Разработчику, не редизайн с нуля. Технические решения (токен-модель на бэкенде,
формат CSV-поля) не пересматриваю — только то, что видит и трогает пользователь.

**Аудитория и сценарий:** тот же, что и в предыдущем ревью этой сессии — Рассказчик (ГМ) за
десктопом, между игровыми сессиями, невысокая частота использования пикеров. Приоритет —
понятность с первого взгляда.

## 1. Пикеры фракций города — «Ничего не найдено» после дедупликации вводит в заблуждение

Часть 7 §7.2.2 фильтрует список пикера по `!added.has(name)`, но переиспользует тот же текст
пустого состояния, что и для «поиск ничего не нашёл»: `'<div class="cdet-empty">Ничего не
найдено.</div>'`. Это два разных по смыслу состояния:

- «Введённый запрос ничему не соответствует» (временное, пропадёт при очистке поля поиска) —
  для этого «Ничего не найдено» — корректная формулировка.
- «В этом разделе библиотеки больше нечего добавлять — всё уже в списке фракций города»
  (устойчивое состояние, естественно для маленького города, где, например, все 7 сект из
  библиотеки уже присутствуют) — «Ничего не найдено» здесь читается как «библиотека пуста/сломана
  поисковая выдача», хотя на деле всё наоборот — раздел полностью укомплектован.

**Рекомендация:** различать причину пустоты. Если пул кандидатов **без учёта поискового запроса**
(`!added.has(name)`, без фильтра по `q`) уже пуст — показывать `'Все доступные записи уже
добавлены.'`; если пуст только после применения `q` — оставлять текущее «Ничего не найдено.».
Правка — один дополнительный `if` в каждой из четырёх ветвей `_renderFactionPickerList`
(Часть 7 §7.2.2), симметрично тому, как уже разделены «группа пуста по фильтру библиотеки» и
«группа пуста по поиску» для `mortal` (`groupEl.style.display` считается отдельно от текста
внутри списка) — тот же принцип, применённый к новому измерению пустоты.

## 2. Токен политической роли в «Титуле» — добавляется в конец, теряется в хвосте списка

Часть 8 §8.3.1: при назначении персонажа на политическую роль (Князь/Сенешаль/Примоген) через
карту фракций города, синк добавляет свой токен через `tokens.push(value)` — **в конец** CSV-
списка. Если у персонажа уже есть один-два вручную добавленных титула (например, «Шериф,
Смотритель дозора»), после назначения на политроль поле станет «Шериф, Смотритель дозора,
Примоген города Париж» — самый статусно значимый и «официальный» титул (тот, что реально
определяет положение персонажа в структуре города) окажется последним в строке, а не первым.
На карточке персонажа (просмотр) поле выводится как один сырой текст без иерархии — при
беглом просмотре карточки взгляд читает начало строки первым, и там окажется второстепенный
титул.

**Рекомендация:** политический токен — `tokens.unshift(value)` вместо `tokens.push(value)`, то
есть добавлять в **начало** списка, а не в конец. Не меняет ни один из уже описанных в техспеке
краевых случаев/тестов (порядок в CSV-строке нигде не используется как значимый для логики,
только для отображения) — правка одного слова в Часть 8 §8.3.1, второй цикл функции
(«Новые/сохранившие роль»). Тест-план §8.5 п.3 нужно обновить: ожидаемый результат —
`'Князь города <город>, Шериф'`, не наоборот.

## 3. Toggle-элементы пикера «Титулы» — genuinely переключаемые, но без `aria-pressed`

Часть 8 §8.2.3 (`_titleItemHtml`) добавляет ✓-пометку и toggle-поведение (клик добавляет/
убирает), зеркально уже существующему `_disciplineItemHtml` — но ни у той, ни у другой кнопки
нет `aria-pressed`. Это ровно обратный случай находке №3 предыдущего дизайн-ревью этой сессии
(там `aria-pressed` был **ошибочно присвоен** элементу, который не является тумблером — чипу
«убрать целиком»). Здесь — противоположная ситуация: элемент **является** настоящим тумблером
(два состояния: выбран/не выбран, клик переключает), и это как раз тот случай, где
`aria-pressed` семантически корректен и полезен для пользователя со скринридером (объявит
«нажато»/«не нажато» вместо простого «кнопка»).

**Рекомендация:** добавить `aria-pressed="${selected}"` в `_titleItemHtml` (новый код этой
техспеки, Часть 8 §8.2.3) — одна строка в шаблоне кнопки. По-хорошему тот же атрибут стоило бы
добавить и в уже существующий `_disciplineItemHtml` (Часть 1, вне объёма этой техспеки, но тот
же паттерн) — отмечаю как желательный побочный ретрофит, не обязательный для приёмки Части 8,
но логичный, раз оба пикера теперь по факту идентичны по поведению.

## 4. `✓` + `⚠️` одновременно у выбранного негативного титула — сознательно не предлагаю правку

`_titleItemHtml` (Часть 8 §8.2.3) для выбранного негативного титула даёт префикс вида
«✓ ⚠️ Изгой» — два разных по смыслу глифа подряд перед названием. Формально это чуть плотнее,
чем один индикатор, но: (а) оба символа несут разную, не дублирующую информацию (✓ — состояние
выбора, ⚠️ — свойство самой записи, не связанное с выбором), (б) паттерн «маркер состояния +
маркер свойства записи» уже используется в других списках библиотеки этого проекта без жалоб
(например, бейдж «Авторское» рядом с иконками действий в детейле). Не считаю нужным жертвовать
информацией (снятие ⚠️ при выборе скрыло бы от Рассказчика, что выбранный титул — негативный,
пока он не откроет карточку и не увидит это в другом месте) ради небольшого визуального
уплотнения. Оставляю как в техспеке — фиксирую, что вариант рассматривался, а не пропущен.
