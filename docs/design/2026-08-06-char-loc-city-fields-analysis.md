# Данные для техспеки: поля персонажа/локации/города (7 задач)

**Собрано:** Аналитик, 2026-08-06. **Передаётся:** Системному аналитику на техспеку.

**Зависимость:** пункты 2 и 3 опираются на вкладку «Титулы» библиотеки
(`GET /api/library/titles`) — реализована и живьём проверена в этой же сессии
(`web/lib/titles.js`, роуты в `web/routes/library.js`, UI в `v20-sheet.js`/
`library-authoring.js`). На момент написания в `system/library/titles/` нет
боевых записей (только `README.md`) — наполнение данными не входит в эту задачу.

**Подтверждено пользователем** (решения по неоднозначностям, см. §0):
1. Переименование «Иерархия»→«Титул» — вампиры + смертные + generic-линейки (оборотни/маги/охотники), **фей не трогаем** (у них уже свой «Титул» с другим смыслом).
2. Автозаполнение «Дисциплины» из библиотеки — только автодополнение в существующем текстовом поле, без переделки в чип-пикер.
3. Новые разделы «Фракции смертных» / «Государственные фракции» — участвуют в общем пуле опций дропдауна «Влияние — Фракции» у района, вместе с сектами/кланами/«Другие».

## 0. Как читать этот документ

Семь исходных пунктов пользователя сгруппированы в 3 темы: **A. Персонаж**
(модалка редактирования, вкладка «Информация»), **B. Тултипы** (персонаж +
локация), **C. Город** (вкладка «Фракции» + «География»). По каждому —
текущее состояние (файл:строка) и что нужно сделать. Открытые технические

а техническая развилка) — отмечены «Решение Аналитика», с обоснованием.

## A. Персонаж — вкладка «Информация»

### A1. Поле «Пол»

**Задача:** отображать в модалке редактирования персонажа (вкладка
«Информация»), связано со значением `Пол` в md-карточке.

**Текущее состояние:**
- Парсер УЖЕ читает поле: `web/lib/parsers/character.js:124` — `if (k === 'Пол') c.gender = v;`.
- Тултип для лейбла «Пол» УЖЕ существует: `web/public/scripts/scripts.js:2466`.
- Но самого поля НЕТ ни в одном из наборов вкладки «Информация» —
  `INFO_FIELDS_BY_LINEAGE` / `INFO_FIELDS_GENERIC` (`web/public/scripts/scripts.js:1997-2073`).
  Значение `c.gender` парсится, но никогда не рендерится и не редактируется через эту вкладку.

**Что сделать:** добавить `['gender', 'Пол']` в `INFO_FIELDS_BY_LINEAGE.vampire`,
`.fairy`, `.mortal` и в `INFO_FIELDS_GENERIC` (пол — общее поле, не
линейко-специфичное). Позиция в списке — сразу после «Статус»/«Детали статуса»
(до клановых/фракционных полей), как наиболее базовый идентифицирующий признак.

**Риск:** минимальный, чисто аддитивная правка конфига + сохранение через
существующий generic-механизм `_saveInfoFields()` (`char-detail.js:1180`) —
он уже умеет писать произвольные простые поля обратно в md по ключу.

### A2. «Иерархия» → «Титул»

**Задача:** переименовать поле «Иерархия» в «Титул» (в UI и в md-файле).
Значение заполняется из библиотеки Титулов или вручную. Список титулов
фильтруется по секте персонажа.

**Текущее состояние:**
- `INFO_FIELDS_BY_LINEAGE.vampire` / `.mortal` и `INFO_FIELDS_GENERIC` содержат
  `['hierarchy', 'Иерархия']` (`scripts.js:2009, 2049, 2067`).
- `INFO_FIELDS_BY_LINEAGE.fairy` содержит **оба** поля отдельно: `['title', 'Титул']`
  (титул феи при Дворе, из md-поля `Титул`) И `['hierarchy', 'Иерархия']`
  (`scripts.js:2028, 2032`) — разного смысла, **не трогаем** по решению пользователя (§0.1).
- Парсер: `web/lib/parsers/character.js:138` — `if (/иерархи/i.test(k)) c.hierarchy = v;`
  (регэксп, комментарий явно фиксирует историю бага с автосохранением пустого
  значения — см. комментарий в файле, строки 105-112, поосторожнее при правке этого блока).
  Отдельно `character.js:158` — `if (k === 'Титул') c.title = v;` (сейчас читает только для фей).
- Тултип для лейбла «Иерархия» существует (`scripts.js:2495`, «Место персонажа во
  внутренней иерархии его фракции») — нужно заменить/добавить тултип для «Титул»
  применительно к вампирам/смертным (смысл другой, чем у фейского «Титул»:
  не титул Двора, а формальный титул во фракции — Князь/Шериф/Приск и т.п.).

**Что сделать:**
1. **UI-конфиг** (`scripts.js`): в `vampire`, `mortal`, generic-наборах заменить
   `['hierarchy', 'Иерархия']` → `['hierarchy', 'Титул']` (ключ `hierarchy` в
   объекте персонажа оставить как есть — только лейбл в UI меняется; ниже
   объясню, почему смена ключа не нужна и даже вредна).
2. **Формат md-карточки**: поле в файле персонажа сейчас пишется как
   `- **Иерархия:** значение` (или вариации, ловится регэкспом `/иерархи/i`).
   Нужно, чтобы НОВОЕ значение сохранялось под лейблом `- **Титул:**`
   — но парсер для вампиров/смертных читает `Титул` только как алиас для фей
   (`c.title`, отдельное поле от `c.hierarchy`). **Решение Аналитика**: не
   меняем внутренний ключ объекта (`c.hierarchy` остаётся `c.hierarchy`) —
   меняем только человекочитаемый лейбл в md с «Иерархия» на «Титул» для
   вампиров/смертных/generic, и добавляем этот лейбл в regex-детектор парсера
   (`/иерархи/i` → расширить на `/^(иерархи|титул)/i`, но ТОЛЬКО когда линейка
   не «fairy» — иначе поле-алиас феи «Титул» начнёт ошибочно матчиться сюда же).
   Это исключает коллизию с фейским `c.title` и не требует переименования
   свойства объекта по всему фронтенду (`data-field="hierarchy"` и т.п. остаются
   рабочими без изменений).
3. **Миграция существующих карточек**: у персонажей, где уже стоит
   `- **Иерархия:** ...`, нужно переписать лейбл на `- **Титул:**` — это
   ломающее изменение формата карточки (пользователь читает термин «Иерархия»
   в существующих md годами), значит по конвенции проекта (`CLAUDE.md`, раздел
   «Если меняется формат файлов городов») требуется миграция в `tools/migrations/`,
   которую сервер прогонит автоматически при следующем старте. Миграция:
   найти строки `- **Иерархия:**` (и известные исторические варианты — в парсере
   их ловит `/иерархи/i`, значит стоит собрать реальный список написаний grep'ом
   по `cities/*/characters/**/*.md` перед миграцией) у персонажей линеек
   vampire/mortal/werewolves/mages/hunters (НЕ fairies) и заменить лейбл на
   `- **Титул:**`.
4. **Пикер «из библиотеки Титулов»**: аналог существующего инлайн-пикера
   дисциплин/нумины в V20-листе (`web/public/scripts/v20-sheet.js:1699` —
   `_v20InlineLibPicker` или соседняя функция, «V20 inline library picker») —
   но здесь это не V20-лист, а вкладка «Информация» в `char-detail.js`, где
   сейчас поля — простые `<input class="cdet-field-input">`
   (`char-detail.js:1073-1115`). Нужна кнопка/иконка рядом с полем «Титул»,
   открывающая список записей `GET /api/library/titles`, отфильтрованный по
   `title.affiliation` (поле «Принадлежность» в карточке титула, техспека
   Титулов §2/§3) **совпадающему** с текущим значением поля «Секта» персонажа
   (`c.sect` в этой же форме — оба поля редактируются в одной вкладке
   одновременно, читать текущее значение соседнего инпута в момент открытия
   пикера). Ручной ввод остаётся доступен всегда — пикер лишь подставляет
   значение в то же текстовое поле, не заменяет его.
   - **Открытый вопрос для техспеки**: `affiliation` в карточке титула —
     свободный текст (Камарилья / Шабаш · Инквизиция / клан Ассамитов / «Общие»
     без фракции, см. `docs/design/2026-08-06-library-titles-data.md` §2.1) —
     точное совпадение строк с полем «Секта» персонажа сработает не всегда
     (например, персонаж-Ассамит с `Секта: Камарилья` не увидит титулы клана
     Ассамитов). Системному аналитику стоит решить: точное совпадение (просто,
     но местами не найдёт нужное) vs. подстрока/фаззи-совпадение (`affiliation`
     содержит текущую секту ИЛИ клан персонажа) vs. просто показывать ВСЕ
     титулы, но с секцией «сначала по твоей секте» сверху. Затронутые записи
     — Ассамиты/Тремеры/Цимисхи/Ревенанты/«Общие» (см. data.md §2.1, вопрос 1).

**Риск:** средний — единственный пункт этой задачи, требующий миграции
формата данных. Нужно сначала выполнить п.3 (собрать реальный список
исторических написаний «Иерархии» в существующих карточках) до финализации
regex в парсере.

### A3. Автозаполнение Клан / Секта / Дисциплины из библиотеки

**Задача:** реализовать заполнение этих трёх полей из соответствующих
библиотек прямо во вкладке «Информация». Дисциплины — можно добавить
несколько, клановые — первыми в списке. По решению пользователя (§0.2) —
только автодополнение в существующем текстовом поле, без чип-пикера.

**Текущее состояние:**
- Поля `clan`/`sect`/`disciplines` — простые `<input class="cdet-field-input">`
  в режиме редактирования вкладки «Информация» (`char-detail.js:1040-1131`,
  `_enterInfoEdit`/`_exitInfoEdit`/`_saveInfoFields`), без какой-либо связи с
  библиотекой сейчас — только plain text.
- Библиотеки уже существуют и доступны через API: `GET /api/library/clans`,
  `GET /api/library/sects`, `GET /api/library/disciplines` (последняя — с полем
  `clans` у каждой дисциплины, строка вида «Бруха, Гангрел, …», см.
  `v20-sheet.js:770` — `_libCleanClans(d.clans)` уже парсит этот формат для
  V20-листа, можно переиспользовать ту же функцию).
- В V20-листе УЖЕ есть готовый паттерн клан→дисциплины: `v20ClanInfo(clan)`
  (используется на `v20-sheet.js:1643, 1667, 1671` — `info.disciplines` даёт
  клановые дисциплины персонажа по названию клана) — им же можно
  воспользоваться здесь для сортировки «клановые — первыми».

**Что сделать:**
1. Клан/Секта — `<input>` → `<input list="...">` с `<datalist>`, заполненным
   именами из `/api/library/clans` / `/api/library/sects` (простое
   браузерное автодополнение, без кастомного JS-виджета — минимальная
   инвазия, соответствует решению §0.2 «только автодополнение»).
2. Дисциплины — сложнее: поле сейчас хранит ОДНУ строку (`c.disciplines`,
   в карточке `- **Дисциплины:** Доминирование 3, Целерити 2, …» — свободный
   текст, а не список). «Можно добавить несколько» здесь означает
   автодополнение отдельных ТОКЕНОВ внутри строки (по аналогии с тем, как
   обычно работают tag-инпуты с datalist на разделителе-запятой), а не
   структурное множественное значение (это как раз то, от чего пользователь
   отказался в §0.2, выбрав лёгкий вариант). Список опций для datalist —
   имена дисциплин из `/api/library/disciplines`, **отсортированные так,
   чтобы клановые (по текущему значению поля «Клан» в этой же форме,
   через `v20ClanInfo`/`_libCleanClans`) шли первыми**, затем остальные.
   Технически: `<datalist>` не поддерживает произвольную сортировку по
   вводу браузером — реально это либо (а) просто расположить клановые
   опции первыми в списке `<option>` внутри `<datalist>` (браузер обычно,
   но не гарантированно, сохраняет порядок при показе совпадений), либо
   (б) полноценный JS-виджет автодополнения (свой dropdown под инпутом,
   полный контроль над сортировкой и рендером). **Открытый вопрос для
   техспеки**: `<datalist>` — быстрее, но порядок в подсказках браузера
   не гарантирован кросс-браузерно; свой мини-виджет — предсказуемо, но
   это уже не «просто автодополнение», а маленький кастомный компонент.
   Рекомендация Аналитика: начать с `<datalist>` (риск разошёлся с духом
   решения §0.2 меньше), при необходимости эскалировать.
3. Клан→Дисциплины должно реагировать на смену значения поля «Клан» в реальном
   времени (пока форма открыта) — событие `input`/`change` на поле «Клан»
   перестраивает `<datalist>` дисциплин.

**Риск:** средний — единственная часть без прямого готового прецедента
(datalist с динамической пересборкой опций по соседнему полю); всё
остальное — переиспользование существующих API и функций.

## B. Тултипы

### B1. Персонаж — недостающие в существующем словаре `CHAR_FIELD_TIPS`

`CHAR_FIELD_TIPS` (`scripts.js:2464-2511`) уже покрывает почти все поля
вкладки «Информация» по всем линейкам. Прямым сравнением со всеми ключами
`INFO_FIELDS_BY_LINEAGE`/`INFO_FIELDS_GENERIC` (`scripts.js:1997-2073`)
**отсутствуют**:
- `'Хочет'`, `'Боится'`, `'Рычаг'` — есть во ВСЕХ линейках (vampire/fairy/
  mortal/generic), тултипов нет ни одного.
- `'Пол'` — тултип уже есть (§A1), просто поле само не рендерилось; после
  правки A1 он автоматически подхватится, доп. действий не требует.
- `'Титул'` (для вампиров/смертных/generic, после переименования A2) —
  нужен НОВЫЙ тултип, отличный от существующего `'Титул'` для фей
  (`scripts.js:2505`, про Двор) — но словарь `CHAR_FIELD_TIPS` **плоский**,
  один ключ `'Титул'` на весь словарь, коллизия с фейским значением.
  **Открытый вопрос для техспеки**: словарь нужно либо расширить до
  линейко-зависимого (`{fairy: {...}, vampire: {...}}`), либо (проще)
  оставить один текст, обобщённый под оба смысла («Формальный титул
  персонажа — при Дворе (феи) или во фракции (остальные линейки)»).
  Рекомендация Аналитика — обобщённый текст, без структурных изменений
  словаря: и то и другое семантически «титул, обозначающий формальный
  статус», разница не настолько велика, чтобы усложнять структуру ради неё.

**Что сделать:** добавить 3 новых ключа (`'Хочет'`, `'Боится'`, `'Рычаг'`) +
скорректировать текст `'Титул'` под общий смысл.

### B2. Локация — тултипов нет вообще ни одного

Проверено: `grep -c "field-tip\|fieldTip\|data-tip" web/public/scripts/locations.js`
→ 0 совпадений. В отличие от персонажа/города (`CHAR_FIELD_TIPS`/
`CITY_FIELD_TIPS`), для локаций аналогичного словаря не существует.

**Поля, которым нужны тултипы** (модалка детального просмотра/редактирования
локации, `locations.js`):
- Вкладка «Метаданные» (`metaFields`, `locations.js:350-356`): `Название`
  (subtype), `Район`, `Дополнение к адресу`, `Адрес`, `Контроль`.
- Вкладка «Контекст ВТМ» (`vtmSections`/`vtmEditHtml`, `locations.js:383-421`):
  `Статус`, `Фракция`, `Постоянные фигуры`, `Угрозы`, `Маскарад`.
- Отдельно (форма полного редактирования локации, за пределами табов
  детальной модалки, `locations.js:1040-1062`): `Зона` (`loc-edit-zone`),
  `Опасность` (`loc-edit-danger`, техспека §13.1 — свой цветной индикатор
  🟢/🟡/🔴, отдельно от «Зоны»).

**Что сделать:** завести `LOCATION_FIELD_TIPS` (та же структура-словарь,
что `CHAR_FIELD_TIPS`/`CITY_FIELD_TIPS`) и `fieldTip()` (уже существует как
общая утилита в `web/public/scripts/utils.js:22` — переиспользуется напрямую,
без дублирования) для каждого лейбла выше — и в `locdet-field-lbl` разметке
табов, и в лейблах формы `loc-edit-*`.

## C. Город

### C1. Вкладка «Фракции» — новые разделы

**Задача:** добавить разделы «Фракции смертных», «Государственные фракции»,
оформить как «Другие фракции».

**Текущее состояние:**
- Секция «Фракции» города сейчас хранит ОДИН composite-список: секты-чипы
  (`CITY_SECTS = ['Камарилья', 'Анархи', 'Шабаш']`, `city.js:74`) +
  независимые кланы-чипы (`CITY_INDEPENDENT_CLANS`, `city.js:75`) +
  свободный текст «Другие фракции» (`data-city-field="factions-other"`,
  `city.js:653-655`) — всё это на СОХРАНЕНИИ схлопывается в одно md-поле
  `factions` (`_collectFactions()`, `city.js:660-665`; сохранение —
  `city.js:1570`, `payload = { fields: { factions: ... } }`).
- При ЧТЕНИИ обратно (`_cityFactionsEditorHtml`, `city.js:636-640`) чипы
  распознаются по точному совпадению строки со списком известных
  секты/кланов, всё остальное автоматически считается «Другие фракции».
  **Это значит: если просто добавить ещё два свободных текстовых поля
  («Фракции смертных», «Государственные») без отдельного хранения — при
  перезагрузке страницы их содержимое неотличимо от «Другие фракции» и
  осядет обратно в одну кучу.**

**Решение Аналитика:** заводить для новых разделов ОТДЕЛЬНЫЕ md-поля
(`factions-mortal`, `factions-state`) — по аналогии с уже существующими
отдельными полями секций «живого города» (`landmarks`/`hunting`/`edicts`/…,
`CITY_RULE_SECTIONS`, `city.js:603-611`), а не пытаться закодировать
категорию внутри одного общего списка. Это:
- не требует миграции существующих карточек (текущее поле `factions`
  не трогается, новые поля у старых городов просто пустые);
- прямо соответствует ответу пользователя по вопросу пула (§0.3, «да, общий
  пул») — при сборке опций дропдауна «Влияние — Фракции» (`_currentFactionNames`,

  сейчас читается один список.

**Что сделать:**

2. `_cityFactionsEditorHtml` — добавить два новых `<textarea data-city-field="factions-mortal">`
   / `data-city-field="factions-state">`, оформленные как существующее «Другие
   фракции» (тот же `.form-group`, `<label>` + `<textarea rows="2">`).
3. `_currentFactionNames()` (`city.js:435`) и обработчик `input`

4. Просмотр (view-режим, `city.js:990-1006`, `group(...)` — сейчас три
