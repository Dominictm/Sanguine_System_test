# Дизайн: карточка локации — бейджи, удаление, VTM-вкладка, таблица «Ключевые локации»

**Роль:** Дизайнер. **Входные данные:**
[2026-08-06-location-card-actions-techspec.md](2026-08-06-location-card-actions-techspec.md)
(Системный аналитик) — контракт полей/функций не пересматриваю, только
визуальный слой и взаимодействие там, где техспека дала код, но не финальный
вид (иконки-кнопки, переключение полей, таблица).

**Принцип:** тот же, что в предыдущем дизайн-документе этой серии
(`2026-08-06-char-loc-city-fields-design.md`) — искать готовый прецедент в
проекте раньше, чем изобретать новый компонент. Для этой задачи прецедентов
нашлось особенно много: почти всё уже visually решено где-то ещё в кодовой
базе, нужно только корректно сослаться и перенести.

---

## Сводка: что реально требует решения

Из 4 тем техспеки визуально нетривиальны две: удаление (иконка на карточке
— но прецедент есть, почти без решений) и VTM-вкладка (переключение
Фракция↔Хозяин — единственное место с реальной интерактивной анимацией).
Бейджи (Тема 1) и таблица «Ключевые локации» (Тема 4) — почти целиком
описаны в техспеке, дизайнерская часть там — проверка контраста/ритма.

## 1. Компактные бейджи (Тема 1 техспеки)

**Порядок и spacing** — `.loc-badges { display:flex; gap:6px; flex-wrap:wrap }`
уже существует и не требует правок: два бейджа (⚔️/🎭) вместо одного
(масштаб-нейтральная правка, `gap:6px` одинаково хорошо смотрится что с
одним, что с двумя круглыми бейджами).

**Различимость без текста** (открытый вопрос техспеки/анализа) — решение:
иконки уже физически разные (⚔️ скрещенные мечи vs 🎭 театральная маска),
на фоне с цветной заливкой/рамкой они не конкурируют визуально — цвет
кодирует УРОВЕНЬ (общий для обеих шкал: зелёный/золотой/красный), иконка
кодирует КАТЕГОРИЮ. Это стандартный паттерн «форма = что, цвет = насколько»
— не создаёт двусмысленности при беглом взгляде на сетку карточек. Доп.
разделитель/рамка между бейджами не нужны — `gap:6px` уже достаточно
отделяет их друг от друга.

**title-тултип** (техспека уже это предлагает) — подтверждаю, добавить
`title="⚔️ Высокий"` и т.п. на каждый бейдж. Не заменяет иконку текстом
визуально, но даёт полный текст по наведению — совпадает с тем, как уже
ведут себя многие компактные элементы этого интерфейса (иконки-кнопки типа
`title="Удалить"` и т.п. повсеместны).

## 2. Иконка удаления (Тема 2 техспеки)

### 2.1 На карточке — реюз готового паттерна `.modp-loc-card-unlink`

Проверил CSS: `.modp-loc-card-unlink`/`.modp-npc-card-del`
(`styles.css:12605-12655`) — уже РОВНО тот компонент, который нужен:
`position: absolute; top: 8px; right: 8px`, полупрозрачный чёрный фон
(`rgba(0,0,0,.55)`), краснеет на hover (`color: var(--c-danger-text)`,
`background: rgba(0,0,0,.75)`), уже имеет `pointer:coarse`-адаптацию до
44px (`styles.css:12628-12631`). **Решение: `.loc-card-del-btn` — не новый
класс с нуля, а `.loc-card-del-btn` наследует ТЕ ЖЕ стили** (проще всего —
добавить `.loc-card-del-btn` в существующий селектор-список вместо
дублирования правил):

```css
.modp-loc-card-unlink,
.modp-npc-card-del,
.loc-card-del-btn {
  position: absolute;
  top: 8px;
  right: 8px;
  z-index: 1;
  background: rgba(0, 0, 0, .55);
  border: none;
  color: var(--text);
  cursor: pointer;
  padding: 2px 4px;
}
.loc-card-del-btn:hover {
  color: var(--c-danger-text);
  background: rgba(0, 0, 0, .75);
}
```
(и добавить `.loc-card-del-btn` в оба `@media (pointer: coarse)`-блока,
`styles.css:12628` и `12634`, рядом с существующими селекторами).

**Всегда видима, не hover-reveal** — сознательное решение, не default по
незнанию: удаление — деструктивное действие с подтверждением (`showConfirm`),
случайный клик не приводит к потере данных без второго шага, значит прятать
иконку за hover не даёт защиты, только вредит обнаруживаемости на touch-
устройствах (hover там не работает вовсе, элемент пришлось бы делать
видимым по tap-и-удержанию — заметно хуже UX ради несуществующей выгоды).
Тот же аргумент уже применён в проекте к `.modp-loc-card-unlink` — просто
следую установленному прецеденту, а не ввожу новый.

**Позиция относительно других элементов карточки**: `top:8px; right:8px` —
верхний правый угол пуст на `.loc-card` (заголовок/бейджи снизу в
`.loc-card-overlay`, `styles.css:5758-5768`), конфликтов с существующей
разметкой нет ни у карточек с артом, ни без. `z-index: 1` — карточка сама
не имеет более высоких слоёв внутри себя, конфликта по стэкингу нет.

### 2.2 В детальной модалке

Кнопка `#locdet-delete-btn` (техспека §2.3) — используется существующий
класс `.cdet-edit-btn` (тот же, что «✏ Редактировать / Генерация» рядом) —
**не заводить отдельный визуальный стиль для деструктивного действия
здесь**: это единственное место в детальной модалке, где кнопка не в
карточке-оверлее, а в обычной панели рядом с другой кнопкой того же типа —
`.cdet-edit-btn` уже нейтрально стилизована (не «опасного» вида) для
недеструктивных действий типа «Редактировать». **Дизайнерская поправка к
технической спеке**: деструктивное действие рядом с обычным той же
визуальной весовой категории — небольшой антипаттерн (кнопка удаления не
должна выглядеть так же спокойно, как кнопка редактирования). Добавить
модификатор:

```css
.locdet-delete-btn {
  color: rgba(220, 100, 100, .85);
  border-color: rgba(139, 0, 0, .5);
}
.locdet-delete-btn:hover {
  background: rgba(139, 0, 0, .18);
  border-color: rgba(180, 60, 60, .7);
}
```
(та же цветовая пара, что уже использует `.loc-edit-delete-btn` в форме
редактирования, `styles.css:12500-12507`, — единообразие с уже
существующей кнопкой удаления того же смысла в соседнем модальном окне).

## 3. VTM-вкладка (Тема 3 техспеки)

### 3.1 Ряд «Фракция/Хозяин» + чекбокс «Частный домен»

Готовый прецедент для «инпут + доп. контрол в одной строке» —
`.locdet-district-row` (`styles.css:6208-6215`, использует `input` +
кнопку-отвязку в одном flex-ряду) — та же вкладка, тот же модуль
(`locations.js`), уже решённая задача «поле + управляющий элемент рядом».
Переносим паттерн:

```css
.locdet-faction-row {
  display: flex;
  align-items: center;
  gap: 10px;
}
.locdet-faction-row .locdet-field-inp { flex: 1; }
.locdet-checkbox-row {
  display: flex;
  align-items: center;
  gap: 6px;
  font-size: var(--fs-2xs);
  font-family: var(--f-heading);
  letter-spacing: .05em;
  text-transform: uppercase;
  color: var(--text3);
  white-space: nowrap;
  cursor: pointer;
}
```
Итоговая разметка ряда (уточнение к техспеке §3.2.2, где чекбокс был просто
дописан в конец `.locdet-field-row` без обёртки):
```html
<div class="locdet-field-row">
  <label class="locdet-field-lbl" id="locdet-vtm-faction-lbl">Фракция</label>
  <div class="locdet-faction-row">
    <input class="form-control locdet-field-inp" id="locdet-vtm-faction" list="locdet-factions-list" ...>
    <label class="locdet-checkbox-row"><input type="checkbox" id="locdet-vtm-private-domain">Частный домен</label>
  </div>
</div>
```

### 3.2 Переключение Фракция ↔ Хозяин — не мгновенная подмена «в никуда»

Техспека (§3.4) очищает поле при переключении чекбокса синхронно со сменой
лейбла/плейсхолдера — с точки зрения UX это резкий разрыв: пользователь
может успеть ввести половину названия фракции, случайно задеть чекбокс — и
потерять текст без предупреждения. **Дизайнерская доработка**: если поле
НЕ пустое на момент переключения — короткое подтверждение не нужно (это
была бы избыточная модалка ради опечатки), но само поле должно СВЕТИТЬСЯ/
подсвечиваться на секунду при очистке — небольшая `transition` на
background, чтобы очистка была явно замечена, а не выглядела как баг
(значение просто исчезло без объяснения):

```css
.locdet-field-inp.field-cleared-flash {
  animation: fieldClearedFlash .6s ease-out;
}
@keyframes fieldClearedFlash {
  0%   { background: rgba(139, 0, 0, .25); }
  100% { background: var(--bg2); }
}
@media (prefers-reduced-motion: reduce) {
  .locdet-field-inp.field-cleared-flash { animation: none; }
}
```
JS (дополняет обработчик `change` из техспеки §3.4): добавить класс
`field-cleared-flash` на `input` при очистке, снять через `animationend`
— только если поле реально было непустым до очистки (не проигрывать
анимацию, когда чистить было нечего — иначе чекбокс «мигает» при каждом
клике вне зависимости от состояния, что быстро надоедает при частом
использовании).

### 3.3 «Опасность» select — без изменений визуально

`locdet-field-inp`-класс уже используется для `<select>` («Маскарад» рядом,
`locdet-vtm-masquerade`) — новый select «Опасность» (техспека §3.3)
рендерится идентично, никаких новых визуальных решений не требуется. Цвет
самого select-контрола не кодирует уровень (только текст опций — «🟢
Низкая» и т.п.) — это НЕ противоречит компактным бейджам на карточке (§1) —
там цвет кодирует уровень на бейдже, здесь — обычный `<select>` формы,
разные контексты (форма редактирования vs read-only карточка), разная
плотность информации уместна.

## 4. Таблица «Отмеченные локации» (Тема 4 техспеки)

### 4.1 Заголовок таблицы

Техспека уже добавляет `.city-loc-view-head` (uppercase, `--text3`,
letter-spacing) — тот же визуальный язык, что заголовки колонок нигде
больше в проекте буквально не встречаются как отдельный ряд (`.locdet-row`
— key/val без заголовка, т.к. там ключ ЕСТЬ в каждой строке слева).
Подтверждаю решение техспеки — трёхколоночная таблица без заголовка была
бы нечитаема (непонятно, что в какой колонке, особенно у «Заметки», где
текст может быть длинным и визуально сливаться с «Название»).

### 4.2 Длинный текст в «Заметки» — не переполнять строку

**Не покрыто техспекой.** `.city-loc-view-note` — `1fr`, обычный текст без
`overflow`/`white-space`-правил. Заметки — потенциально длинные (пример из
существующей подсказки поля: «Статус «Элизиум» → Локация «Опера Гарнье»» —
это же ПОЛЕ может содержать куда более длинный вольный текст). Добавить:
```css
.city-loc-view-note {
  word-break: break-word;
  overflow-wrap: anywhere;
}
```
(не `text-overflow: ellipsis` с обрезкой — заметка это содержательный текст,
не лейбл, обрезать её молча означает прятать информацию; перенос строк
внутри ячейки — правильный компромисс для таблицы без фиксированной высоты
строки, `align-items: start` уже есть в `.city-loc-view-row`, значит длинная
ячейка просто растягивает всю строку по высоте, не ломает сетку).

### 4.3 Узкий экран — 3 колонки `140px 1fr 1fr`

Фиксированная первая колонка (`140px`) под «Статус локации» — самый
длинный возможный статус («Приёмная князя», 14 символов) на `--fs-body`
уместится без переноса в 140px в большинстве случаев, но **не проверено на
реальном узком экране**. Веб-интерфейс проекта — десктопное приложение
Рассказчика (не мобильный клиент игроков, см. `CLAUDE.md`/`AGENT_BRIEF.md`
— нет упоминаний мобильного use-case для этой конкретной страницы), поэтому
жёсткий адаптив под узкие вьюпорты здесь не требуется той же строгости, что
у карточек персонажей/локаций в сетке (те правда открывают на телефоне по
ссылке). Рекомендация — оставить `140px 1fr 1fr` как есть, но **проверить
глазами** при реализации на ширине ~900px (свёрнутая боковая панель) — если
станет тесно, снизить первую колонку до `120px` или включить перенос
заголовка «Статус локации» на две строки (`white-space: normal` уже
default, ничего доп. делать не придётся, если не задан `nowrap`).
