## 1. 🔴 Молчаливая перезапись чужой локации при коллизии slug

### 1.1 Точная причина (подтверждена дословным репро в отчёте QA)

**Файл:** `web/public/scripts/city.js`, функция `_saveCityTabEdit`, строки
1627-1643.

```js
if (tab === 'geography' && _pendingNewLocations.length) {
  for (const req of _pendingNewLocations) {
    try {
      const lr = await fetch(`/api/locations?city=${encodeURIComponent(d.slug)}`, {
        method: 'POST', headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ name: req.name, district: req.district }),
      }).then(x => x.json());
      if (lr.slug && req.note) {
        await fetch(`/api/locations/${encodeURIComponent(lr.slug)}/fields?city=${encodeURIComponent(d.slug)}`, {
          method: 'PUT', headers: { 'Content-Type': 'application/json' },
          body: JSON.stringify({ fields: { atmosphere: req.note } }),
        });
      }
    } catch { /* одна неудавшаяся локация не должна срывать сохранение вкладки */ }
  }
  _pendingNewLocations = [];
}
```

`fetch()` не бросает исключение на HTTP-ошибках (`409` и т.п.) — `try/catch`
здесь ловит только сетевые сбои. `POST /api/locations`
(`web/routes/locations.js:408-442`) при коллизии slug возвращает `409` с
телом **`{ error: '...', slug: locSlug }`** — `slug` присутствует в ОБОИХ
вариантах коллизии, что при коллизии в том же районе (`locations.js:423`),
что при коллизии в другом районе (`locations.js:438-441`, §16-фикс). Условие
`if (lr.slug && req.note)` не различает «локация создана» от «409, но в теле
есть slug чужой, уже существующей локации» — в обоих случаях условие истинно,
и код пишет `req.note` в `atmosphere` **резолвнутой по этому slug карточки**,
которая при коллизии — не та, что пользователь пытался создать.

**Наблюдаемое поведение:** ни ошибки, ни какого-либо сигнала пользователю
(`showToast` для этого случая не вызывается вовсе — только `catch` на сетевой
сбой, который тут не срабатывает); новая локация не создаётся; существующая
локация с тем же именем в другом районе получает чужой текст в `atmosphere`
вместо своего.

### 1.2 Контракт исправления

Проверять успех `POST` явно — по HTTP-статусу, не по факту наличия `slug` в
теле ответа:

```js
if (tab === 'geography' && _pendingNewLocations.length) {
  const failedNames = [];
  for (const req of _pendingNewLocations) {
    try {
      const res = await fetch(`/api/locations?city=${encodeURIComponent(d.slug)}`, {
        method: 'POST', headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ name: req.name, district: req.district }),
      });
      const lr = await res.json();
      if (!res.ok) {
        // 409 (коллизия slug — того же района или другого, оба варианта дают
        // slug ЧУЖОЙ карточки в теле ответа, techspec «карточка локации» §QA-1)
        // или любая другая ошибка создания — НЕ трогаем lr.slug ни в каком виде.
        failedNames.push(`«${req.name}»: ${lr.error || 'не удалось создать'}`);
        continue;
      }
      if (lr.slug && req.note) {
        await fetch(`/api/locations/${encodeURIComponent(lr.slug)}/fields?city=${encodeURIComponent(d.slug)}`, {
          method: 'PUT', headers: { 'Content-Type': 'application/json' },
          body: JSON.stringify({ fields: { atmosphere: req.note } }),
        });
      }
    } catch (e) {
      failedNames.push(`«${req.name}»: ${e.message}`);
    }
  }
  _pendingNewLocations = [];
  if (failedNames.length) {
    showToast(`Не удалось создать локации из «Отмеченных локаций»: ${failedNames.join('; ')}`, 'error');
  }
}
```

Ключевые изменения:
1. `fetch()` без `.then(x => x.json())`-цепочки — сохраняем `res` для проверки
   `res.ok` (HTTP-статус) ОТДЕЛЬНО от разбора тела.
2. `if (!res.ok)` — ранний `continue`, ветка записи `atmosphere` физически
   недостижима при 409/любой другой ошибке создания, вне зависимости от того,
   что лежит в `lr.slug`.
3. Ошибки собираются в `failedNames` и показываются ОДНИМ `showToast('error')`
   после цикла (не блокирующим — остальная вкладка уже сохранена, тот же
   принцип, что уже есть для `r.warnings`, строка 1623) — пользователь
   впервые узнаёт, что часть «новых локаций» не создалась и почему, вместо
   тихой деградации.
4. `catch` на сетевые сбои — тоже теперь пишет в `failedNames` вместо
   молчаливого пропуска (тот же полноценный сигнал, а не два разных класса
   молчания на два разных типа сбоя).

### 1.3 Что НЕ меняется

- `POST /api/locations` (`web/routes/locations.js`) — не трогаем, эндпоинт
  ведёт себя корректно (подтверждено QA), баг целиком на стороне
  необновлённого клиентского потребителя.
- Остальной код `_saveCityTabEdit` (сохранение самой вкладки, `warnings`) —
  не трогаем.
- Формат `_pendingNewLocations`/`_collectLocationRows` — не трогаем.

## 2. 🟡 Унификация текста ошибки 409 (тот же участок кода, что фикс §1)

### 2.1 Причина

**Файл:** `web/routes/locations.js`. Два разных по информативности текста
ошибки на 409 для семантически одной и той же проблемы («локация с таким
именем уже есть в городе»):

```js
// строка 423 — коллизия В ТОМ ЖЕ районе
return res.status(409).json({ error: 'Локация уже существует', slug: locSlug });

// строки 438-441 — коллизия В ДРУГОМ районе (техспека §16-фикс)
return res.status(409).json({
  error: `Локация «${locName}» уже существует в районе «${conflictDistrict}» — выбери другое название`,
  slug: locSlug,
});
```

### 2.2 Контракт исправления

Унифицировать оба текста под второй (более информативный) вариант — назвать
и локацию, и район конфликта в обоих случаях:

```js
if (await fs.stat(locFile).catch(() => null))
  return res.status(409).json({
    error: `Локация «${locName}» уже существует в районе «${district || distFolder}» — выбери другое название`,
    slug: locSlug,
  });
```

`district || distFolder` — используем то же имя района, что пользователь
указал в запросе (или дефолтное «Другие», если не указано) — район конфликта
здесь заведомо тот же самый (проверка на строке 422 — коллизия в
`distFolder`, который и есть целевой район запроса), поэтому не требует
похода в `getAllLocations()`, как у соседней ветки (§16-проверка резолвит
район конфликта из НАЙДЕННОЙ чужой карточки, потому что там конфликт может
быть в произвольном ЧУЖОМ районе — здесь конфликт всегда в целевом районе
запроса).

**Риск:** нулевой — чисто текстовая правка сообщения, `slug` в теле ответа
не меняется, HTTP-статус не меняется, клиенты (включая исправленный в §1)
продолжают работать по тому же контракту `{ error, slug }`.

## 3. Тест-план

**§1 (перезапись чужой локации):**
- Воспроизвести ТОЧНО сценарий из отчёта QA (локация «Target» в районе A с
  известной atmosphere → через сохранение вкладки «География» добавить
  «Target» в район B с заметкой) → ожидается: `showToast('error', ...)` с
  текстом, называющим «Target» и причину; atmosphere локации в районе A
  **не изменилась**; в районе B новая локация **не создалась** (как и
  раньше — это не меняем, меняем только видимость сбоя и защиту от побочной
  записи).
- Позитивный сценарий (без коллизии) — новая локация из «Отмеченных
  локаций» с уникальным именем создаётся и получает `atmosphere` из заметки,
  как раньше (регресс-тест на то, что фикс не сломал рабочий путь).
- Смешанный сценарий — 2 новые локации в одном сохранении вкладки, одна
  коллизирует, другая нет → коллизирующая не создаётся и попадает в
  `showToast`, вторая создаётся нормально (цикл `for` не прерывается целиком
  из-за одной ошибки — `continue`, не `return`/`break`).

**§2 (унификация сообщения):**
- `POST /api/locations` с именем, коллизирующим В ТОМ ЖЕ районе → `409`,
  текст теперь называет и локацию, и район (сверить дословно с текстом
  межрайонной коллизии — оба должны следовать одному шаблону).
- Проверено заранее (`grep` по `web/tests/all.test.js`): точный текст
  `'Локация уже существует'` ни в одном тесте не ассертится — правка §2 не
  требует обновления существующих тестов.
