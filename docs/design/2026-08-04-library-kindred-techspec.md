Все решения workplan'а (защита канона сохраняется; wod.fandom.com читается

## Сквозной технический контекст

### Что уже есть (переиспользуется, не пишется заново)

- **CRUD уже работает** для custom-записей всех 5 существующих категорий
  библиотеки (`web/routes/library.js`): `POST/PUT/DELETE
  /api/library/disciplines[/:slug]`, `.../psychics[/:slug]`, и общий
  генератор `_jsonLibRoutes()` (строка 339) для `merits/flaws/backgrounds`
  (адресация `/:category/:slug`). PUT/DELETE проверяют `custom`/
  `**Авторское:** да` и возвращают 403 на канон (строки 239-240, 256-257 и
  т.д.) — эта защита не трогается (решение №1).
- **Мягкое удаление** — файл уезжает в `_deleted/<slug>_<ts>.md`
  (disciplines/psychics) или запись вырезается из JSON-массива
  (merits/flaws/backgrounds — там soft-delete нет, это существующее
  поведение, не предмет этой задачи).
- **Форма создания/правки** — `#lib-edit-modal` (`index.html:804-856`) +
  `web/public/scripts/library-authoring.js`: `_LIB_KIND_CONFIG` (строка 23)
  — конфиг per-kind (какие поля показывать, как собрать тело запроса, как
  перезагрузить список). Единый источник правды уже есть — расширяется, не
  переписывается.
- **Общая read-only модалка** — `_v20EnsureLibModal()`
  (`web/public/scripts/v20-sheet.js:929`), один DOM-инстанс на все категории
  (диспиплины/психика/комбо/пути/merits/flaws/backgrounds), с фокус-
  ловушкой, Escape, возвратом фокуса инициатору. **Эта же модалка** —
  основа для K1 (не новый компонент).
- **`showConfirm(message, {danger, confirmText, cancelText})`**
  (`web/public/scripts/utils.js:52`) → `Promise<boolean>` — единственный
  диалог подтверждения в проекте, использовать для удаления и для
  «сохранить перед закрытием».

### Что не совпадает с запросом (и меняется)

Сегодня «просмотр» и «правка/удаление» — **три раздельных экрана**:
1. Клик по карточке → read-only модалка (`_v20OpenDisciplineModal` и т.п.).
2. Карандаш на карточке (только у custom) → **другая** модалка
   `#lib-edit-modal` (форма).
3. Корзина на карточке (только у custom) → **третья** модалка
   `#lib-delete-modal`.

K1 объединяет 1+2+3 в одну модалку с переключением режима внутри неё же.

## K1 · 🔴 Единая модалка библиотеки (просмотр/правка/удаление)

### Контракт шапки

Расширить `_v20EnsureLibModal()`: рядом с `✕` — заголовок записи и, когда
открыт **top-level** просмотр записи (не Path/Combo-детейл, см. ниже),
кнопки `✏ Редактировать` (→ `✓ Сохранить` в режиме правки) и `🗑 Удалить`.
Видимость кнопок — только если запись `custom === true`; для канона шапка
рендерится без них (решение по умолчанию из workplan'а — скрыть, не
дизейблить, простое решение без лишнего текста-объяснения).

Состояние текущего просмотра — новая переменная модуля:
```js
// null, когда открыт Path/Combo-детейл (у них нет CRUD) — Edit/Delete
// в шапке не рендерятся вовсе, не просто дизейблятся.
let _v20CurrentLibView = null; // { kind, slug, category, custom }
```
Каждый `_v20RenderXDetail(...)` для top-level записи (дисциплина, психика,
merit, flaw, background, клан, секта) устанавливает
`_v20CurrentLibView = { kind, slug, category, custom: rec.custom }` перед
рендером тела; `_v20RenderDisciplinePathDetail`/`_v20RenderComboDetail`
устанавливают `_v20CurrentLibView = null`.

### Режим правки — рендер внутри той же модалки

**Не переиспользует DOM `#lib-edit-modal`** (та форма остаётся отдельным
модальным окном для потока «+ Добавить» — см. ниже почему). Вместо этого:
новая функция `_v20RenderLibEditForm(kind, slug, category)` рендерит форму
**внутрь `#v20-disc-modal-body`**, используя тот же источник правды, что и
`#lib-edit-modal`, — `_LIB_KIND_CONFIG[kind].fields`. Чтобы не дублировать
логику полей/сбора значений, `_libSetFieldVisibility`/значения-полей/
`_libCollectLevels` из `library-authoring.js` **обобщаются**: принимают
корневой элемент (`root = document`) вместо жёстко зашитых
`document.getElementById('lib-edit-…')`, и вызываются с двумя разными
корнями — старым (`#lib-edit-modal`, поток создания) и новым
(`#v20-disc-modal-body`, поток правки). Один источник конфигурации полей
на оба потока — не два независимых списка полей, которые могут разойтись.

**Почему «+ Добавить» не переезжает в общую модалку:** создание записи не
привязано к конкретной уже открытой карточке — у него нет «текущего
review-состояния» для дальнейшего переключения назад в просмотр. Общая
модалка спроектирована как «просмотр записи ↔ правка записи», не «пустая
форма создания» — смешивать эти два сценария в одном DOM усложнило бы K1
без выигрыша (в запросе создание вообще не упоминается). `#lib-edit-modal`
остаётся как есть, только внутренние функции обобщаются (см. выше) для
переиспользования разметки полей.

### Кнопка «✏ Редактировать» → «✓ Сохранить»

```js
  _v20LibEditDirty = false;
  // ... переключить текст/обработчик кнопки на «✓ Сохранить»
}
async function _v20SaveLibEdit() {
  // Собрать поля из #v20-disc-modal-body (тем же обобщённым коллектором,
  // что и _libSaveEdit), PUT на тот же URL, что и сегодня использует
  // library-authoring.js. По успеху — сбросить кэш соответствующего kind,
  // перерендерить detail в READ-режиме, обновить карточку в фоне (список
```

`#lib-edit-error` сегодня), форма остаётся в режиме правки, ничего не
закрывается (не терять ввод при ошибке).

### 🗑 Удалить

```js
async function _v20DeleteCurrentLibRecord() {
  const v = _v20CurrentLibView;

  const rec = _libFindRecord(v.kind, v.slug, v.category);
  const ok = await showConfirm(`Удалить «${rec?.name || v.slug}»? Это действие необратимо.`, { danger: true, confirmText: 'Удалить' });
  if (!ok) return;
  // DELETE тем же URL, что и _libConfirmDelete сегодня; по успеху —
  // закрыть модалку, invalidate кэш kind, перезагрузить список карточек.

```
Переиспользует существующий `DELETE` эндпоинт как есть — на бэкенде
ничего не меняется.

### Несохранённые правки при закрытии

Новая логика, прецедента в проекте нет:
```js
let _v20LibEditDirty = false; // true с первого input/change в форме правки

async function _v20CloseDisciplineModal() {
  if (_v20LibEditMode && _v20LibEditDirty) {
    const save = await showConfirm('Есть несохранённые правки. Сохранить перед закрытием?',
      { confirmText: 'Сохранить', cancelText: 'Не сохранять' });
    if (save) { await _v20SaveLibEdit(); return; }   // сохранение само решает, закрывать ли модалку
  }
  // ... существующая логика закрытия модалки как есть
}
```
Два исхода (Сохранить / Не сохранять, оба закрывают модалку) — это предел
возможностей `showConfirm()` (булев результат, не трёхвариантный выбор).
Если нужен и третий вариант «Отмена, остаться в модалке» — это уже не
`showConfirm()`, а отдельный диалог; запрос описывает ровно двухвариантное
предложение («…должно всплыть окно с предложением сохранить»), поэтому
двух исходов достаточно.

Триггеры проверки — оба существующих способа закрытия: клик по `✕`
(`#v20-disc-modal-close`) и клик по фону (`e.target === modal`,
`v20-sheet.js:940`) — оба должны звать один и тот же обёрнутый
`_v20CloseDisciplineModal`, не два разных пути закрытия с разной логикой.

Dirty-флаг взводится делегированным `input`/`change` на
`#v20-disc-modal-body`, пока модалка в режиме правки — не по каждому полю
отдельно (одна точка входа, не 10 обработчиков на 10 инпутов).

### Приёмка K1
- Открыть карточку авторской дисциплины → модалка показывает шапку с
  ✏/🗑. Открыть канон (например, `animalism`) → шапка без этих кнопок.
- ✏ → все поля становятся редактируемыми, кнопка меняется на ✓ Сохранить.
- Правка + ✓ Сохранить → модалка возвращается в просмотр с новыми
  значениями, карточка в сетке обновлена после закрытия.
- 🗑 → `showConfirm` с предупреждением → подтверждение → запись удалена
  (файл в `_deleted/`), модалка закрыта, карточка пропала из сетки.
- Режим правки → изменить поле → закрыть по ✕ или клику мимо →
  `showConfirm` «Сохранить перед закрытием?» — оба исхода закрывают
  модалку, «Сохранить» перед этим пишет изменения.
- Path-детейл/Combo-детейл — шапка без ✏/🗑 (у них нет CRUD).

## K2 · 🔴 (после K1) Перевод ВСЕХ пяти категорий на K1

**Решено — расширяется на все пять существующих категорий**, не только
disciplines/psychics: дисциплины, психические способности, достоинства,
недостатки, факты биографии. У всех пяти сегодня одинаковая структура
(карточка → `_v20Open*Modal` → read-only detail в общей модалке + отдельные
карандаш/корзина на карточке для custom-записей) — K1 применяется
единообразно ко всем, не оставляя часть библиотеки на старом UX.

Технически ничего нового сверх контракта K1 — точки входа схлопываются:
- Карандаш/корзина на карточке (`_libCardActionsHtml`, вызывается из
  `_libDisciplineCardsHtml`/`_libPsychicCardsHtml`/`_libMeritCardsHtml`/
  `_libFlawCardsHtml`/`_libBackgroundCardsHtml` — все пять в
  `v20-sheet.js`) — убираются у всех пяти. Правка/удаление — только через
  открытую детейл-модалку (K1).
- Каждый из пяти `_v20RenderXDetail` (`_v20RenderDisciplineDetail`,
  `_v20RenderPsychicDetail`/аналог, `_v20RenderMeritDetail`,
  `_v20RenderFlawDetail`, `_v20RenderBackgroundDetail`) должен установить
  `_v20CurrentLibView = { kind, slug, category, custom }` перед рендером
  тела — сегодня это делают не все (`_v20RenderMeritDetail`/
  `_v20RenderFlawDetail` пока просто рендерят детейл без учёта состояния
  «что сейчас открыто», см. `v20-sheet.js:1093-1098`, `1158-1163`) — без
  этого шага Edit/Delete в шапке не появятся у merits/flaws/backgrounds.
- `merits`/`flaws`/`backgrounds` уже полностью описаны в
  `_LIB_KIND_CONFIG` (`library-authoring.js:32-43`) — новых записей конфига
  не требуется, только сама точка входа правки (K1) начинает их
  использовать вместо `_libOpenEditModal`.

**Приёмка:** `.lib-card-actions` (карандаш/корзина) не рендерится ни у
одной из пяти категорий; `_libCardActionsHtml` и все её вызовы удаляются
как мёртвый код. Открытие любой из пяти категорий (канон и custom) через
карточку показывает шапку по правилам K1 (custom → Edit/Delete видны,
канон → скрыты); правка/сохранение/удаление работают одинаково во всех
пяти.

## K3 · 🟡 Библиотека кланов — данные + бэкенд

### Формат файла — `system/library/clans/<slug>.md`

Клан — **не силовая шкала** (в отличие от дисциплин/психики), одна запись
на файл без `## Уровень N`. Схема ближе к city.md-секции, чем к
дисциплине:
```markdown
# 🧛 Тремер (Tremere)

- **Секта:** Камарилья
- **Дисциплины:** Аспект, Доминирование, Тауматургия
- **Слабость:** <текст>
- **Источник:** https://wod.su/vampire/clans/tremere

> (опц.) короткая цитата-эпиграф

## Описание

<основной текст — образ жизни, история, эстетика клана, своими словами>
```
Новый файл `system/library/clans/README.md` документирует формат — по
образцу `disciplines/README.md`/`psychics/README.md` (см. workplan K6 —
конвенция «своими словами, не копипаста», ссылка-источник в шапке).

### Парсер — `web/lib/clans.js`

```js
function parseClanMd(rawContent, slug) {
  // Переиспользует field()-подход disciplines.js (regex по «- **Label:**»),
  // но БЕЗ разбора H2-«Уровень N» — единственная секция «## Описание»
  // читается целиком регуляркой /^##\s+Описание\n+([\s\S]*)$/mi.
  return { slug, name, sect, disciplines, weakness, source, note, description, custom };
}
module.exports = { parseClanMd };
```

### Роуты — `web/routes/library.js`

Один в один по образцу дисциплин (строки 21-63 — загрузка/кэш по mtime;
212-264 — CRUD), с своим `CLANS_DIR`/`_clanCache`/`_clanTemplate`:
```js
router.get('/api/library/clans', ...);                  // как loadDisciplines
router.post('/api/library/clans', ...);                 // custom: true, шаблон без levels
router.put('/api/library/clans/:slug', ...);             // 403 на canon, как disciplines PUT
router.delete('/api/library/clans/:slug', ...);          // soft-delete в _deleted/, как disciplines DELETE
```
`_clanTemplate({name, sect, disciplines, weakness, source, note, description})`
— все свободные поля через `sanitizeInlineText` (тот же FIX-16, что у
`_discTemplate`/`_psyTemplate` — без этого текст с `\n## ` подделал бы
структуру записи).

### Приёмка K3
- `GET /api/library/clans` возвращает 7 базовых кланов из K6.
- POST создаёт custom-запись, PUT/DELETE работают только для неё (канон —
  403), то же поведение, что уже покрыто тестами дисциплин — новые тесты
  зеркалят существующие (`web/tests/all.test.js`, искать `disciplines` в
  описаниях `it(...)` как образец).

Поля `discipline-list`/`weakness` — **новые слоты** в `#lib-edit-modal`
(`index.html`, рядом с существующими `data-lib-field="clans"` и т.п.) со
своими подписями — по уже установленному в этой форме прецеденту (у
психики/merits разные слоты для похожих по смыслу полей с разными
подписями, не один слот с динамической подписью) — не первый случай
такого рода в этой форме, паттерн просто повторяется.

`categories`/`category-select` для «Секта» клана переиспользует
существующий `category-select`-тип поля (`index.html:820-823`) — список
опций собирается из **уже загруженных** 7 записей `sects` (`ensureSects()`),
не хардкодится отдельным константным массивом — иначе список сект
задан в двух местах и может разойтись, когда K6-расширение добавит секты
сверх базовых 7.

### Приёмка K5
- В сайдбаре появляется пункт «Сородичи», открывает страницу с двумя
  вкладками.
- «Кланы» показывает 7 карточек (после K6), на каждой видно название и
  секту.
- «Секты» показывает 7 карточек.
- Клик по карточке клана/секты открывает ту же единую модалку (K1), с
  теми же правилами Edit/Delete (canon защищён).
- «+ Добавить клан»/«+ Добавить секту» открывает `#lib-edit-modal` с
  нужным набором полей (список Сект в `<select>` — те же 7, что на
  вкладке «Секты»).

## Порядок реализации
