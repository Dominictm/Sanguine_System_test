# Дизайн-ревью: управление связями (Фаза 1 — «Постоянные»/«Авторские связи»)

**Роль:** Дизайнер. **Входные данные:**
[2026-08-08-relations-management-techspec.md](2026-08-08-relations-management-techspec.md)
(Системный аналитик, Фаза 1: библиотека «Постоянные связи», модалка, интеграция с графом).
Разметка/CSS в техспеке уже детально расписаны — UX/визуальный аудит поверх готового
технического решения, точечные правки перед передачей Разработчику.

**Аудитория и сценарий:** тот же, что и в предыдущих двух ревью этой сессии — Рассказчик (ГМ) за
десктопом, между игровыми сессиями. Здесь добавляется нюанс: управление связями открывается со
страницы «Граф» — это уже не форма редактирования одной карточки, а справочник на весь город,
вероятная точка входа — «хочу понять/навести порядок в том, что уже накопилось» (особенно колонка
«Авторские связи»), не «быстро добавить одну запись».

## 1. `alert()`/`confirm()`/`prompt()` — в проекте уже есть темизированные замены, техспека их не использует

Техспека §3 использует нативные `alert(...)` (ошибки), `confirm(...)` (удаление) и `prompt(...)`
(переименование). Это не мелочь стиля — в кодовой базе **уже есть** готовые, оформленные под
тёмную тему интерфейса замены, и они уже применяются ровно для такого же действия в другом месте
(`archive.js:479-484`, удаление фракции влияния):
```js
const ok = typeof showConfirm === 'function'
  ? await showConfirm(`Удалить фракцию «${name}» из карты влияний?`, { confirmText: 'Удалить' })
  : window.confirm(`Удалить фракцию «${name}»?`);
```
`showConfirm(message, {danger, confirmText, cancelText})` и `showToast(message, type)` — обе
объявлены в `utils.js:74-98`, глобально доступны (тот же файл, что даёт `openModal`/`closeModal`,
которые техспека и так уже использует для самой модалки). Нативный `confirm()`/`alert()` внутри
уже открытой кастомной модалки визуально выбивается — серый системный диалог поверх готической
тёмной темы — и не проходит через тот же UX (например `danger: true` даёт красную кнопку
подтверждения для деструктивного действия, которого у голого `confirm()` нет).

**Рекомендация**: заменить `alert(d.error || …)` → `showToast(d.error || …, 'error')`,
`confirm('Удалить эту связь…')` → `await showConfirm('Удалить эту связь из постоянных?', {
danger: true, confirmText: 'Удалить' })`. Для `prompt()` готового аналога в проекте нет — см.
следующий пункт, там другое решение.

## 2. `prompt()` для переименования — заменить на инлайн-редактирование по месту

В отличие от `confirm`/`alert`, штатной темизированной замены `prompt()` в проекте нет — но и не
нужно её изобретать: приложение уже everywhere использует инлайн-редактирование по клику (поле
превращается в `<input>` на месте, без отдельного диалога) — тот же паттерн, что вкладка
«Информация» карточки персонажа (`.cdet-field-input`). Модальное окно поверх уже открытого
модального окна (`prompt()` — по сути третий слой поверх графа → модалки управления связями) —
лишний скачок контекста для действия «поправить одно слово».

**Рекомендация**: клик по ✏ превращает `.relmgr-item-name` в `<input>` с текущим значением,
Enter/blur — сохраняет (тот же `PUT`, что уже в техспеке), Escape — отменяет. Правка локальна —
меняет обработчик `data-relmgr-edit` в `relations-manage.js` (§3 техспеки), не архитектуру.

## 3. Иконка кнопки — обычный «+», не декоративный ⊞

Техспека сама помечает выбор глифа как временный (`§2.1`, «финальный выбор — на усмотрение
Дизайнера»). `.btn-icon` (`styles.css:2009-2021`, класс, которым уже оформлена кнопка-соседка
`#btn-reset`) **уже рисует прямоугольную рамку с `border-radius`** — то есть «квадрат» из запроса
пользователя даёт сама кнопка, а не обязательно глифом внутри. Приложение последовательно
использует голый `+` как визуальный маркер добавления везде — `+ Добавить связь`
(`char-detail.js:184`), `+ Создать` (`index.html:169`), `+ Новый город`
(`index.html:39`) — декоративный юникодный ⊞ (квадрат-в-квадрате, раз рамку уже даёт сама
кнопка) не только избыточен, но и выбивается из этой более простой, уже установленной визуальной
конвенции.

**Рекомендация**: `+` вместо `⊞` в тексте кнопки (§2.1 техспеки) — один символ, `.btn-icon`
даёт всё остальное «квадратности» бесплатно.

## 4. `title` и `aria-label` кнопки не совпадают

§2.1: `title="Добавить связи" aria-label="Управление связями"` — разный текст для двух атрибутов
одной и той же кнопки. Зрячий пользователь на hover увидит одно, пользователь скринридера
услышит другое — расхождение неоправданно (в отличие от предыдущего дизайн-ревью этой сессии,
где `aria-label` намеренно **заменял** `title`/визуальный смысл ради другой, более точной
семантики — здесь оба атрибута описывают ОДНО и то же действие, просто по-разному
сформулированное, без причины для расхождения).

**Рекомендация**: одна и та же формулировка в обоих атрибутах — раз название модалки уже
«Управление связями» (`chr-modal-title`, §2.2), логичнее унифицировать оба на неё же:
`title="Управление связями" aria-label="Управление связями"`.

## 5. Нет поля поиска ни в одной из двух колонок — единственный список в библиотеках приложения без него

Все остальные списки «из библиотеки» в этом приложении (Дисциплины/Титулы/Секта/Организация/
Должность/Фракции города — включая то, что реализовано в этой же сессии буквально сегодня)
имеют `<input class="v20-lib-search">` для живой фильтрации. Модалка управления связями (§2.2
техспеки) — единственное новое место без него вообще, для ОБЕИХ колонок. Для «Постоянных связей»
это не критично (11 стартовых записей, короткий список), но для «Авторских связей» — это по
определению открытый, ничем не ограниченный список: каждая уникальная формулировка, когда-либо
вписанная в «Отношения» любого персонажа города. В городе с историей в несколько десятков
персонажей и активной хроникой список легко может перевалить за полсотни строк — без поиска
находить нужную формулировку (чтобы, например, сделать её постоянной) станет неудобно именно
тогда, когда эта колонка наиболее полезна.

**Рекомендация**: добавить `<input class="v20-lib-search">`-подобное поле над
`#relmgr-authored-list` как минимум (над `#relmgr-permanent-list` — по желанию, для
консистентности разметки обеих колонок, но там менее критично при 11-это записей). Правка
локальна — фильтрация тем же паттерном `!q || text.toLowerCase().includes(q)`, что уже
используется по всему приложению.

## 6. Кнопки ✏/🗑/«Сделать постоянной» — только `title`, без `aria-label`

Симметрично находке №3 предыдущего дизайн-ревью этой сессии (там `aria-pressed` был к месту у
toggle-элемента, но отсутствовал) — здесь три icon-only действия (`_relItemHtml`/`_renderAuthoredList`,
§3 техспеки) полагаются только на `title`, который не всегда надёжно озвучивается скринридерами
(в отличие от `aria-label` — уже устоявшийся в проекте стандарт для icon-only кнопок, см. хотя бы
кнопку из находки №4 выше или чипы фракций, доработанные сегодня раньше).

**Рекомендация**: добавить `aria-label`, дублирующий текст `title`, на все три кнопки
(`data-relmgr-edit`/`data-relmgr-del`/`data-relmgr-promote`) — для «Сделать постоянной» текст
уже самодостаточен и виден как надпись кнопки (не icon-only в строгом смысле), но раз она в
одном ряду с двумя icon-only соседками — для консистентности стоит тоже явно проставить.

## 7. Цветовая палитра сид-набора — техспека прямо просит свести с Дизайнером (§1.1)

Единственная пара, вызывающая сомнение при первом взгляде — **Сир (`#DC143C`, яркий багровый) и
Чайлд (`#B2374A`, тёмный кирпичный)**: оба из одного красного семейства, различимы рядом, но на
графе с десятками рёбер и беглым сканированием взглядом легко спутать друг с другом — а именно
различимость типов с первого взгляда и есть единственная функция этой цветовой палитры.
«Родственная» палитра для парных типов (Сир↔Чайлд, Домитор↔Гуль) звучит тематически красиво, но
цветовым сходством смысловая парность всё равно не считывается зрителем без предварительного
знания — то есть выгоды от близости цветов нет, а разборчивость на графе теряется. Остальные пары
(Домитор `#8B5A2B` / Гуль `#6B8E23`, Брат `#4472C4` / Сестра `#C94AA0`) достаточно различимы,
менять не предлагаю.

**Рекомендация**: увести Чайлд из красного семейства — например тёплый янтарный/охровый тон
(в духе уже занятого Домитором `#8B5A2B`, но нужен новый, не дублирующий его — например
`#C4821E`), чтобы сохранить читаемость графа как основной критерий. Точное значение — не
принципиально, правка одной строки в сид-JSON (§1.1 техспеки), не код.
