## 1. Бейджи карточки локации — решено: B + A

Разбор проблемы (скриншот: «ОПАСНАЯ», «ВЫСОКИЙ», «ВЫСОКИЙ» — два разных бейджа
с одинаковым текстом без подписи оси) и код-грунд — см. обсуждение в
конверсации; коротко:

- `_locCardHtml()` (`web/public/scripts/locations.js:112-130`) рендерит 3
  бейджа подряд: `zoneBadge` (текстовая классификация зоны — Элизиум/
  Носферату/Нейтральная/Опасная/Локация), `dangerBadge` (числовой уровень
  опасности — читает цветной кружок 🟢🟡🔴 из ТОГО ЖЕ поля «Зона», см.
  `zoneDangerLevel()`, строки 38-46), `masqBadge` (уровень Маскарада —
  отдельное поле `masqueradeLevel`).
- `zoneBadge` и `dangerBadge` — производные одного поля, показывают
  «опасно» дважды разными словами. `dangerBadge` и `masqBadge` рендерятся
  одинаковым цветом/форматом («🔴 Высокий») без подписи — неотличимы друг
  от друга на карточке.
- `.loc-badges{flex-wrap:wrap}` (`styles.css:5595-5600`) — при 3 бейджах в
  узкой карточке третий чип виснет один на второй строке.

**Важная находка:** детальная модалка локации (`openLocDetail()`,
`locations.js:439-452`, `.locdet-legend-row`) уже решает эту проблему
правильно — там каждый бейдж идёт с явным текстовым лейблом («Зона
контроля», «Уровень опасности», «Маскарад»). Проблема — только в
компактной карточке грид-сетки (`_locCardHtml`), которая переиспользуется
и на главной сетке локаций, и в панели «Связанные локации» модуля
(`modules.js`, `modp-loc-cards`).

### Решение

- **B (убрать дублирование):** убрать `dangerBadge` из `_locCardHtml`
  полностью — это производная того же поля, что и `zoneBadge`; тонкая
  градация «Высокий/Средний/Низкий» уровня опасности остаётся только в
  детальной модалке (`.locdet-legend-row`), где она уже подписана и не
  теряется. На карточке-превью остаются максимум 2 бейджа
  (`zoneBadge` + `masqBadge`) — в подавляющем большинстве случаев
  перенос строки больше не понадобится.
- **A (подписать оставшийся):** добавить иконку-лейбл к `masqBadge`, чтобы
  «Высокий» не читался как неопределённое значение — например
  `🎭 Высокий` вместо голого `🔴 Высокий` (иконка вместо слова «Маскарад:»,
  чтобы не удлинять чип). `MASQ_BADGE_LABELS` (`locations.js:16-20`)
  правится с `'🟢 Низкий'` на `'🎭 🟢 Низкий'` (или аналогичный вариант —
  финальную иконку/формулировку уточнить при реализации).

### Затронутые места

- `web/public/scripts/locations.js`: `_locCardHtml()` (убрать
  `dangerBadge` из сборки `textBlock`), `MASQ_BADGE_LABELS` (добавить
  иконку-лейбл).
- `web/public/styles.css`: `.loc-badges` — после ухода третьего бейджа
  можно упростить (`flex-wrap` может больше не понадобиться в типичном
  случае, но лучше оставить как защиту от длинных названий зон).
- Панель «Связанные локации» модуля переиспользует `_locCardHtml` —
  правка применится и там автоматически, отдельно трогать не нужно.
- `.locdet-legend-row` в детальной модалке — **не трогаем**, там уже всё
  подписано корректно (эталон, на который равнялись при выборе A).

## 2. Вкладка «Сенсорика» модалки локации — обязательные разделы Свет/Звук/Запах

### 2.1 Текущее состояние (проверено по коду и по реальным данным)

`_renderSensPanel()` (`locations.js:178-217`) уже использует
`DEFAULT_CHANNELS = ['Свет', 'Звук', 'Запах', 'Тактильное']` как
дефолтный набор — но **только когда `loc.sensoryPalette` пуст**. Как
только сохранён хоть один канал (правка/генерация/добавление), дефолты
больше не подставляются — сохранённый список становится единственным
источником, и любой из 4 каналов, включая «Свет»/«Звук»/«Запах», можно
удалить кнопкой ✕ (`_locDeleteSensChannel`, строки 262-284) без всякой
защиты. То есть сегодня «обязательности» нет вообще — это чисто
дефолт-подсказка для новой пустой локации, не гарантия для сохранённой.

Проверил реальные данные по обоим городам (28 файлов локаций,
`grep -rl "## .*Сенсорная палитра" cities`):

- **27 из 28** файлов уже имеют секцию «Сенсорная палитра» с реальным
  (не ⚠️-плейсхолдерным) текстом — де-факто требование по большей части
  уже выполняется контентом, не защищено интерфейсом.
- **1 файл вообще без секции:**
  `cities/balmont/locations/district_01/podzemnyy_dok/podzemnyy_dok.md`.
- **3 файла используют другие названия каналов**, не «Свет»/«Тактильное»:
  `district_11/bastiliya/fobur_sent_antuan`,
  `district_12/vensen/tsirk_vensen`,
  `district_18/monmartr/port_de_la_shapel` — там каналы называются
  «Зрение» и «Прикосновение» (плюс у них другой заголовок таблицы
  «Чувство | Деталь» вместо «Канал |», и добавлен внеплановый канал
  «VtM-ощущение»). Раз «обязательность» будет матчиться по точному
  названию канала («Свет», не «Зрение»), эти 3 локации на вкладке
  формально не будут засчитаны как заполненные по каналу «Свет» — хотя
  содержательно он есть, просто под другим именем.
- **1 файл содержит постороннее поле в этой секции:**
  `cities/balmont/locations/Ценр/metro/metro.md` — под заголовком
  «Сенсорная палитра» там всего одна строка `| **Маскарад** | 🔴/🟡/🟢 |`
  — похоже на ошибку при ручном заполнении (Маскарад — отдельное поле
  карточки, не канал ощущений). Не трогаю без подтверждения — фиксирую
  находку, релевантно для миграции ниже.

### 2.2 Что означает «обязательные» — предложение

Два уровня строгости, нужно выбрать (в задаче явно не указано):

- **(i) UI-only (рекомендую для первого этапа):** убрать кнопку ✕
  («Удалить канал») у каналов «Свет», «Звук», «Запах» конкретно —
  «Тактильное» и произвольные добавленные каналы остаются удаляемыми.
  Незаполненный обязательный канал показывает не нейтральное «Пусто», а
  явный ⚠️-индикатор (по конвенции проекта — как в шаблоне
  `tools/new_location.js`), плюс небольшой значок-предупреждение на самой
  кнопке вкладки «Сенсорика» в `cdet-tab-bar`, если хотя бы один из трёх
  пуст — так редактор видит незаполненность, не открывая вкладку.
  Никакого сохранения не блокирует — совместимо с уже существующими
  локациями без миграции.
- **(ii) Backend-валидация:** `PUT /api/locations/:slug/fields` отклоняет
  сохранение, если один из трёх каналов пуст — по аналогии с
  `required:true` в `LINEAGE_DEFS` для создания персонажа. Жёстче, но
  требует сначала решить судьбу файла без секции вообще (`podzemnyy_dok`)
  и трёх файлов с другими названиями каналов (§2.1) — иначе они станут
  «невалидными» задним числом при первом же сохранении. Похоже по риску
  на историю с обязательными полями округа/района в городском плане —
  сначала бэкофилл, потом enforcement.

### 2.3 Решено

- **Обязательный набор — только 3 (Свет/Звук/Запах).** «Тактильное»
  остаётся 4-м дефолтным, но необязательным каналом, как сегодня —
  статус-кво, без изменений в логике удаления/предупреждения.
- **Нормализация каналов-алиасов — отложена.** 3 файла с
  «Зрение»/«Прикосновение» вместо «Свет»/«Тактильное» (§2.1) на этом
  этапе не трогаем. Позже — отдельным шагом собрать перечень допустимых
  названий-переменных канала (канонiчное имя + алиасы: «Свет» ⊇
  «Зрение», «Тактильное» ⊇ «Прикосновение» и т.п.), под который
  подстроится и матчинг обязательности, и, если понадобится,
  миграция/нормализация существующих файлов. Пока что эти 3 локации
  формально считаются не заполнившими «Свет»/«Тактильное» по имени
  канала (см. §2.1) — это принятое временное ограничение, не баг текущего
  этапа.

### 2.4 Ещё открыто

- **UI-only (i) vs backend-валидация (ii)** — §2.2, не выбрано.
- **CLI-паритет.** `tools/new_location.js` сегодня НЕ создаёт секцию
  «Сенсорная палитра» вообще (только упоминание внутри «Атмосферы» как
  подсказка) — расходится с тем, что фактически производит веб-форма.
  Если Свет/Звук/Запах становятся обязательными, шаблон CLI стоит
  привести в соответствие (сразу scaffold-ить 3 обязательных канала с
  ⚠️-плейсхолдерами), иначе локация, созданная через CLI, откроется в
  веб-модалке уже «невалидной» по новому правилу.
- **`balmont/Ценр/metro/metro.md`** (§2.1, поле «Маскарад» вместо
  сенсорики) — вероятно ошибка ручного заполнения, но это чужие данные
  города; не исправляю без подтверждения пользователя.

### 2.5 Затронутые места (при выборе (i), UI-only)

- `web/public/scripts/locations.js`: `_renderSensPanel()` — убрать кнопку
  `data-sens-del` для каналов из фиксированного mandatory-набора; показ
  ⚠️ вместо «Пусто» для них. `_locDeleteSensChannel()` — не требует правки
  по логике (просто кнопка не рендерится для этих трёх), но стоит
  сохранить серверную защиту на всякий случай (не полагаться только на
  скрытие кнопки в UI).
- `web/public/scripts/locations.js`: рендер `cdet-tab-bar` (строка ~458,
  кнопка «Сенсорика») — добавить индикатор незаполненности.
- `tools/new_location.js` — привести шаблон в соответствие (см. открытый
  вопрос про CLI-паритет).
- Миграция (`tools/migrations/`) — только если решаем нормализовать
  каналы-алиасы и/или бэкофилить `podzemnyy_dok` тремя пустыми
  обязательными каналами с ⚠️.

## 3. Форма редактирования локации: «Сенсорная палитра» — из textarea в редактор по каналам

> **Обновление (revision 2):** реализовано в рамках техспеки
> `2026-08-02-city-creation-restructure-techspec.md` §13.1-13.3 (`#loc-edit-sens-rows`
> + «+ Добавить канал», `index.html:1313-1319`; `_locEditSensRowHtml()`/
> `_renderLocEditSensRows()`/`_collectLocEditSensRows()` в `locations.js`).
> Новый запрос (см. §6 ниже) — противоположный: убрать этот раздел из формы
> целиком как дублирующий функционал детальной модалки. Секция ниже
> оставлена как есть — историческая фиксация решения, не текущее состояние.

Проверил код (`web/public/index.html:1304-1306`,
`web/public/scripts/locations.js:892,983,1014,1127`) — в форме
создания/редактирования локации (`openLocEditModal`, не путать с
детальной модалкой просмотра) поле «Сенсорная палитра» сегодня — голый
`<textarea id="loc-edit-sensory">`, куда нужно руками печатать/вставлять
сырой markdown построчно (`| **Свет** | ... |`). Это **другой,
менее удобный путь**, чем уже существующий структурированный редактор по
каналам во вкладке «Сенсорика» ДЕТАЛЬНОЙ модалки просмотра локации
(`_renderSensPanel()`, `locations.js:178-217` — дропдаун/список каналов,
кнопки добавить/редактировать/сгенерировать/удалить на каждый). Два разных
UI для одного и того же поля `sensoryPalette`, разного уровня удобства.

**Запрошено:** заменить `loc-edit-sensory` textarea на такой же по духу
редактор — дропдаун выбора вида сенсорики (тот же набор, что и в
`_renderSensPanel`: Свет/Звук/Запах/Тактильное + «Другое…» свой вариант),
рядом текстовое поле описания, и кнопка «+ Добавить канал» для новой
строки.

**Технический нюанс (важно для реализации, не для решения сейчас):** это
НЕ то же самое, что просто переиспользовать `_renderSensPanel()` как есть
— та живёт в детальной модалке и сохраняет каждый канал СРАЗУ, отдельным
запросом на канал (своя кнопка «Сохранить» на строку). Форма
редактирования локации работает иначе — копит все поля в один payload и
шлёт одним `PUT .../fields` только по нажатию общей кнопки «Сохранить»
формы (`_saveLocEdit`, `locations.js:970-990`). Значит нужен **облегчённый
вариант того же визуального паттерна** (дропдаун+текст, повторяемые
строки, кнопка добавить/удалить — тот же класс компонента, что уже
используют «Властители города»/«Примогенат»/«Отмеченные локации» в форме
города, `.cdet-rel-row`-семейство), который на сборке формы просто
собирает строки обратно в тот же табличный текстовый формат
(`_sensRebuildTable`-подобная логика), а не сохраняет каждый канал
отдельным запросом. Не пытаться сделать один универсальный компонент на
оба контекста (детальная модалка vs форма редактирования) — у них разные
модели сохранения, попытка унификации усложнит оба места без выгоды.

## 4. Вкладка «VtM» детальной модалки локации — из пустого textarea в форму по полям

Проверил код (`web/lib/parsers/location.js:60-70`, `locations.js:358-375`)
— режим ПРОСМОТРА вкладки «VtM» уже показывает 5 структурированных
разделов, распарсенных из таблицы markdown-карточки (`| **Статус** |
значение |` и т.д.): **Статус**, **Фракция**, **Постоянные фигуры**,
**Угрозы**, **Маскарад** — плюс отдельно вольную прозу (`vtmText`), если
она есть. Режим РЕДАКТИРОВАНИЯ той же вкладки (`vtmEditHtml`,
`locations.js:374-375`) даёт только ОДНУ textarea, привязанную к
`vtmText` — все 5 табличных полей там не редактируются вообще. Если у
локации нет отдельной прозы (только заполненная таблица), textarea при
открытии редактирования выглядит пустой, хотя вкладка в режиме просмотра
показывает контент — именно это несоответствие и описал пользователь.

**Запрошено:** добавить 4 перечисленных поля (Статус, Фракция, Постоянные
фигуры, Угрозы) как обычную форму в режиме редактирования этой вкладки,
рядом с уже существующей textarea для прозы.

**Пересечение с §13.6 плана `2026-08-02-city-creation-restructure-spec.md`**
(добавлен ранее в этой же сессии): та задача просила редактируемое поле
«Маскарад» в ФОРМЕ СОЗДАНИЯ/РЕДАКТИРОВАНИЯ локации (`openLocEditModal`) —
выяснилось, что «Маскарад» физически хранится в ТОЙ ЖЕ таблице VtM-
контекста, что и Статус/Фракция/Угрозы здесь. Значит это не два отдельных
куска работы — реализация формы по полям для вкладки «VtM» в детальной
модалке (этот пункт) естественно закрывает и «Маскарад» из §13.6, если
его добавить туда же пятым полем формы (просмотр уже показывает его
пятым в этом списке, `vtmSections`, строка 364). Делать это дважды в двух
разных местах (детальная модалка и форма редактирования) не нужно —
выбрать одно.

**Технический нюанс:** сегодня нет отдельного эндпоинта/ключа для записи
этих табличных VtM-полей — `PUT /api/locations/:slug/fields` умеет только
`vtmText` (сохраняет текст ПРОЗЫ, таблицу сохраняет как есть нетронутой,
`web/routes/locations.js`, обработчик `key === 'vtmText'`) — нужен новый
способ записи, который правит конкретные строки таблицы (`| **Статус**
| ... |` и т.д.) отдельно от прозы, не задевая её.

Разработка не начата.

## 5. Вкладка «Ключевые точки» детальной модалки локации — форма по полям вместо raw-textarea

Проверил код (`locations.js:408-417,498,682-683`; `routes/locations.js:195-201`;
`lib/parsers/location.js:101-112`) — тот же паттерн, что уже описан и решён
в §4 для вкладки «VtM»: режим ПРОСМОТРА вкладки «Ключевые точки» уже
показывает структурированные пары Место/Описание (`.locdet-table`,
`.locdet-row`, из `loc.keyPoints`), но режим РЕДАКТИРОВАНИЯ той же вкладки
— голая `<textarea id="locdet-keys-ta">`, в которую данные подставляются
как сырой pipe-текст (`keyRawTable = kp.map(({place,desc}) => '| ${place} | ${desc} |')`)
и которую нужно руками писать/парсить в markdown-синтаксисе построчно.
Сохранение — `_locSavePanel('keys')` шлёт весь текст textarea как есть в
`fields.keyPoints` (`locations.js:682-683`); бэкенд (`routes/locations.js:195-201`)
кладёт его в карточку без изменений (заменяет тело секции «## 🗺️ Ключевые
точки» целиком); парсинг обратно — построчный `|`-сплит
(`lib/parsers/location.js:101-112`).

**Запрошено:** форма добавления/редактирования по 2 полям — «Место» и
«Описание» — вместо textarea. Естественный образец — уже существующий в
этой же модалке паттерн «Крючки» (`hooksEditHtml`, `locdet-hooks-edit-list`,
кнопка «+ Добавить крючок», `_renumberHooks()`) или структурные редакторы
формы города («Властители города»/«Примогенат», `.cdet-rel-row`-семейство):
повторяемые строки с полями, кнопка добавить, кнопка удалить на строку.

## 6. Форма создания/редактирования локации — убрать раздел «Сенсорная палитра»

**Контекст:** §3 этого документа предлагал заменить голую textarea
`loc-edit-sensory` в форме создания/редактирования локации
(`openLocEditModal`, не путать с детальной модалкой просмотра) на редактор
по каналам — реализовано (см. пометку в начале §3). Раздел
«Сенсорная палитра» сегодня живёт в форме создания/редактирования в виде
`#loc-edit-sens-rows` + кнопки «+ Добавить канал» (`index.html:1313-1319`).

**Новый запрос:** убрать раздел «Сенсорная палитра» из этой формы целиком
— весь функционал добавления/редактирования каналов уже есть в детальной
модалке просмотра локации (вкладка «Сенсорика», `_renderSensPanel()`,
`locations.js:178-217`): там дропдаун канала, текст значения, кнопки

сохранением сразу по клику (не общей кнопкой формы, как в §3/§5). Форма
создания/редактирования дублирует ту же функциональность в облегчённом
виде и без AI-генерации по каналу — два разных UI на одно и то же поле
`sensoryPalette`.

**Вопрос для Аналитика (нужно решение перед реализацией):** убрать раздел
из формы — значит, **на этапе СОЗДАНИЯ** локации сенсорную палитру
задать будет негде: карточка создастся с пустыми

только ПОСЛЕ создания — открыв только что созданную локацию и перейдя на
вкладку «Сенсорика» детальной модалки. Это тот же паттерн, что уже
работает для «Ключевые точки» и VtM-таблицы (§4/§5 — тоже не входят в
форму создания, правятся только после), так что решение стыкуется с уже

настройка — после, в детальной модалке». Фиксирую как решение по

от «Ключевые точки»/VtM, СЕЙЧАС уже имеет форму на этапе создания (§3), а
не «никогда не имело», удаление воспринимается как шаг назад, если не
