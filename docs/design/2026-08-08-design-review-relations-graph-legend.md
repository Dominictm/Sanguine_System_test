## 1. «Старые типы первыми» — обоснование не работает на практике, порядок стоит поменять на алфавитный

Техспека (§2.1) сортирует легенду: сначала ключи из хардкодного `REL_LABELS`, потом всё
остальное — с комментарием «стабильный, привычный порядок». Проверил это предположение на
реальных слагах: `slugify()` (Фаза 1) даёт для всех 11 сид-записей библиотеки совершенно другие
строки, чем старые ключи классификатора — `Сир→sir` (не `sire`), `Чайлд→chayld` (не `childe`),
`Фамильяр→familyar` (не `familiar`, другая транслитерация), `Союзник→soyuznik` (не `ally`),
`Враг→vrag` (не `enemy`), `Семья→semya` (не `family`), `Тайная связь→taynaya_svyaz` (не
`secret`) — ни один слаг библиотеки не совпадает буквально со старым хардкодным ключом. Значит,
как только связь совпадает с «Постоянной связью» (а это теперь основной, поощряемый путь — пикер
из библиотеки, не сомодельный ввод), её тип **всегда** попадает во «новую» часть списка, а
«старая» часть на практике почти всегда пустая (заполняется только для легаси-связей без матча —
случай, который со временем становится реже, не чаще). То есть «привычный порядок», который
обещает комментарий, не привычен и не наблюдаем — легенда на деле почти всегда сортируется как
попало (порядок появления в `data.links`).

**Рекомендация**: сортировать по алфавиту отображаемого лейбла (`m.label`/`REL_LABELS[k]`), а не
по принадлежности к старому хардкодному набору — это единственный порядок, который у растущего,
пополняемого пользователем набора типов действительно остаётся стабильным и предсказуемым для
глаза, независимо от того, легаси тип или из библиотеки:
```js
const keys = [...present].sort((a, b) => {
  const la = meta.get(a)?.label || REL_LABELS[a] || a;
  const lb = meta.get(b)?.label || REL_LABELS[b] || b;
  return la.localeCompare(lb, 'ru');
});
```

## 2. Граф кеширует данные между заходами — не увидит новый тип без ручной перезагрузки

Ключевая находка живой проверки Фазы 3 этой же серии — `STATE.characters` не обновлялся при
обычной навигации, потому что `loadCharacters()` пропускает повторный запрос, если массив уже не
пуст — была найдена и исправлена именно потому, что иначе фича «работает, но не видно». У графа
**та же самая конструкция**, отдельным флагом: `loadGraph()` (`graph.js:74-76`) —
`if (STATE.graph.inited) return;` — и в проекте уже есть устоявшийся паттерн её сброса: минимум
четыре места (`log-session.js:233,329`, `scripts.js:1606,1630,2411,2762`) сознательно делают
`STATE.graph.inited = false` после действий, меняющих данные графа (логирование сессии, удаление
персонажа и т.п.), чтобы следующий заход на «Граф» гарантированно перечитал свежие данные. Ни
сохранение связей персонажа (`char-detail.js`), ни создание новой «Постоянной связи»
(`relations-manage.js`) этого не делают.

Практическое следствие для ЭТОЙ техспеки конкретно: Рассказчик открывает «Граф» (кеш
инициализируется), переходит на карточку персонажа, добавляет связь с новым типом «Гуль» — по
логике техспеки должен появиться новый чип в легенде и цвет на ребре — возвращается на «Граф» **в
той же сессии, без перезагрузки страницы** — и не видит изменений вообще, пока не нажмёт
«Сбросить» (который, по счастью, тоже не форсирует новый fetch — `applyGraphFilters` работает по
уже загруженным данным) или не перезагрузит страницу целиком. Вся ценность техспеки — «новый тип
виден на графе» — временно не реализуется в самом типичном сценарии использования (открыть граф,
уйти редактировать персонажа, вернуться посмотреть).

**Рекомендация**: там, где сегодня уже меняются данные, влияющие на связи/тип (сохранение
«Отношений» персонажа — `char-detail.js`, панель `rels`; создание/переименование/удаление записи
в `relations-manage.js`), добавить `STATE.graph.inited = false;` — тот же однострочный паттерн,
что уже используется в перечисленных местах. Не входит в объём серверной части техспеки (§1), но
обязательная часть §2 (клиент) — без неё три клиентских фикса технически корректны, но не
понаблюдаемы без обходного пути (перезагрузка страницы).

## Итог — что поправить в техспеке перед реализацией

Пункт 1 — переставить один блок сортировки, косметика. Пункт 2 — важнее: без него вся техспека
остаётся «тихо работающей», не видимой пользователю в естественном сценарии использования, хотя
формально каждая строка кода в §1-§2 будет работать правильно при следующей полной перезагрузке
страницы. Рекомендую внести оба пункта в техспеку до передачи Разработчику, не оставлять на
усмотрение реализации.
