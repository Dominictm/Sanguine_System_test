# Техспека: вкладки редактирования города + районы-спойлеры + переименование полей локации

**Дата:** 2026-08-05 · **Роль:** Системный аналитик

Четыре связанных изменения из одного запроса. Не независимые куски — Часть II
использует уже существующий, но сейчас «спрятанный» в старой форме
редактирования код (`_cityDistrictsEditEditorHtml`/`_districtCardHtml`), а
Часть III/IV трогают одну и ту же пару полей карточки локации с разных
сторон (город → локация, локация → город).

Уточнено с постановщиком (три вопроса, все — рекомендованный вариант):

1. Старая форма-полотно `_renderCityEdit()` (общая кнопка «Редактировать»,
   один длинный список полей без вкладок) — **убирается полностью**, не
   остаётся запасным входом.
2. «Удалить Локацию в форме района» / «удаление района из карточки
   локации» — это **открепление** (локация переезжает в общий район
   «Другие», как уже делает создание без указанного района), не полное
   удаление самой локации.
3. Строка «Привязать» внутри карточки района — без изменений в механике,
   просто теперь скрыта до раскрытия спойлера.

## Находка, важная для Части III/IV — уже есть незакрытый разрыв в данных

Сравнил формат карточки (`_locCardTemplate`, `web/routes/locations.js:20`) с
реальным файлом `cities/paris/locations/antrepo/gar_dyu_nor/gar_dyu_nor.md`:
`**Округ:** 10-й` (свободный текст) при факте, что папка лежит в
`locations/antrepo/…`, а `**Район:** Антрепо` (совпадает с папкой). То есть
поле `district` (подпись «Округ» в карточке) физически **не обязано**
совпадать с фактическим расположением папки — это уже разошедшиеся данные
до этой задачи (комментарий в коде, `web/routes/locations.js:273-275`,
прямо ссылается на прошлую миграцию «округ→район», которая, похоже, не
дочистила текст самих карточек).

Более серьёзная находка — **действующий баг, не просто устаревшая
терминология**: инлайн-правка поля `district` в детальной карточке
локации (`locations.js:750-753`, панель `meta`) сегодня уходит через
`PUT /api/locations/:slug/fields` — это **только текст**, папка не
переезжает. Единственное место, где смена района физически двигает папку —
`PUT /api/locations/:slug/district` (специальный эндпоинт,
`web/routes/locations.js:276`), который сегодня вызывается только со
страницы просмотра города (`_attachLocationToDistrict`, `city.js:1131`), не
из самой карточки локации. Значит, поле «Район» (после переименования)
**обязано** при сохранении в карточке локации идти через
`PUT /district`, а не через общий `PUT /fields` — иначе выбор нового района
из списка будет чисто косметическим и запись снова разойдётся с папкой,
теми же граблями, что уже наступили один раз.

## Часть I · Вкладки просмотра города — своя кнопка редактирования на вкладку

**Образец в проекте, 1:1** — `char-detail.js`: каждая панель персонажа
(`bio`/`rels`/`desc`) имеет собственную кнопку `.cdet-edit-btn[data-editpanel]`,
переключающую `#cdet-<panel>-view`/`#cdet-<panel>-edit`/`#cdet-<panel>-bar`
через общие `_togglePanelEdit(panel, on)`/`_savePanelEdit(panel, charSlug)`
(`char-detail.js:464-491`). Для города — тот же паттерн, свои функции
(`_cityToggleTabEdit(tab, on)`/`_saveCityTabEdit(tab)`), т.к. поля другие и
PUT-эндпоинт другой (`/api/cities/:slug`, не `/api/characters/:slug/…`).

**Важно: не все содержимое вкладок попадает под этот тумблер.** «Районы» и
«Значимые места» на вкладке «География» уже (Значимые места) или должны
стать (Районы, Часть II) отдельными всегда-интерактивными блоками со
своим собственным сохранением по записи — ровно как «Дневники» персонажа
не участвуют в `_togglePanelEdit`, а имеют свой CRUD. Кнопка «Редактировать»
вкладки «География» переключает только оставшиеся текстовые поля
(«Ключевые локации», «Охотничьи угодья»).

### Разметка (замена в `_renderCityView()`, `city.js:1088-1128`)

Убрать общую кнопку `data-city-edit`/`_renderCityEdit()`-переход
(`city.js:1115`, `1389`). Каждая `.city-view-panel` получает в начале свою
`<button class="cdet-edit-btn" data-city-tab-edit="<tab>">✏ Редактировать</button>`
и разметку `-view`/`-edit`/`-bar`, как у персонажа:

| Вкладка | view-контейнер | edit-контейнер | Поля внутри edit |
|---|---|---|---|
| `general` | текущий вывод `_cityViewGeneralHtml` | новый `_cityGeneralEditHtml(sec)` | Сеттинг/Законы домена/Календарь/Технологии и Маскарад/4 поля «Голос и стиль»/спойлер «Правила и ограничения» (mortals/limits/naming) — те же textarea, что сегодня в `_renderCityEdit()`, просто перенесённые |
| `political` | `_cityViewPoliticalHtml` | `_cityPolEditorHtml(sec)` — **уже существует** (`city.js:293`), просто монтируется не в старую форму, а в панель `political` |
| `factions` | `_cityViewFactionsHtml` | `_cityFactionsEditorHtml(sec)` — **уже существует** (`city.js:663`) |
| `geography` (частично) | `_cityViewFieldHtml('Ключевые локации', …)` + `_cityViewFieldHtml('Охотничьи угодья', …)` | `_cityLocEditorHtml(sec)` (Ключевые локации, **уже существует**, `city.js:335`) + textarea для `hunting` (по образцу остальных простых полей) |

`_cityGeneralEditHtml` — единственная реально НОВАЯ функция разметки в этой
части; всё остальное — существующий код `_renderCityEdit()`
(`city.js:1183-1254`), который сейчас собирается в одну форму через
`CITY_SECTION_DEFS`-цикл, а должен просто вызываться по отдельности внутри
своей `-edit`-панели.

### Сохранение — свой PUT на вкладку, backend уже поддерживает частичные fields

`_saveCityTabEdit(tab)` — аналог `_savePanelEdit`, но целится в
`PUT /api/cities/:slug`. Бэкенд **уже** игнорирует ключи, не пришедшие в
`fields` (комментарий `city.js:1520`: «Ключ, не пришедший в fields, PUT
/api/cities не трогает») — новых серверных изменений не требуется, только
собрать на каждой вкладке свой подмножество полей:

```js
async function _saveCityTabEdit(tab) {
  const editRoot = document.querySelector(`[data-city-view-pane="${tab}"]`);
  let fields;
  if (tab === 'general') {
    fields = {
      description: editRoot.querySelector('[data-city-field="description"]').value.trim(),
      edicts: editRoot.querySelector('[data-city-field="edicts"]').value.trim(),
      calendar: editRoot.querySelector('[data-city-field="calendar"]').value.trim(),
      tech: editRoot.querySelector('[data-city-field="tech"]').value.trim(),
      leitmotif: editRoot.querySelector('[data-city-field="leitmotif"]').value.trim(),
      specifics: editRoot.querySelector('[data-city-field="specifics"]').value.trim(),
      avoid: editRoot.querySelector('[data-city-field="avoid"]').value.trim(),
      sources: editRoot.querySelector('[data-city-field="sources"]').value.trim(),
      mortals: editRoot.querySelector('[data-city-field="mortals"]').value.trim(),
      limits: editRoot.querySelector('[data-city-field="limits"]').value.trim(),
      naming: editRoot.querySelector('[data-city-field="naming"]').value.trim(),
    };
    // «Название»/«Год» — не в fields.<section>, а в display/year (H1/подпись),
    // отдельная пара ключей верхнего уровня в PUT-контракте, как и сегодня
    // в _saveCityEdit (city.js:1513) — если вкладка «Общая» тоже должна их
    // редактировать, эти два поля дублируются сюда же с ключами display/year
    // ВНЕ fields (см. текущий payload.fields vs payload.display в _saveCityEdit).
  } else if (tab === 'political') {
    fields = { political: _collectPoliticalRows(editRoot) }; // уже существует
  } else if (tab === 'factions') {
    fields = { factions: _collectFactions(editRoot) }; // уже существует
  } else if (tab === 'geography') {
    fields = { locations: _collectLocationRows(editRoot), hunting: editRoot.querySelector('[data-city-field="hunting"]').value.trim() };
  }
  // … disabled/⏳/PUT/showToast — тот же паттерн, что _savePanelEdit; по успеху
  // обновить _cityDetail.parsed локально и вернуть панель в view-режим, БЕЗ
  // полного _renderCityView() (не терять раскрытые спойлеры Районов/Значимых
  // мест в других частях той же вкладки «География» — тот же принцип, по
  // которому Значимые места уже не дёргают loadCityPage(), см. вчерашний цикл).
}
```

**Открытый нюанс, на который стоит обратить внимание при реализации:**
поле «Название» (H1 города) и «Год» сегодня в `_renderCityEdit()` лежат ВНЕ
цикла `CITY_SECTION_DEFS`, отдельными `data-city-field="display"/"year"`
(`city.js:1226-1232`), и уходят в `payload.display`/`payload.year`, а не в
`payload.fields`. Раз в новой раскладке «Название»/«Год» видны только на
вкладке «Общая» (`_cityViewGeneralHtml`, `city.js:882-888`) — они логично
переезжают в edit-режим именно этой вкладки, с тем же особым путём в PUT
(верхнеуровневые ключи, не `fields.*`).

`_pendingNewLocations` (новые локации, вводимые прямо в списке «Ключевые
локации» — `city.js:728`) — логика создания карточек после успешного PUT
(`_saveCityEdit`, `city.js:1541-1560`) переезжает в `_saveCityTabEdit('geography')`
без изменений по сути, только вызывается из другого места.

## Часть III · Переименование полей карточки локации + миграция

**Схема сегодня** (несовпадение подписи в карточке ⇄ подписи в форме — то,
что и просил поправить постановщик):

| Ключ | Подпись в карточке (`.md`) | Подпись в форме создания/правки (`loc-edit-*`) | Подпись в детальной карточке (`locations.js:352-353`) |

| `district` | **Округ** | Район | Округ |

**Становится:**

| Ключ | Новая подпись везде |
|---|---|
| `district` | **Район** |
| `neighborhood` | **Дополнение к адресу** |

5. **`web/public/scripts/locations.js`**

     `['district', 'Округ', …]` → `['district', 'Район', …]`,

### Миграция — `tools/migrations/005_location_district_label_rename.js`

Контентная миграция (см. `tools/migrations/README.md`), идемпотентная,
единственная замена по обеим подписям за один проход (не два
последовательных `.replace()` — иначе `**Округ:**`→`**Район:**`, а затем
`**Район:**`→`**Дополнение к адресу:**` тем же проходом задвоило бы
переименование заново переименованных полей):

```js
module.exports = {
  description: 'Переименование полей карточки локации: Округ→Район, Район→Дополнение к адресу',
  test(text)    { return /\*\*(Округ|Район):\*\*/.test(text); },
  migrate(text) {
    return text.replace(/\*\*(Округ|Район):\*\*/g,
      (_, label) => label === 'Округ' ? '**Район:**' : '**Дополнение к адресу:**');
  },
};
```

Проверено: паттерн `**Округ:**`/`**Район:**` встречается в репозитории
только внутри инлайн-метаданных карточек локаций (grep по `cities/` —
только в файлах `locations/**/*.md`, ни разу в `city.md`/персонажах/
хрониках) — миграция безопасна для всего дерева `cities/<город>/**/*.md`
(стандартный обход раннера), точечно бить только по `locations/` не
требуется.

### card_schema.md / документация

`system/schema/card_schema.md` не документирует эти два поля явно
(проверено, точечных упоминаний нет) — правок не требует.
`docs/guide.md` (§10 «Локации», строка ~362: «Район: автозаполнение из
структуры папок») — свериться и поправить подпись при финальной вычитке
документации в конце цикла.

## Часть IV · Поле «Район» в форме локации — выбор из существующих + открепление

Из находки в начале документа: **сохранение поля `district` из карточки
локации обязано идти через `PUT /api/locations/:slug/district`**, не
через общий `PUT /fields` — иначе выбор перестаёт быть структурным
действием и превращается в косметическую правку текста, расходящуюся с
реальной папкой (тот самый уже случившийся баг).

### Датаlist уже есть, детальной карточке его не хватает

`loc-district-list` (`index.html`) + `_populateDistrictDatalist`
(`locations.js:1013-1032`, дёргает `GET /api/cities/:slug/districts`) —
уже работает в модалке СОЗДАНИЯ/общего редактирования (`loc-edit-modal`).
Детальная карточка локации (`locdet-meta-district`, инлайн-редактор поля в
`metaEditHtml`, `locations.js:361-365`) сейчас — голый `<input>` без
датаlist. Правка: `metaEditHtml` для ключа `district` рендерит тот же
`<input list="loc-district-list">` (id датаlist общий на страницу, как
сегодня использует создание — новых датаlist не заводим), с кнопкой
очистки рядом (`✕`, аналог хедера K1-модалки библиотеки) — очистка не
шлёт пустую строку в `PUT /district` (эндпоинт её отклоняет, 400 «Укажи
район») — очистка **подставляет** значение `Другие` и отправляет его
явно, тот же приём, что и открепление из Части II.

### Сохранение панели `meta` — развилка по ключу `district`

`_saveLocPanel`/аналог (`locations.js:750-753`, логика сбора полей панели
`meta`) — вынести `district` из общего цикла `for (const key of
['subtype', 'district', 'neighborhood', 'address', 'control'])` в отдельную
ветку:

```js
} else if (panel === 'meta') {
  for (const key of ['subtype', 'neighborhood', 'address', 'control']) {
    const el = document.getElementById(`locdet-meta-${key}`);
    if (el) fields[key] = el.value;
  }
  // district — НЕ в fields (общий PUT /fields только про текст, не про
  // папку) — отдельный PUT /district ниже, тем же путём, что уже
  // проверен _attachLocationToDistrict/дет-обработчик Части II.
}
```

а сохранение панели `meta` целиком становится двухшаговым: если поле
`district` изменилось относительно исходного значения — сначала
`PUT /api/locations/:slug/district` (с подтверждением, физический
перенос — та же формулировка диалога, что у привязки/открепления в Части
II), и только затем (или параллельно) обычный `PUT /fields` с остальными
четырьмя полями панели. Если `district` не менялся — вторым запросом
можно вообще не ходить, обычный `PUT /fields` покрывает остальное как
сегодня.

### Итог по Части IV

- Выбор из существующих районов — датаlist, уже готовый источник данных
  (`GET /districts`), не хватает только подключить его ко ВТОРОМУ месту
  (детальная карточка), не изобретать заново.
- Открепление — переиспользует то же решение, что Часть II (`district:
  'Другие'` через `PUT /district`), просто из другого места UI (сама
  карточка локации, не карточка района) — симметрия, о которой просил
  постановщик («так же удаление района из карточки локации»).

## Порядок выполнения

Части не равноправны по риску и по тому, что от чего переиспользует код —
оптимальный порядок **III → II → IV → I**, не по номерам документа:

1. **Часть III (переименование полей + миграция) — первой.** Полностью
   изолирована от `city.js` (только `locations.js`/парсер/CLI/схема),
   ничего не ломает по пути, и все остальные части либо ссылаются на
   переименованное поле «Район» (Часть IV), либо не зависят от него вовсе
   (I, II) — логичнее один раз сразу назвать поле правильно, чем сначала
   строить на «Округ», а через два шага переименовывать написанное.
   Отдельная причина ставить именно первой: миграция формата — та вещь,
   которую полезнее всего проверить в изоляции (round-trip, идемпотентность
   повторного прогона) до того, как на этом поле начнёт стоять новый UI.

2. **Часть II (Районы → спойлер спойлеров) — второй.** Не зависит от
   Части I (трогает `_cityViewDistrictsHtml`, отдельную функцию от
   `_renderCityEdit`, который убирает Часть I) — можно сделать раньше без
   конфликтов. Важнее другое: здесь появляется `_detachLocationFromDistrict`
   (открепление со стороны района) — Часть IV делает **симметричную**
   операцию со стороны карточки локации и логично переиспользовать один
   и тот же паттерн/PUT-вызов, а не изобретать его дважды параллельно.
   Побочный эффект такого порядка: старая форма редактирования (ещё не
   убрана Частью I) и новые интерактивные карточки района временно
   сосуществуют как два способа править район — избыточно, но не
   ломает — пока не выполнена Часть I.

3. **Часть IV (выбор района + открепление из карточки локации) —
   третьей.** Зависит от Части III (целится в уже переименованное поле —
   иначе датаlist/лейблы пришлось бы трогать дважды) и переиспользует
   паттерн подтверждения/PUT из Части II.

4. **Часть I (вкладки редактирования города, снос старой формы) —
   последней.** Самое инвазивное изменение (удаляет `_renderCityEdit`/
   `_saveCityEdit` целиком, ~150+ строк, переписывает диспетчеризацию
   кликов) — и единственное, для которого важно, чтобы вкладка
   «География» уже была в финальном виде: Района/Значимые места как
   отдельные всегда-интерактивные блоки (Часть II уже сделана), а не то,
   что «Редактировать» вкладки заново придётся выковыривать из-под
   капота. Итог: за один этот шаг исчезает старый способ редактирования
   ЦЕЛИКОМ и на его месте сразу оказывается финальная картина, без
   промежуточных состояний внутри самой Части I.

Каждая часть — самостоятельно тестируемый и коммитируемый шаг (`npm run
test:all` + живая проверка после каждой, не только в конце всех четырёх) —
порядок III→II→IV→I даёт удобные точки остановки, если реализацию нужно
будет прервать между частями.
