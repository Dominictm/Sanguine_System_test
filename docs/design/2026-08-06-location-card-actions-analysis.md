# Данные для техспеки: карточка локации — бейджи + удаление

**Собрано:** Аналитик, 2026-08-06. **Передаётся:** Системному аналитику на техспеку.

**Подтверждено пользователем:** при удалении локации, на которую ссылаются
модули (§3.3) — тихий cascade-unlink (вариант 2): сервер сам находит все
модули со ссылкой на удаляемый slug и убирает его из их списка привязанных
локаций, без отдельного UI-выбора у пользователя.

**Подтверждено пользователем (§4, первая итерация — см. ниже §7, ОТМЕНЕНО
второй итерацией):** поле «Зона» в форме создания/редактирования полностью
заменяется на список фракций города.

## 7. Вторая итерация (пересмотр §4-6) — VTM-вкладка как «полноценная страница»

Пользователь предложил альтернативное решение взамен §4-6 (переиспользовать
уже существующие поля VTM-вкладки локации вместо новых сущностей/полей и
вместо переделки «Зоны»). **Это решение принято и заменяет §4, §5, §6
целиком** — они оставлены в документе для истории решения (видно, что
рассматривалось и почему отклонено), но не описывают финальный план.

### 7.1 Ключевая находка — на «Географии» города уже есть sync-механизм на локацию

На вкладке «География» города уже реализован блок «Отмеченные локации»
(`_cityLocEditorHtml`, `city.js:304-330`, рендерится внутри
`data-city-view-tab="geography"`, `city.js:1140,1185`) — привязка конкретной
существующей (или новой) локации к одному из 5 статусов
(`CITY_LOCATION_TYPES`, `city.js:83`: Элизиум / Приёмная князя / Убежище /
Шериф / Сенешаль). При сохранении города это уже **синкается на карточку
локации автоматически** — `syncSignificantPlaceStatus()`
(`web/routes/cities.js:307-364`, вызывается из `PUT /api/cities/:slug`):

```js
const SIGNIFICANT_PLACE_TYPES = {
  'Элизиум':        { field: 'zone',    mdKey: 'Зона',     value: '🏛️ Элизиум' },
  'Приёмная князя':  { field: 'control', mdKey: 'Контроль', value: '[Город] Приёмная князя' },
  'Убежище':         { field: 'control', mdKey: 'Контроль', value: '[Город] Убежище' },
  'Шериф':           { field: 'control', mdKey: 'Контроль', value: '[Город] Шериф' },
  'Сенешаль':        { field: 'control', mdKey: 'Контроль', value: '[Город] Сенешаль' },
};
```

То есть ровно то, о чём говорит пользователь («на вкладке География мы
присваиваем статус выбранной локации») — уже работает, только пишет
результат в «Зона»/«Контроль» (метаданные), а не в «Статус» вкладки VTM,
хотя семантически это один и тот же смысл под двумя разными именами —
исторически «Статус» на VTM-вкладке и «статус» из «Отмеченных локаций» на
Географии никогда не были связаны, отсюда и путаница, которую пользователь
предлагает устранить.

**Подтверждено пользователем:** переключить `syncSignificantPlaceStatus()` на
запись в `loc.locStatus` (md-лейбл «Статус», VTM-вкладка) вместо
«Зона»/«Контроль». `SIGNIFICANT_PLACE_TYPES` меняется на единый `field: 'locStatus', mdKey: 'Статус'`
для всех 5 типов (единообразно — раньше Элизиум был особым случаем из-за
привязки к `zoneClass()`, что и создавало путаницу). Формат значения (маркер
`[Город] <Тип>[ — заметка]`, сброс по `startsWith`, диф по имени локации,
`_significantPlaceValue()`) — не меняется, меняется только поле-получатель.

**Подтверждено пользователем: «Зону» отдельно не трогаем** — п.4 в прежней
формулировке (замена «Зона» на список фракций) отменяется. `zoneClass()`,
4 цветных бейджа, фильтр «Все зоны» остаются как есть, без изменений. Задача
«выбрать фракцию для локации» полностью закрывается через поле «Фракция»
(см. §7.2) — «Зона» и «Фракция» перестают конкурировать за одну и ту же
задачу, у каждой свой смысл: «Зона» — фиксированная типология (осталась
прежней), «Фракция» — свободный выбор из реальных фракций города.

### 7.2 Поле «Фракция» (VTM-вкладка) — выбор из фракций города

Сейчас `loc.faction` (`vtmEditHtml`, `locations.js:410-413`) — обычный
`<input>` без даталиста/select, без связи с фракциями города. Меняется на
`<input list="...">`/`<select>`, источник — тот же список фракций города,
что уже используется для дропдауна «Влияние — Фракции» района
(`_currentFactionNames()`, `city.js:435-440`, после C1 включает секты +
независимые кланы + «Другие»/«Фракции смертных»/«Государственные») —
**этот же источник**, не `/api/factions` (тот, что сейчас питает соседнее
поле «Контроль» на вкладке «Метаданные», см. ниже §7.5 про дублирование
смысла с «Контроль»).

Технически нужен эндпоинт/маршрут, отдающий список фракций текущего города
клиенту ВНЕ контекста уже открытой формы редактирования города (сейчас
`_currentFactionNames()` читает DOM формы города, которая не смонтирована на
странице локаций) — например, лёгкий `GET /api/cities/:slug/factions`,
парсящий `sec.factions`/`factionsMortal`/`factionsState` из `city.md` тем же
способом, что и `_currentFactionNames()`, но на бэкенде. **Открытый вопрос
для техспеки** — заводить ли новый эндпоинт или переиспользовать имеющийся
`/api/factions` (другой формат данных — таблица «политического ландшафта»,
не секция «Фракции» city.md, см. §4 выше, где это уже отмечено как
расхождение) — эту развилку явно решает Системный аналитик, не Аналитик.

### 7.3 Поле «Опасность» — добавить в VTM-вкладку

Сейчас `dangerLevel` — `<select id="loc-edit-danger">` только в отдельной
форме создания/редактирования (`index.html:1286-1293`), НЕ в
`vtmEditHtml`/`vtmSections` детальной модалки просмотра. Добавить туда же
`<select>` по образцу уже существующего в этой же вкладке для «Маскарад»
(`VTM_MASQ_OPTS`/`locdet-vtm-masquerade`, `locations.js:402-404,424-426`) —
симметрично, 3 уровня + пусто, `🟢/🟡/🔴`. С этой правкой вкладка VTM
собирает всё «политическое лицо» локации в одном месте: Статус (из города,
§7.1) + Фракция (выбор, §7.2) + Опасность (новое) + Постоянные фигуры +
Угрозы + Маскарад — то, что пользователь и назвал «полноценной страницей».

### 7.4 Чекбокс «Частный домен» — переключает «Фракция» ↔ «Хозяин»

То же решение, что в прежнем п.6, но БЕЗ нового поля — переключает
СУЩЕСТВУЮЩЕЕ поле «Фракция»:
- новое булево md-поле `- **Частный домен:** да` (та же конвенция, что уже
  использована для `- **Негативный:** да` в карточках Титулов) —
  `loc.privateDomain = /^да$/i.test(metaField('Частный домен') || '')`;
- чекбокс рядом с полем «Фракция» на VTM-вкладке (и в форме создания);
- при включении — лейбл поля меняется «Фракция» → «Хозяин», источник
  автодополнения — `STATE.characters`, отфильтрованный по линейке `vampire`
  (то же обоснование, что в прежнем п.6.3 — личный/частный домен, вампирское
  понятие);
- значение хранится в том же md-поле «Фракция» (`loc.faction`) — при
  `privateDomain: true` там имя персонажа, при `false` — название фракции;
  парсер не различает, различение — на уровне UI (что показывать как список
  автодополнения) и подписи поля;
- при переключении чекбокса — очищать текущее значение поля (та же
  рекомендация, что в прежнем п.6.2 — избежать хранения фракции там, где
  теперь концептуально ожидается персонаж, и наоборот).

### 7.5 Побочный эффект — пересекается ли «Фракция» со старым полем «Контроль»?

**Замечено, не решаю сам.** После §7.2 поле «Фракция» (VTM) и поле
«Контроль» (Метаданные, `loc.control`, «кто фактически контролирует
локацию», сейчас datalist из `/api/factions`) становятся семантически ОЧЕНЬ
похожи — оба, по сути, «какая фракция здесь главная», просто с разным
источником списка и на разных вкладках. Раньше (до этой задачи) у «Контроль»
не было альтернативы, поэтому дублирования не было. Три варианта на
усмотрение Системного аналитика/пользователя:
1. Оставить оба поля как есть — «Контроль» описывает более широкое понятие
   (может быть НЕ вампирская фракция — мэрия/полиция/т.п., как и раньше),
   «Фракция» на VTM теперь конкретно про политику сородичей — разные по
   охвату, сосуществование оправдано.
2. Унифицировать источник данных «Контроль» на тот же список фракций города
   (§7.2), раз он уже заводится для «Фракция» — минимум лишней работы,
   раз даталист всё равно перестраивается.
3. Считать «Контроль» устаревшим полем, оставить только «Фракция» — самый
   радикальный вариант, требует миграции существующих значений `loc.control`
   и правки формы (убрать поле) — вне минимального объёма этой задачи, не
   рекомендую делать сейчас без отдельного запроса.

Рекомендация Аналитика — вариант 1 (ничего не трогать в «Контроль») как
самый низкий риск для этой задачи; вариант 2 — разумный follow-up, если
захочется убрать расхождение данных `/api/factions` vs `city.md`-секция
«Фракции» одним махом, но это отдельное решение, не часть текущего запроса.

## 8. Просмотр «Ключевые локации» (География) — таблица вместо текстового блока

**Задача:** сейчас «Ключевые локации» в РЕЖИМЕ ПРОСМОТРА (не редактирования)
— один нечленимый текстовый блок. Хотим таблицу «Статус локации — Название
локации — Заметки» для структурных записей, а под ней отдельным блоком —
свободный текст «Общее описание ключевых локаций города».

### 8.1 Текущее состояние — расхождение между edit и view

Данные хранятся ОДНОЙ md-секцией `sec.locations`, где вперемешку живут
свободный текст (нарратив) и структурные строки вида `Тип: Название — Заметка`
— разбор на два потока уже есть и уже используется, просто только в РЕЖИМЕ
РЕДАКТИРОВАНИЯ:
- `_splitCitySectionRecords(sec.locations, _LOC_LABELS)` (`city.js:106-111`)
  — делит на `narrative` (свободные строки) и `recordLines` (строки вида
  `Тип: Название`, где `Тип` — одно из 5 значений `CITY_LOCATION_TYPES`).
- `_parseLocationLines(recordLines)` (`city.js:132-145`) — превращает
  `recordLines` в объекты `{type, name, note}` (третье поле, заметка,
  отделено тире « — », см. комментарий `city.js:129-131`).
- `_cityLocEditorHtml(sec)` (`city.js:304-330`) уже рисует их РАЗДЕЛЬНО как
  два блока формы: «Ключевые локации» (`narrative`, textarea,
  `data-city-field="locations-narrative"`, идёт ПЕРВЫМ) и «Отмеченные
  локации» (структурные строки-редакторы, идут ВТОРЫМ, `_locRowHtml` на
  каждую запись — уже включает выбор «Название локации» из уже существующих
  локаций через `<datalist>`, `city.js:241`, то есть требование «выбирается
  из списка существующих» технически уже выполнено в редактировании,
  осталось только в просмотре).

А вот РЕЖИМ ПРОСМОТРА (`_cityViewGeographyHtml`, `city.js:1143-1150`) не
делает этого разбора вообще — рендерит `sec.locations` целиком одним куском
через общий `_cityViewFieldHtml('Ключевые локации', sec.locations)`
(`city.js:848-854`, markdown → HTML как есть, без структуры). Это и есть то,
что пользователь называет «просто текстовое поле».

### 8.2 Готовый прецедент для структурной части

В этой же кодовой базе уже есть ТОЧНО такой же по духу переход
«отредактированные структурные записи → read-only отображение» —
`_cityViewPoliticalHtml(sec)` (`city.js:966-983`, вкладка «Политика»,
«Властители города»/«Примогенат»): парсит те же `recordLines` тем же
`_splitCitySectionRecords`, рендерит записи через `.locdet-table`/
`_cityViewRecordRow(key, val)` (`city.js:958-960`) — **но это готовая
2-колоночная сетка** (`.locdet-row { grid-template-columns: 160px 1fr }`,
`styles.css:6266-6268`) — под запрошенные пользователем **три** колонки
(Статус / Название / Заметки) не подходит без изменений, нужен новый
компонент.

### 8.3 Что сделать

1. **Новая функция `_cityViewLocationsHtml(sec)`** (по образцу
   `_cityViewPoliticalHtml`) — парсит `sec.locations` тем же
   `_splitCitySectionRecords`/`_parseLocationLines`, что уже используется
   в редакторе (round-trip не ломается, это тот же формат данных, меняется
   только КАК его рисуем в просмотре).
2. **Таблица записей** — новый CSS-класс (3 колонки: Статус локации /
   Название локации / Заметки), т.к. `.locdet-row` — фиксированный 2-колоночный
   грид, не переиспользуется напрямую. Пустой список — `<div class="cdet-empty">Нет
   отмеченных локаций</div>` (тот же принцип, что везде в этом файле view-рендеров
   секции города — не показывать пустую таблицу без объяснения).
3. **Опционально, но напрашивается**: ячейка «Название локации» — кликабельная
   ссылка на карточку локации, если запись резолвится в реально существующую
   (`_cityEditLocs`/`getAllLocations` уже дают список названий — можно
   проверить совпадение и открывать `#loc-detail-modal` по клику, аналогично
   тому, как уже кликабельны карточки локаций в сетке `/locations`). **Не
   обязательно для MVP** — сама задача не просила интерактивности, только
   визуальную таблицу; отмечаю как естественное расширение, решает Дизайнер/
   Системный аналитик, включать ли сразу.
4. **«Общее описание ключевых локаций города»** — отдельный блок ПОД
   таблицей, через уже существующий `_cityViewFieldHtml(...)`, но с НОВЫМ
   заголовком («Общее описание ключевых локаций города» вместо текущего
   «Ключевые локации» — старое имя явно переезжает на таблицу, значит для
   нарратива нужен новый, более точный заголовок, иначе после появления
   таблицы у пользователя будет два блока с одинаковым названием «Ключевые
   локации» на экране одновременно).
5. **Точка подключения** — `_cityViewGeographyHtml` (`city.js:1147-1149`):
   заменить `_cityViewFieldHtml('Ключевые локации', sec.locations)` на
   `_cityViewLocationsHtml(sec)`.
6. **Edit-режим — привести порядок и подпись в соответствие с view** (иначе
   после правки view будет противоречить редактированию тем же данным):
   в `_cityLocEditorHtml` (`city.js:311-324`) поменять местами блоки —
   «Отмеченные локации» (структурные строки) ПЕРВЫМ, «Ключевые локации»
   (нарратив) ВТОРЫМ, и переименовать лейбл нарратива в «Общее описание
   ключевых локаций города» (тот же текст, что в п.4) — `data-city-field`
   (`locations-narrative`) не меняется, меняется только видимый `<label>`
   и визуальный порядок блоков.

**Риск:** низкий — переиспользует уже существующий парсинг (не трогает
формат хранения/round-trip), новизна только в разметке read-only таблицы
(1 новый CSS-компонент) и порядке/подписях уже существующих блоков
редактора. Полностью самостоятельная задача, не зависит от §1-§7.

## 1. Не показывать «Зона контроля» на карточке

**Текущее состояние:** `_locCardHtml()` (`web/public/scripts/locations.js:115-143`)
рендерит `<div class="loc-badges">${zoneBadge}${masqBadge}</div>` — `zoneBadge`
берётся из поля `Зона` md-документа (`ZONE_CLASS_LABELS`, значения вроде
«🏛️ Элизиум» / «🟣 Носферату» / «🔴 Опасная» — это и есть то, что в UI
подписано «Зона контроля», см. `locdet-legend-lbl` в детальной модалке,
`locations.js:516`). Помимо бейджа на карточке, у безартовых карточек (нет
`imageUrl`) слева ещё показан крупный значок `${ZONE_CLASS_LABELS[zc][0]}`
(первый символ метки — тот же самый источник, `locations.js:139`).

**Уточнение важное для техспеки:** «Зона контроля» — это НЕ поле `Контроль`
(`loc.control`, «кто фактически контролирует локацию» — то, что показано в
метаданных модалки, `locations.js:355`). Это поле `Зона` (`loc.zone`,
«тип локации по принадлежности» — Элизиум/Носферату/Нейтральная/Опасная).
Именно `loc.zone` и есть источник «Зоны контроля» в существующей UI-подписи.
Задача — убрать его с КАРТОЧКИ (сетка + панель модуля), детальную модалку
(`locdet-legend-row`, где есть подпись «Зона контроля» явным текстом) задача
не упоминает — трогать её не просили.

**Что сделать:** убрать `zoneBadge` из `.loc-badges` в `_locCardHtml()`.
Отдельный вопрос — безартовая карточка без изображения (`locations.js:138-142`)
сейчас показывает крупный значок зоны СЛЕВА от текста как замену обложки
(`<span class="loc-zone-icon">`) — это не бейдж «Зона контроля» в буквальном
смысле пользовательского запроса (он не подписан, просто визуальный якорь
взамен фото), но использует тот же источник данных. **Открытый вопрос**:
трогать ли `.loc-zone-icon` (замена картинки-обложки для локаций без арта)
или оставить — по буквальной формулировке запроса («не отображать значение
«Зона контроля»») это, скорее, про сам бейдж с подписью, не про
плейсхолдер-обложку. Рекомендация Аналитика: оставить `.loc-zone-icon` как
есть (он не подписан текстом «Зона контроля», решает другую задачу — визуально
идентифицировать безартовую карточку), убрать только `zoneBadge`.

## 2. Показывать «Уровень опасности» и «Маскарад» в сокращённом виде

**Текущее состояние:** оба поля УЖЕ существуют и парсятся
(`loc.dangerLevel`/`loc.masqueradeLevel`, `web/lib/parsers/location.js:40,91-92`)
и уже полностью реализованы в ПОЛНОМ виде — но только в детальной модалке
(`locdet-legend-row`, `locations.js:519-526`: подпись «Уровень опасности» /
«Маскарад» текстом + бейдж с полным текстом типа «⚔️ Высокий»). Компактная
карточка (`_locCardHtml`) сейчас показывает только `masqBadge` (тоже с полным
текстом «🎭 Высокий») и НЕ показывает `dangerBadge` вообще — переменная
`dLvl`/`DANGER_BADGE_LABELS` в `_locCardHtml` не используется, только в
детальной модалке.

**Что значит «в сокращённом виде — только значок и фон с окантовкой
соответствующего цвета»:** CSS-классы `.badge-danger-low/medium/high` и
`.badge-masq-low/medium/high` (`styles.css:5850-5886`) УЖЕ реализуют цветную
заливку+рамку по уровню (зелёный/золотой/красный) — компактный вид не требует
новых цветов, только **убрать текст из содержимого бейджа**, оставив только
эмодзи-иконку (`⚔️`/`🎭`), при этом сам класс `badge-danger-${dLvl}`/
`badge-masq-${mLvl}` (и его фон+рамка) остаётся — значит достаточно рендерить
`<span class="badge badge-danger-${dLvl}">⚔️</span>` вместо
`${DANGER_BADGE_LABELS[dLvl]}` (который включает и иконку, и слово).

**Что сделать:**
1. В `_locCardHtml()` добавить `dangerBadge` (сейчас отсутствует полностью)
   — компактный вариант, `dLvl !== 'unknown'` (та же защита, что в детальной
   модалке — не показывать бейдж, если поле не заполнено).
2. `masqBadge` в `_locCardHtml()` — заменить полный текст на компактную
   иконку (сейчас показывает «🎭 Высокий» целиком, надо оставить только «🎭»).
3. **Открытый вопрос для техспеки**: два одноцветных круглых бейджа без
   подписи рядом («⚔️» и «🎭», у обоих может быть, например, одинаковый
   золотой цвет при уровне «средний») визуально неотличимы ПО СМЫСЛУ друг от
   друга без текста — только иконка внутри отличает «это про опасность» от
   «это про маскарад» (комментарий в коде уже фиксирует именно эту проблему
   для другого бейджа, `locations.js:16-18` — «без иконки-оси два «Высокий»
   неотличимы друг от друга» — та же логика применима и здесь, но теперь для
   ДВУХ бейджей без подписи вместо одного). Иконки разные (⚔️ vs 🎭), поэтому
   технически различимо, но стоит решить порядок/группировку бейджей на
   карточке (danger + masq рядом или раздельно) и — не будет ли третий
   маленький бесподписный кружок рядом перегружать компактную карточку
   визуальным шумом. Дизайнеру стоит проверить на реальных карточках, не
   Аналитику решать этот эстетический вопрос.
4. Точка подключения та же — `.loc-badges` в `_locCardHtml()`, плюс тот же
   рендер нужен и в «Связанных локациях» модуля, т.к. `_locCardHtml()` —
   общая функция для обеих поверхностей (`locations.js:112-114`, комментарий
   явно это фиксирует) — правка в одном месте покрывает обе.

## 3. Удаление локации — иконка на карточке + в модалке, с подтверждением

### 3.1 Бэкенд и confirm-логика — уже полностью реализованы

Это ключевая находка: **удаление локации уже есть end-to-end**, просто не
выведено на два запрошенных места. Существующий контур:
- `DELETE /api/locations/:slug` (`web/routes/locations.js:479-496`) —
  soft-delete, папка переезжает в `locations/_deleted/<slug>_<timestamp>/`,
  обратимо (по аналогии с персонажами/городами).
- `deleteLocCurrent()` (`web/public/scripts/locations.js:1209-1239`) —
  ПЕРЕД подтверждением делает `GET /api/locations/:slug/backlinks` (сканирует
  ВСЕ md-файлы города на предмет ссылок на путь этой локации — см. §3.3) и
  вставляет предупреждение о найденных обратных ссылках прямо в текст
  confirm-диалога; сам confirm — `showConfirm(..., { danger: true })`
  (единый компонент подтверждения проекта, не самодельный `confirm()`).
- Кнопка `#loc-edit-delete-btn` (`index.html:1351`, `🗑 Удалить») уже существует
  и уже подключена (`locations.js:1333`) — но **только внутри отдельной формы
  редактирования/генерации локации** (`#loc-edit-modal`, судя по
  `document.getElementById('loc-edit-delete-btn')`), не в компактной карточке
  и не в детальной модалке просмотра. `style="display:none"` по умолчанию —
  видимо, скрыта в режиме СОЗДАНИЯ новой локации, показывается только в
  режиме редактирования существующей (**проверить точную логику видимости
  при реализации** — `locations.js:1014`, `delBtn` — вне зоны, прочитанной в
  этом анализе).

**Вывод: задача — не «реализовать функционал удаления» с нуля (он есть), а
добавить ДВЕ ДОПОЛНИТЕЛЬНЫЕ точки входа** к уже существующей логике:
1. Значок 🗑 прямо на компактной карточке (`.loc-card`).
2. Значок 🗑 в детальной модалке `#loc-detail-modal`, рядом с кнопкой
   «✏ Редактировать / Генерация» (`locations.js:513`, `#locdet-open-edit-modal`).

### 3.2 Техническая проблема, которую нужно решить в техспеке

`deleteLocCurrent()` читает slug из **модуль-уровневой переменной**
`_locEditSlug` (устанавливается при открытии формы `#loc-edit-modal»), а не
принимает slug параметром. Вызов из карточки/детальной модалки — не через
эту форму — значит либо:
(а) функцию параметризовать (`deleteLoc(slug)`, `_locEditSlug` как
дефолт-фоллбэк для обратной совместимости с существующим вызовом), либо
(б) перед вызовом принудительно выставлять `_locEditSlug = slug` из нового
обработчика клика по иконке — грязнее, полагается на побочный эффект.
**Рекомендация Аналитика: (а)** — параметризовать, это чище и не создаёт
скрытой зависимости от состояния формы, которая физически не будет открыта
при клике по иконке на карточке.

Также после удаления функция делает `closeLocEditModal()` +
`closeModal('loc-detail-modal')` — при вызове с карточки НИ ОДНА из этих
модалок не будет открыта, эти вызовы безвредны (закрытие уже закрытого
модала — no-op в существующем `closeModal`, **проверить при реализации**,
не предположение этого документа).

### 3.3 «Учесть взаимосвязи с районами, фракциями и элементами из раздела Панель»

Проверено по каждому из трёх:

**Район** — не требует cascade-логики. Локация физически лежит ВНУТРИ папки
района на файловой системе (`cities/<город>/locations/district_NN/<район>/<локация>/`,
`web/lib/parsers/district.js:5-6`) — район не хранит отдельный список
slug'ов локаций, принадлежность чисто структурная (по расположению папки).
Soft-delete локации (перенос ЕЁ ОДНОЙ папки в `_deleted/`) автоматически
убирает её из списка локаций района без каких-либо дополнительных правок —
район как сущность вообще не в курсе, что за локации у него внутри, кроме
как через обход файловой системы.

**Фракции** — тоже не требует cascade-логики, но по другой причине: поля
`Контроль`/`Фракция` (`loc.control`/`loc.faction`) — это **свободный текст
НА САМОЙ локации**, ссылающийся на имя фракции города. Обратной связи
«фракция → список своих локаций» нигде не хранится (фракции города —
`system/library/...` нет, это просто чипы/текст в `city.md`, см. недавнюю
техспеку `2026-08-06-char-loc-city-fields-techspec.md` C1) — удаление
локации не оставляет висячих ссылок ни в одну сторону.

**Раздел «Панель»** — **единственное место, где реально есть cascade-риск**.
«Панель» — это модуль-страница (`modp-*` префикс классов/id, `Панель» —
общий заголовок вкладки Dashboard тоже, но там локации по slug не
хранятся — проверено, `loadDashboard()`/`scripts.js:367+` не ссылается на
конкретные локации, только агрегированная статистика). Внутри карточки
МОДУЛЯ есть секция «ЛОКАЦИИ» (`_renderModuleLocPanel`, `modules.js:1776`,
`.modp-loc-cards`) — список локаций, **явно привязанных к модулю по slug**
(`_parseModuleLocSlugs(mainRaw)` читает список из самого файла модуля,
`web/routes/modules/locations.js:24-39`). Фронтенд уже подстраховывается
от отсутствующей локации (`allLocs.find(l => l.slug === s) || { slug: s }`,
`modules/locations.js:36` — не крашится), но рисует пустую карточку-заглушку
(без названия/района/бейджей — только slug) там, где раньше была нормальная
карточка локации. **Это реальный, не гипотетический, дефект UX после
удаления**, если ничего не делать сверх статус-кво.

Соответствующий unlink-эндпоинт уже существует: `DELETE
/api/chronicles/:chr/modules/:mod/locations/:locSlug`
(`web/routes/modules/locations.js:64-84`) — убирает slug из списка модуля.

**Открытый вопрос для техспеки (главный в этом документе):** что делать с
модулями, ссылающимися на удаляемую локацию — три варианта:
1. **Статус-кво** — полагаться на уже существующий `backlinks`-предикат
   (`GET /api/locations/:slug/backlinks`, сканирует ВСЕ md-файлы города,
   включая модули, т.к. они хранят ссылки как markdown-пути) — он уже
   покажет пользователю в confirm-диалоге, что «на эту локацию ссылаются
   файлы: chronicles/.../modules/.../module.md», пользователь решает сам,
   удалять ли. Минимум работы, но заглушка-карточка в модуле останется
   висеть после удаления (source of truth — сам modXXX.md, где slug
   физически не убирается).
2. **Автоматический cascade-unlink** — при успешном `DELETE /api/locations/:slug`
   сервер сам находит все модули, ссылающиеся на этот slug через
   `_parseModuleLocSlugs`, и вызывает эквивалент unlink-логики для каждого
   (нужен обход `chronicles/*/modules/*/*.md` по городу — не готовая функция
   сейчас, но `backlinks`-сканер уже даёт список путей, можно отфильтровать
   на `*.md`, совпадающие с шаблоном модуля, и переиспользовать
   `_parseModuleLocSlugs`/`_writeModuleLocSlugs` из `modules/shared.js`).
3. **Confirm с чекбоксом** — тот же список из backlinks, но с явным выбором
   «удалить и отвязать от N модулей» / «удалить, оставить ссылки как есть» —
   компромисс между 1 и 2, самый явный для пользователя, но больше UI-работы.

Рекомендация Аналитика: **вариант 2** (тихий cascade-unlink), т.к.
soft-delete уже обратим (папка не удаляется физически, а переезжает в
`_deleted/`) — если пользователь передумает, локацию можно вернуть, но
восстановить связь с модулем придётся вручную в любом случае (slug убрали
из module.md) — то есть риск варианта 2 симметричен риску текущего
поведения персонажей/городов при soft-delete (там тоже никто не
восстанавливает обратные ссылки автоматически при возврате из `_deleted/`,
это уже принятый в проекте компромисс). Финальное решение — за пользователем,
не решаю сам, т.к. меняет объём работы Разработчика ощутимо (вариант 1 —
без правок бэкенда сверх экспонирования кнопки, вариант 2/3 — новый код).

## 4. Форма создания/редактирования — поле «Зона» из фракций города

**Текущее состояние:** `#loc-edit-zone` (`index.html:1276-1283`) — жёстко
закодированный `<select>` с 4 опциями (Элизиум/Носферату/Нейтральная/Опасная),
без источника данных — не даталист, не факт из API, просто статичный HTML.
Значение поля (`loc.zone`) — вход для `zoneClass()` (`locations.js:31-39`),
которая матчит текст ПОДСТРОКОЙ на строго определённые русские слова
(«элизиум», «носферату», «нейтральн», «опасн»/«шабаш») и определяет:
- цвет/тип бейджа на карточке (`badge-loc-elysium/nosferatu/neutral/danger/other`,
  `styles.css:5819-5848`) — не только «Зона контроля» из п.1 (которую убираем
  с карточки), но и `.loc-zone-icon` — крупный значок-заглушка для карточек
  БЕЗ изображения (`locations.js:139`), который решили оставить в п.1;
- значения фильтра «Все зоны» на странице «Локации» (`#loc-filter-zone`,
  `index.html:696-703` — свой отдельный жёсткий список из 5 опций
  `elysium/nosferatu/neutral/danger/other`, задействован в `renderLocations()`,
  `locations.js:85`).

**Подтверждено пользователем:** заменить `#loc-edit-zone` полностью на
список фракций города (не гибрид «старые 4 + фракции»). Значит:

1. **Опции `<select id="loc-edit-zone">`** — заполняются динамически из
   фракций текущего города, тем же источником, что уже подготовлен для
   дропдауна «Влияние — Фракции» района (`_currentFactionNames()`,
   `city.js:435-440`, после доработки C1 включает секты + независимые кланы
   + «Другие»/«Фракции смертных»/«Государственные») — **не** тем источником,
   что сейчас использует соседнее поле «Контроль» этой же формы
   (`_loadFactionsList()`, `locations.js:1095-1110`, парсит `/api/factions` —
   ДРУГОЙ, более старый источник: таблица «политического ландшафта», не
   секция «Фракции» city.md). **Открытый вопрос для техспеки**: в проекте
   сейчас фактически ДВА параллельных понятия «список фракций города» с
   разными источниками (`/api/factions` для «Контроль» vs. `sec.factions`
   city.md для «Влияние — Фракции» района) — стоит ли на этой задаче унифицировать
   оба под один источник (`sec.factions` + новые `factionsMortal`/`factionsState`
   из C1, раз он уже становится образцовым для «Зоны») или оставить «Контроль»
   как есть, заведя для «Зоны» третий похожий, но отдельный загрузчик. Системному
   аналитику стоит явно решить — иначе в кодовой базе будет три похожих,
   но разных списка «фракций города» (`/api/factions`, `sec.factions` C1,
   и «Зона» здесь).
2. **`zoneClass()` теряет смысл в текущем виде** — подстрочное угадывание по
   русским словам не сработает ни для одной реальной фракции («Камарилья»,
   «Ассамиты», «Инконню» не матчат ни один из 4 паттернов) → все локации
   попадут в `'other'`, бейдж-заглушка и `.loc-zone-icon` станут одинаковыми
   у всех локаций города независимо от того, чья это территория —
   **фактическая потеря функциональности**, если ничего не менять сверх
   замены `<select>`. Нужно новое решение для окраски — варианты (решает
   Системный аналитик/Дизайнер, не Аналитик):
   - окраска не по конкретной фракции (их в городе может быть 5-10, у
     каждой свой цвет — дорого поддерживать палитру), а по ГРУППЕ (секта /
     независимый клан / «другое») — переиспользовать существующие 3
     класса чипов из C1 (`.cdet-faction-chip`, там уже есть смысловое деление);
   - вообще убрать цветовое кодирование по «Зоне» и оставить один нейтральный
     бейдж/иконку с текстом названия фракции (просто, но менее выразительно
     на сетке карточек);
   - оставить `.loc-zone-icon`/бейдж без цвета вовсе — только текст фракции.
3. **Фильтр `#loc-filter-zone`** — та же проблема, список из 5 опций
   (`elysium/nosferatu/neutral/danger/other`) должен стать динамическим по
   фракциям города (тот же источник, что и `<select>` формы) — иначе фильтр
   после этой правки будет фильтровать по категориям, которых больше не
   существует в данных.
4. **Миграция не нужна** технически (поле `zone` как текстовое остаётся,
   просто теперь туда пишется название фракции вместо «🏛️ Элизиум» и т.п.) —
   но у существующих локаций старые значения («🏛️ Элизиум», «🟣 Носферату» и
   т.д.) физически останутся в md-файлах и не будут матчить ни одну опцию
   нового `<select>` при следующем редактировании (`<select>` без
   соответствующего `<option>` просто откроется на пустом/дефолтном значении,
   не потеряет данные при простом просмотре, но при сохранении формы без
   явного повторного выбора — фактически обнулит поле). Стоит решить, нужен
   ли явный проброс старого текста как «текущее, не входит в список» опции
   (по аналогии с `_districtSectOptionsHtml`, `city.js:343-353`, которая уже
   умеет сохранять «осиротевшее» текущее значение отдельной опцией) —
   рекомендация Аналитика: да, тот же паттерн, не терять данные молча.

## 5. Новое поле «Влияние сородичей» (клан) — ⚠️ ОТМЕНЕНО, см. §7.2/§7.4

> Заменено второй итерацией (§7) — вместо нового поля переиспользуется уже
> существующее «Фракция» на VTM-вкладке. Раздел оставлен для истории решения.

**Задача:** добавить в модальное окно детального просмотра (режим
редактирования) и в форму создания/редактирования локации новое поле —
указывается клан.

**Текущее состояние:** такого поля нет ни на бэкенде (`web/lib/parsers/location.js`
не парсит ничего подобного), ни на фронтенде. Ближайшие по смыслу существующие
поля — «Контроль» (`loc.control`, свободный текст, кто ФАКТИЧЕСКИ контролирует
территорию — может быть не вампирская фракция вовсе, полиция/мэрия/etc.) и
секция VtM-контекста «Фракция» (`loc.faction`, `vtmSections`,
`locations.js:385` — тоже общий свободный текст). «Влияние сородичей» — уже
специально ПРО вампирский клан, точечнее обоих существующих полей.

**Что сделать:**
1. Новое md-поле, например `- **Влияние сородичей:** <клан>` — парсер
   (`location.js`) добавляет `loc.kindredInfluence = metaField('Влияние сородичей')`
   по образцу соседних полей (`zone`/`dangerLevel`, `location.js:39-40`).
2. Место в форме (`index.html`, `#loc-edit-modal`) — логично рядом с
   «Контроль» (`loc-edit-row2` с «Зона»/«Опасность» уже занят, но можно
   завести новую пару-строку «Контроль» + «Влияние сородичей», раз оба
   про «кто здесь главный», просто с разной степенью специфичности).
3. Место в детальной модалке просмотра — та же вкладка «Метаданные»
   (`metaFields`, `locations.js:350-356`) или вкладка «VtM» (`vtmSections`,
   `locations.js:383-421`) — **открытый вопрос для техспеки/дизайнера**:
   поле явно вампирское по смыслу (клан), значит по духу ближе к «VtM»
   вкладке (где уже «Фракция»/«Постоянные фигуры»/«Угрозы»/«Маскарад»), а не
   к нейтральным «Метаданным» (Название/Район/Адрес/Контроль). Рекомендация
   Аналитика: вкладка «VtM», рядом с «Фракция».
4. **Источник значений для выбора клана**: даталист из `/api/library/clans`
   (уже есть, уже используется как образец в техспеке `2026-08-06-char-loc-city-fields-techspec.md`
   §A3.1 для аналогичного поля «Клан» персонажа) — переиспользовать тот же
   паттерн `<input list="loc-clans-list">` + `<datalist>`, заполняемый при
   открытии формы.

## 6. Чекбокс «Личный домен» — переключает клан ↔ персонаж — ⚠️ ОТМЕНЕНО, см. §7.4

> Заменено второй итерацией (§7.4) — та же идея, но чекбокс называется
> «Частный домен» и переключает существующее поле «Фракция», а не новое
> поле §5. Раздел оставлен для истории решения.

**Задача:** чекбокс «Личный домен»; при активации поле «Влияние сородичей»
выбирает не клан, а персонажа.

**Что сделать:**
1. Новое булево md-поле, например `- **Личный домен:** да` (та же конвенция
   присутствия/значения «да», что уже используется в этой сессии для
   `- **Негативный:** да` в карточках Титулов, `web/lib/titles.js`) —
   парсер: `loc.personalDomain = /^да$/i.test(metaField('Личный домен') || '')`.
2. Чекбокс в форме (`#loc-edit-modal`) — рядом с полем «Влияние сородичей»
   (сразу под ним или сбоку) — при клике переключает:
   - источник `<datalist>` у поля «Влияние сородичей»: клановый список
     (§5.4) ↔ список персонажей;
   - `placeholder` инпута: «Клан» ↔ «Персонаж»;
   - **вопрос, не решаю сам**: очищать ли текущее значение поля при
     переключении чекбокса (если там уже было название клана, а
     пользователь включил «Личный домен» — оставшийся текст семантически
     невалиден до нового выбора) — рекомендация Аналитика: очищать, во
     избежание сохранения клана в поле, которое теперь концептуально
     хранит персонажа (или наоборот).
3. **Источник списка персонажей**: `STATE.characters` (уже загружаемый
   глобальный реестр персонажей города, `scripts.js:610` и другие точки
   загрузки) — **отфильтрованный по линейке `vampire`** (личный домен —
   вампирское понятие; рекомендация Аналитика, не строгое требование —
   если у Рассказчика в практике бывают личные домены не-вампиров, стоит
   переспросить, но по умолчанию сужаю список до вампиров, чтобы не путать
   смертных/фей в даталисте, где семантически ожидается вампир-владелец).
4. **Хранение значения** — то же поле `- **Влияние сородичей:**`, что и в
   §5 (не заводить два раздельных поля «клан» и «персонаж» — раз чекбокс
   явно указывает, как это значение читать, отдельное поле избыточно):
   при `personalDomain: true` строка хранит имя персонажа, при `false` —
   название клана. Парсер это не различает (просто текст), различение —
   только на уровне UI (какой даталист показывать) и, при необходимости,
   рендера в детальной модалке (можно опционально сделать значение
   кликабельной ссылкой на карточку персонажа, если `personalDomain` —
   **опция для техспеки, не обязательна для MVP**).
