## Дефект №1 (средняя/высокая severity): «Авторские связи» показывают описание УЖЕ типизированных связей, позволяя превратить фрагмент прозы в «Постоянную связь»

### Причина
`_authoredDescriptions()` (`web/public/scripts/relations-manage.js:56-72`) была написана в Фазе
1 — **до** того, как Фаза 2 разделила поле «Вид отношений» на структурный `relType` и свободное
`description`. Логика функции не изменилась при выходе Фазы 2: она по-прежнему берёт `r.description`
у **любой** связи, независимо от того, есть ли у неё уже `relType`, и предлагает превратить его в
новую «Постоянную связь», если текст не совпадает буквально с именем существующей.

До Фазы 2 это было корректно — поле было одно, весь текст либо совпадал с постоянной связью,
либо был кандидатом на неё. После Фазы 2 семантика поля `description` изменилась — это
**необязательное развёрнутое описание** к уже выбранному типу («доверенное лицо, помогает в
делах» при типе «Союзник»), не альтернативный/несформированный тип. Функция этого не учитывает.

### Воспроизведение
1. Создать персонажа A, связь на персонажа Б: тип «Союзник» (из пикера), описание «общее дело».
2. Открыть граф → 📚 «Управление связями».
3. Колонка «Авторские связи» показывает «общее дело» с кнопкой «Сделать постоянной» — как будто
   это нераспознанный тип, хотя связь **уже** структурно типизирована как «Союзник».
4. Нажать «Сделать постоянной» — запрос проходит успешно (`POST /api/library/relation-types`
   не проверяет осмысленность имени), создаёт новую каноническую «Постоянную связь» с именем
   `«общее дело»` и случайным цветом — полноценную запись библиотеки, неотличимую от осмысленно
   заведённых пользователем типов, кроме содержания.

Подтверждено вживую (headless Chrome) — `pollutedByTypedDesc: true`; отдельно подтверждено
через прямой вызов API, что `POST` создающий такую запись действительно завершается `ok:true` (не
блокируется по существу, только по формальной slug-валидации).

### Практическое влияние
Модалка «Постоянные связи» — общий, растущий, пополняемый пользователем справочник (Фаза 1) —
рискует со временем накопить записи-обрывки прозы вместо коротких типов-ярлыков, как только
пользователь начнёт активно пользоваться разделённым полем (Фаза 2/3), для которого модалка
изначально не переработана. Чем больше в городе типизированных связей с непустым описанием, тем
больше таких ложных «кандидатов» в «Авторских связях» — колонка быстро теряет практическую
ценность (найти реально нераспознанную формулировку среди прозы становится сложнее).

### Рекомендация
`_authoredDescriptions()` — пропускать связи, у которых уже есть `relType` (непустой), не только
пустое `description`:
```js
for (const c of (STATE.characters || [])) {
  for (const r of (c.relationships || [])) {
    if (r.relType) continue; // уже типизирована — description здесь не кандидат в тип (Фаза 2)
    const desc = (r.description || '').trim();
    ...
```
Однострочная правка, не меняет остальную логику функции (сортировка/дедупликация/поиск).

## Что проверено дополнительно и работает корректно

Все сценарии — через прямые вызовы `PUT /api/characters/:slug/relations`, где это быстрее и
точнее браузерного клика (серверная логика синхронизации не завязана на UI):

- **Авто-пара Домитор↔Гуль** — ни разу не проверялась ни автотестами (Фаза 3 покрыла только
  Сир↔Чайлд и Брат/Сестра), ни живьём отдельно от Сир↔Чайлд. Проверено: `A —
  ↔[Домитор] …` → Б получает `relType: 'Гуль', mutual: true` корректно.
- **Каскадное удаление ВСЕЙ строки** (не только снятие чекбокса «Взаимно» при сохранённом
  тексте — ранее покрытый тестами сценарий) — очистка `lines: []` целиком корректно убирает
  зеркальную запись у цели, не оставляя висячих записей.
- **Смена цели у взаимной связи** (тип «Домитор» с персонажа Б переставлен на персонажа В, тем
  же сохранением) — зеркальная запись у Б корректно удаляется, у В — корректно создаётся; ранее
  не тестировалось (тесты Фазы 3 меняли только флаг взаимности, не саму цель).
- **Несколько целей в одной строке + взаимность** (`Б, В — ↔ [Союзник] …`) — обе цели корректно
  получают свою зеркальную запись; ранее не тестировалось (многоцелевые строки и взаимность
  проверялись только по отдельности).
