# План адаптивной вёрстки под разные форматы экрана — Sanguine System

Дата: 2026-08-10
Автор: аудит по `DESIGN.md`/`PRODUCT.md` (impeccable, register `product`, команда `adapt`)
Скоуп: `web/public/index.html`, `web/public/styles.css` (13 426 строк), `web/public/scripts/*.js` (18 модулей)

## Вердикт

Фундамент уже на месте: `viewport` задан правильно (`index.html:5`), карточные сетки в
основном на `auto-fill/auto-fit + minmax()` (не хардкод колонок), тач-таргеты на
`@media (pointer: coarse)` систематически подняты до 44px (20+ мест), модалки уже
кэпаются через `min(px, vw)`, а не фиксированный px. Это не проект, где адаптив
«не начинали» — это проект, где адаптив **делали по месту, без единой схемы
брейкпоинтов**, и несколько компонентов выпали из процесса целиком (0 медиа-правил,
не «недоделано», а не тронуто вообще). Ниже — конкретные пробелы с приоритетом, не
переизобретение системы с нуля.

**Важно для регистра `product`** (`reference/product.md`): «Responsive behavior is
structural (collapse sidebar, responsive table, breakpoint-driven columns), not fluid
typography.» Это ровно то, что уже делает проект (breakpoint-driven, не fluid-first) —
план ниже усиливает этот подход, а не заменяет его на `clamp()`-везде.

## 1. Текущее состояние (факты)

- **Viewport**: `<meta name="viewport" content="width=device-width, initial-scale=1.0">`
  (`index.html:5`) + `color-scheme: dark` (`index.html:6`) — корректно.
- **Брейкпоинты в styles.css** (россыпь, без именованной схемы):
  `699` (`chars-belonging-tabs` паддинг), `700` (сайдбар → icon-rail),
  `720` (V20-лист grid → 1 колонка), `820` (детальные модалки: картинка сверху текста),
  `900` (session-grid → 1 колонка), `960` (общее сжатие паддингов/форм),
  `1099` (`chars-belonging-tabs` паддинг, шаг 2). Семь разных чисел на семь ситуаций —
  работает, но без документированной схемы каждое новое место рискует придумать
  восьмое своё число.
- **Навигация**: `#sidebar` — постоянный flex-child (не off-canvas/drawer), ширина
  `--sidebar-w: 210px` (`styles.css:108`), схлопывается в icon-rail 52px ниже 700px
  (`styles.css:2759-2779`) + есть ручной toggle-коллапс. Полного скрытия (hamburger)
  нет — это осознанный паттерн, допустимый для `product`-регистра
  (`reference/product.md`: «Standard navigation patterns: top bar + side nav»
  разрешены), не дефект сам по себе.
- **Модалки**: один общий `.modal-overlay`/`.modal-box` (`styles.css:2972`, `2993`,
  `width: min(560px, 95vw)`, паддинг `40px 44px`) + 3 именованных размера
  (`.modal-detail` `min(1600px,96vw)`, `.modal-loc-detail` `min(1300px,96vw)`,
  `.modal-module-detail` `min(900px,96vw)`). Внутренний стек (картинка/текст) ломается
  в колонку только на 820px (`styles.css:13179`).
- **Таблицы**: нет ни одного `<table>` — вся плотная табличная информация сделана на
  CSS Grid-строках. Основной риск — `.v20-combat-row`
  (`styles.css:11279-11284`, `grid-template-columns: 2fr 1fr 1fr 1fr 1fr 1fr 1fr`,
  **`min-width: 540px` без media-переопределения**) — гарантированный горизонтальный
  скролл на любом экране уже, а не адаптация.
- **Фиксированные `repeat(3, ...)` без брейкпоинта**:
  `.lineage-picker` (`styles.css:3048`), `.audio-lib-columns`
  (`styles.css:10614`, `repeat(3, minmax(0,1fr))`) — обе сетки не переопределены ни
  одним `@media`.
- **Типографика**: 480 использований токенов `--fs-*` (система соблюдается почти
  везде) против 14 «сырых» `px`-заголовков без какого-либо переопределения:
  `styles.css:1787` (44px), `2150` (36px), `3079` (30px), `3246` (80px), `5951` (30px),
  `6362` (32px), `6412` (72px), `6952` (26px), `11648` (28px), `12938` (32px).
  `clamp()` использован **один раз за весь файл** (`styles.css:3516`).
- **Тач-таргеты**: `@media (pointer: coarse)` — 20+ блоков, паттерн единообразный
  (`min-height`/`width`+`height` → ровно 44px), качество хорошее, менять не нужно.
- **Container queries**: не используются нигде (0 `@container`) — не проблема сейчас,
  но отмечено для раздела 5.

## 2. Приоритет P0 — ломает целевые экраны, не просто «не оптимально»

### 2.1 `.v20-combat-row` — горизонтальный скролл боевой таблицы V20-листа
`styles.css:11279-11284`. `min-width: 540px` на 7-колоночной grid-строке без единой
media-адаптации. V20-лист — самый плотный и часто используемый экран (боевые статы
персонажа), и именно он ломается первым на телефоне/узком планшете-портрете.

**План:** ниже ~700px переключить `.v20-combat-row` на паттерн
«таблица → карточки» (`grid-template-columns: 1fr`, каждая ячейка получает
`data-label`/псевдоэлемент с подписью поля, как рекомендует `reference/adapt.md`,
раздел Layout Adaptation Patterns → Tables). Не горизонтальный скролл-костыль —
GM должен читать боевые статы одним взглядом, не листая вбок в бою.

### 2.2 `.audio-lib-columns` — фиксированные 3 колонки без брейкпоинта
`styles.css:10614`. `repeat(3, minmax(0,1fr))` — на телефоне это 3 колонки шириной
~100px каждая, нечитаемо. Нет ни одного `@media`, переопределяющего эту сетку.

**План:** `@media (max-width: 700px) { .audio-lib-columns { grid-template-columns: 1fr; } }`,
возможно 2 колонки в диапазоне 700–960px (по аналогии с существующим `960`-tier).

### 2.3 `.lineage-picker` — то же самое, третья фиксированная сетка без адаптации
`styles.css:3048`. Тот же дефект, что 2.2, компонент выбора линейки (вампир/фэйри/
смертный/…) при создании персонажа — экран, которым пользуются часто.

**План:** тот же паттерн — 1 колонка ≤700px, опционально 2 в tablet-диапазоне.

### 2.4 Паддинг модалок на самых узких телефонах — требует проверки
`.modal-box` (`styles.css:2993-3000`): `width: min(560px, 95vw)`, паддинг
`40px 44px` **фиксирован на всех ширинах**. На 320–375px (iPhone SE и похожие)
`95vw` ≈ 304–356px, минус 88px горизонтального паддинга — на контент остаётся
~220–270px. Аудит не нашёл media-правила, уменьшающего этот паддинг на узких экранах.

**План:** добавить `@media (max-width: 480px) { .modal-box { padding: 24px 20px; } }`
(и аналогично для трёх именованных вариантов, если у них свой паддинг) — проверить
воочию на 320px перед тем как считать закрытым.

## 3. Приоритет P1 — структурная непоследовательность, видно на планшете

### 3.1 Нет именованной схемы брейкпоинтов
Семь разных чисел (699/700/720/820/900/960/1099) появились по одному на компонент,
без записанного стандарта. Content-driven брейкпоинты — это правильный подход
(`reference/adapt.md`: «Don't chase device sizes; let content tell you where to
break»), но без документации каждый следующий компонент будет придумывать восьмое
число вместо переиспользования одного из существующих семи.

**План:** не менять существующие рабочие точки (они уже calibrated по контенту), а
задокументировать их как **три именованных tier'а** в комментарии наверху
`styles.css` (или в `DESIGN.md`, раздел Layout):
- **phone** (≤ 699px) — сайдбар в icon-rail, все grid → 1 колонка, таблицы → карточки.
- **tablet** (700–1023px) — 2-колоночные гибриды, plotted breakpoints 720/820/900/960
  живут в этой полосе.
- **desktop** (≥ 1024px) — полные сетки, сайдбар развёрнут.
Новые компоненты сверяются с этой шкалой вместо изобретения нового числа; исключение
допустимо только когда контент реально ломается в другой точке (тогда это тоже
content-driven, просто задокументированное).

### 3.2 `.v20-header`/`.v20-grid3` — 3-колоночная сетка держится до 720px
`styles.css:9724`, `9768`, схлопывается в 1 колонку только на 720px
(`styles.css:11241`). На типичном tablet-портрете (768px, iPad) это уже выше порога —
сетка остаётся 3-колоночной. Стоит проверить на реальном iPad-портрете: возможно
нужен промежуточный 2-колоночный tier в диапазоне 720–1023px, а не сразу 1↔3.

**План:** добавить `@media (min-width: 721px) and (max-width: 1023px)` с
`grid-template-columns: repeat(2, 1fr)` для `.v20-grid3`, если визуальная проверка
на 768px подтвердит проблему.

### 3.3 10 «сырых» px-заголовков без адаптации
Список в разделе 1 (`1787/2150/3079/3246/5951/6362/6412/6952/11648/12938`).
Крупные из них (72px `6412`, 80px `3246`) — кандидаты на переполнение в узкой
карточке/панели на телефоне. Это **не** сигнал «добавить `clamp()` везде» — по
`reference/product.md` для `product`-регистра это правильно, что заголовки на
фиксированном `rem`/`px`, а не fluid. Сигнал — что именно эти 10 мест не входят ни в
одну breakpoint-адаптацию вообще, в отличие от остального интерфейса.

**План:** для каждого из 10 мест — проверить в контексте компонента: если элемент
уже стоит в контейнере, который схлопывается в 1 колонку на phone-tier (раздел 3.1) —
достаточно добавить уменьшенный `font-size` в существующий phone-брейкпоинт этого
компонента. Отдельный `clamp()` — только если элемент не привязан ни к одному
существующему компонентному брейкпоинту (изолированный hero-элемент).

## 4. Приоритет P2 — полировка, не блокирует работу

- **`clamp()` используется 1 раз на весь файл** (`styles.css:3516`) — не ошибка сама
  по себе (продуктовый регистр предпочитает breakpoint-driven), но стоит явно
  зафиксировать правило в `DESIGN.md`: `clamp()` — только для изолированных
  display/hero-чисел вне сетки; для всего, что живёт в grid/card-компоненте — брейкпоинт
  из шкалы п. 3.1. Иначе следующий контрибьютор либо начнёт злоупотреблять `clamp()`,
  либо не будет знать, что он вообще доступен.
- **Container queries** — не нужны сейчас (0 компонентов используются в двух разных по
  ширине контекстах одновременно). Отметить как опцию на будущее, если карточные
  компоненты (`.chars-grid`, `.locs-grid`) когда-нибудь начнут переиспользоваться
  и в боковой панели, и на всю ширину — тогда `@container` лучше медиа-запроса
  вьюпорта.
- **Sidebar на самом узком tier** — icon-rail 52px допустим по правилам продуктового
  регистра, но раз 2.1–2.3 показывают, что телефон — реальный целевой контекст, стоит
  визуально проверить на 320px: 52px rail + узкий V20-combat-card (после фикса 2.1)
  должны вместе давать читаемую компоновку, а не соревноваться за те же ~270px.

## 5. Фазы реализации

1. **Фаза 1 (P0, раздел 2)** — 4 точечных фикса: `.v20-combat-row` → карточный
   реflow, `.audio-lib-columns` и `.lineage-picker` → брейкпоинт на 1 колонку,
   `.modal-box` паддинг на ≤480px. Каждый — независимый, безопасно мёржить по одному.
   Приёмка: ручная проверка на 320/375/390px в DevTools + один реальный телефон.
2. **Фаза 2 (P1.1)** — задокументировать три tier'а в `DESIGN.md`/шапке `styles.css`
   (без изменения существующих чисел). Чисто документационный шаг, разблокирует
   осмысленное продолжение.
3. **Фаза 3 (P1.2–P1.3)** — точечная проверка `.v20-grid3` на 768px (реальный iPad
   или эмуляция) и адаптация 10 px-заголовков по списку из раздела 3.3.
4. **Фаза 4 (P2)** — правило по `clamp()` в `DESIGN.md`, финальный визуальный проход
   через `/impeccable polish` на измененных экранах.
