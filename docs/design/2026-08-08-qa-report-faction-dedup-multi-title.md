## Дефект №1 (высокая севериti): пикеры «из библиотеки» на форме создания города перестают работать после посещения страницы текущего города

### Предусловия
- Пользователь хотя бы раз за сессию открывал страницу города (`navigate('city')` — сама
  страница «Город», не обязательно режим редактирования) — то есть практически любой реальный
  сценарий использования, так как это одна из основных страниц приложения.

### Шаги воспроизведения
1. Открыть страницу текущего города (просто посмотреть, без правок).
2. Перейти в «Города» → «+ Новый город» (форма создания, `#page-city-new`).
3. Раскрыть доп. поля формы создания (спойлер), найти секцию «Фракции».
4. Нажать 📚 рядом с «Секты» (или «Независимые кланы» / «Фракции смертных» /
   «Государственные фракции» — дефект одинаков для всех четырёх).

### Фактический результат
Ничего не открывается — панель выбора не появляется, хотя по логам JS клик обработан без ошибок
и внутренне какая-то панель действительно переключилась в `hidden = false`. Пользователю кнопка
кажется полностью нерабочей.

### Ожидаемый результат
Открывается выпадающая панель со списком секций/кланов/организаций для добавления во ФРАКЦИИ
СОЗДАВАЕМОГО города.

### Причина (подтверждено разбором DOM в headless-браузере, не догадка)
`_cityFactionsEditorHtml(sec)` (`web/public/scripts/city.js`) рендерит панели-пикеры с
**фиксированными, не зависящими от контекста id** (`cdet-faction-sects-picker`,
`cdet-faction-sects-list`, `cdet-faction-sects-search` и аналоги для clans/mortal/state).
Эта функция вызывается **дважды независимо**, и оба вызова остаются в DOM одновременно (SPA не
размонтирует неактивные страницы):

- `loadCitiesGrid()` (city.js:23-29) — лениво инжектит копию в форму создания
  (`_cityFactionsCreateHost`), один раз за сессию, при первом посещении `city-new`.
- `_renderCityView()` (city.js:1427-1434) — независимо инжектит СВОЮ копию в
  `#city-detail-content` при каждом рендере страницы текущего города.

Обе копии используют **одинаковые id**. Весь код Части 6/7 (клик-делегаты, `_renderFactionPickerList`,
`_factionAlreadyAdded`) обращается к элементам через `document.getElementById(...)` и
`document.querySelector('.cdet-faction-chips[data-faction-group="…"]')` / `[data-pick-faction="…"]`
— **без какого-либо скоупинга к контейнеру конкретной страницы**. `getElementById`/`querySelector`
детерминированно возвращают ПЕРВЫЙ элемент с таким id/селектором в порядке DOM, а не тот, что
реально видим пользователю.

В статическом HTML (`index.html`) `<section id="page-city">` идёт раньше
`<section id="page-city-new">` — поэтому:

- **Редактирование фракций СУЩЕСТВУЮЩЕГО города — не страдает**: первый DOM-элемент всегда
  принадлежит `#page-city`, что и есть видимая пользователю страница в этом сценарии. Именно
  поэтому и собственная проверка Разработчика, и моя первая проверка того же пути прошли чисто
  — тестовый сценарий просто не задевал вторую страницу.
- **Форма создания города — страдает всегда**, если `#page-city` уже был отрендерен раньше:
  клик по реально видимой (глазами пользователя) кнопке 📚 на `#page-city-new` вызывает
  `document.getElementById('cdet-faction-sects-picker')`, который возвращает элемент внутри
  `#page-city` — невидимый в этот момент (пользователь на другой странице). Открывается «не та»
  панель, а пользователь не видит вообще ничего.

Подтверждено прямым замером в headless Chrome (без предположений): клик по кнопке 📚, реально
видимой на активной `#page-city-new` (`offsetParent !== null`), приводит к тому, что
`document.getElementById('cdet-faction-sects-picker')` возвращает элемент с
`offsetParent === null` внутри `#page-city` — т.е. код открыл панель, принадлежащую невидимой
странице, а не той, где реально произошёл клик.

### Кто отвечает и что делать
Корень — в инфраструктуре Части 6 (`_cityFactionsEditorHtml`, шаблон существует до текущей
доработки), не в изменениях самой Части 7/8. Но Часть 7 (дедупликация) целиком построена поверх
этих же нескоупленных селекторов и наследует дефект без изменений — форма создания города
эффективно теряет всю функциональность «добавить из библиотеки» (не только дедупликацию — саму
возможность открыть панель) при обычном порядке навигации.

**Рекомендация Разработчику/Системному аналитику**: скоупировать все обращения к пикеру
конкретным контейнером страницы (аналогично тому, как `_collectFactions(root)` уже параметризован
`root` для разделения формы создания и модалки редактирования — тот же принцип, только
последовательно применённый и к панелям-пикерам, а не только к сбору итоговых значений). Либо
различать id по контексту (`cdet-faction-sects-picker-create` / `…-edit`), либо резолвить панель
от самой кликнутой кнопки (`pickBtn.closest('.form-group').querySelector(...)`) вместо глобального
`getElementById`. Это отдельная, самостоятельная задача — не входит в объём Части 7/8, но крайне
желательно завести отдельным тикетом, так как без неё «Фракции» в форме создания города
фактически нерабочи в любом реалистичном сценарии использования.

## Что проверено и работает корректно

### Часть 7 — дедупликация (в контексте редактирования СУЩЕСТВУЮЩЕГО города — единственный
рабочий контекст, см. дефект №1 выше)
- Секты: добавление убирает запись из списка пикера; повторное открытие панели не возвращает её;
  удаление чипа возвращает запись обратно в список. 0 JS-исключений.
- Пустое состояние: после добавления всех 7 сект список показывает именно «Все доступные записи
  уже добавлены.» (не «Ничего не найдено.») — правка дизайн-ревью п.1 подтверждена.
- Государственные фракции (textarea-модель, не чипы): ручной ввод в поле (без клика по пикеру)
  корректно убирает вписанную вручную запись из открытой панели — правка §7.2.4 (ранее не
  проверялась вживую ни Разработчиком, ни в этой сессии до сих пор) отработала верно.

### Часть 8 — мульти-титулы
- Добавление двух титулов подряд — панель не закрывается, оба помечаются ✓/`aria-pressed="true"`,
  поле принимает вид `«Титул1, Титул2»`.
- **Toggle-off** (повторный клик по уже выбранному титулу убирает его) — не проверялось
  Разработчиком, проверено отдельно: работает корректно, ✓-пометка снимается.
- **Ручной ввод в поле** (пользователь печатает titles через запятую напрямую, не через пикер) —
  открытая панель верно обновляет ✓-пометки по факту ввода (§8.2.6, ранее не проверялось вживую).
- Сохранение и обратное чтение через API — оба сценария (toggle-off, ручной ввод) корректно
  дошли до диска.
- Токен-синк с картой фракций города (регресс-тест из техспеки) — `npm test`, 713/713, включая
  новый тест на назначение/снятие политроли с сохранением вручную добавленного титула.

### Общее

## Итог

Часть 7/8 сама по себе реализована корректно и без регрессов — все сценарии, которые
Разработчик не успел проверить (toggle-off титула, ручной ввод + синхронизация панели, ручная
правка textarea государственных фракций, пустое состояние «всё добавлено»), при независимой
проверке отработали как задумано. Единственная находка — не в самой доработке, а в
общей инфраструктуре Части 6, на которую Часть 7 опирается: форма создания города практически
не может пользоваться пикерами «из библиотеки» в обычном порядке навигации. Рекомендую завести
это отдельной задачей, не блокируя приёмку уже сделанной Части 7/8.
