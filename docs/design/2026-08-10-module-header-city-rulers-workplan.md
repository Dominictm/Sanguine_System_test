## M1. Кнопки управления модулем — из левой колонки в горизонтальный ряд под шапкой

### M1.1 Текущее состояние

`index.html:290-301` — `.modp-header` (`styles.css:8647`) сегодня flex-row из двух
блоков «плечом к плечу»:

```html
<div class="modp-header">
  <div class="modp-header-btns">          <!-- ← 5 кнопок, левая колонка -->
    <button class="modp-back-btn">← Модули</button>
    <button class="modp-gen-btn">🪄 Сгенерировать</button>
    <button class="modp-edit-btn">✏ Редактировать</button>
    <button class="modp-close-btn">🔒 Закрыть модуль</button>
    <button class="modp-del-btn">🗑 Удалить модуль</button>
  </div>
  <div class="modp-header-main">          <!-- ← заголовок + бейджи, справа -->
    <h1 class="modp-title">…</h1>
    <div class="modp-badges">…</div>
    …
  </div>
</div>
```

`.modp-header-btns { flex-direction: column; gap: 8px; }` (`styles.css:8657-8662`) —
именно это даёт вертикальный столбик на первом скриншоте пользователя. На ≤960px уже
есть частичный костыль (`styles.css:2759-2768`): `.modp-header` → column,
`.modp-header-btns` → row+wrap — то есть на планшете кнопки и так становятся
горизонтальными, но пользователь просит сделать это **дефолтным поведением на любой
ширине**, а не только узкой, и сменить не только направление, но и **позицию**
(под заголовком+бейджами, не отдельным блоком слева).

### M1.2 Требование

Кнопки — горизонтальный ряд **под** строкой бейджей (`.modp-badges`), то есть новый
порядок сверху вниз: заголовок → бейджи → ряд кнопок. Слева отдельной колонки
`.modp-header-btns` больше нет — это меняет и HTML-порядок (кнопки должны физически
переехать внутрь/после `.modp-header-main`), не только CSS-направление.

### M1.3 Последствия, которые нужно проверить

- `.modp-header-edit` (форма правки заголовка/типа/даты и т.п., `index.html:302-330`,
  `display:none` пока не открыта) сейчас тоже внутри `.modp-header-main`, после
  `.modp-badges` — после переноса кнопок под бейджи нужно решить порядок: кнопки перед
  формой правки или после (скорее всего — кнопки сразу под бейджами, форма правки
  ниже, т.к. она открывается уже ПОСЛЕ клика «Редактировать», одной из этих кнопок).
- Существующий ≤960px override (`styles.css:2759-2768`) после этой правки, вероятно,
  становится **не нужен** (кнопки и так горизонтальны на любой ширине) — Системному
  аналитику стоит явно решить, удалять его или оставлять (возможно, там останется
  только `flex-wrap` на случай переполнения при 5 кнопках на очень узком экране).
- `.modp-header { align-items: flex-start }` (`styles.css:8649`) был рассчитан на
  двухколоночный layout — после переноса кнопок вниз это правило, скорее всего,
  становится избыточным (шапка превращается в одну колонку).

## M2. Сворачиваемая шапка модуля — по образцу сайдбара

### M2.1 Референс-паттерн (уже в проекте, переиспользовать, не изобретать заново)

`web/public/scripts/scripts.js:59-82` — сворачивание сайдбара:

```js
(function () {
  const KEY = 'sanguine-sidebar-collapsed';
  const btn = document.getElementById('btn-sidebar-collapse');
  const sidebar = document.getElementById('sidebar');
  function apply(collapsed) {
    sidebar.classList.toggle('collapsed', collapsed);
    btn.setAttribute('aria-expanded', String(!collapsed));
    // + title/aria-label
  }
  let collapsed = false;
  try { collapsed = localStorage.getItem(KEY) === '1'; } catch {}
  apply(collapsed);
  btn.addEventListener('click', () => { … localStorage.setItem(KEY, …) });
})();
```

CSS-сторона — `styles.css:2810-2877` (`#sidebar.collapsed …`): анимация через
`max-width`/`max-height`/`opacity` с transition, **не** `display:none` (иначе не
плавно) — комментарий на `styles.css:2815-2818` явно объясняет, почему.

### M2.2 Требование

Кнопка-тумблер на шапке модуля (аналог `#btn-sidebar-collapse`), сворачивающая
`.modp-header` в компактную полосу — цель пользователя: «увеличить рабочее
пространство» под сценарий/заметки модуля, которые скроллятся под шапкой.

## C1. «Властители города» — поля не в один ряд (баг, не просто «тесно»)

### C1.1 Текущее состояние — воспроизведено и измерено вживую (headless Chrome, CDP)

`web/public/scripts/city.js:167-174` (`_polRowHtml`) рендерит ряд
`<div class="cdet-rel-row cdet-pol-row">` с 4 полями:
`<select class="cdet-pol-role-sel">` (Должность) + `<input class="cdet-pol-name-inp">`
(Имя) + `<input class="cdet-pol-name-inp cdet-pol-name2-inp">` (Второе имя) +
`<button class="cdet-rel-del-btn">` (✕).

**Корень проблемы — не брейкпоинт, а отсутствующее `flex-direction: row`.**
`.cdet-rel-row` (`styles.css:3786-3793`) задаёт `flex-direction: column` как БАЗОВОЕ
правило. `.cdet-pol-row` (`styles.css:3886-3888`) переопределяет только
`flex-wrap: wrap`, но не `flex-direction` — то есть все 4 поля наследуют `column` и
рендерятся **одно под другим на любой ширине экрана**, а не сжимаются при сужении
окна. Скриншот live-проверки на 1280px: `<select>` растянут на всю ширину панели
(~990px) с аномальной высотой — визуальное подтверждение бага, не тесноты.

Затронуты тем же паттерном (используют тот же `.cdet-rel-row` + аналогичный
override без `flex-direction`): `.cdet-prim-row` (Примогенат) и `.cdet-loc-row`
(Ключевые локации) — тот же баг, три места, не одно.

### C1.2 Проверено: одного `flex-direction: row` НЕДОСТАТОЧНО на текущих ширинах полей

Смоделировал фикс (`flex-direction: row` + `align-items: center` поверх текущего
`flex-wrap: wrap`) и измерил ширину ряда на разных viewport (сайдбар развёрнут,
кроме 700px):

| Viewport | Доступная ширина ряда | Помещается в одну строку? |
|---|---|---|
| 1280px | 1009px | ✅ да (53px высоты — одна строка) |
| 960px | 689px | ✅ да |
| 900px | 629px | ✅ да |
| 768px | 497px | ❌ нет — перенос на 2 строки (94px высоты) |
| 700px (сайдбар в icon-rail) | 587px | ❌ нет — перенос на 2 строки (84px высоты) |

Сумма текущих `flex-basis` четырёх полей: `.cdet-pol-role-sel` 150px
(`styles.css:3890-3891`) + `.cdet-pol-name-inp` (Имя) 200px (`3911-3913`, через
`flex: 1 1 200px`, база роста) + `.cdet-pol-name2-inp` тоже 200px (тот же селектор) +
кнопка-крестик ~36px + `gap: 8px`×3 ≈ **610px минимум** — не помещается там, где
доступно < 610px (диапазон примерно 700–820px по имеющейся сетке брейкпоинтов,
см. `docs/design/2026-08-10-responsive-adaptive-layout-techspec.md`, R5).

### C1.3 Требование

1. Добавить `flex-direction: row` (плюс `align-items: center`, т.к. `<select>` и
   `<input>` разной естественной высоты) для `.cdet-pol-row`, `.cdet-prim-row`,
   `.cdet-loc-row` — это чинит 1280/960/900px сразу.
2. Для диапазона, где сумма `flex-basis` всё ещё не помещается (≤ ~820px доступной
   ширины панели, эмпирически измерено выше как 768px viewport) — уменьшить
   `flex-basis` полей (например, `.cdet-pol-role-sel` 150px→120px,
   `.cdet-pol-name-inp` 200px→150-160px) **в этом диапазоне**, не отбирая ширину
   глобально на широких экранах, где сейчас всё умещается свободно.
3. Проверить оба других использования того же паттерна (`.cdet-prim-row` —
   Примогенат, `.cdet-loc-row` — Ключевые локации) — вероятно, тот же фикс применим
   один в один, но состав полей у них другой (`.cdet-loc-row` — 4 текстовых поля +
   select, `.cdet-prim-row` — свой набор), нужно свериться с их `_locRowHtml`/
   `_primRowHtml` перед копированием чисел.
