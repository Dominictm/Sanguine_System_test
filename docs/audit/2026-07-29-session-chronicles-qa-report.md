## Executive Summary

Нашёл **два системных класса дефектов**, оба — прямое продолжение уже
описанных в предыдущих отчётах этого цикла паттернов, но здесь они
проявились серьёзнее:

1. **Path traversal при создании хроники и модуля** — то же самое, что
   находка №1 в `2026-07-28-links-factions-locations-qa-report.md` (там
   — «Локации»), но здесь **достижимо прямо из формы создания хроники**
   (видимое, редактируемое поле «slug» в модалке), и в модуле —
   **эскалируется вдвое** из-за повторного использования одного и того
   же непроверенного значения в двух разных путях.
2. **Свободный текст заметок → фиктивная запись сессии/сцены при
   следующем сохранении** — то же семейство, что «символ `\|`/`\n` рвёт
   структуру» из прошлых отчётов (FIX-2 в `2026-07-28-fix-plan.md`), но
   здесь пострадавший разделитель — заголовок markdown (`##`/`###`), а
   не разделитель ячейки — то есть инъекция не искажает поле, а
   **создаёт полноценную поддельную запись** с придуманным номером
   сессии и статусом.

## Найденные дефекты

### 1. [КРИТИЧНЫЙ] Path traversal через поле `slug` при создании хроники — доступно из формы

**Компонент:** `POST /api/chronicles` (`web/routes/chronicles.js:166-199`).

**Контракт сейчас:**
```js
const slug = req.body.slug?.trim() || slugify(display);
...
const chrDir = path.join(chroniclesDir(city), slug);
```
Если `slug` передан явно — используется **как есть**, `slugify()` к нему
не применяется вообще (в отличие от `display`/`name`).

**Кто может это ввести:** модалка «+ Новая хроника»
(`web/public/scripts/modules.js:763-800`) — поле `#chr-create-slug`
автозаполняется из названия, но **редактируется вручную**; после первого
ручного изменения (`_slugEdited = true`) перестаёт синхронизироваться с
названием и отправляется на сервер как ввёл пользователь, без какой-либо
клиентской или серверной проверки на `../`.

**Шаги:**
```
POST /api/chronicles?city=qa_test_city_3
{ "name": "Тест Хроника", "slug": "../../qa_chronicle_traversal" }
```

**Фактический результат (подтверждено на диске):** файлы
`chronicle.md`, `events.md`, `open_threads.md` созданы по пути
`cities/qa_chronicle_traversal/` — **на два уровня выше домена города**,
рядом с самим `cities/` (не `cities/<city>/chronicles/...`, а прямо
`cities/qa_chronicle_traversal/`).

**Рекомендация:** `slug` — всегда через `slugify()`, даже если передан
явно клиентом (как уже сделано для персонажей/локаций — там альтернативы
клиентскому slug вообще нет, только автогенерация; здесь стоит либо
убрать возможность задавать slug вручную с фронта, либо прогонять его
через `slugify()` перед использованием, а не доверять `.trim()`).

### 2. [КРИТИЧНЫЙ] То же самое в создании модуля — с усугублением: значение переиспользуется дважды, эскейп удваивается

**Компонент:** `POST /api/chronicles/:slug/modules` (`web/routes/modules/list.js:94-166`).

**Контракт сейчас:** идентичная находке №1 конструкция
(`modSlug = req.body.slug?.trim() || slugify(name.trim())`), но
**значение `modSlug` используется дважды** в двух отдельных
`path.join`:
```js
const modDir = path.join(chroniclesDir(city), chr, 'modules', modSlug);   // строка 105
...
await writeFileAtomic(path.join(modDir, `${modSlug}.md`), mainContent, 'utf-8');  // строка 163
```

**Шаги:**
```
POST /api/chronicles/kachtesthronika/modules?city=qa_test_city_3
{ "name": "Траверсал", "time": "2020", "slug": "../../../qa_module_traversal" }
```

**Фактический результат (подтверждено на диске, оба уровня эскейпа):**
1. `modDir` резолвится в `cities/qa_test_city_3/qa_module_traversal/`
   (эскейп из `chronicles/kachtesthronika/modules/` на 3 уровня вверх —
   до уровня самого города).
2. Файл содержимого модуля **резолвится ЕЩЁ РАЗ через тот же
   traversal-путь**, потому что `` `${modSlug}.md` `` подставляется в
   `path.join(modDir, ...)` со своим собственным `../../../` внутри —
   в итоге файл `qa_module_traversal.md` оказался **в корне
   репозитория** (`f:\...\VTM-project-Claude\qa_module_traversal.md`),
   на 5 уровней выше исходной точки, а не 3.

**Почему это хуже находки №1:** одна и та же непроверенная строка
используется дважды в построении путей без единой точки санитизации —
глубина эскейпа складывается, а не ограничивается. Чем глубже
`../`-последовательность во входных данных, тем дальше от `cities/`
можно писать файлы, вплоть до произвольного места на диске, до
которого у процесса Node есть доступ на запись — сегодняшний тест
специально ограничился неглубоким traversal (до корня репозитория, не
дальше), чтобы не рисковать реальными данными вне проекта.

**Рекомендация:** та же, что в находке №1 — `slugify(modSlug)` сразу
после получения значения из тела запроса, **до первого использования**
в любом `path.join`. Общая рекомендация по всем находкам такого рода в
этом цикле (Локации/Хроники/Модули): один общий хелпер
`safePathSegment(input)` = `slugify()`-подобная функция, вызываемая
**обязательно** на любом пользовательском значении перед тем, как оно
попадёт в `path.join(...Dir(city), ...)`, а не точечные патчи в каждом
роуте по отдельности — тем более что паттерн уже повторился три раза
independently.

### 3. [ВЫСОКИЙ] Заметка о сессии с встроенным `## Сессия N` создаёт фиктивную запись после следующего сохранения

**Компонент:** `_parseSessions`/`_renderSessionBlock`/`_writeSessionsFile`
(`web/routes/modules/shared.js:371-391, 586-601`), используются
`POST/PUT /api/chronicles/:chr/modules/:mod/session[/:idx]`.

**Контракт сейчас:** записи журнала сессий разделяются построчным
сканированием на `## Сессия` (`text.split(/\n(?=##\s+Сесси)/)`). Текст
поля «Что произошло» (`notes`) пишется в файл **без проверки** на
совпадение с этим паттерном.

**Шаги:**
1. Записать сессию 1 с текстом заметки:
   `Всё прошло гладко.\n## Сессия 99 — ИНЪЕКЦИЯ\n- **Сыграно сцен:** 100\n- **Статус модуля:** 🟢 Закрыт\nПоддельная запись сессии.`
2. Записать ещё одну (настоящую) сессию 2 — это вызывает `_parseSessions`
   на всём файле и полную пересборку через `_writeSessionsFile`.

**Фактический результат (подтверждено содержимым `sessions.md` до и
после шага 2):** после шага 1 файл выглядит нормально — инъекция ещё не
«активировалась». **После шага 2** — три секции вместо двух:
```
## Сессия 1 — 2026-01-15   (реальная)
## Сессия 2 — ИНЪЕКЦИЯ     (сфабрикована из текста заметки: «Сыграно сцен: 100»,
                             «Статус модуля: 🟢 Закрыт», «Поддельная запись сессии»)
## Сессия 3 — 2026-02-01   (моя настоящая вторая сессия, сдвинутая с №2 на №3)
```
Ответ API на шаге 2 — `{"ok":true,"n":3}}`, то есть сервер искренне
считает, что сессий три, а не две.

**Почему это важно:** это не искажение поля (как символ `|` в таблице),
а **создание полноценной ложной записи** с придуманными «Сыграно сцен»
и «Статус модуля» — причём **«Статус модуля: 🟢 Закрыт»** особенно
опасен, если где-то в приложении статус модуля читается из последней/
любой записи журнала сессий (не проверял этот конкретный путь чтения в
рамках сегодняшнего раунда — стоит отдельно свериться). Нумерация
последующих реальных сессий тоже съезжает.

**Рекомендация:** нормализовать `notes` перед записью — не давать
строкам внутри тела начинаться с `## ` (например, экранировать как
`\## ` или просто заменять начальные `#` на похожий символ), либо (более
общее решение) не сплитить по regex-паттерну, а хранить количество
сессий/границы явно в структуре, которую текст заметки не может
подделать.

### 4. [ВЫСОКИЙ] Тот же дефект в заметках по сценам (scene_notes.md) — другой парсер, та же уязвимость

**Компонент:** `_upsertSceneNoteEntry` → `parseScenarioSections`/
`splitH3Body` (`web/lib/parsers/scenario.js:37+`), используется
`PUT /api/chronicles/:chr/modules/:mod/scene-note`.

Формально другой код (структурное дерево секций по уровням `##`/`###`
через `parent`, не плоский regex-сплит, как у находки №3) — но
первопричина идентична: `parseScenarioSections` тоже сканирует сырой
текст на строки, начинающиеся с `##`/`###`, и текст заметки (`text`) в
`_upsertSceneNoteEntry` не защищён от совпадения с этим паттерном.

**Шаги:** записать заметку к сцене «Сцена 1: Клуб» для сессии 1 с
текстом `Заметка по сцене.\n### Сессия 5\nПоддельная запись заметки.`,
затем записать заметку для сессии 2 той же сцены (триггерит повторный
парсинг/пересборку).

**Фактический результат (подтверждено содержимым `scene_notes.md`):**
после второй записи в файле появляется самостоятельный подраздел
`### Сессия 5` между настоящими `### Сессия 1` и `### Сессия 2` — то
есть в истории заметок сцены «Сцена 1: Клуб» появляется несуществующая
пятая сессия. Раздел «История прошлых записей» на экране «Сессия»
(режим только для чтения, см. прошлый QA-отчёт по этому же экрану)
показал бы Рассказчику эту выдуманную запись как настоящую прошлую
сессию.

**Общая рекомендация для находок №3 и №4:** обе — частные случаи одной
и той же проблемы, что уже задокументирована в FIX-2
(`2026-07-28-fix-plan.md`) — свободный текст пользователя не должен
интерпретироваться как разметка формата хранения при обратном разборе.
Стоит расширить объём FIX-2 на markdown-заголовки (`#`/`##`/`###`) в
дополнение к уже описанным `|` и `\n` — единый список символов/паттернов,
которые нужно экранировать/нормализовать на любом пути записи
свободного текста в структурированный markdown-файл этого проекта.

## Что проверено и работает корректно

- **`PUT /:mod/move`** (перенос модуля между хрониками) — в отличие от
  находок №1/№2, здесь **есть** защита: `chr.includes('..') ||
  mod.includes('..') || toChronicle.includes('..')` отклоняет `400`
  явный traversal-паттерн. Также корректно обрабатывает: перенос в ту
  же хронику (no-op, `200`), несуществующую хронику назначения (`404`),
  занятое имя модуля в целевой хронике (`409`), несуществующий модуль
  (`404`). **Важное наблюдение:** это показывает, что защита от
  traversal в проекте есть, но применяется непоследовательно — одни
  роуты (`move`, `scene-note`) её имеют, другие (создание хроники/
  модуля/локации) — нет, при том что все они относятся к одному классу
  риска. Усиливает рекомендацию про общий хелпер вместо точечных
  проверок.
- **Журнал сессий** — валидация индекса при `PUT`/`DELETE
  /session/:idx` (несуществующий индекс — `404`, а не падение),
  обязательность «Сыграно сцен» или «Что произошло» хотя бы одного из
  двух.
- **Создание хроники/модуля** — обязательность названия, `409` на
  дубликат slug (после исправления traversal-находок эта проверка
  продолжит работать корректно, она не пострадала).
