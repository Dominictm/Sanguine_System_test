## 1. [ВЫСОКАЯ] Нити: свободный текст ломает pipe-таблицу — подтверждена потеря нити

**Компонент:** `web/routes/threads.js` — `POST /api/threads` (строка `row = ...`, ~72) и `PATCH /api/threads/:id` (`cells[4]`/`cells[5]`, ~102-103).

**Первопричина:** `title`, `description`, `source` (создание) и `priority` (правка) вставляются в pipe-таблицу `archive/open_threads.md` без `sanitizeInlineText`/`escapeTableCell` — тот же класс, что FIX-2 закрывал в 11 других местах в прошлом цикле, здесь остался незакрытым.

**Шаги (создание, воспроизведено):**
1. `POST /api/threads` с `description: "строка1\nстрока2"`.
2. `GET /api/threads` → нить **отсутствует в ответе целиком** (не «испорчена», а буквально исчезла — вторая физическая строка не начинается с `|`, парсер строки таблицы её не находит).
3. Сырой файл:
   ```
   | 3 | **Нить с переносом** — строка1
   строка2 | — | 🔴 Активна | Средний |
   ```

**Шаги (правка приоритета, воспроизведено):**
1. `PATCH /api/threads/1` с `priority: "Высокий | ВЗЛОМ | лишняя ячейка"`.
2. Строка нити №1 стала 8-колоночной вместо 5 — `ВЗЛОМ` и `лишняя ячейка` осели как настоящие ячейки таблицы:
   ```
   | 1 | **Тестовая нить** — Обычное описание | модуль X | 🔴 Активна | Высокий | ВЗЛОМ | лишняя ячейка | ... |
   ```

**Live-подтверждение:** страница «Нити» в браузере показывает «2 активных» вместо 3 созданных — третья нить пропала и в интерфейсе, не только в API.

**Рекомендация:** обернуть `title`/`description`/`source` в `sanitizeInlineText` + `escapeTableCell` при создании (`POST /api/threads`), `priority` — при правке (`PATCH /api/threads/:id`), по образцу уже сделанного в `web/routes/modules/list.js` (создание модуля) и `web/routes/locations.js`.

## 2. [ВЫСОКАЯ] Сессия — журнал: `:chr`/`:mod` не проверяются на path traversal

**Компонент:** `web/routes/modules/sessions.js` — `POST /session`, `PUT /session/:idx`, `DELETE /session/:idx` (строки 26, 55, 85).

**Первопричина:** в этом же файле у `scene-notes`/`scene-note`/`session-notes` (GET и PUT) есть охрана `if (chr.includes('..') || mod.includes('..')) return res.status(400)...` — а у трёх роутов записи журнала сессий её нет вообще.

**Прямое сравнение (одинаковый payload, воспроизведено):**
```
GET  /api/chronicles/..%2Ftestovaya_hronika/modules/testovyy_modul/scene-notes
     → 400 {"error":"Недопустимое имя"}              ← защищено

POST /api/chronicles/..%2Ftestovaya_hronika/modules/testovyy_modul/session
     → 404 {"error":"Модуль не найден"}               ← НЕ отклонён на входе,
                                                          прошёл до resolve пути и
                                                          упал только потому, что
                                                          конкретная цель не существует
```
404 здесь — не защита, а совпадение (эта конкретная траектория не указала на существующую папку); при подходящей цели `..`-путь дойдёт до `fs.readFile`/`writeFileAtomic` вне `chronicles/<chr>/modules/<mod>/`.

**Рекомендация:** добавить ту же охрану `chr.includes('..') || mod.includes('..')` в начало всех трёх роутов записи журнала. Отдельно стоит проверить остальные роуты `modules/*.js` (fields.js, lifecycle.js, scenario.js, npc.js, locations.js) на этот же паттерн — беглый просмотр показал, что явную охрану имеют не все; это тянет на отдельный точечный аудит, я не проверял каждый из них так же детально, как session-роуты выше.

## 3. [СРЕДНЯЯ] Создание модуля: свободный `content` фабрикует заголовок в «Концепции»

**Компонент:** `web/routes/modules/list.js`, `POST /api/chronicles/:slug/modules` — поле `content` (→ секция `## 💡 Концепция`), не проходит через `sanitizeFreeformBody`, в отличие от `time`/`type`/`tone`/`format` (которые уже под `sanitizeInlineText`/`escapeTableCell`, FIX-2).

**Шаги (воспроизведено):**
1. `POST /api/chronicles/:slug/modules` с `content: "Обычный текст.\n## Фальшивый Заголовок\nЕщё текст."`.
2. Файл `<mod>.md` получает секцию как есть:
   ```
   ## 💡 Концепция

   Обычный текст.
   ## Фальшивый Заголовок
   Ещё текст.
   ```

**Почему это не только косметика:** `web/routes/modules/fields.js:82-85` и `web/routes/modules/list.js:239-242` читают/правят именно секцию «Концепция» через regex с lookahead на следующий `## ` — то есть **любое** последующее чтение описания модуля (превью в списке модулей) или правка через форму полей увидит текст только ДО фальшивого заголовка, а хвост («Ещё текст.») останется вне зоны, которую эти функции считают «телом секции» — при следующем сохранении через `fields.js` рискует быть молча потерян.

**Рекомендация:** `sanitizeFreeformBody(concept)` перед вставкой в `mainContent`, по аналогии с тем, как уже сделано для «📝 Заметки сессии» (`_upsertModuleSection`) и «Что произошло» (`_renderSessionBlock`) — тот же паттерн, тот же файл-механизм (`_moduleSectionBodyBoundary`), просто не применён к моменту СОЗДАНИЯ модуля.

## 4. [НИЗКАЯ] Экранированный `#`/`##` в заметках рендерится как настоящий заголовок

**Компонент:** `web/public/scripts/modules.js:1785` (`mdToHtmlPlain`) — общий markdown-рендерер, используется, в частности, для `.modp-session-body` (тело записи в журнале сессий).

**Проверено, что НЕ баг:** на диске текст с `##` в теле сессии/заметки сцены корректно хранится экранированным (`\## ...`, — подтверждено чтением `sessions.md` напрямую), и `_parseSessions` при повторном чтении НЕ фабрикует лишнюю запись. Защита FIX-2 работает как задумано на уровне хранения.

**Что действительно происходит:** сервер отдаёт УЖЕ разэкранированный текст (`unescapeFreeformBody`) — это правильно для формы редактирования (Storyteller должен видеть свой оригинальный текст, не бэкслеши). Но тот же разэкранированный текст уходит и в `mdToHtmlPlain` для read-only отображения записи в журнале — а этот рендерер не знает, что `##` тут «безопасный» (изначально экранированный), и рисует `<h2>Сессия 99 — Поддельная</h2>` — визуально неотличимо от настоящего заголовка сессии.

**Подтверждено live:** запись сессии 2 в браузере отображается с врезанным жирным заголовком «Сессия 99 — Поддельная» посреди текста заметки — Мастер может ошибочно подумать, что это отдельная (третья) запись, хотя структурно данные целы (одна запись, `sessLogEntries`/парсинг корректны).

**Рекомендация:** архитектурно сложнее, чем находки 1-3 (нет простого «добавить экранирование») — конфликт между «безопасно для повторного парсинга» и «безопасно для визуального рендера» требует либо не разэкранировать для read-only путей отображения, либо научить `mdToHtmlPlain` распознавать экранированный `\#`/`\##` и рендерить его как литеральный текст, а не отдавать общему заголовочному regex. Отдельная, не блокирующая задача.

## 5. [НИЗКАЯ/СРЕДНЯЯ] Загрузка звука: нет проверки содержимого, `/audio-lib` без `nosniff`

**Компонент:** `web/routes/audio.js`, `POST /api/audio`; `web/server.js:92` (`app.use('/audio-lib', express.static(AUDIO_DIR, ...))`).

**Сравнение с FIX-1 (изображения):** `validateImageUpload` (`web/lib/http.js`) проверяет магические байты файла против заявленного расширения; `/city-img` явно получил `X-Content-Type-Options: nosniff`. У звука ничего из этого нет — `ext = MIME_EXT[mimetype]` берёт расширение из **клиентского** поля `mimetype` без проверки реального содержимого `data`.

**Шаги (воспроизведено):**
1. `POST /api/audio` с `mimetype: "audio/mpeg"`, `data` = base64 от `<script>alert(1)</script>`.
2. `200 OK`, файл сохранён как `<uuid>.mp3`.
3. `GET /audio-lib/<uuid>.mp3` → `200`, `Content-Type: audio/mpeg`, `X-Content-Type-Options` отсутствует, тело ответа — буквально `<script>alert(1)</script>`.

**Оценка риска:** ниже, чем было у FIX-1 до фикса — расширение всегда одно из `mp3`/`ogg`/`wav` (жёсткий whitelist `MIME_EXT`), так что `Content-Type` от `express.static` всегда будет настоящим аудио-типом, а не «угадан» браузером как HTML/JS — практическая эксплуатируемость через прямой переход по ссылке маловероятна. Тем не менее это несогласованность с уже установленным в проекте паттерном защиты, и best practice — не хранить непроверенный бинарник с доверенным Content-Type.

**Рекомендация:** добавить проверку магических байт (ID3/`\xFF\xFB` для mp3, `OggS` для ogg, `RIFF...WAVE` для wav) аналогично `validateImageUpload`; добавить `nosniff` на `/audio-lib` для консистентности с `/city-img`.

## Проверено и работает корректно

- **Создание модуля** — happy path (`ok:true`, файл создан, синхронизация с `chronicle.md`); отсутствие обязательных `name`/`time` → `400` с понятной ошибкой; дублирующийся slug → `409`; `time`/`type`/`tone`/`format` корректно экранированы (FIX-2 уже применён здесь).
- **Заметки по сцене** (`scene-note`) — создание/повторное сохранение той же сцены+сессии (апдейт, не дубликат), отсутствие `heading` → `400`, `session < 1` → `400`; текст с `### Сессия N` внутри корректно экранируется на диске, GET отдаёт неповреждённый список записей по каждой сцене.
- **Заметки сессии модуля** (`session-notes`, `## 📝 Заметки сессии` в `<mod>.md`) — round-trip с `##`-строкой внутри подтверждён и на диске, и через textarea в реальном UI («Сессия» → выбор хроники/модуля → поле «Заметки сессии»).
- **Журнал сессий** (`POST/PUT/DELETE /session`) — создание/правка записи, `400` при отсутствии и «Что произошло», и «Сыграно сцен» одновременно; UI-вкладка «🎲 Сессии» на странице модуля корректно рендерит обе тестовые записи (при этом см. находку 4 — по отображению фейкового заголовка).
- **Слухи** (Elysium/Dreaming) — `GET`/`PUT` по обоим типам, `400` при нестроковом `content`; т.к. это редактирование сырого markdown целиком (не структурный парсинг полей), класс уязвимостей FIX-2 здесь неприменим по конструкции.
- Полный live-обход открытых страниц (Нити, Слухи, Звуки, Сессия, Модули) — 0 ошибок в консоли браузера.
