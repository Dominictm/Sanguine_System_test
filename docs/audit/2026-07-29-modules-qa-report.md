## Найденные дефекты (новое)

### 1. [СРЕДНИЙ, уже в продакшене] `getCityDisplayName()` — неверный путь, никогда не находит `city.md`, тихий фолбэк на слаг

**Компонент:** `web/routes/modules/shared.js:60-67`.

```js
async function getCityDisplayName(city) {
  try {
    const cityMdPath = path.join(__dirname, '..', 'cities', city, 'city.md');
    ...
  } catch { return city; }
}
```

`__dirname` здесь — `web/routes/modules/`. `path.join(__dirname, '..',
'cities', ...)` резолвится в `web/routes/cities/<city>/city.md` —
**каталога `web/routes/cities/` не существует** (`web/routes/cities.js`
— файл роутера, не директория с данными города). Настоящий `cities/`
лежит в корне проекта, на три уровня выше `web/routes/modules/`, а не
на один.

**Подтверждено:** прямая проверка пути (`fs.existsSync`) — `false` для
любого города, включая `paris`. Функция **всегда** уходит в `catch` и
возвращает сырой слаг города.

**Где это видно пользователю:** поле «Родной город» в карточке любого
НПС модуля (`web/routes/modules/npc.js:82`,
`` `- **Родной город:** ${await getCityDisplayName(city)}` ``) —
показывает `paris` вместо «Париж» (или как он там называется в
`city.md`). Проверено на тестовом городе: карточка продвинутого в канон
НПС так и осталась с `qa_test_city_4` вместо «QA Test City 4».

**Важно:** это не гипотетический риск — функция сломана **для всех
городов без исключения**, включая боевые данные (`paris`, `balmont`) —
любой НПС, когда-либо созданный через «Добавить НПС» на странице
модуля, несёт это неверное значение прямо сейчас.

**Рекомендация:** `path.join(__dirname, '..', '..', '..', 'cities', city, 'city.md')`
(три уровня вверх, не один) — либо, надёжнее, взять уже существующий
`cityDir(city)` из `web/lib/db.js` (используется в остальном проекте
именно для этого) вместо повторной сборки пути вручную.

### 2. [СРЕДНИЙ] Продвижение НПС модуля в канон не обновляет поле «Линейка WoD» под целевую линейку

**Компонент:** `POST /api/chronicles/:chr/modules/:mod/npc/:slug/promote`
(`web/routes/modules/npc.js:274-338`).

**Контракт сейчас:** карточка модульного НПС копируется как есть в
`characters/<lineage>/<slug>/`, патчится только поле «Родной город»
(строка 321-325). Сама карточка **при создании** (в `npc.js:83`) всегда
получает `` `- **Линейка WoD:** mortals` `` — константа, независимо от
того, какая линейка будет выбрана при продвижении позже.

**Шаги:**
1. Создать модульного НПС (по умолчанию — «mortals» в самой карточке).
2. Продвинуть с `{ lineage: 'vampires', force: true }`.

**Фактический результат (подтверждено содержимым карточки):**
```
- **Слаг:** chistyynps
- **Линейка WoD:** mortals        ← осталось
```
— карточка физически лежит в `characters/vampires/chistyynps/`, но сама
СЕБЯ описывает как `mortals`. Заголовок (`# 🎭 ЧистыйНПС`) и эмодзи
линейки тоже не обновляются под целевую линейку.

**Почему это важно:** `system/schema/card_schema.md`/`validate_cards.js`
как раз проверяет соответствие «Линейка WoD: X» и папки, в которой
лежит карточка (`E(«Линейка WoD: ${lin}» не соответствует папке
${grp.lineage})` — этот же самый линтер использовался при тестировании
раздела «Персонажи» ранее в этом цикле) — то есть продвижение молча
создаёт персонажа, которого штатный линтер проекта тут же пометит как
ошибку.

**Рекомендация:** при продвижении — патчить не только «Родной город», но
и «Линейка WoD» (по `LINEAGE_MAP[lineage]`, значение уже вычисляется
для валидации на строке 296) и заголовок/эмодзи карточки под целевую
линейку.

## Что проверено и работает корректно

- **Продвижение НПС в канон** — условия продвижения (`survived` /
  `inFinale` / `inMultipleModules`) корректно блокируют без `force`
  (`422` с деталями), `force:true` их обходит осознанно; дубликат слага
  в каноне — `409`; невалидная линейка — `400`; несуществующий модульный
  НПС — `404`. `characters_index.md` пополняется корректной строкой.
- **`delete-preview`/`delete` модуля** — точный подсчёт файлов и
  затронутых модульных НПС в превью, `404` на несуществующий модуль,
  повторное удаление — `404`, не падает.
- **`PUT /fields` модуля** — обязательные проверки `chr.includes('..')`/
  `mod.includes('..')` есть (та же защита, что и у `move`/`scene-note`
  из прошлого отчёта) — контрастирует с находками путей в самом
  создании модуля/хроники, где этой защиты нет вовсе.
