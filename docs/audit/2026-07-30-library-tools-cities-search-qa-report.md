## 1. [КРИТИЧЕСКАЯ] `POST /api/run-tool` — command injection через ключи `params`

**Компонент:** `web/routes/tools.js:508-565`.

**Первопричина:**
```js
const regularParamStr = Object.entries(params)
  .filter(([k, v]) => !SWITCH_PARAMS.includes(k) && v !== undefined && v !== null && String(v).trim() !== '')
  .map(([k, v]) => `-${k} '${String(v).replace(/'/g, "''")}'`)
  .join(' ');
...
const cmd = [
  '[Console]::OutputEncoding = ...', '$OutputEncoding = ...',
  `& '${script...}' ${allArgs}`
].join('; ');
spawn('powershell.exe', ['-ExecutionPolicy', 'Bypass', '-NoProfile', '-Command', cmd], ...);
```
**Значение** параметра (`v`) экранируется корректно (одинарные кавычки дублируются — стандартный приём для PowerShell single-quoted strings). **Ключ** (`k`) — нет: вставляется в шаблон как есть, `-${k}`, без проверки формата и без белого списка допустимых имён параметров. `tool` ограничен списком `['validate_links', 'search']` — но `params` (объект, чьи КЛЮЧИ становятся частью команды) целиком приходит от клиента без ограничений.

Любой ключ вида `X'; <произвольная PowerShell-команда>; #` при подстановке `-${k}` превращает финальную команду в несколько независимых PowerShell-инструкций, выполняемых от имени процесса сервера — то есть **произвольное выполнение кода** на машине, где запущен сервер, с правами того же пользователя.

**Проверка:** статический разбор кода однозначен — ключ объекта интерполируется в команду оболочки без какой-либо санитизации. Живой PoC (полностью безобидный: легитимный вызов `search.ps1` + `Write-Output` с меткой, без единой деструктивной команды) был заблокирован защитным классификатором среды выполнения раньше, чем ушёл на сервер — поэтому эта находка подтверждена **статически**, не runtime-трассировкой; уверенность в ней тем не менее высокая — код читается однозначно, второй экранируемый путь (значения) в том же роуте это подтверждает как задуманный, но неполный контур защиты.

**Рекомендация (для роли Разработчик):**
- Свести список допустимых КЛЮЧЕЙ к белому списку на инструмент (`validate_links` реально принимает не более 1-2 параметров, `search` — `Query`/`Root`/`Case`) — как уже сделано для `tool` и `SWITCH_PARAMS`.
- Либо полностью отказаться от построения команды строкой и звать `spawn('powershell.exe', ['-File', script, '-Query', value, ...], { shell: false })` с параметрами как отдельными элементами массива argv — тем же способом, каким уже безопасно сделан соседний `POST /api/tool/:name` (Node-инструменты, `spawn('node', [script, ...args])` без построения команды строкой).

## 2. [СРЕДНЯЯ] Библиотека: `:slug` в PUT/DELETE дисциплин/способностей — path traversal

**Компонент:** `web/routes/library.js:222-252` (`disciplines`), `267-311` (`psychics`).

```js
const slug = req.params.slug;               // из URL, как есть
const file = path.join(DISC_DIR, `${slug}.md`);
```
В отличие от `POST` (там `slug = slugify(name)` — безопасно), `PUT`/`DELETE` берут `:slug` напрямую. `..`-путь дошёл бы до `fs.readFile`/`writeFileAtomic`/`fs.rename` вне `system/library/disciplines/`.

**Смягчающий фактор:** оба маршрута требуют, чтобы файл по итоговому пути (а) существовал и (б) содержал `- **Авторское:** да` — так что произвольная запись «в никуда» невозможна, только точечное редактирование/перемещение уже существующего, специально помеченного файла. Ниже серьёзности, чем находки FIX-10 в прошлом цикле (там был чистый unrestricted write), но тот же класс бага.

**Рекомендация:** `slugify(req.params.slug)` или явная проверка `slug.includes('..')` в начале обоих роутов (для дисциплин и способностей) — по образцу уже применённого в `web/routes/modules/*.js`.

## 3. [ВЫСОКАЯ] Библиотека: создание дисциплины фабрикует фальшивый уровень силы

**Компонент:** `web/routes/library.js:195-220` (`_discTemplate` / `POST /api/library/disciplines`); идентичный паттерн в `_psyTemplate` для `/psychics` (не тестировал psychics отдельно — код идентичен по конструкции).

**Первопричина:** `clans`/`source` вставляются как однострочные bullet-поля (`- **Клан / принадлежность:** ${clans}`) без `sanitizeInlineText`. Парсер `lib/disciplines.js:parseDisciplineMd` бьёт файл строго по `\n##\s+` — эмбеддед `\n## ` в `clans` создаёт настоящую (фальшивую) H2-секцию, которую `parsePowerHeading` распознаёт как «Уровень N — Название».

**Шаги (воспроизведено):**
```
POST /api/library/disciplines
{ "name": "QA Тестовая Дисциплина",
  "clans": "Тест\n## Уровень 99 — Фальшивая сила\n**Система.** поддельная",
  "levels": [{ "level": 1, "name": "Реальная сила", ... }] }
```
`GET /api/library/disciplines` после этого отдаёт дисциплину с **двумя** уровнями: настоящим (level 1) и полностью выдуманным (`level: 99, name: "Фальшивая сила"`, чьё поле `system` вдобавок «съело» соседнюю строку `- **Авторское:** да` из-за жадности `splitPowerBody`'s regex).

**Почему это весомо, а не мелочь:** это справочная библиотека — фальшивый уровень силы был бы виден ЛЮБОМУ пользователю приложения, открывшему эту дисциплину (не только автору записи), как будто это часть настоящего описания.

**Рекомендация:** `sanitizeInlineText(clans)`, `sanitizeInlineText(source)` в `_discTemplate`/`_psyTemplate` перед вставкой — `note` уже безопасен (построчно с `> ` — блок-цитатой), `levels[].literary`/`.system` тоже стоит прогнать через `sanitizeFreeformBody`, если они лежат в теле секции (не проверял отдельно, тот же принцип).

## 4. [ВЫСОКАЯ] Создание города: `|` в «Политическом ландшафте» ломает «Карту фракций»

**Компонент:** `web/routes/cities.js` — `parsePoliticalRecords` (127-147) и `syncPoliticalStateTable` (150-181), вызывается и при `POST /api/cities` (создание), и при `PUT /api/cities/:slug` (правка).

**Первопричина:** валидация значения роли (`valueOk = value.length > 0 && value.length <= 48 && !/[.!?,;]/.test(value)`) не исключает `|` — строка вида `Князь: Тест|ВЗЛОМ_ЯЧЕЙКА` проходит фильтр как «структурная» запись и попадает в таблицу без экранирования.

**Шаги (воспроизведено):**
```
POST /api/cities
{ "name": "QA Тестовый Город", "year": "2010", "political": "Князь: Тест|ВЗЛОМ_ЯЧЕЙКА" }
```
`archive/political_state.md` получает строку из 5 колонок вместо 4:
```
| Князь | Тест|ВЗЛОМ_ЯЧЕЙКА |  |  |
```

**Рекомендация:** `escapeTableCell` на `persons`/`clan`/`role` в `syncPoliticalStateTable` перед сборкой строки (`newRows.map(r => [...])`), либо добавить `|` в список запрещённых символов в `parsePoliticalRecords`'s `valueOk`/`labelOk` (что просто отбросит такую строку из структурного разбора, а не исправит её).

## 5. [НИЗКАЯ/СРЕДНЯЯ] Поиск: невалидный UTF-16 в имени при определённых эмодзи

**Компонент:** `web/routes/dashboard.js:195`:
```js
const h1 = s => { const m = s.match(/^#\s+(.+)$/m); return m ? m[1].replace(/[🧛🧚🧑🐺🔮🏹⚔️🩸*_]/g, '').trim() : ''; };
```

**Первопричина:** символьный класс с эмодзи вне astral-safe `/u`-флага компилируется в JS как набор отдельных UTF-16 code units, а не кодпоинтов. Эмодзи из одного суррогатного блока с любым эмодзи из списка (например `🐺` U+1F43A и `👤` U+1F464 — оба в блоке `U+1F400-1F4FF`, значит с одинаковым старшим суррогатом `\ud83d`) — при замене теряют только СВОЮ половину суррогатной пары, если она совпала с половиной из списка, оставляя вторую половину «осиротевшей».

**Доказано напрямую в Node:**
```
> "👤 Аня Грос".replace(/[🧛🧚🧑🐺🔮🏹⚔️🩸*_]/g, '')
'\udc64 Аня Грос'      // невалидный UTF-16 — одинокий low surrogate
```

**Подтверждено live** — в результатах поиска по «вампир» минимум 3 персонажа (Аня Грос, Эмбер, Ален Дюбуа — все с `👤` в H1 карточки) показывают «�» вместо эмодзи в начале имени.

**Рекомендация:** заменить символьный класс на построение из `Array.from()` конкретных эмодзи (кодпоинт-safe) либо на общий паттерн `[^\wА-Яа-яЁё]*` (тот же, что уже используют `parseCharacter`/`EMOJI_RE` в `lib/disciplines.js`/`lib/parsers/character.js`) — не хардкодить список конкретных эмодзи по одному.

## Проверено и работает корректно

- **Создание НПС/модуля через «Инструменты»** — вкладки переключаются, формы валидны (см. также FIX-9 и предыдущий QA-цикл по модулям).
- **Node-инструменты** (`POST /api/tool/:name`) — белый список `NODE_TOOLS`, `args` передаются как argv-массив в `spawn` без построения команды строкой → безопасно от инъекции (в отличие от находки 1).
- **Библиотека** — список дисциплин/способностей/достоинств/недостатков грузится, `merits`/`flaws`/`backgrounds` PUT/DELETE безопасны от path traversal (категория — по белому списку, slug используется только как ключ поиска в JSON-массиве, не как путь на диске).
- **Создание города** — happy path (валидный `name`+`year` → `200`, каркас файлов создан), отсутствие `name`/`year` → `400`, невалидный формат года → `400`, дубликат slug → `409`, откат при ошибке записи (частично созданная папка сносится).
- **Поиск** — граница минимальной длины запроса (3 символа) соблюдается, пустой запрос не роняет сервер, запрос со спецсимволами (`+*?[]`) не ломает поиск (сервер ищет как строку через `.indexOf`, не как regex — не подвержен ReDoS/regex-инъекции), несуществующий город → `400`, результаты по категориям (персонажи/локации/модули/события/архив) корректно агрегируются, HTML в описании персонажа корректно экранируется на фронте перед вставкой (`escHtml` до подсветки совпадения).
- Полный live-обход открытых страниц — 0 ошибок в консоли браузера (не считая визуальной находки 5, которая не бросает JS-исключение).
