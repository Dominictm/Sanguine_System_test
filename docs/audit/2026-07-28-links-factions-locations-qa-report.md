## Executive Summary

Нашёл **одну критическую находку** — путь до файла при создании локации
собирается из пользовательского ввода без какой-либо санитизации,
подтверждённый **выход за пределы `cities/<город>/locations/`** на
файловой системе. Плюс **четыре дополнительных подтверждения** уже
известного из прошлого отчёта паттерна «символ `\|` рвёт
pipe-структуры» — теперь counted пять мест, а не три (см. FIX-2 в
[`2026-07-28-fix-plan.md`](2026-07-28-fix-plan.md), этот отчёт расширяет
его объём). Отдельно — два по-настоящему новых дефекта в резолвинге
связей графа (нечёткое сопоставление имён и потеря одной стороны
несимметричной связи).

## Найденные дефекты

### 1. [КРИТИЧНЫЙ] Path traversal через поле `district` при создании локации

**Компонент:** `POST /api/locations` (`web/routes/locations.js:270-325`).

**Контракт сейчас:**
```js
const distFolder = district?.trim() || 'Другие';
const locDir = path.join(locsDir(city), distFolder, locSlug);
```
`name` перед использованием в пути проходит `slugify()` (только
`[a-z0-9_]`). **`district` — нет**: используется как сегмент пути после
одного лишь `.trim()`.

**Шаги:**
```
POST /api/locations?city=qa_test_city_2
{ "name": "ПробаТраверсал", "district": "../../qa_traversal_probe" }
```

**Фактический результат (подтверждено на диске):** файл создан по пути
`cities/qa_traversal_probe/probatraversal/probatraversal.md` — **на два
уровня выше `cities/qa_test_city_2/locations/`, полностью вне домена
города**, как отдельная папка-сосед `cities/`. В тесте намеренно
использовал короткий, безопасный traversal (уход на 2 уровня внутрь
`cities/`, не глубже) — но санитизации нет вообще никакой, глубина
ограничена только тем, что введёт вызывающий: `district` с достаточным
количеством `../` способен писать markdown-файлы в произвольное место
файловой системы, куда у процесса Node есть доступ на запись.

**Для сравнения:** соседний эндпоинт загрузки арта (`upload-image`)
хотя бы фильтрует `ext` через `[^a-z]`; здесь — вообще без обработки.

**Рекомендация:** прогонять `district` через тот же `slugify()`, что и
`name` (или через строгий `/^[\p{L}\p{N} _-]+$/u`-вайтлист, раз для
округа хочется сохранить читаемое название папки, а не транслит) —
**до** любого использования в `path.join`. Отдельно стоит аудитом
пройтись по `web/routes/generation.js:516` и
`web/routes/characters.js:818` (`req.body.chronicle`/`req.body.chr`+`mod`
используются в `path.join(...)` для ЧТЕНИЯ файлов, без вайтлиста) — та
же первопричина, только на чтение, а не на запись; не тестировал глубоко
(вне объёма «Связи/Фракции/Локации» на сегодня), но стоит того же фикса
по аналогии.

### 2. [ВЫСОКИЙ] Символ `\|` ломает pipe-структуры — ещё два новых места (расширяет FIX-2)

Прошлый отчёт (`2026-07-28-characters-chronology-qa-report.md`) уже
фиксировал этот паттерн в «Отношениях» (`\n`) и «Хронологии
мира»/«Состоянии мира» (`\|`). Сегодня нашёл его ещё в двух местах:

**2а. Название фракции с `\|` при создании через структурированный
эндпоинт**

`PUT /api/factions/influence` с `{ name: "Анархи | Шабаш QA", influence: 30 }`
на несуществующую фракцию → строка новой фракции собирается как
`` | ${name} | ${cellText} |  |  | `` (`web/lib/parsers/city.js:282`,
ветка «таблицы ещё нет», и аналогично в ветке добавления новой строки
при существующей таблице) — без экранирования. **Подтверждено на
диске и в UI** (скриншот): после инъекции `parsePoliticalFactions`
разбирает строку неверно — `name: "Анархи"`, `influence: 0` (в ячейке
«Сила» оказался текст `"Шабаш QA"`, из которого не извлечь число), а
реальное значение `30%` тихо съехало в колонку «Территория». На
странице «Фракции» это видно напрямую: полоса влияния «Анархи» пустая
(0%), при этом в таблице «Баланс сил» строка `Анархи | Шабаш QA | 30% | `.

**2б. Инлайн-метаданные локации (`Округ`/`Район`/`Адрес`/`Зона`/
`Контроль`) — та же уязвимость, но в ДРУГОМ формате хранения**

Эти поля живут не в pipe-**таблице**, а в pipe-разделённой инлайн-строке
сразу под заголовком карточки локации:
```
> **Название:** X | **Округ:** Y | **Район:** Z | ...
```
`PUT /api/locations/:slug/fields` с `{ fields: { district: "Новый Округ | с пайпом" } }`
пишет значение как есть (`web/routes/locations.js:207-215`, та же
lookahead-регулярка `(?=\s*\|\s*\n|$)`, что ищет следующий `|` как
границу поля). **Подтверждено на диске** (сохранённая карточка):
```
> **Название:** КачТестЛокация | **Округ:** Новый Округ | с пайпом | **Район:** [район] | ...
```
— «с пайпом» повисает между «Округ» и «Район» как посторонний текст,
неотличимый от валидного поля на вид, но не являющийся им.

**Итого мест с одной и той же первопричиной — уже пять**: Отношения
(`\n`), Хронология мира (`\|`), Состояние мира (`\|`), Влияние фракций
(`\|`, новое), инлайн-метаданные локации (`\|`, новое, ещё и другой
формат хранения — не таблица, а строка). Рекомендация не меняется
(общий модуль санитизации/экранирования), но объём фикса в
`2026-07-28-fix-plan.md` (FIX-2) стоит расширить на эти два места
перед реализацией.

**Проверил отдельно и НЕ нашёл той же проблемы** в поле `vtmText`
локации — туда `|`-текст ложится как обычный абзац прозы перед
таблицей, а не в саму ячейку, так что структуру не рвёт (этому полю
конкретно повезло с реализацией, не системная защита).

### 3. [ВЫСОКИЙ] Граф связей: нечёткое сопоставление имени резолвит связь к случайному «похожему» персонажу без предупреждения

**Компонент:** `resolveTarget()` внутри `GET /api/graph`
(`web/routes/dashboard.js:80-87`).

**Контракт сейчас:** если текст связи не совпадает с именем персонажа
**точно**, включается fuzzy-фолбэк: `id.startsWith(target) ||
target.startsWith(id.split(' ')[0])`, и возвращается **первый** элемент
`Set`, подошедший под условие — порядок не документирован, не
детерминирован для внешнего наблюдателя.

**Шаги:** создать «Иван Петров» и «Иван Сидоров» (разные, оба валидные
персонажи). У третьего персонажа — связь с текстом цели `"Иван"` (без
фамилии).

**Фактический результат (подтверждено в JSON и на графе):** связь
резолвится к **«Иван Петров»** — «Иван Сидоров» остаётся полностью
изолированным узлом на графе, никак не помечен как «была
неоднозначность». Пользователь, вписавший укороченное имя, получит
тихо неверную связь без единого сигнала о том, что имя не было
однозначным.

**Рекомендация:** либо убрать fuzzy-фолбэк совсем (только точное
совпадение, несовпавшие связи явно не рисовать — так честнее, чем рисовать
неверно), либо, если фолбэк нужен для опечаток по одному
персонажу-цели, — при **множественных** кандидатах не выбирать первого
молча, а не резолвить вовсе (эквивалент `return null`), раз выбор
неоднозначен.

### 4. [СРЕДНИЙ] Граф связей: несимметричная связь между двумя персонажами — видна только одна сторона

**Компонент:** дедупликация рёбер в `GET /api/graph`
(`web/routes/dashboard.js:95-97`): `key = [a, b].sort().join('\x00');
if (seen.has(key)) continue;`.

**Контракт сейчас:** ребро между двумя персонажами считается
неориентированным и добавляется **один раз** — по тому, чья связь
попалась первой при переборе персонажей.

**Шаги:** «АлексТест» → «БорисТест»: `Враг, давняя вражда`.
«БорисТест» → «АлексТест» (отдельно, с другим текстом):
`Союзник, боевое братство`.

**Фактический результат (подтверждено в JSON и на графе):** видно
только ребро «Враг» (со стороны Алекса). Про то, что Борис в своей
карточке считает Алекса союзником, на графе — ни следа, эта половина
данных не теряется на диске (обе карточки хранят свой текст верно), но
**визуально недостижима**.

**Оценка важности:** для игры про политические интриги
(«несимметричная лояльность», «думает, что друг, а его считают
врагом») это не техническая мелочь, а потеря именно того типа
информации, ради которой граф и нужен. Минимум — показывать оба
направления отдельными рёбрами (или одним двухцветным/двухподписным
ребром), а не тихо оставлять только одно.

## Что проверено и работает корректно

- **Фракции** — валидация влияния (0-100, шаг 5 с округлением),
  обязательность имени, `404` на удаление несуществующей фракции — всё
  корректно. Отдельно проверил: обновление влияния **существующей**
  фракции по точному совпадению имени не подвержено находке №2а — там
  меняется только числовая ячейка, инъекция актуальна именно для ветки
  создания **новой** строки.
- **Локации** — создание с уникальным `slug` (`409` на дубликат имени),
  обязательность `name` (`400`), мягкое удаление (архивация в
  `_deleted/`), повторное удаление — `404`, список пуст/не пуст
  корректно.
- **Граф** — при отсутствии неоднозначностей резолвинг по точному имени
  работает верно, узлы/рёбра/раскраска по типу связи, фильтры по
  линейке и типу связи (сохраняется в прошлых отчётах этой сессии —
  сегодня отдельно не перепроверял, фокус был на резолвинге данных).
- Ни на одной из трёх страниц (Связи/Фракции/Локации) не найдено ошибок
  в консоли браузера при обычной навигации.
