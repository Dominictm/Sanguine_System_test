# QA-отчёт: создание персонажей — для аналитика

**Дата:** 2026-07-28
**Автор:** роль «Тестировщик» (QA Lead)
**Объект тестирования:** мастер создания персонажа («Инструменты → Новый НПС», форма `#tab-new-npc`
в `web/public/index.html`, обработчик `web/public/scripts/scripts.js:1790`, backend
`POST /api/characters` в `web/routes/characters.js:315`, а также сопутствующий
`POST /api/characters/:slug/upload-image`).

**Оговорка по объёму (логическая неточность в исходной задаче):** задача
«глубокое тестирование создания персонажей» не уточняла канал — форма в вебе,
прямой вызов REST API или CLI-инструмент `tools/new_npc.js`. Протестирован
основной пользовательский путь: веб-форма + REST API, который она вызывает
(это единственный путь, которым реально пользуется Рассказчик). `tools/new_npc.js`
(CLI-дублёр той же функциональности) и конкурентное создание (несколько
одновременных запросов) в объём не входили — отдельная задача, если нужно.

**Тестовое окружение:** локальный dev-сервер (`localhost:4295`), город
**`balmont`** — существующий тестовый/черновой домен проекта (плейсхолдер в
`city.md`, персонажи с именами вроде `vapvapva`), не боевые данные
Рассказчика (`paris`). Все тестовые персонажи созданы и удалены в рамках
тестирования, `git status` после — чист.

## Executive Summary

Позитивный сценарий (создание персонажа по всем 6 линейкам с валидными
данными) работает корректно и полностью соответствует контракту
`system/schema/card_schema.md`: слаг, реестр `characters_index.md`, файловая
структура (`art/`, `journal/`, `<slug>-sheet.json`) — без нареканий.

Найдено **6 дефектов**, один из них — **высокой серьёзности (потенциальный
stored-XSS через загрузку арта)**. Остальные пять — по одному в валидации
(тихий fallback линейки), по одному в целостности данных (утечка
клан/секта вампира в карточку оборотня при смене линейки на форме) и по
одному в обработке ошибок (необработанный 500 на длинном имени), плюс два
низкоприоритетных наблюдения об охвате формы и городе по умолчанию.

## Найденные дефекты

### 1. [ВЫСОКИЙ] Stored XSS через загрузку «Арта» персонажа

**Компонент:** `POST /api/characters/:slug/upload-image` (`web/routes/characters.js:540`),
раздаётся статикой через `express.static` (`web/server.js:85`, без `helmet`/`nosniff`/CSP
где-либо в проекте).

**Предусловия:** персонаж уже создан (эндпоинт переиспользуется и полем «Арт» в
форме создания, и загрузкой арта у существующей карточки).

**Шаги:**
1. `POST /api/characters/:slug/upload-image` с телом `{ base64: <base64 от `<script>...</script>`>, ext: "html" }`.
2. Открыть URL из ответа (`url` в JSON-ответе).

**Ожидаемый результат:** сервер отклоняет не-изображение (проверка
magic-bytes/MIME) либо отдаёт файл с `Content-Disposition: attachment` /
`X-Content-Type-Options: nosniff`, чтобы браузер не исполнял содержимое.

**Фактический результат:** файл сохраняется как `<slug>_01.html`
(`ext` фильтруется только `[^a-z]` — «html» проходит как «буквы»), отдаётся
с `Content-Type: text/html`, без `nosniff`. При открытии URL напрямую —
встроенный `<script>` выполняется в origin приложения.

**Причина:** клиентский `accept="image/jpeg,image/png,image/webp,image/gif"`
на `<input type="file">` — это подсказка UI, не проверка; сервер не
верифицирует ни фактическое содержимое (magic bytes), ни расширение против
белого списка.

**Риск в контексте приложения:** локальный однопользовательский инструмент
(обычно `localhost`/LAN), поэтому не «публичный интернет XSS», но всё равно
реальный: ссылка на карточку персонажа может быть переслана (скрин/бэкап
папки города, будущий мультиплеерный доступ через LAN — сервер слушает на
всех интерфейсах, см. наблюдение №6 ниже), либо файл откроется случайно.

**Рекомендация:** на сервере — белый список расширений (`jpg|jpeg|png|webp|gif`)
+ проверка magic bytes (или простая проверка первых байт буфера), отклонять
остальное 400-й; отдавать `art/` с `X-Content-Type-Options: nosniff`.

### 2. [СРЕДНИЙ] Тихий fallback на `mortals` при невалидной/отсутствующей `lineage`

**Шаги:**
1. `POST /api/characters` с `lineage: "vampires"` (опечатка/множественное число вместо `"vampire"`) либо вовсе без поля `lineage`.
2. Остальные поля валидны (`name`, `gender`).

**Ожидаемый результат:** `400` с понятной ошибкой («неизвестная линейка»).

**Фактический результат:** `200 OK`, персонаж молча создаётся как
**Смертный** (`_LIN_FOLDER[b.lineage] || 'mortals'`, `web/routes/characters.js:320`).

**Почему это важно:** через саму веб-форму это не воспроизвести (`<select>`
всегда шлёт одно из 6 валидных значений) — риск только при прямом вызове
API (скрипт, будущая интеграция, ручной вызов из консоли), но именно
поэтому дефект «тихий» — ни один из существующих тестов/линтеров его не
поймает, а результат (персонаж не той линейки) обнаружится не сразу.

**Рекомендация:** `if (!_LIN_FOLDER[b.lineage]) return res.status(400).json({error: 'Неизвестная линейка'})` вместо `|| 'mortals'`.

### 3. [СРЕДНИЙ] Утечка «Клан»/«Секта» вампира в карточку другой линейки при смене линейки на форме

**Предусловия:** открыта форма «Новый НПС».

**Шаги:**
1. Линейка = Вампир, вписать Клан = «Бруха», Секта = «Камарилья».
2. Переключить Линейку на «Оборотень» (или любую невампирскую) — **не
   трогая руками поля Клан/Секта**.
3. Заполнить обязательные Имя/Пол, нажать «Создать карточку».

**Ожидаемый результат:** поля «Клан»/«Секта» либо очищаются при смене
линейки, либо не попадают в карточку не-вампира без явного заполнения
пользователем заново.

**Фактический результат (воспроизведено живьём через API+файл):**
```
- **Клан / Раса:** Бруха
- **Секта / Двор:** Камарилья
```
— в карточке **Оборотня**. `_updateNpcForm()` (`scripts.js:1779`) переключает
только `display` блоков `#npc-vamp-fields`/`#npc-fairy-fields` и `*`-индикаторы
обязательности — сами инпуты `#npc-clan`/`#npc-sect` (общий `.form-row`,
строки 1026–1035 `index.html`) **всегда видимы и никогда не очищаются** при
смене `<select id="npc-type">`.

**Почему это важно:** данные лорно бессмысленны («Клан: Бруха» у оборотня)
и никем не перепроверяются — ни клиентской, ни серверной валидацией, ни
`validate_cards.js` (линтер сверяет «Линейка WoD» с папкой, но не
семантику клана/секты против линейки).

**Рекомендация:** очищать `#npc-clan`/`#npc-sect` в `_updateNpcForm()` при
каждой смене линейки (или хотя бы при уходе с «Вампир»/«Фея»).

### 4. [СРЕДНИЙ] Необработанный `500` на очень длинном имени персонажа

**Шаги:** `POST /api/characters` с `name` длиной ~500 символов (валиден по
всем прочим полям).

**Ожидаемый результат:** `400` с понятной ошибкой («слишком длинное имя»).

**Фактический результат:** `500 Внутренняя ошибка сервера`. В логе сервера —
`ENOENT: no such file or directory, mkdir '...\characters\mortals\<464-символьный
слаг>'` (`web/routes/characters.js:392`, `fs.mkdir`) — упирается в лимит
длины пути Windows (легаси `MAX_PATH` ~260 символов без включённой
поддержки длинных путей).

**Рекомендация:** ограничить `name` разумной длиной (например, 100 симв.)
на клиенте (`maxlength`) и на сервере (`400`, а не падать в `fs.mkdir`).

### 5. [НИЗКИЙ] Отсутствующий параметр `city` не отклоняется, а тихо уходит в город «по умолчанию»

`reqCity()` (`web/lib/db.js:28`) при отсутствии `?city=` подставляет
`DEFAULT_CITY` — переменную окружения `CITY` либо (если не задана — как в
этой инсталляции) **первый по алфавиту каталог в `cities/`** на момент
старта сервера. Сейчас это `balmont`, но это случайность алфавита, а не
осознанный выбор; будь порядок другим — тем же путём можно было бы
случайно создать персонажа в чужом/боевом городе. Обычная форма всегда
шлёт `?city=`, поэтому риск только при прямом вызове API. Рекомендация:
require `city`, `400` при отсутствии, вместо тихого fallback.

---

### 6. [НИЗКИЙ / полнота формы] Оборотень / Маг / Охотник не получают
специфичных для линейки полей при создании — в отличие от Вампира и Феи

Форма даёт доп.-поля только для Вампира (Поколение/Год рождения/Год
обращения/Сир) и Феи (Обличье/Двор/Дом). Для Оборотня/Мага/Охотника —
только общие Биография/Внешность; при этом:
- у Оборотня/Мага/Охотника **не создаются** поля «Натура»/«Маска»
  (`hasNatureDemeanor = isVamp || mortal || fairy`, `characters.js:354`,
  хотя это общие классические черты WoD, не вампирские);
- при этом `system/rules/character_sheet_werewolf.md` и `character_sheet_mage.md`
  **существуют** и описывают специфику (Племя/Каста/Дары — оборотень;
  Традиция/Сферы — маг) — то есть система «знает» об этих линейках глубже,
  чем форма создания позволяет заполнить сразу.

Это не баг в строгом смысле (ничего не падает, персонаж создаётся
корректно), а вопрос полноты UX — актуальность решает аналитик/продукт:
дозаполнять эти поля сейчас можно только вручную после создания через
редактирование карточки/вкладку «Лист V20».

## Non-functional / контекстные наблюдения (не баг конкретно этой фичи)

- **Сервер слушает на всех интерфейсах** (`app.listen(PORT, ...)` без
  `host`, `web/server.js:1075`) — не только `localhost`, но и LAN. В
  сочетании с находкой №1 (XSS через арт) и отсутствием CORS/CSRF-защиты
  это расширяет теоретическую поверхность атаки за пределы «только я на
  своей машине». Не проверялось глубже — вне объёма задачи по созданию
  персонажей, но стоит держать в поле зрения при следующем security-review.
- CSRF по POST `/api/characters` вручную не воспроизведён: `express.json()`
  требует `Content-Type: application/json`, а кросс-origin `fetch` с таким
  заголовком триггерит CORS preflight, который без настроенных
  `Access-Control-Allow-*` браузер блокирует сам — то есть простая
  форма-CSRF или fetch с чужого сайта здесь не проходит «из коробки».

## Что проверено и работает корректно (не дублировать в фиксах)

- Валидация обязательных полей (Имя/Пол, Клан+Секта для вампира, Обличье
  для феи) — идентична на клиенте и сервере, ошибки понятные.
- Пустое имя / имя из пробелов / имя из одних эмодзи-пунктуации —
  корректно отклоняются (`400`, включая явную ошибку «не удалось
  сформировать slug»).
- Дубликат имени (точное совпадение и через регистр/пробелы, слагifицирующиеся
  в тот же slug) — `409` с понятным сообщением, второй персонаж не создаётся.
- `characters_index.md` — корректно пополняется при каждом создании, без
  повреждений после серии из 9 подряд идущих созданий в тесте.
- Карточка персонажа при позитивном сценарии полностью соответствует
  `system/schema/card_schema.md` (обязательные поля, секция «🖼️ Изображения»).
- `ext` в загрузке арта защищён от path traversal (`[^a-z]` фильтр отсекает
  `../`, `\`, `%2e%2e` и т.п.) — сама загрузка не может писать за пределы
  `art/`, проблема (находка №1) именно в отсутствии проверки содержимого.
