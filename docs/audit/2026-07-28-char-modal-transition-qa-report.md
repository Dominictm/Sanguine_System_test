## Найденные дефекты

### 1. [ВЫСОКИЙ] Панель «Описание»: снятие значения поля не сохраняется на сервере — интерфейс лжёт об успехе

**Компонент:** `_savePanelEdit('desc', ...)` (`web/public/scripts/char-detail.js:528-556`).

**Шаги:**
1. Открыть персонажа → вкладка «Описание» → Редактировать.
2. Заполнить «Голос»: `Хриплый голос с придыханием` → Сохранить.
   *(файл на диске: `- **Голос:** Хриплый голос с придыханием` — верно)*
3. Снова Редактировать → очистить поле «Голос» полностью → Сохранить.

**Ожидаемый результат:** поле «Голос» пустеет и в интерфейсе, и в файле
карточки.

**Фактический результат:** интерфейс показывает пустое поле (секция
«Голос» пропадает из вида, «✓ Сохранено»), но **файл на диске не
меняется** — строка `- **Голос:** Хриплый голос с придыханием` остаётся
как была. Подтверждено прямым чтением файла до/после в одном прогоне.

**Причина:** `_savePanelEdit` для панели «desc» кладёт в `fields` только
ПРАВДИВЫЕ (non-empty) значения:
```js
if (appearance)   fields.appearance    = appearance;
if (voice)        fields.voice         = voice;
...
```
Если поле очищено, `voice === ''` — falsy — ключ `voice` вообще не попадает
в тело запроса `PUT /fields`, а серверный обработчик обновляет только
ключи, которые реально присутствуют в `fields` (`web/routes/characters.js:228`)
— то есть для сервера «поле не упомянуто» неотличимо от «поле не
трогали». Локально в `STATE.characters` и во view при этом значение
затирается на пустое (`Object.assign(ch, {voice: '', ...})`,
`web/public/scripts/char-detail.js:547`) — отсюда и расхождение: до
перезагрузки страницы интерфейс показывает «пусто», а сервер хранит
старое значение; после **обновления страницы старый текст молча
возвращается**, что выглядит как «правки потерялись».

**Затронутые поля** — все пять на вкладке «Описание»: Внешность, Голос,
Характер, Промт для генерации изображения, Негативный промт. Для
сравнения: панель «Биография» (соседний код, `_savePanelEdit('bio', ...)`)
эту ошибку не повторяет — там `biography` шлётся безусловно, даже пустой
строкой, поэтому там очистка работает корректно.

**Рекомендация:** убрать условие `if (x) fields.x = x` в `desc`-ветке —
слать все пять полей всегда (как это уже сделано для `bio`), доверяя
серверу писать пустое значение как есть.

### 2. [ВЫСОКИЙ] Совпадение имён персонажей → клик по «второй» карточке открывает данные «первой»

**Компонент:** `openCharDetail(name)` (`web/public/scripts/char-detail.js:30-32`)
и вспомогательный `_charSlug(name)` (`scripts.js:1575`) — оба резолвят
персонажа **по отображаемому имени**: `STATE.characters.find(ch => ch.name
=== name)`, что при совпадении возвращает первый по порядку элемент, вне
зависимости от того, по какой именно карточке кликнули.

**Предусловие:** два персонажа с одинаковым именем в одном городе — это
возможно: слаг (использующийся для проверки дубликатов при создании)
уникален, а вот **переименование через `PUT /fields`
(`key === 'name'`) не проверяет уникальность нового имени вообще** — так
можно легко довести до коллизии, переименовав одного персонажа под имя
другого.

**Шаги:**
1. Создать «КачТестКоллизияА» и «КачТестКоллизияБ» (разные слаги).
2. Переименовать «КачТестКоллизияБ» → «КачТестКоллизияА» через `PUT /fields`.
3. В списке «Персонажи» теперь две визуально идентичные карточки
   «КачТестКоллизияА». Кликнуть по **второй** (соответствующей слагу
   `kachtestkolliziyab`).

**Ожидаемый результат:** открывается персонаж, соответствующий именно той
карточке, по которой кликнули (`kachtestkolliziyab`).

**Фактический результат (подтверждено кликом именно по второму DOM-узлу):**
всегда открывается **первый** по порядку в `STATE.characters`
(`kachtestkolliziyaa`) — независимо от того, по какой из двух карточек
кликнули. **Персонаж `kachtestkolliziyab` становится полностью недостижим
через интерфейс** — открыть, отредактировать или удалить его через модалку
нельзя, только прямым вызовом API по слагу.

**Рекомендация:** либо (а) добавить проверку уникальности имени в `PUT
/fields` при переименовании (аналогично проверке слага при создании) —
самый простой и, возможно, единственно нужный фикс, раз коллизия и есть
корень проблемы; либо (б), если коллизии имён должны быть разрешены
осознанно (два игровых персонажа с одинаковым именем — не редкость в
художественном тексте), резолвить персонажа по слагу, а не по имени, во
всех местах, включая `data-name` на карточках.

## Non-functional / мелкие наблюдения

- **[НИЗКИЙ] Таймер карусели портретов не останавливается при закрытии
  модалки через Escape или клик по фону** — только явный клик по кнопке
  ✕ (`#char-detail-close`) отменяет `_carouselTimer`
  (`web/public/scripts/char-detail.js:439`, `{capture:true}`, только на
  этой кнопке). Подтверждено живьём: после Escape-закрытия модалки с
  персонажем о 2+ фото `_carouselTimer !== null` остаётся `true`. Не
  критично — при следующем открытии ЛЮБОЙ карточки `initCarousel()`
  корректно чистит предыдущий таймер (`web/public/scripts/char-detail.js:372`),
  так что залипает он не дольше, чем до следующего открытия модалки, и
  просто крутит скрытые/удалённые DOM-узлы вхолостую. Рекомендация:
  вынести очистку таймера в общий обработчик закрытия (по клику на фон и
  по Escape тоже), а не только на кнопку ✕.

## Проверенная гипотеза, которая НЕ подтвердилась (важно для протокола)

Читая код удаления персонажа из модалки (`scripts.js:2380`, обновление
списка после `DELETE`), заметил, что вызов `fetch('/api/characters')` в
явном виде не дописывает `location.search` (`?city=...`), в отличие от
соседних вызовов в той же функции — предположил риск «после удаления
список молча переключится на город по умолчанию сервера». **Проверил
живьём (одноразовый третий город, отличный от серверного дефолта) — не
воспроизвелось**: список персонажей после удаления остался на правильном
городе. Причина — в проекте есть глобальный перехватчик
`window.fetch` (`web/public/scripts/scripts.js:5-13`), который
прозрачно дописывает `?city=` **на каждый** `/api/`-запрос, если его там
ещё нет — так что этот конкретный вызов защищён на уровне транспорта,
несмотря на то что сам не заботится об этом явно. Упоминаю, чтобы
никто больше не наступал на те же грабли при чтении этого кода: находка
№5 из первого отчёта («молчаливый city-фолбэк») актуальна **только для
прямых вызовов API в обход браузера** (curl/скрипт/интеграция) — из
самого веб-интерфейса не воспроизводится никогда, ровно из-за этого
перехватчика.

## Что проверено и работает корректно

- **Переключение вкладок** (Информация/Биография/Отношения/Дневники/Лист
  V20/Описание) — активный класс, видимость панели и объём отрисованного
  содержимого корректны на всех 6 вкладках, без ошибок в консоли.
- **Ленивая подгрузка «Лист V20»** — контент подгружается только при
  первом клике на вкладку (не заранее), полноценно рендерится (~57 КБ
  разметки листа).
- **Модальная фокус-ловушка и Escape** — `Escape` закрывает модалку,
  фокус возвращается на элемент, с которого её открыли (`openModal`/
  `closeModal` в `utils.js` — общая, хорошо спроектированная реализация:
  защита от «двойного» открытия без утечки обработчика, Tab-циклирование
  внутри модалки).
- **Открытие модалки по клику на карточку** — для персонажей с уникальным
  именем открывается корректный персонаж, все связанные данные (портрет,
  бейджи, отношения, дневники) соответствуют кликнутой карточке.
