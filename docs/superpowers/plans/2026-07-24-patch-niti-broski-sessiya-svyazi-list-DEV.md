#### Тикет 1.2 — Скролл + подсветка целевой нити на странице Нити
**Зависит от 1.1** (использует `_pendingThreadFocus`, который 1.1 объявляет и наполняет — можно делать в одном тикете одним агентом, либо строго последовательно, если разными).

**Целевое состояние.**
- В конце `loadThreads()`, после установки `innerHTML`: если `_pendingThreadFocus` задан — найти `document.querySelector('.thread-card[data-id="…"][data-file="…"]')` (экранировать значения при подстановке в селектор через `CSS.escape` или атрибутный поиск через `querySelectorAll` + `find`, чтобы избежать поломки на спецсимволах в пути файла), вызвать `el.scrollIntoView({ behavior: reduced ? 'auto' : 'smooth', block: 'center' })` (где `reduced = matchMedia('(prefers-reduced-motion: reduce)').matches` — **скролл-поведение, не только CSS-анимация, обязано учитывать reduced-motion**, иначе плавный `scrollIntoView` сам по себе останется движением при заявленном отключённом), добавить класс `thread-card--focus`, снять его через `setTimeout(…, 2000)`. Обнулить `_pendingThreadFocus = null` сразу после обработки (чтобы обычный повторный заход на «Нити» не переигрывал фокус).

Это согласуется с «The Whisper-Until-Touched Rule»: сигнал не в покое, а как одноразовая реакция на конкретное действие (переход по клику), что и оправдывает его временность. Обернуть анимацию появления/затухания в `@media (prefers-reduced-motion: no-preference)`, при reduced-motion — подсветка статична (класс есть/нет, без транзишена).
**Критерий готовности.** Переход из дашборда прокручивает список Нитей к конкретной карточке и на ~2 секунды подсвечивает её; обычный переход на «Нити» без клика по «Висящим нитям» — без скролла/подсветки.
**Тесты (source-guard).** Новый `it()` в `all.test.js`: `scripts.js` содержит `data-thread-id`; `archive.js` содержит `_pendingThreadFocus` и `scrollIntoView`; `styles.css` содержит `.thread-card--focus`.

#### Тикет 2.1 — Бросок без выбранного персонажа
**Файл.** `web/public/scripts/dice.js`.
**Текущее состояние.** `_diceFillFromModel(m)` (строки ~59-80): при `!m || !m.attributes` — `attrSel.disabled = abilSel.disabled = true`, оба селекта получают только placeholder. Без персонажа выбрать атрибут/способность невозможно.
**Целевое состояние.**
- При `!m` — вместо отключения селектов заполнить их **полным** статическим списком: атрибуты — из `V20_ATTRS` (объявлен в `v20-sheet.js`, глобален, `dice.js` его уже читает на строке 68), способности — из `V20_ABILITIES` (аналогично глобален в `v20-sheet.js`, применить тот же паттерн обхода групп, что и для `V20_ATTRS` в строке 68: `for (const [group, list] of Object.entries(V20_ABILITIES)) for (const [key, label] of list) …`).
- Без персонажа значения атрибута/способности неизвестны — опции подставлять без числа в скобках (просто имя) или с плейсхолдером; значение `<option value="">` не задаётся автоматически, а пул (`#dice-pool`) пользователь вводит **вручную** числом, как сейчас работает при полностью пустом состоянии. `_diceApplySheetPool` (строка ~114-118) при отсутствии персонажа не должен пытаться просуммировать `attrSel.value + abilSel.value` (там нет чисел) — вызывать `_diceApplySheetPool` только когда `_diceModel` не `null`; при `_diceModel === null` выбор атрибута/способности в списке — чисто информационный (для истории броска), `#dice-pool` остаётся редактируемым как есть.
- База сложности при отсутствии персонажа остаётся дефолтной `6` (поле `#dice-diff` уже имеет такое значение по умолчанию в разметке — проверить `index.html`, при необходимости не менять, т.к. это уже дефолт).
**Критерий готовности.** Без выбора персонажа (`charSel.value === ''`) оба селекта показывают полный список атрибутов/способностей и НЕ отключены; пул задаётся вручную; сложность по умолчанию 6.

#### Тикет 2.2 — Скрыть нулевые способности/атрибуты из списка + опция «Не владеет» (+2 к сложности однократно)
**Файл.** `web/public/scripts/dice.js`.
**Зависит от 2.1** (правит ту же функцию `_diceFillFromModel`).
**Текущее состояние.** В `_diceFillFromModel` (строки ~71-78, с персонажем) в `abils` попадают все слоты с `slot.name` независимо от `val`, включая 0; атрибуты (строка ~67-69) — все безусловно.
**Целевое состояние.**
- При построении `attrs`/`abils` (ветка «есть персонаж») фильтровать `val > 0` — не включать в список пункты со значением 0. Это автоматически уберёт единственный штатный ноль-атрибут (Внешность Носферату) и любые непрокачанные способности.
- В список **способностей** (не атрибутов) добавить синтетическую опцию `«Не владеет»` со спец-value (напр. `unskilled`), добавляется **всегда**, независимо от того, есть ли у персонажа реальные способности с 0 (это не то же самое, что «показать нулевые» — это явный флаг «беру без специализации»).
- Ввести переменную/атрибут для базовой (введённой пользователем) сложности, отдельно от эффективной: при рендере `abilSel` навесить обработчик `change`, который проверяет `abilSel.value === 'unskilled'` и переключает состояние `_diceUnskilled = true/false`. Эффективная сложность = `base + (_diceUnskilled ? 2 : 0)`, где `base` — значение, которое сейчас лежит в `#dice-diff` **на момент выбора способности** (не значение поля после применения +2 — иначе повторное переключение накопит). Практическая реализация: хранить `diffEl.dataset.base` — устанавливать его при явном изменении пользователем `#dice-diff` (обработчик `input`/`change` на `diffEl`, если такого ещё нет — добавить) и при первой инициализации персонажа (= 6 по умолчанию); при выборе/снятии «Не владеет» — пересчитывать `diffEl.value = base + (unskilled?2:0)`, никогда не читая текущее `diffEl.value` как источник базы.
- При `abilSel.value === 'unskilled'`: способность даёт **0** к пулу (в `_diceApplySheetPool` — если `abilSel.value === 'unskilled'`, слагаемое способности = 0, а не `parseInt('unskilled')` = `NaN`→0, что технически уже сработало бы случайно, но нужно сделать это явным, не полагаясь на совпадение).
- Пример из ТЗ должен воспроизводиться буквально: Ловкость 4 + Вождение 2 → сложность 6 (база); переключить на «Не владеет» → сложность 8; переключить обратно на «Вождение 2» → сложность снова 6 (не 10).
- **Дизайн-находка (добавлено дизайн-ревью, не было в исходной формулировке тикета):** молчаливая мутация `#dice-diff` — поле, которое пользователь считает «своим» ручным вводом, вдруг меняется само на +2 без объяснения. Пользователь может не заметить прыжок 6→8 и не понять, откуда он взялся при следующем ручном изменении поля. У проекта уже есть готовый паттерн именно для «объяснить, что сейчас происходит с полем» — `fieldTip()`/`data-tip` (`ⓘ`, `tabindex="0"`, keyboard-accessible; используется «во всех формах», `web/public/scripts/utils.js:22`, вызывается напр. в `char-detail.js:21`, `city.js:436`). Добавить рядом с `#dice-diff` индикатор в этом же визуальном языке (`ⓘ`/бейдж), видимый ТОЛЬКО когда `_diceUnskilled === true`, с текстом вида «+2 — Не владеет»: не изобретать новый стиль подсказки, переиспользовать существующий `ⓘ`-паттерн (можно напрямую переиспользовать функцию `fieldTip`, передав статичный текст, либо short-inline `<span class="v20-auto-badge">`-подобный бейдж — свериться, какой из двух существующих в проекте паттернов «авто-значение» ближе; `_v20AutoBadge` в `v20-sheet.js` — тоже прецедент индикации «значение выставлено автоматически», возможно ближе по смыслу, чем `fieldTip`, — выбрать при реализации).
**Критерий готовности.** У персонажа с нулевыми способностями они не отображаются в списке; «Не владеет» присутствует всегда, даёт 0 кубиков и ровно +2 к БАЗОВОЙ сложности без накопления при повторных переключениях; ручное изменение `#dice-diff` пользователем обновляет базу; при активном «Не владеет» рядом с полем сложности виден индикатор, что +2 применено автоматически (в установленном визуальном языке проекта, не новый ad hoc элемент).
**Тесты (source-guard).** `dice.js` содержит `'unskilled'`, `dataset.base` (или эквивалентное имя, зафиксировать при реализации и заматчить именно его), фильтрацию `val > 0` в контексте `abils`/`attrs`, и индикатор авто-изменения сложности (искать по выбранному классу/тексту после реализации).

Вместо этого — узкий, не разрушающий regex-апсерт в духе уже существующего `_patchModuleMain` (`shared.js:604-617`, читает файл, точечно вставляет/правит строго определённые фрагменты регэкспами, не трогая остальное):

```js
// Добавить в shared.js рядом с _patchModuleMain
async function _upsertModuleSection(modDir, mod, heading, body) {
  const p = path.join(modDir, `${mod}.md`);
  let txt = await fs.readFile(p, 'utf-8').catch(() => '');
  const headingRe = new RegExp(`^##\\s+${heading.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')}\\s*$`, 'm');
  const m = headingRe.exec(txt);
  if (m) {
    // Заменить тело до следующего `## ` или конца файла
    const start = m.index + m[0].length;
    const rest = txt.slice(start);
    const nextIdx = rest.search(/\n##\s+/);
    const end = nextIdx === -1 ? txt.length : start + nextIdx;
    txt = txt.slice(0, start) + '\n\n' + body.trim() + '\n' + txt.slice(end);
  } else {
    txt = txt.replace(/\s*$/, '') + `\n\n---\n\n## ${heading}\n\n${body.trim()}\n`;
  }
  await writeFileAtomic(p, txt, 'utf-8');
}
```
(Псевдокод для передачи агенту-реализатору — не финальный код, но фиксирует принцип: точечная regex-замена одной секции, не полная реконструкция файла.)

- `PUT /api/chronicles/:chr/modules/:mod/session-notes` с телом `{ text }` → `_upsertModuleSection(modDir, mod, '📝 Заметки сессии', text)`.
**Критерий готовности.** Секция дописывается в конец файла при первом сохранении (после `---`-разделителя, как остальные секции модуля); повторное сохранение заменяет только её тело; участники/метаданные (`list.js` регэкспы по своим заголовкам — `## 👥 Участники`/таблица метаданных) не ломаются после апсерта.

## Порядок запуска через subagent-driven-development

Рекомендуемая практическая последовательность (не единственно возможная, но минимизирует риск конфликтов):

1. **W0** (сам оператор, не под-агент — git-гигиена).
2. Параллельно: **под-агент A** — вся Фаза 1 (тикеты 1.1+1.2 подряд); **под-агент B** — вся Фаза 2 (2.1→2.2→2.3 подряд, один агент из-за общего файла); **под-агент C** — Фаза 4 (4.1→4.2 подряд, один агент из-за общего `index.html`-узла); **под-агент D** — Фаза 5, тикеты 5.1+5.2+5.8 (независимые); **под-агент E** — Фаза 5, объединённый тикет 5.3-5.7 (самый рискованный, отдельный агент, чтобы не смешивать diff с D). Пять агентов параллельно, ноль пересечений по файлам между A/B/C и минимальное пересечение D/E (оба в `v20-sheet.js`, но в разных функциях — держать в уме при ревью общего диффа).
3. Параллельно (не дожидаясь п.2, т.к. другая область файлов): **под-агент F** — W2 (3.5-BE + 3.6-BE, один агент, общий файл `sessions.js`/`shared.js`); **под-агент G** — W3 (3.1 + 3.4, разные части `session-screen.js`/`styles.css`, можно один агент для простоты координации).
4. После F и G — **под-агент H** — W4 (тикет 3.2), последовательно.
5. После F и H — **под-агент I** — W5 (3.5-FE + 3.6-FE, один агент, соседние виджеты одной боковой панели).
6. После H и I — **под-агент J** — W6 (тикет 3.7).

## Открытые технические риски при реализации (обнаружены в ходе подготовки этого плана, отсутствовали в плане требований)

1. **Id-коллизия `#sess-notes`** между экраном живой сессии (`session-screen.js`) и формой записи сессии на странице модуля (`modules.js`) — детали в тикете 3.7. Требует контекстных селекторов, не голого `getElementById`.
2. **`.v20-box` — две разные семантики под одним классом**: одиночный независимый чекбокс (здоровье, `data-bpath` без `data-i`) и связанный массив (временная Воля/Кровь, `data-bpath`+`data-i`). Рефакторинг клика (тикет 5.3-5.7) обязан различать их по наличию `data-i`, иначе есть риск случайно сделать здоровье кумулятивным или наоборot сломать боксы Воли/Крови.
3. **Запас крови 3-го поколения — не боксы, а числовой инпут** (`v20-blood-counter`) — кумулятивная логика 5.3 к нему неприменима, эта ветка рендера не должна быть тронута объединённым тикетом 5.3-5.7.
4. **`serializeScenarioSections` небезопасен для `<mod>.md`** — полная реконструкция файла через существующий сценарный сериализатор годится ТОЛЬКО для нового, целиком принадлежащего фиче файла `scene_notes.md`; для `<mod>.md` (общий файл с чужими секциями) нужен узкий non-destructive regex-апсерт по образцу `_patchModuleMain`, иначе патч рискует незаметно переформатировать несвязанные секции существующих модулей пользователя.
5. **`_upsertScenarioLikeSection` — единственная реально новая функция парсинга** в этом патче; всё остальное для `scene_notes.md` — переиспользование `web/lib/parsers/scenario.js`. Экономит объём кода и риск багов по сравнению с писать-парсер-с-нуля, которое подразумевалось планом требований.
6. **Порядок `<script>`-тегов в `index.html`**: `session-screen.js` (тикет 3.2) может понадобиться вызывать `renderModuleCardInChr` из `modules.js` — переставить порядок подключения, если `session-screen.js` сейчас грузится раньше `modules.js` (проверить при реализации 3.2, до написания кода).
7. **Сверка ключей заголовков сцен между `_parseScenarioScenes` (бэкенд, `shared.js`) и клиентским разбором `_sessBlocks` в `session-screen.js`** (тикет 3.7) — оба парсят один `scenario.md` по `## `-заголовкам, но независимыми кусками кода; если один нормализует текст заголовка (обрезает эмодзи/пробелы) иначе, чем другой, агрегация заметок по сценам в 3.7 будет молча промахиваться мимо части заметок. Явно сверить на реальных данных модуля с эмодзи в заголовках сцен (`GM-справка` с 🔒 — уже есть в примерах ТЗ) при реализации.
8. **`aggregate`-тип связи в фильтре типов (тикет 4.2)** — синтетический тип, существующий только в `?compact=true` режиме графа; решение оставить его в общем списке типов (строится по факту присутствия, как линейки) — не баг, но стоит держать в уме при визуальной проверке (чекбокс «Агрегировано» появится только в compact-режиме, это ожидаемо).
9. **Порядок правок в `index.html` `#graph-toolbar`** (тикеты 4.1 и 4.2 оба меняют этот блок) — при параллельном выполнении двумя агентами возможен merge-конфликт на одном участке разметки; конфликт неопасен (независимые правки на соседних строках), но проще сериализовать одним агентом или чётко развести зоны правки заранее (см. тикет 4.2, примечание о зависимости).
10. **DOM/unit-тестовая инфраструктура для `v20-sheet.js`**: не подтверждено, экспортирует ли файл свои `_v20*`-функции для прямого Node-теста (в отличие от `dice.js`, у которого явный `module.exports = { rollV20Pool }` в конце файла). Если нет — тикет 5.3-5.7 полагается на source-guard + визуальную проверку, не на unit-тест кумулятивной логики боксов; проверить в начале тикета и, если экспорта нет, не тратить время на попытку писать unit-тест, которого инфраструктура не поддерживает.
